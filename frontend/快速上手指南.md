# 沙漏 · 快速上手指南

> 目标读者：第一次接触沙漏的团队。在已部署的环境中，预留约 30 分钟体验从想法到周回顾的基本链路；这是练习安排，不是安装、实际交付或采用效果的承诺。
> 已部署好？直接从第 1 步开始。还没部署？先看 [管理员指南](管理员指南.md)。

---

## 上手总览

你要做的事，就是下图这条线：

![沙漏·协作主链路](diagrams/main-flow.png)

第一次使用先走六步：**建空间 → 建项目 → 提想法 → 拆工作项 → 看板推进 → 周回顾**。部分计时记录随操作产生，仍需核对与修正；正式发布另见后文。沙漏的主张是让投入可解释，让交付可追溯，不替代结算、部署执行或客户验收。

---

## 第 1 步 · 创建空间（2 分钟）

1. 登录后创建**空间**——空间是团队协作的边界，成员、看板列、标签、分支等配置都在空间层维护；模块挂在项目下，可在项目驾驶舱的「模块」面板直接新增 / 删除，也可在「设置 → 工作流 → 模块」或编辑项目时配置。
2. 邀请成员加入，再在「设置 → 成员与权限」调整角色：**空间主 / 管理员 / 成员 / 查看者**。日常干活给「成员」，只看不改的干系人给「查看者」；邀请链接加入时默认是成员。
3. **给成员分配项目**：新加入的「成员」默认不参与任何项目，登录后项目列表为空。可以在创建邀请时就勾选「可参与 / 只读」的项目，也可以在建完项目（第 2 步）后，回到「设置 → 成员与权限」点成员行的「分配项目」，或在「项目可见范围」矩阵里逐格调整。空间主 / 管理员天然看到全部项目，查看者全局只读，无需分配。

> 首次登录且未带页面链接时，所有角色固定进入「我的工作」；刷新或分享链接保留当前页面。本文示意图已按当前实现更新，界面截图以《用户使用手册》为准。

## 第 2 步 · 建第一个项目（3 分钟）

1. 在「规划 > 项目」里点「新建项目」，填名称、描述，状态选「进行中」。
2. 项目是交付单元，后面的工作项都归属项目。

## 第 3 步 · 需求池提想法（5 分钟）

1. 进「需求池」，把团队要做的想法提交为需求。先别纠结怎么排——**先提出来，评审再定**。
2. 填写「业务价值、紧迫度、风险缓解、工作量」，WSJF 自动打分排序，四项填齐才计分。
3. 评审通过 / 拒绝 / 重开仍仅空间主；管理者（空间 owner/admin 或项目 ownerUserId 且可写）负责正式排期，目标版本可先留空；指定时须选择同项目未发布版本。计划起止独立于期望日期。
4. 调期 / 撤排 / 取消 / 恢复带原因与 revision，不自动改旧任务；取消不取消任务，恢复到已通过并清目标版本。

工作项有自己的状态机（由看板列驱动），需求池则是评审状态机——两者对照如下：

![沙漏·工作项状态机](diagrams/state-machine.png)

## 第 4 步 · 拆成工作项（10 分钟）

1. 已通过 / 已排期的需求，在详情中点「**拆分为任务**」——生成的工作项自动关联该需求。
2. 类型按粒度选：**任务**（1–2 天的具体工作）、**用户故事**（迭代内可交付）、**缺陷**（问题反馈）、**史诗**（需要拆解的大需求）。
3. 给每个工作项填：负责人、优先级、开始日 / 截止日、预估耗时（可选）。
4. 任务可关联多个同项目计划版本，使用 versionIds/versionNames 数组，保存省略 / null 保留、[] 解绑，不根据需求目标隐式改绑。显式改变关联须原因及管理者或任务负责人可写权限；Demand / TestPlan 仍为单目标 versionId，成功事实冻结的关联不能修改。
5. 有方案要沉淀的，写到「文档」里——支持把文档拆成任务草稿。

## 第 5 步 · 看板推进（10 分钟）

这是日常最常用的动作：

1. **拖入「进行中」→ 自动开表计时**。开始下一个任务会自动停掉上一个——你不需要手动掐表。
2. **拖入「已完成」→ 自动停表**；满足条件时接力原列的下一个任务，请确认接力对象就是你正在做的工作。忘计时可手工补记，记错可作废重算。自动计时按个人工作时段（默认 09:00–18:00）裁剪、跳过周末、共享每日额度（默认 8 小时，可配置）；补记不受这些裁剪，但会占用当天后续自动计时的额度。
3. 筛选条件在看板、列表、日历、甘特之间**共享**；甘特图上能看到依赖、里程碑、关键路径和成员负载。

> **为什么是拖拽驱动计时？** 它减少事后回忆与重复填写，但操作记录不等于专注工作的证明。及时纠正忘停、误接力和漏记，才能让投入记录更可信；这些时长也不自动等于可收费工时。详见 [数据流转图](diagrams/data-flow.png)。

## 第一次周回顾（第 6 步 · 收尾）

到周五，打开「我的 > 周回顾」：

- 自动总结一周的**已完成、待确认、进行中**三个分区，互斥不重复；
- 可选 AI 生成周报草稿（结果需人工确认才落库）；
- 月度清单从完成快照自动生成，不需要任何人维护。

这些视图复用工作项、工时、流转和完成快照等记录。比较数字时，先对齐项目、成员、日期和筛选条件；当前状态、完成快照与发布快照不是同一口径：

## 需要记录正式发布时（已部署）

先在实际部署流程中确认结果，再由有权限的人预览并提交记录。系统不执行部署、不独立校验制品与流水线，也不提供客户签收；SHA256 是记录的制品标识，不是第三方防篡改证明。正式证据需完整数据库与附件备份，不能只导出任务 JSON。

A–E 已实施，本地正确性门禁通过（Java、真实 API / MySQL、真实 headless Chrome 1440/390px 仿真及未知请求恢复）；七对 delivery PNG 已重拍、SHA256 配对一致并视觉查看，部署安全隔离验证通过。线上部署版本以更新日志中最近一次实际发布记录为准，本文不再内联提交号，完整生产模拟与只读验收完成，生产 Chrome 1440/390px、24 次入口导航、93 项有效断言通过，0 runtime/console/HTTP 错误。用户单独授权原 `hourglass` 46 表经受限备份与恢复验证后重建为 52 表；认证 JDBC 与 `DB_NAME=hourglass`，`hourglass_20261110` 保留额外回退点，原历史仅在备份中保留。不回放 61/62、不迁移旧历史；完整基线会重建表，不是幂等无损脚本，正常部署脚本仍只支持新空库，原库重建不是默认授权。详见 [管理员指南](管理员指南.md) 与 [更新日志](../CHANGELOG.md)。

1. 仅空间 owner/admin 或项目负责人且项目可写可管理发布；任务负责人没有整版本权，计划负责人字段不赋权。计划可覆盖多个版本 / 项目，当前版本固定包含，版本选择器按项目分组；更新选定计划带 id+revision。计划保存 versionIds、plannedAt/ownerUserId、plannedTaskIds、环境 production/staging/test、targetKeys 数组、coverage full/partial/unknown 与说明 / 风险 / 原因；状态可写 draft/ready/canceled，completed 只读且不可改，后续另建计划。
2. 区分版本内容、计划范围与实际范围。preview/release 显式提供同一 context：planId（紧急可不选但需 deviationReason）、带 UTC offset 的 occurredAt（不同于服务器 recordedAt）、环境 / 目标 / 覆盖、制品引用与 64hex SHA256、deploy/redeploy/rollback、关联事件、执行人及显式唯一 ≤500 项 actualTaskIds。预览显示 not_selected、候选与警告，不静默排除未完成等事实；未完成事实须管理权限和偏离理由。
3. 确认另带 result、notes、failureReason、scopeToken、planRevision、idempotencyKey，服务器重新检查权限。失败只留尝试；成功保存不可变快照，releasedBy 为服务器登录者。实际记录只属当前版本；计划须其全部包含版本都完成成功生产部署 / 重部署（关联同一计划）才完成，test/staging、rollback 与部分成功不算。一个版本生产只成功部署一次，改动走新 hotfix 版本；同一制品可 redeploy、可 rollback，替换制品须新建版本；rollback 新增事件并按目标撤销关联引用，不抹 ever 历史或后续不同成功。
4. 响应未知时 sessionStorage 保留原 body/key，先 GET release-records?key=... 查记录，再重复原请求，确定结果后才决定新键；不刷新即清理、不换键盲重发。范围或计划冲突需重新预览。
5. 发布徽标只读，publishSource=record，由成功 production 记录推导 publishedAt/publishedReleaseId/everPublished/publicationState/publicationTargets；状态 unpublished/effective/partial/rolled_back/unknown。test/staging 和失败不代表生产发布，无人工标记 / 撤标。成功事实冻结内容关联，但任务完成 / 回退 / 计时照常。
6. 删除版本不自动解绑，发布尝试和现有引用（含回收站、已取消需求）受保护，不得删历史证据。快照与当前工时分开，多版本 / 多事件不放大全局工时，需求取消不抹历史、零任务不能 100% 验收。JSON 只搬运任务版本数组、version.startDate、需求日期与 canceled，不转移正式证据；正式证据用完整数据库备份恢复。不新增迭代模块、不做历史迁移；overview 配图已于 2026-11-10 按当前实现重出，仅用户手册七张本地 delivery PNG（docs/frontend 七对）为仓库本轮真实 Chrome 1440/390px 仿真新图，生产四张私有验证截图未入库，不声称物理手机测试。
7. 入口在菜单「版本」→「按版本」→ 版本卡片的「计划与历史」（打开发布工作区的计划页签）或「记录实际发布」（直达实际页签）；工具栏「发布计划」在单版本时直接打开，多版本时先选版本；「发布日程」标签页则跨项目列出所有计划，可按项目、环境、状态和时间范围筛选，点行打开对应计划的发布工作区（含全部覆盖版本）。默认「按阶段」口径不渲染版本行，所以看不到入口不代表功能缺失。线上若仍缺少按钮，先强制刷新（Cmd/Ctrl+Shift+R）让 PWA 换取新版本，详见 [常见问题](常见问题.md)。
