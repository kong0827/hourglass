适用场景：**全新环境上线**。已有环境的日常升级不使用完整基线，应使用 `sql/` 增量脚本及对应环境的启停方式；一体部署环境可按 `deploy/deploy.sh` 流程执行。

## 部署形态说明

本项目同时支持两种部署形态，本次目标环境为**前后端分离部署（并入现有 39800 网关）**。

| 部署形态 | 适用场景 | jar 位置 | 前端位置 | Nginx 静态处理 |
|---|---|---|---|---|
| 前后端一体 | 独立部署（80/443 独占） | `/opt/hourglass/hourglass-server.jar` | 前端资源已打包进 jar | `proxy_pass` 到 jar，由 Spring Boot serving |
| 前后端分离 | 并入现有网关（本次目标） | `/project/hourglass/back/target/hourglass-server.jar` | `/project/hourglass/front/` | Nginx `alias` 直接托管 |

`deploy/build.bat` 产物中同时包含 `hourglass-server.jar`（前端资源已内嵌）和独立的 `frontend/` 目录：
- 一体部署：只需上传 jar。
- 分离部署：jar 传到 `/project/hourglass/back/target/`，`frontend/` 内容传到 `/project/hourglass/front/`。

`deploy/deploy.sh` 默认按一体部署设计（只换 jar），本次分离部署的前端更新需手动同步 `frontend/` 目录。

## 五、Nginx 与暴露面

### 5.1 并入现有网关（192.168.52.12:39800，total.conf）——本次目标环境

沙漏复用现有 39800 server 块，**不新增监听端口**：前端静态文件由 nginx 直接托管，API 反代到本机 jar，对外统一走 `/hourglass/` 前缀。

- [ ] 前端上传：交付包 `frontend/` 目录内容传到服务器 `/project/hourglass/front/`（与 fund-client 等系统同惯例）
- [ ] jar 按第三节部署，`application.yml` 默认后端端口为 **39991**；部署前先确认未被占用：`ss -tlnp | grep :39991`
- [ ] 在 total.conf 的 39800 server 块内追加以下 location，然后 `sudo nginx -t && sudo systemctl reload nginx`

```nginx
# ===== 沙漏（Hourglass）：前端静态 + API 反代 =====
location = /hourglass {
    return 302 /hourglass/;
}

# API 反代：proxy_pass 不带 URI，原样转发 /hourglass/api/...（后端 context-path=/hourglass）
location ^~ /hourglass/api/ {
    proxy_pass http://127.0.0.1:39991;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 12m;
    proxy_read_timeout 60s;
}

# SSE 实时同步：关缓冲关压缩，拉长读超时
location = /hourglass/api/events {
    proxy_pass http://127.0.0.1:39991;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_buffering off;
    proxy_cache off;
    gzip off;
    proxy_read_timeout 300s;
}

# AI 生成可能跑几十秒：单独放宽超时，避免前端先拿到 504
location ^~ /hourglass/api/ai/ {
    proxy_pass http://127.0.0.1:39991;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_read_timeout 200s;
    proxy_send_timeout 200s;
}

# 备份导入：需求文档正文可能带内嵌图片，放宽请求体上限
location = /hourglass/api/import {
    proxy_pass http://127.0.0.1:39991;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    client_max_body_size 128m;
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
}

# 前端静态：必须 ^~（见注意事项 1）；不加 expires，走默认协商缓存（见注意事项 2）
location ^~ /hourglass/ {
    alias /project/hourglass/front/;
    index index.html;
}
```

注意事项：

1. **`^~` 不能省**：total.conf 里已有一条通用正则 `location ~* \.(js|css|png|...)$ { expires 1y; }`，正则优先于普通前缀匹配——若沙漏静态用普通 `location /hourglass/`，js/css 请求会被那条正则抢走，落到 `root /project/api/front` 下找文件直接 404。`^~` 命中后跳过正则检查，与 fund-client 的写法一致。
2. **不要给沙漏 js/css 套 `expires 1y; immutable`**：business-platform 能长缓存是因为 Vite 构建产物带内容 hash；沙漏是零构建原生 JS，文件名不变，长缓存会导致发版后浏览器一直用旧文件。不加 `expires` 时 nginx 自动用 ETag/Last-Modified 协商缓存，发版即生效。
3. **SSE / AI / import 三个特殊 location 不能省**：server 级 `proxy_read_timeout 30s` 会把 SSE 长连接和 AI 生成掐断；import 默认 10M 请求体上限不够。
4. 可选加固——分享接口限流：`location ^~ /hourglass/api/share/` 内加 `limit_req zone=share_zone burst=10 nodelay;`，zone 定义（`limit_req_zone $binary_remote_addr zone=share_zone:1m rate=2r/s;`）必须放在 nginx.conf 的 **http 块**，不能放 server 块。
5. 沙漏不是 SPA 前端路由（多页面 html），静态块**不需要** `try_files ... /index.html`。

| 关键注意点 | 说明 |
|---|---|
| 后端端口固定 `39991` | 上传 jar 前先确认未被占用：`ss -tlnp \| grep :39991` |
| 静态 location 必须用 `^~` | 防止被 total.conf 通用正则缓存规则抢走 |
| js/css 不设置长缓存 | 零构建文件名无 hash，长缓存会导致发版后仍用旧文件 |
| 暴露面控制 | `39991` 仅监听 127.0.0.1；`3306` 仅允许服务器内网访问，均不得新增公网暴露 |
| 前端目录权限 | nginx 必须能读取 `/project/hourglass/front/` |

验证：

```bash
curl -s http://127.0.0.1:39991/hourglass/api/health          # 后端直连，期望 "db":"up"
curl -s http://192.168.52.12:39800/hourglass/api/health     # 走网关，结果应一致
# 浏览器访问 http://192.168.52.12:39800/hourglass/ 应跳登录页
```

- [ ] `ss -tlnp | grep -E ':(39991|3306)'` 确认 `39991` 仅监听 127.0.0.1、`3306` 仅监听内网地址；防火墙只放行既有 39800 等入口，不新增 39991/3306 公网暴露

## 八、后续升级与回滚

本次分离部署形态下，按改动范围选择升级方式：

| 改动范围 | 操作 |
|---|---|
| 只改后端 | 替换 `/project/hourglass/back/target/hourglass-server.jar` → `/project/hourglass/back/bin/restart.sh` |
| 只改前端 | 重新上传 `frontend/` 到 `/project/hourglass/front/`（无需重启后端） |
| 改表结构 | 执行对应 `sql/` 增量脚本 → 换 jar → `/project/hourglass/back/bin/restart.sh` |
| 全量升级 | 同步后端 jar、脚本/配置及前端文件 → `/project/hourglass/back/bin/restart.sh` |

通用说明：

- 升级：看发布说明，涉及表结构的在服务器执行对应 `sql/` 增量脚本（幂等），再换 jar 重启；本测试环境不直接使用默认 `deploy/deploy.sh`，其目标目录和启停方式不同。
- 回滚：部署前保留上一版 jar，需要回滚时替换到 `/project/hourglass/back/target/hourglass-server.jar` 并执行 `restart.sh`；数据库用第六节的每日备份恢复。
- 种子数据如需按新口径重新生成：改 `tools/gen_seed_yunying.py` 后重跑生成器，产物写入 `sql/seeds/seed_yunying.sql`。

> 注意：本测试环境的前端由 Nginx 独立托管，前端变更只需同步 `frontend/`，无需重启后端。
