# 沙漏博客专栏 · 口径与边界

> 这页把各篇反复出现的口径集中说明。它不是功能清单，也不是合规、性能或交付承诺；具体能力以仓库文档、当前版本和实际环境为准。

---

## 一、先分清五个概念

| 概念 | 说明 | 容易混淆的地方 |
| --- | --- | --- |
| 计划 | 当时准备做的范围，可以调整 | 计划不是已经交付 |
| 完成 | 工作项推进并确认的结果 | 完成不等于已发布 |
| 实际发布 | 人工确认后保存的发布事实 | 不执行部署，也不等于客户验收 |
| 投入 | 自动计时、人工补记、作废之后的记录 | 不是在线时长，也不是可结算工时 |
| 交付说明 | 向接收人解释承诺、实际、变更、质量、投入与证据的一页记录 | 不是合同、发票或验收单 |

这五个概念分开，是理解本专栏的前提。把它们合成一个绿色状态，报表会更好看，追问时却更容易断。

## 二、工时口径

- **自动计时**：按工作日累计，周末不计；个人工作时段默认 9–18 点；每日上限可配置，默认 8 小时，按人跨空间共享。
- **人工补记**：单条 1 分钟至 24 小时，日期不能在未来；不经过周末、工作时段或每日封顶裁剪，但会加入当天已用额度，影响后续自动计时的可用额度。
- **接力**：只在本人没有运行中的计时、且原列还有任务时发生；接上的任务是否就是当前工作，仍要人工核对。
- **有效工时**：用于解释投入，缺少计费率、审核锁账和客户签认，不能直接当作可结算工时，也不建议单独用于人员绩效定论。
- **作废**：错误记录应作废并说明原因，而不是把小时数直接改成想要的结果。

自动计时和人工补记必须一起解释。不能用「系统跳过周末」否定一条周末补记，也不能用补记去覆盖自动计时的规则差异。

## 三、完成、发布与验收

- 工作项完成、版本规划范围和实际发布记录是三件事。工作项可以关联多个计划版本，但有关联不表示已经随每个版本发布。
- 实际发布由发布负责人先在工作台之外完成部署和必要检查，再回到系统人工确认范围；系统保存发布快照、制品引用和 SHA256。
- 工作台**不执行部署，不自动验证流水线结果**。SHA256 用于核对制品一致性，不是部署成功证明，也不提供数据库之外的防篡改保护。
- 客户验收、电子签名和合同签认，应在适当的流程或系统中完成。沙漏当前没有客户验收电子签名能力。
- 发布快照保存的是应用内的历史记录，不代替备份；正式证据还需要全库与附件备份。

## 四、自托管、备份与运维

- 沙漏当前采用单实例自托管形态：Java 服务、MySQL、前端托管和附件存储。核心数据可以放在团队自己的基础设施上，维护责任也留在团队。
- 服务器在内网，并不自动满足权限、审计、保留期限或合规要求；自托管不等于自动合规。
- 空间 JSON 导出可用于支持范围内的数据迁移与整理，但**不是正式发布证据备份**。正式证据使用全库与附件备份，检查数据库与附件的时间一致性、保存位置和访问权限，并实际做恢复演练。
- 制品引用指向外部位置时，还要另行保证该位置的可访问性和留存。
- 当前形态不提供横向扩展或高可用保证。50 人只是参考规模，服务器配置、并发、附件体量和项目数量都需要实际验证。
- 必须有人负责升级、故障、权限、凭据、补丁和监控；负责人不必是专职岗位，但要有交接人。

## 五、审计、集成与外部发送

- 审计最小集已实现，覆盖登录、权限、导出、删除等关键事件，支持 CSV 导出，默认保留 90 天且可配置；它不是对每项业务操作的全面审计，也不是合规认证。
- 当前没有 SSO、API Token、任务 CSV 导入和 Docker 部署支持。上线前要确认这些缺口是否影响身份管理、迁移和日常运维。
- 机器人 Webhook 只处理消息投递，不等于企业微信免登。
- 配置外部 AI、邮件服务或机器人 Webhook 时，会向外部发送相应内容。开启前应核对服务地址、发送内容、访问凭据和组织允许的范围；敏感项目不能仅凭「自托管」三个字作判断。
