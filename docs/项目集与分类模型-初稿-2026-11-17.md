# 项目集与分类模型（初稿）

> 状态：初稿待评审 · 2026-11-17（已导入正式数据）
> 关联：[项目集（项目分组）方案](项目集（项目分组）方案-2026-11-17.md)、[简化版原型](preview/project-group-redesign-2026-11-17.html)、[初版原型](preview/project-group-preview-2026-11-17.html)
> 本文回答三个问题：增加项目集后哪些地方要同步调整；存量模块如何改；模块改称“分类”后边界放在哪里。第 10–12 节基于 2026-11-17 导出的正式库（`hourglass.sql`，22 MB / 78 表）给出具体迁移结果与页面调整清单。

## 1. 结论摘要

1. 采用 **项目集 → 项目 → 分类** 三层。项目集只做归组和项目级只读汇总，不授权、不承载版本与发布；**版本和按阶段始终按项目，不引入项目集维度**。
2. **项目**仍是成员、权限、版本、发布、文档、分支、里程碑、测试计划、交付说明和工时的唯一宿主。
3. **分类**由现有“模块”降级而来，只在项目内做归类、筛选、列和分组；不参与跨项目归属、权限、版本和工时汇总。
4. 存量**一级模块按内容一次性升格为项目**：有工作项/需求的一级模块升格，空的默认“其他”和空模块不升格；项目是否包成项目集按门槛判定（见 4.1 与第 10 节），单分类项目保持项目、不建“1 个项目”的空集。
5. 数据库表名和字段名继续使用 `category`，只改产品文案与接口语义，避免全库改名带来的回归。
6. 主要成本不在建表，而在迁移：成员/权限、版本/发布、测试计划、里程碑、编号、保存视图、用例集、分支、文档和交付说明；正式数据里最硬的约束是 `version_task`、`test_case_task` 和需求的 `version_id` 跨项目历史引用。
7. 正式数据（2026-11-17）按本方案迁移后：**2 个项目集、14 个子项目、2 个容器项目、10 个未分组项目**；真正需要拆的是“流程引擎”和“机构服务平台一期”。

## 2. 概念与边界

| 对象 | 定义 | 承载 | 不承载 |
| --- | --- | --- | --- |
| 项目集 | 空间级容器：名称、颜色、排序；可选 | 项目归组；项目级只读汇总（项目数、进度、工时、风险） | 权限、成员、版本、按阶段、发布、工时记录 |
| 项目 | 现有 `requirement` 对象 | 成员、权限、版本、发布、文档、分支、里程碑、测试计划、交付说明、工时汇总 | —— |
| 分类 | 现有 `category` 树，项目内使用 | 工作项/需求/用例的归类、项目内筛选与分组 | 跨项目归属、权限、版本、发布、工时汇总 |
| 容器项目 | 拆分后保留的原项目 | 未挂模块的工作项/需求/用例、文档、仓库、分支、用例集、交付说明 | 新项目的版本与发布 |

命名建议：

- 一期如果只做归组，界面叫**项目分组**更准确；如果叫**项目集**，一期至少提供项目级只读汇总（项目数、进度、工时、风险），否则会超出“哑容器”的预期。
- “模块”在产品文案、列名、导出表头、空值提示中统一改为**分类**（如“未指定模块”改为“未分类”）。代码中的 `category`、`categoryId` 不改名。

### 2.1 版本与按阶段保持项目口径（已定）

- 版本属于项目（`project_version.req_id`），按阶段是项目内的查看方式；两者都不升到项目集。
- 版本页的“按版本 / 全部版本 / 按阶段”继续以项目为范围，不增加项目集筛选、分组或汇总。
- 项目集不生成版本、发布计划、发布记录，也不合并这些对象。
- 跨项目看版本时，最多按项目分组，不按项目集分组。
- 项目集二、三期的只读汇总也不包含版本与按阶段，避免出现“集里还有一套版本口径”。

## 3. 项目集是否强制（待确认 D1）

### 方案 A（推荐）：项目集可选，未分组平铺

- `requirement.set_id` 允许为空；没有项目集的项目在列表中平铺在“未分组”。
- 不为无模块项目自动创建同名项目集。
- 好处：不产生“X / X”的重复层级；小团队不被迫多点一层；迁移不产生空容器；与云效、TAPD、禅道的可选项目集一致。
- 代价：项目列表需要同时支持“分组”和“平铺”两种展示。

### 方案 B：每个项目必须有项目集

- 无模块项目自动包一层同名项目集，原项目保留在集内，保证模型统一。
- 需要额外规则避免歧义：
  - 项目集与项目同名时，面包屑只显示一层，或项目名显示为“X（原项目）”；
  - 只有 1 个项目的项目集在列表里默认折叠；
  - 项目集删除只解除归属，不删除项目。
- 代价：多一层实体和一次点击；迁移会为每个小项目创建容器；用户容易问“这两个 X 有什么区别”。

结论：除非产品上明确要求“所有项目必须归集”，否则按方案 A 落地；方案 B 只作为统一展示的备选。

## 4. 存量模块处置规则

### 4.1 判定

先判定“项目要不要包成项目集”，再判定“哪些一级模块升项目”：

- **包集门槛**：项目内至少 2 个一级分类承载内容（不含默认“其他”），且项目有 ≥10 个未删除工作项或 ≥10 条需求。低于门槛的项目保持项目，模块只改称分类，避免产生只有 1–2 个工作项的空项目。
- **升格范围**：有工作项或需求的一级分类升格；只有空分类的项目不升格。
- 该门槛是为了避免“技术平台（2 个工作项）”“消息中心（1 个模块）”这类项目被拆成多个空项目；门槛可按评审意见调整，但应当在迁移前一次定死。

| 存量对象 | 判定 | 处置 |
| --- | --- | --- |
| 一级模块（`parent_id` 为空，名称不是默认“其他”）且名下有工作项/需求/用例 | 升格 | 新建项目，模块子树成为该项目的分类 |
| 一级模块但名下没有内容 | 不升格 | 保留为分类，或随容器项目保留；避免产生空项目（待确认 D5） |
| 默认“其他”模块 | 不升格 | 留作分类；其内容留容器项目 |
| 二级及以下模块 | 不升格 | 成为新项目内的分类；原层级整体上提一级 |
| 未挂模块的工作项/需求/用例 | 不迁 | 留在容器项目，分类为空 |
| 直接挂在一级模块上的工作项/需求/用例 | 迁 | 迁到新项目；分类指向新项目的根分类或为空 |
| 项目不足包集门槛 | 不拆 | 模块改称分类；项目、工作项、需求、版本都不动 |

### 4.2 示例

原项目“结算平台”有一级模块“清分”“对账”，以及未挂模块的工作项：

- 项目集：“结算平台”
- 新项目：“清分”“对账”
- 容器项目：“结算平台-公共”，承载未挂模块的数据和项目级资源
- “清分”下保留原二级模块作为分类，例如“通道”“银行”
- 时间记录随工作项迁移，不单独重算
- 已发布版本与发布记录默认留在容器项目；未发布版本按成员任务所属项目迁移（见 D9）

### 4.3 一级模块升格后，原 `category` 记录怎么处理

三种做法，建议选 A：

| 做法 | 说明 | 影响 |
| --- | --- | --- |
| A. 保留原 ID 作为新项目的根分类（推荐） | 新项目下保留一个同名根分类，旧 `category_id` 继续可用 | 保存视图、旧链接、历史日志兼容性最好；界面上根分类可弱化为“全部/未分类” |
| B. 归档原记录，二级模块上提 | 旧 `category_id` 失效 | 保存视图和旧链接必须映射；历史日志中的模块名需快照 |
| C. 删除原记录 | 最干净 | 兼容性最差，不建议 |

### 4.4 存量引用怎么改

| 引用位置 | 现状 | 调整 |
| --- | --- | --- |
| 工作项 `task.req_id` / `task.no_scope` | `no_scope` 等于项目 ID，与 `item_no` 组成唯一键 | 两者必须同时改；只改 `req_id` 会留下错误编号分组，取号也会错 |
| 工作项 `task.category_id` | 模块 ID | 迁到新项目后重新指向新项目的分类；一级模块直属工作项指向根分类或空 |
| 需求 `demand.category_id` | 模块 ID | 同上；跨项目移动需求时，若分类不属于目标项目则清空（现有逻辑已如此） |
| 需求 `demand.version_id` | 目标版本属于原项目 | 版本留容器时，迁出需求的实时版本引用失效；保留 `version_name` 快照或清空 `version_id`，见 D9/D10 |
| 工作项版本关系 `version_task` | 版本必须属于工作项所在项目（保存时强校验） | 迁出工作项与容器版本的关系不能保留，否则该工作项每次保存都会报“影响版本不属于任务所在项目”；历史由 `version_release_item` 快照保留 |
| 用例 `test_case.module_id` | 与项目目录同一棵树 | 随用例迁到新项目；测试目录树同步拆分；测试计划随版本复制 |
| 用例—任务关联 `test_case_task` | 关联时要求同项目（`TestCaseService`） | 跨分类关联在拆分后变成跨项目；需清理或放宽为只读跨项目，见 D10 |
| 完成归档 `task_completion_record` | 保存 `req_id`、`req_name`、`category`（模块名快照） | 随工作项改 `req_id`/`req_name`，`category` 改为新项目/分类名；归档是报表口径，不能留旧项目 |
| 编号 `number_seq` | 需求、用例按项目取号；`next_no` 保存“最后已用号” | 为新项目补需求序列 `next_no = 该项目内最大 demand_no`；用例序列随用例迁到新项目；任务编号按 `no_scope` 取最大值 +1，无需回填 |
| 全局筛选 `cats` | 跨项目模块筛选 | 全局去掉模块 chip；仅选中单项目时出现“分类”筛选 |
| 保存视图 | `cats`、`group=category`、`ganttGroup=category`、需求 `groupBy=module/moduleSub` | 按映射表改写；映射不到就裁剪并在界面上提示（正式库当前 0 条保存视图，但仍要兼容旧备份） |
| 设置页模块配置 | 跨项目模块管理 | 收进项目设置，改叫“分类”；`/api/categories` 的跨项目列表下线或收窄 |
| 模块删除 | 删除时把工作项/需求迁到另一个模块 | 改为“清空分类/改分类”，不再承担跨项目搬数据 |
| 分析页模块分布/系数 | 按模块统计 | 主维度改项目；分类作为项目内二级分析 |
| 交付说明按模块汇总 | `effortDim=module` | 项目内保留“按分类”；跨项目按项目 |
| 项目模板默认模块 | 建项目时生成默认模块 | 保留为默认分类，不再生成“项目级模块”概念 |
| 搜索 | 检索范围含模块名 | 继续可搜，但结果主跳项目；模块名只作为分类关键词 |
| 审计/通知/AI | 文案与参数带模块 | 文案改“分类”；AI 建单以项目为主参数，分类可选 |

## 5. 数据模型变更

| 变更 | 内容 | 说明 |
| --- | --- | --- |
| 新增 `project_set` | `id`、`workspace_id`、`name`、`description`、`owner_user_id`、`status`、`planned_start`、`planned_end`、`archived_at`、`color`、`sort_order`、`created_at`、`updated_at` | 空间内名称唯一；从原 `requirement` 迁入负责人、状态、计划日期，项目集卡片才有信息可展示；删除只解除归属 |
| `requirement.set_id` | 可空，加索引 | 方案 A 允许为空；方案 B 非空 |
| `requirement.origin_category_id` | 可空 | 记录由哪个模块升格而来，便于追溯 |
| `requirement.container_kind` | 可空，`split_container` / `null` | 标记容器项目，列表与统计默认折叠或弱化，避免与真实项目混在一起 |
| `project_split_map` | `workspace_id`、`old_project_id`、`old_category_id`、`new_project_id`、`new_category_id`、`action`、`created_at` | 迁移幂等、旧链接映射、回滚核对 |
| `category` | 表结构不变 | 产品语义改为“分类”；不重命名表/字段 |
| 备份/导出 | 纳入 `project_set`、`project_split_map` | 导入时按版本处理；旧备份默认无项目集 |

不建议把 `category` 表改名为 `classification`，也不建议把 `task.category_id` 改名为 `classification_id`：收益低，回归面大，产品文案改称“分类”即可。

## 6. 需要同步调整的清单

### P0：数据、权限、迁移

- 项目集 CRUD、项目归属、列表筛选/分组、删除只解绑。
- 项目成员、项目角色、负责人、邀请授权、发布权限复制到新项目；项目集不授权。
- 版本、测试计划、里程碑、编号序列、软删除任务、用例集的迁移规则。
- 迁移预览、备份、单事务、幂等、回滚。
- 任务跨项目移动：现有任务更新会保留原 `req_id`，迁移后分类错了没有补救入口；需求已有跨项目移动但有关联限制。

### P0：产品文案与入口

- “模块”统一改“分类”：项目表单、设置页、列名、导出、空值、删除确认、帮助文案。
- 项目驾驶舱的“模块”面板降级为“分类统计”（数量、工时），主 KPI 回到项目。
- 全局模块筛选、跨项目模块接口、跨项目模块配置入口收口。

### P1：视图与筛选

- 看板、列表、树、甘特、日历、我的、评审：全局默认按项目分组/筛选；项目内保留按分类。
- 需求池、测试域、交付说明：模块列/筛选/分组改称分类，项目为主维度。
- 保存视图迁移：`cats`、`category` 分组、`moduleSub` 等。
- 默认列、排序、导出表头同步。

### P1：统计与报表

- 投资、负载、分析、交付说明：项目维度为主；项目集只做项目级只读汇总（不含版本/阶段）；避免重复计数。
- 版本与按阶段保持项目口径：不增加项目集筛选/分组/汇总；跨项目看版本时最多按项目分组，项目内可看分类。
- Portfolio 增加项目集分组/筛选（这是项目集的主要价值）。

### P1：测试域

- 测试目录与项目目录同树：一级模块升项目时用例和目录一起迁。
- 测试计划随版本复制；用例集留在容器还是拆分，见第 7 节。
- 缺陷的模块筛选、批量改模块、AI 用例草稿同步改“分类”。

### P2：周边

- 搜索、通知、审计/活动、AI 助手、CSV/周报导出、备份导入导出、移动端。
- 演示数据、接口契约、ER 图、用户手册/管理员指南、E2E 与单测。

## 7. 关键口径与风险

| 问题 | 建议口径 | 理由 |
| --- | --- | --- |
| 发布记录是否复制到新项目 | **不复制**。保留在容器项目；子项目按 `version_release_item.task_id` 关联任务推导“本项目相关条目”只读视图 | 发布记录是历史事实；复制会产生第二条事实并导致全局统计重复计数 |
| 版本是否迁到新项目 | **默认留容器**；已发布版本的历史成员关系以发布快照为准，实时 `version_task` 关系清理；未发布版本按“多数成员所属项目”人工归属 | 版本是项目级对象，历史一次发布常跨多个分类；强行按模块复制会产生多套版本号和两套发布事实（D9） |
| 迁出工作项的版本关系怎么处理 | 清理 `version_task`（正式数据 97 行），发布历史仍可由 `version_release_item` 还原；迁出需求的 `demand.version_id` 保留 `version_name` 快照后清空 | 现有保存逻辑强校验“版本必须属于工作项所在项目”，不清理会导致工作项无法编辑（D10） |
| 用例集是否拆分 | 含升格模块用例的用例集，**复制/拆分到新项目**；不含的留在容器 | `case_set.req_id` 是项目级，跨项目引用会让列表、计数、可见范围不一致 |
| 分支/仓库是否迁移 | 分支本身不绑项目，保留空间级；被迁走任务引用的分支把 `dev_branch.req_id` 改为新项目（正式数据 21 条），未引用的留容器/置空 | 分支属于仓库，不属于模块；复制分支会产生两套提交历史 |
| 文档是否迁移 | 留在容器；子项目页提供“项目级资源”入口；可按标题人工改归属（如三份东证期货 PRD 分到注册、首页、后台项目） | 文档使用独立的 `doc_category`，现有数据全部未挂分类，无法自动按模块拆分 |
| 里程碑是否复制 | 版本型复制到新项目；人工型留容器；任务型仅在所有关联任务都迁走时重映射 | 里程碑状态按证据推导，复制后要保证证据链完整 |
| 编号是否重排 | 历史 `item_no`、`demand_no`、`case_no` 保留不重排；新项目补 `number_seq`，需求序列取该项目内最大号，任务取号按 `no_scope` 最大值继续 | 重排会打断 WI-/DM-/TC- 外部引用；`number_seq.next_no` 是“最后已用号”，回填时不要 +1 |
| 成员权限 | 原项目成员全部复制到新项目，保持原可见范围；之后允许管理员收窄（正式数据仅“机构服务平台一期”有 9 条项目成员，需复制到 7 个新项目） | 不复制会导致新项目对团队不可见；按模块拆权限会改变原有可见性 |
| 容器项目 | 建议命名为“原项目名-公共”，标记 `container_kind`，在集内固定排最后或折叠；承载未分类数据和项目级资源 | 避免内容“凭空消失”；与项目集同名但后缀区分，减少“X / X”歧义 |
| 任务跨项目移动 | 补一个“移动到项目”的操作；需求已有但受关联限制 | 迁移后需要纠错入口；否则分类错了只能改数据 |
| 保存视图 | 按映射表改写；映射不到则裁剪并提示 | 不处理会静默筛出空结果 |

## 8. 迁移流程

1. **只读预览**：列出将创建的项目集、新项目、容器项目，以及工作项/需求/用例/工时/版本/测试计划/里程碑的计数；空模块不建项目。
2. **备份数据库**。
3. **结构变更**：建 `project_set`、加 `requirement.set_id`、建映射表。
4. **数据迁移（单事务）**：
   - 建项目集与新项目；
   - 复制成员、角色、负责人、邀请授权、发布权限；
   - 拆分分类树；
   - 迁工作项、需求、用例（含软删除）；
   - 按 D9 处置版本（已发布留容器、未发布按成员归属迁移），复制测试计划、版本型里程碑；
   - 清理会阻断编辑的跨项目版本关系，回填编号；
   - 写审计日志与映射表；
   - 容器项目改名/标记。
5. **校验**：逐项目对比迁移前后工作项数、工时、版本数、测试用例数、发布记录数；核对无悬空外键；核对每个项目至少有一个负责人。
6. **切换应用**；保留回退窗口。
7. **回退**：迁移后仅回退应用无法恢复数据，必须用备份恢复；结构与数据脚本分离。

幂等口径：只处理未归属项目集/未拆分的项目；映射表存在记录则跳过；重复执行不产生新项目。

### 10.6 拆分后才会暴露的跨边界数据

这些不是“迁移脚本能自动判定”的问题，必须先定口径：

1. **工作项与需求的分类不一致 20 条**：基础功能→外接 10、外接→基础功能 4、主机托管→外接 3，另有 3 条跨其他分类。拆分后工作项和它关联的需求会落在不同项目。现有保存逻辑只校验“需求所属项目在编辑期间未变化”，不要求与工作项同项目，因此数据能保留；但需要在界面上明确展示，或迁移时让工作项跟随需求（D10）。
2. **用例与任务跨分类 11 条**：用例迁到基础功能后，关联任务在别的项目。`TestCaseService` 关联时要求同项目，拆分后这些关系在编辑时会失败；需要清理，或把“用例验证其他项目任务”定义为合法的只读跨项目关系。
3. **工作项版本关系 97 条、需求目标版本 111 条**：版本留容器则都不能保留实时引用。需求可保留 `version_name` 快照后清 `version_id`；工作项必须清 `version_task`，否则每次保存都报错。若选择“已发布版本随主项目（外接）”，则只清约 5 条跨到基础功能的关系，但 18 个版本和 18 条发布都会集中到外接（D9）。
4. **分支 21 条**：分支不绑项目，任务换项目不会报错；但分支列表按 `dev_branch.req_id` 过滤时，新项目会看不到自己的分支。按被引用情况改归属即可。
5. **发布记录明细跨项目**：`version_release_item` 是快照，不随任务迁移；子项目要用发布历史，只能按 `task_id` 反查容器发布，属于只读派生，不应产生新的发布记录。

### 10.7 迁移 SQL 骨架（先预览、后事务）

正式数据迁移不要直接跑全量脚本。建议按“预览 SQL → 建映射 → 单事务迁移 → 校验 → 回退”执行；映射表 `project_split_map` 是幂等和回滚的依据。关键预览 SQL：

```sql
-- 1. 预览：哪些项目达到包集门槛（子查询避免分类×任务重复计数）
SELECT r.workspace_id, r.id, r.name,
       (SELECT COUNT(*) FROM category c
         WHERE c.project_id = r.id AND c.parent_id = '' AND c.name <> '其他'
           AND (EXISTS (SELECT 1 FROM task t WHERE t.category_id = c.id)
                OR EXISTS (SELECT 1 FROM demand d WHERE d.category_id = c.id))) AS cats,
       (SELECT COUNT(*) FROM task t WHERE t.req_id = r.id AND t.deleted_at IS NULL) AS live_tasks,
       (SELECT COUNT(*) FROM demand d WHERE d.req_id = r.id) AS demands
FROM requirement r
WHERE r.archived_at IS NULL
HAVING cats >= 2 AND (live_tasks >= 10 OR demands >= 10);

-- 2. 预览：每个一级分类的迁移量
SELECT c.project_id, c.id AS category_id, c.name,
       SUM(t.deleted_at IS NULL) AS live_tasks,
       (SELECT COUNT(*) FROM demand d WHERE d.category_id = c.id) AS demands,
       (SELECT COUNT(*) FROM test_case tc WHERE tc.module_id = c.id) AS cases
FROM category c
LEFT JOIN task t ON t.category_id = c.id
WHERE c.parent_id = '' AND c.project_id IN ('Xkp02','Rmwe9zg68c51hkegw')
GROUP BY c.project_id, c.id, c.name;

-- 3. 预览：拆分后会跨项目的关联
SELECT 'version_task' AS kind, COUNT(*) FROM version_task vt JOIN task t ON t.id = vt.task_id
WHERE t.req_id = 'Xkp02'
UNION ALL
SELECT 'demand_version', COUNT(*) FROM demand WHERE req_id = 'Xkp02' AND version_id IS NOT NULL AND version_id <> ''
UNION ALL
SELECT 'task_demand_mismatch', COUNT(*) FROM task t JOIN demand d ON d.id = t.demand_id
WHERE t.req_id = 'Xkp02' AND t.category_id <> d.category_id
UNION ALL
SELECT 'case_task_cross', COUNT(*) FROM test_case_task ct
JOIN test_case tc ON tc.id = ct.case_id JOIN task t ON t.id = ct.task_id
WHERE tc.req_id = 'Xkp02' AND t.req_id = 'Xkp02' AND IFNULL(tc.module_id,'') <> IFNULL(t.category_id,'');
```

迁移事务的顺序固定为：建 `project_set` 与映射表 → 建子项目 → 改分类 `project_id` → 改工作项 `req_id`/`no_scope` → 改需求 `req_id` → 迁用例与用例集 → 复制成员 → 补 `number_seq` → 清理/迁移版本关系 → 写审计与映射 → 校验。全部在一个事务内完成，失败整体回滚；回退以导入前的本地备份为准，应用回退不能恢复已改的数据。

## 12. 有了项目集和项目，分类还重要吗

重要，但只在一个位置重要：**项目内的工作归类**。它不是第三层项目，也不应该再承担版本、权限、排期和独立统计。

### 12.1 竞品口径

| 工具 | 层级 | 模块/组件的位置 |
| --- | --- | --- |
| 禅道 | 项目集 → 产品/项目 → 执行 | “模块”是需求/任务/用例的分类树，不是项目层级；子项目用“执行”承载 |
| TAPD | 项目集 → 项目（支持父子项目） | 模块/需求分类不升为项目 |
| 云效 Projex | 项目集 ⇄ 项目 | 项目集是聚合查看与规划层，成员自动获得关联项目只读；分类在项目内 |
| Jira | Project → Component | Component 用于分组工作、可设负责人，但不是项目；跨项目归组用 Plans/Program |
| Azure DevOps | Project → Area Path → Team | Area Path 可做团队层级和权限范围，但 Project 仍是容器 |
| PingCode | 项目集 → 项目 → 工作项 | 模块/组件是项目内分类 |

共同点：**项目集是归组/只读聚合层；模块/组件是分类维度；没有主流工具让模块长期充当项目。** 因此“模块升项目”应是一次性的治理动作，而不是保留两套并行语义。

### 12.2 正式数据给出的证据

- 12 个项目、29 个一级分类，只有 2 个项目的分类真正承载了多条业务线（流程引擎 7 个、机构服务平台一期 11 个）。
- 其余项目大多是“1 个项目 1 个同名分类”（资金通/资金监控、消息中心/消息中心等），分类层只是在重复项目名；技术平台 2 个分类总共 2 个工作项。
- 拆分后，剩余分类大多为 0–1 个/项目。如果把分类继续当层级展示，会产生大量“项目里只有一个同名分类”的空壳视图。

### 12.3 分类还必须保留的四个用途

1. **项目内拆分工作**：一个项目里的功能域/子系统（如一期拆分后的“其他”、未升格的空分类）需要归类、筛选、分组。
2. **不需要独立版本的轻量维度**：临时专项、跨迭代的特性分组，不值得为它建项目、配成员、开版本。
3. **测试目录**：用例和缺陷的目录天然是树，分类树比项目层级更适合做用例组织。
4. **导入、报表和用户习惯**：Excel 导入、周报、外部系统映射仍需要一个“分类”字段；直接删掉会造成迁移成本。

### 12.4 什么时候必须升级为项目

满足任一条，就不该继续留在分类里：需要独立版本/发布节奏；需要独立成员与权限；需要独立负责人、排期和工时口径；需要作为对外交付单元单独统计。流程引擎的“外接/主机托管”满足，资金通的“资金监控”不满足，所以只拆前者。

产品上保留一个后置动作即可：分类详情提供“升级为项目”（人工触发、可预览影响），不做自动升级；这样以后新长出来的子系统仍有出口，但不会再次出现“模块事实上是项目”的历史包袱。
