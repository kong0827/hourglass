# 多产品接入方案：企微、飞书与 Qoder（2026-11-28）

> 状态：方案分析，未实施；不改产品代码、不改数据库。
> 结论：可行。一条开放主线（REST + MCP）、三种入口形态（Agent、免登、机器人），产品差异只留在薄适配层。
> 前置：对外身份与只读开放属于 P0 底座，见第 8 节。

## 1. 判断

不要按产品各写一套对接。沙漏已有的功能全部走 REST，权限复核在服务层，跨空间 404、越权 403 的口径已经稳定（见[接口契约](接口契约.md)）。接入多家产品时，真正要补的是「身份」和「入口」，不是业务逻辑。

2026 年一个关键变化：飞书和企微的机器人入站都支持长连接（WebSocket 出站长连），不需要公网回调域名。沙漏是内网单实例部署（`application.yml:4` 只绑回环），长连接正好绕开公网暴露与备案，只要服务器能出网访问平台域名。

## 2. 四类接入形态

| 形态 | 代表 | 身份 | 模型在哪 | 交互 |
| --- | --- | --- | --- | --- |
| Agent 工具调用 | Qoder、Cursor、自研脚本 | 个人令牌（PAT） | 客户端自带 | 工具调用、结构化结果 |
| 人工免登 | 企微工作台、飞书网页应用 | OAuth 换沙漏会话 | 无 | 完整 Web 界面 |
| 群 / 单聊机器人 | 飞书机器人、企微智能机器人 | 应用身份 + 绑定到提问人 | 沙漏服务端（或平台智能体） | 自然语言 + 卡片 |
| 事件与通知 | 群机器人 webhook、审批卡片回调 | 空间级配置 | 无 | 单向推送、按钮回调 |

后两类常被混为一谈。企微群机器人 webhook 只能发不能收；能接收用户消息的是 2026 年上线的智能机器人（`aibot_msg_callback`，支持长连接或 URL 回调）。飞书同理：群 webhook 只出站，收消息要靠自建应用的事件订阅。

## 3. 目标架构

```
Qoder ──MCP(HTTP)──────┐
飞书 / 企微 机器人 ─────┤
（长连接侧车）          ├─► 沙漏开放层 ─► 既有 Controller / Service（权限口径不变）
自研脚本 ──REST────────┤         │
飞书 / 企微 工作台 ──OAuth────────┘         ├─ 审计（actor + channel + external id）
                                          ├─ 限流与配额
                                          └─ 通知（已有 webhook 出站，复用）

integration 侧车（同机、单实例）：
  飞书长连接 / 企微智能机器人长连接 / 卡片回调 / MCP server
  统一消息模型 → 渠道适配器 → 调沙漏 REST
```

三个原则：

1. **MCP 给自带模型的客户端**，如 Qoder；机器人是我们自己的 Agent，直接走 REST 更简单，不必绕 MCP。
2. **平台差异只在侧车**：消息格式、卡片结构、文件下载、长连接鉴权都放适配器，核心服务不出现按平台分支的判断。
3. **契约只有一份**：开放层和 MCP 共用同一套接口，MCP 工具名是给 Agent 的稳定契约。等需要对外部客户正式承诺时再固化带版本的网关。

## 4. 身份与权限模型

三种主体，互不复用：

| 主体 | 用途 | 权限上限 | 关键约束 |
| --- | --- | --- | --- |
| 人（会话） | Web 界面 | 本人权限 | 现状不变 |
| 个人令牌 | Qoder、脚本 | 本人权限，P0 只读 | 随密码 / 角色变更失效；只本人可签发与撤销 |
| 应用身份 | 机器人侧车 | 提问人的权限（act-as） | 未绑定不执行；仅受限端点；审计双记 |

阶段 2 引入两张绑定表：

- `channel_identity`：`provider + external_user_id → user_id`，把企微 userid、飞书 open_id 绑定到沙漏账号。
- `channel_room`：`provider + external_chat_id → workspace_id`，确定这个群默认操作哪个空间，避免 Agent 猜空间。

群聊是最容易出事故的场景：群里问「本周谁最忙」，结果发到群里，别人看到了自己无权看的数据。建议规则：

- 机器人一律以提问人身份执行；未绑定回复「请先绑定账号」并附链接。
- 群内默认只回不含敏感明细的汇总，明细走私聊；「仅自己可见」的卡片能力按平台支持情况再议，不作为安全前提。
- 写操作在群里先回预览卡片加二次确认，不直接落库。

## 5. 各产品接入方式

### 5.1 Qoder（最优先）

- 走 P0 的个人令牌与只读 MCP，P1 增加写工具（建任务 / 需求 / 用例、导入文档）。
- 每名成员一个令牌，审计落到人；令牌存 Qoder 的 MCP 配置或环境变量，不共享团队令牌。
- 文档导入：Markdown 走建文档接口；Word 走已有的 `import-word`（不超过 10MB）。

### 5.2 飞书

- 网页免登：自建应用 OAuth 换沙漏会话，工作台入口直达。这是「人用沙漏」的主路径，成本最低。
- 机器人：自建应用加事件订阅，推荐用长连接接收事件，无需公网 URL。收到消息后进入统一管道，回复交互卡片；写操作按钮回调另行处理。
- 文件导入：用户把 Word 发给机器人，侧车用平台文件下载接口取文件，再调 `import-word`。
- 飞书开放平台已把自身 OpenAPI 封装为 MCP 工具。若其智能体后续支持挂载外部 MCP，沙漏 MCP 可直接复用；否则维持侧车桥接。

### 5.3 企业微信

- 免登：OAuth2 自建应用方案此前评估过，尚未落码，可直接复用，优先落地。
- 智能机器人：2026 年新开放的接收消息能力，支持长连接或 URL 回调与流式回复。已知限制是只接收 @ 机器人或单聊消息，群能力仍有灰度，权限需要申请。
- 群机器人 webhook 只用于出站通知。沙漏的空间推送配置已经支持企微 / 钉钉机器人，不需要改。

### 5.4 其他（钉钉、Teams、Slack）

同一适配层再实现一个 provider，不新增核心逻辑。

## 7. 关键决策

**模型归属决定成本模型。** Qoder 用客户端模型，沙漏没有模型成本；飞书 / 企微机器人要么用沙漏服务端模型（复用现有 AI 设置、团队额度与 `sql/133_ai_usage_daily.sql` 的用量表，按渠道计费），要么等平台智能体支持外部 MCP 后借用平台模型。先用服务端模型跑通，额度按空间与渠道单独限制。

**入站优先长连接，出站才需要网络放行。** 长连接只要求服务器能出网访问 `open.feishu.cn` 和 `qyapi.weixin.qq.com`，不需要公网域名、证书和回调白名单。这是内网部署能否接入的分水岭，需要先确认生产机出网权限。

**侧车单实例，事件去重。** 长连接同一应用多实例会抢连接，与沙漏单实例、进程内缓存的现状一致。侧车按 `event_id` 去重（平台会重试），写操作带幂等键；侧车与主服务同机直连回环地址，机器人令牌只存在侧车环境变量里，不进日志。

## 8. 前置：P0 开放底座

多产品接入依赖同一层能力，P0 先把它做出来：

- 个人访问令牌：只存哈希，支持只读 / 读写作用域、过期、撤销；随账号代次失效。
- Bearer 鉴权：纯令牌请求跳过 CSRF，带会话 Cookie 的请求仍受 CSRF 保护；令牌不建会话。
- 令牌请求禁入管理员接口与令牌管理接口。
- 按令牌限流，写操作留审计。
- 受控 OpenAPI：只开只读白名单分组，文档本身也要求登录或令牌。
- MCP 只读工具：列空间、查项目 / 任务 / 需求 / 文档 / 用例、我的任务、搜索。

当前 [接口契约](接口契约.md) 明确不是对外 Token 承诺，P0 落地后需要新增「对外只读 API」章节，并把本文第 8 节内容作为实施依据。实施细节（令牌表、过滤器、CSRF 边界、OpenAPI 白名单与工具映射）见[对外 API 与 MCP P0 实施设计](对外API与MCP-P0实施设计-2026-11-28.md)。

## 9. 分期与工作量

单人估算，不含平台侧权限审批的等待时间：

| 阶段 | 内容 | 估算 |
| --- | --- | --- |
| 0 | 个人令牌、只读 API 与 MCP | 2 周 |
| 1 | 写工具、幂等与确认，Qoder 全能力 | 1.5–2 周 |
| 2 | 身份绑定、飞书免登、企微免登 | 1.5–2 周 |
| 3 | 飞书机器人（长连接、私聊查询、卡片确认、文件导入） | 2–3 周 |
| 4 | 企微智能机器人（复用同一管道） | 1.5–2 周 |

「Qoder 可用」约 2–4 周；「飞书 / 企微能进能用」再 4–6 周。平台侧权限申请（飞书事件订阅、企微机器人能力、免登可信域名）是并行项，通常比编码更耗时。

## 10. 风险与取舍

- **群聊数据泄露**（最高风险）：以提问人身份执行、默认私聊明细、群内只回汇总、写操作卡片确认。
- **平台限制与审核**：企微智能机器人只接收 @ 与单聊消息，部分能力灰度；飞书需要企业管理员审批权限。演示能力不等于稳定承诺。
- **出网依赖**：完全无外网的部署无法接飞书 / 企微，只能做通知代理或走客户自建网关。
- **模型成本与合规**：机器人对话消耗模型额度；走公网模型需与「内网、数据不出域」的口径对齐，现有默认是局域网网关。
- **许可口径**：对外提供 API 与机器人与 PolyForm Noncommercial 加双许可的边界，正式对外前确认一次。
