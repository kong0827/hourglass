# 测试工时与「开发 / 测试时长」可行性分析

> 日期：2026-11-09　对应版本：v1.1.0-rc1（未发布）
> 方法：静态阅读代码与 SQL 脚本，未连接实例执行查询；文末 SQL 为草案，需在测试库验证后再用于生产。

## 一、结论

| 问题 | 现在能不能直接用 | 说明 |
| --- | --- | --- |
| 体现测试工时 | **不能按阶段**，只能按人勉强推断 | `time_log` 只有任务、人、起止、分钟，没有「工时类型 / 阶段」。 |
| 体现测试开始、结束时间 | **部分可以** | 任务级靠「测试」看板列的流转日志；分支级有 `test_at`；测试计划只有计划日期和执行流水，没有实际起止字段。 |
| 一个任务开发了多久、测试多久 | **没有现成指标** | 有总工时、日历跨度、列平均停留，但没有「按任务的开发段 / 测试段拆分」。 |

一句话：**沙漏把「投入了多少时间」记得很清楚，把「时间花在开发还是测试」记得不清楚。**

如果今天就要一个数，只能靠「配置一个测试列 + 团队按约定拖动和计时 + 财务/PM 用 SQL 或时间线人工核对」，属于运营口径，不是产品能力。

---

## 二、先分清三种「时长」

讨论「开发多久 / 测试多久」前，必须先定义量的是哪一种，否则数字会对不上：

| 口径 | 定义 | 沙漏现状 |
| --- | --- | --- |
| 投入工时 | 人实际投入的分钟数，经工作时段、每天 8 小时上限裁剪 | 有，`time_log.minutes`，所有报表都用它 |
| 墙钟跨度 | 从 A 时刻到 B 时刻的自然时间，包含夜里、周末和等待 | 有原始时间戳（计时起止、流转日志），但没有按阶段汇总 |
| 阶段跨度 | 任务在某一状态（如「测试中」）停留的自然时间 | 只有流程体检的「按列平均停留」，不是按任务，也不是工时 |

「开发了多久」通常指墙钟跨度或阶段跨度；「开发花了多少」指投入工时。两者不能互相换算，沙漏的 8 小时/天、工作时段裁剪会让 `minutes` 小于墙钟时间。

## 三、数据里到底有什么

### 3.1 工时记录：只有「谁、在哪个任务、什么时候、多少分钟」

`time_log`（`sql/01_schema.sql`、`sql/44_manual_time_log.sql`）：

| 字段 | 含义 |
| --- | --- |
| `task_id` / `workspace_id` | 工时只挂任务，不挂阶段、版本、用例 |
| `user_id` | 计时人；同一人同一时刻只允许一个运行中的计时 |
| `started_at` / `ended_at` | 墙钟起止（手工补记两者都落在当天 12:00） |
| `minutes` | 计入工时（已裁剪：工作时段、跳过周末、每天上限） |
| `origin` | `timer` 计时器 / `manual` 手工补记 |
| `note` | 仅补记备注 |

关键缺口：**没有 `phase`、`work_type`、`stage` 之类的字段**。一条 3 小时的记录，从数据上无法判断是开发、测试还是改缺陷。

`TimeLogService` 里还有两条影响口径的规则：

- 拖入「进行中」（或任何非「待处理」、非「已完成」的列）会自动开始计时；拖入「已完成」会停掉该任务上所有人的计时；拖回「待处理」也会停表。**从测试列拖到「待合并」之类的列不会停表**。
- 手工补记不经过工作时段和 8 小时上限裁剪，但日期落在当天仍占用当天额度；落库时间固定为 `date 12:00`。

### 3.2 任务状态：不是字段，而是看板列 + 流转日志

- `task.board_column` 是当前列；没有独立的 `status` 字段。
- 每次跨列移动写一条 `task_log`，`action='move'`，带 `from_column` / `to_column` / `created_at`（`sql/09_task_flow.sql` 补齐结构化列并回填历史）。
- 看板列是**空间级**的（`board_column.workspace_id`），不是项目级；默认只种「待处理」「进行中」，「已完成」是内置列不落表。项目模板「产品研发」会往空间里加「联调」「待验收」，「测试管理」会加「待复测」（`ProjectTemplateService`）。

这意味着：

- 想按阶段拆分，只能依赖列名/列 id 的约定；
- 加一个「测试中」列会影响该空间所有项目；
- 列改名后，历史 `detail` 文本解析可能失效，结构化 `from/to` 不受影响（但 `sql/09` 之前的日志可能仍为空）。

### 3.3 分支：四个首次进入时间，是「测试开始」最干净的数据源

`dev_branch`（`sql/14_branch.sql`）：

- `dev_at`：进入开发中
- `test_at`：**首次**进入待测试（提测时间）
- `merge_at`：进入待合并（测试通过、等人合）
- `released_at`：发布

`dev_branch_log` 记录每一次状态变更（含从待测试退回开发中），可以还原「测试停留」和「返工」。

限制：分支是分支级，不是任务级；一条分支下可以挂多个任务（`task.branch_id`），无法直接摊到某个任务；「待测试」是等人测，不等于测试人员已经动手。

### 3.4 测试模块：有用例执行时点，没有测试时段，也不挂任务

- `test_case`：项目级用例，可选关联需求池 `demand_id`，**不关联任务**；`latest_at` 是最近一次执行时间（时点）。
- `test_case_run`：每次执行一行，`created_at` 是执行时点，`plan_id` 标识是否属于某个测试计划；没有耗时字段。
- `test_plan`：只有 `planned_start` / `planned_end`（**计划**日期，DATE 精度）、`status`（draft/running/done）、`created_at` / `updated_at`；**没有实际开始/结束时间戳，也没有状态流水**。
- `test_plan_case`：计划内每个用例的最新结果与 `executed_at`，每次批量执行会覆盖。

补充两点关联：

- 用例和任务都可以挂到同一个需求池条目（`test_case.demand_id`、`task.demand_id`），所以能做到「需求级」的测试—开发关联，但一对多，落不到具体任务。
- 用例执行失败转缺陷后，`test_case.latest_bug_task_id` / `test_case_run.bug_task_id` 指向缺陷任务；这是测试活动唯一直接连到任务的地方，而且只连缺陷，不连原始开发任务。

所以测试模块能回答「哪条用例什么时候执行过、结果如何」，不能回答「这个任务测了多久、测试人员投入了多少」。

### 3.5 完成快照与报表：有总账，没有阶段账

- `task_completion_record`：完成瞬间落快照，含 `first_started_at`、`last_ended_at`、`total_minutes`、`completed_at`。任务被彻底删除后快照仍在，但快照里没有阶段信息。
- 分析页「完成记录」展示的是 `start_date`（计划开始日）、`completed_at`（完成日）、`total_minutes`，**不是**计时起止。
- 报表「交付周期」= `start_date`（没有则 `created_at`）→ `completed_at`，按天计算 P50 / P85（`ManagerService.delivery`）。
- 流程体检「各列停留」按列聚合平均/中位/P90，默认近 90 天，排除已完成列，**不提供按任务的展开**。

## 四、把「测试开始 / 结束」拆到四个粒度看

| 粒度 | 开始 | 结束 | 数据源 | 可靠性 |
| --- | --- | --- | --- | --- |
| 任务 | 移入测试列 | 移出测试列（到已完成/待合并等） | `task_log` 的 `to_column` / `created_at` | 需要空间级测试列 + 团队纪律；列改名不影响结构化日志 |
| 分支 | `test_at`（首次提测） | `merge_at` 或 `released_at` | `dev_branch`、`dev_branch_log` | 时间最干净，但粒度是分支；分支可挂多任务 |
| 测试计划 | 计划 `planned_start`；实际可取首条执行 `test_case_run.created_at` | 计划 `planned_end`；实际只能取状态 done 时的 `updated_at` | `test_plan`、`test_case_run` | 计划日期不是实际；状态无流水，重新打开会覆盖 `updated_at` |
| 用例 | `test_case_run.created_at` | 无（单次执行是时点，不是时段） | `test_case_run`、`test_case.latest_at` | 只能看执行时点 |

结论：**任务级「测试开始/结束」在数据上可行，但前提是先有「测试列」这个约定；计划级缺少一等公民的实际起止字段；用例级没有时段概念。**

## 五、现在就能算的近似方法

### 5.1 运营约定（零改动）

1. 在空间看板加一列「测试中」（或沿用已有的「联调 / 待测试 / 待验收」），放在「进行中」和「已完成」之间。
2. 约定：**进入该列 = 测试开始，离开该列 = 测试结束**。
3. 测试人员用自己的账号计时；不要用开发负责人账号代计。
4. 缺陷单独建 `bug` 工作项并计时，缺陷修复工时不要混进测试工时。
5. 补记只作为总量修正，不作为阶段工时依据（它固定落在 12:00，没有可用的时段）。

这样至少可以做到：

- 任务详情「操作时间线」里能看到每次进入/离开测试列的时刻；
- 任务详情「工时记录」里能看到每条计时的起止与计时人；
- 流程体检能看到测试列的平均停留时间；
- 项目/版本/成员的工时总量仍然准确（它们本来就不分阶段）。

### 5.2 任务级阶段工时参考 SQL

思路：用 `task_log` 的跨列移动构造「列区间」，再和 `time_log` 求交，按墙钟重叠比例分摊 `minutes`。

```sql
-- 参数：@ws 空间ID，@task 任务ID；测试列 id 按实际配置替换
WITH mv AS (
  SELECT l.id, l.created_at, l.from_column, l.to_column,
         LEAD(l.created_at) OVER (ORDER BY l.created_at, l.id) AS next_at
  FROM task_log l
  WHERE l.workspace_id = @ws
    AND l.task_id = @task
    AND l.action = 'move'
    AND l.to_column IS NOT NULL
),
seg AS (
  -- 首段：任务创建 → 第一次移动，列取第一次移动的 from_column
  SELECT COALESCE((SELECT from_column FROM mv ORDER BY created_at, id LIMIT 1),
                  (SELECT board_column FROM task WHERE id = @task AND workspace_id = @ws)) AS col,
         (SELECT created_at FROM task WHERE id = @task AND workspace_id = @ws) AS seg_start,
         (SELECT created_at FROM mv ORDER BY created_at, id LIMIT 1) AS seg_end
  UNION ALL
  SELECT to_column AS col, created_at AS seg_start, next_at AS seg_end
  FROM mv
),
logs AS (
  SELECT id, started_at, ended_at, minutes, origin,
         TIMESTAMPDIFF(SECOND, started_at, ended_at) AS wall_sec
  FROM time_log
  WHERE workspace_id = @ws AND task_id = @task AND ended_at IS NOT NULL
)
SELECT CASE
         WHEN s.col = 'done' THEN 'done'
         WHEN s.col IN ('Cxmtest') THEN 'test'   -- 可配置多个测试列
         WHEN s.col = 'backlog' THEN 'backlog'
         ELSE 'dev'
       END AS phase,
       ROUND(SUM(l.minutes * TIMESTAMPDIFF(SECOND,
             GREATEST(l.started_at, s.seg_start),
             LEAST(l.ended_at, COALESCE(s.seg_end, l.ended_at)))
           / NULLIF(l.wall_sec, 0))) AS minutes
FROM logs l
JOIN seg s
  ON l.started_at < COALESCE(s.seg_end, l.ended_at)
 AND l.ended_at  > s.seg_start
WHERE l.origin = 'timer'
GROUP BY phase
ORDER BY minutes DESC;
```

看「墙钟跨度」而不是工时时，按阶段取 `MIN(seg_start)` 与 `MAX(seg_end)` 相减即可；注意 `seg_end` 为空表示仍在当前阶段。

### 5.3 这个算法的误差来源（必须一起看）

- **按墙钟比例分摊**：`minutes` 已经被工作时段、周末、每天 8 小时裁剪，一条跨阶段的计时按墙钟分摊只是近似；夜里跑表会让比例失真。
- **边界记录**：一条计时横跨「开发→测试」，开发与测试各分到一部分，和真实动作不完全一致。
- **补记记录**：`started_at = ended_at = 12:00`，没有可用时段，只能单列「未分阶段补记」，不能硬塞进阶段。
- **多人并行**：同一任务可多人同时计时（每人一条），阶段拆分后可能同时出现「开发工时」和「测试工时」，这通常是对的，但会被误读成重复计算。
- **跑表不停**：从测试列拖到待合并/其他列不会自动停表，开发或测试的计时可能延伸进下一阶段。
- **历史日志**：`sql/09` 之前或列改名导致 `from_column` / `to_column` 为空的移动，会被归到「dev」或直接漏掉。
- **任务删除**：彻底删除任务时 `task_log` 一并删除；完成快照保留，但快照没有阶段信息。
- **有效期**：流程体检默认只看 90 天，但手写 SQL 不受此限制；上表数据本身是全量。

### 5.4 今天在界面上能看到的证据

- **任务详情 → 工时记录**：每条计时记录的 `开始 → 结束`、计时人、分钟数；补记只显示日期和备注。最多取最近 50 条。
- **任务详情 → 操作时间线**：每次跨列移动的「从…到…」和时间，能人工还原测试窗口。
- **流程体检 → 各列停留**：每个列的平均/中位/P90 停留，以及当前在制最久；不按任务展开。
- **测试 → 测试计划 → 详情**：每条用例的计划内执行人、执行时间；计划本身只显示计划起止。
- **测试 → 用例 / 测试报告**：最近执行人、最近执行时间、失败/阻塞与缺陷；没有耗时。
- **分支**：当前状态已停留多久；已发布分支显示「创建 → 发布」周期。

## 六、建议：分三档，先小后大

### 方案 A：只用现有能力（0 开发）

- 加「测试中」列 + 明确约定 + 测试人员自己计时 + 缺陷独立建项。
- 用任务时间线和工时记录人工核对；用流程体检看测试列平均停留。
- 适合：先验证团队是否真的需要按阶段统计，成本几乎为零。
- 不足：报表没有阶段维度；补记无法分阶段；依赖纪律。

### 方案 B：最小产品化（建议）

**B1（先做，读时计算，不改历史数据）**

1. 给 `board_column` 加 `stage`（`backlog/dev/test/done`），列改名不影响统计，并明确哪些列算测试（可多列，如「联调 / 待测试 / 待验收」）。
2. 服务端新增「阶段工时」查询：按第五节思路从 `task_log` + `time_log` 计算，任务抽屉和项目驾驶舱展示「开发 X 小时 / 测试 Y 小时」，并标注口径与近似说明。
3. 报表新增按阶段筛选/汇总（项目、版本、成员三个维度复用现有聚合）。
4. 成本估算：迁移 1 个 + 接口/聚合 + 两处前端 + 测试，约 2–3 人日；不动存量数据，风险低。

**B2（按需再做，写时快照）**

1. `time_log` 增加 `phase`，计时开始时按任务当前列的 `stage` 写入；任务在计时中途跨阶段时，服务端在移动动作处切分计时记录（而不是等到读时按比例猜）。
2. 测试计划补 `actual_start_at` / `actual_end_at`（或状态流水表）；批量执行首次写入开始时间，标记完成写入结束时间；重新打开时保留历史。
3. 成本约 3–5 人日；能给出精确的阶段工时和测试周期，但会改动计时写入路径，需要更完整的回归测试。

### 方案 C：完整阶段模型（不建议现在做）

- `task_phase_event`（任务 × 阶段 × 起止 × 操作人）+ 测试活动挂任务 + 阶段目标/偏差 + 返工率。
- 能回答 DORA 类问题，但会引入状态机和更多录入负担，与沙漏「小而美、范围克制」的定位冲突；建议等 B 方案被真实使用后再评估。

## 七、需要产品拍板的口径

1. **测试开始**：提测（开发完成、进入待测试）算开始，还是测试人员实际动手算开始？
2. **测试结束**：测试通过、进入待合并、上线、还是测试计划完成？
3. **测试工时**是否包含缺陷修复、回归、环境搭建、等待时间？
4. 统计粒度是**任务、需求、版本、项目还是人**？测试用例目前只挂项目/需求，不挂任务；如果按任务统计，需要补关联。
5. 「多久」要**墙钟**还是**投入工时**？是否排除周末和非工作时段？
6. 能否接受**空间级看板列**作为阶段依据（会影响该空间所有项目）？

这几个问题不先定，做出来的数字一定会在复盘会上被质疑。
