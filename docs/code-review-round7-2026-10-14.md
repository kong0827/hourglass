## 发现

### 1. [P2，修复遗漏] 计时回调仍会提前启用其他任务的按钮，状态查询也能覆盖新的操作结果

- 位置：`src/main/resources/static/js/app.js:2432`、`:2436`、`:2464`、`:2470`。
- 上一轮已修好的部分：开始/停止请求捕获任务 ID，迟到的 A 响应不会再通过 `renderWork` 直接把 A 的工时显示到 B。
- 遗漏路径一：A 开始请求尚未完成，用户打开 B；`loadWorkStatus(B)` 正确禁用按钮等待状态确认。但 A 的成功/失败回调在检查任务 ID **之前**执行 `btnTimer.disabled = false`，仍然解除 B 的禁用。B 的查询尚未返回时，用户就能按照默认“开始计时”文案操作。如果 B 原本运行中，该次点击发出的仍是 start，而不是 stop。服务器的幂等开始避免重复插入，但用户想停止时没有停止，且界面“先查状态再允许操作”的新规则被绕过。
- 遗漏路径二：同一任务的旧状态 GET 与 start/stop 操作交错时，仅比较任务 ID 不够。例如定时刷新先查到未运行并延迟交付，用户的 start 先完成并显示“停止计时”，随后旧 GET 返回 `running=false`，界面又变成“开始计时”。旧 GET 也可能在写操作尚未完成时重新启用按钮。关闭后重新打开同一任务同样缺少弹窗代次判断。
- 验证：提取当前 `clearWorkTick/renderWork/fetchTimer/loadWorkStatus` 与点击处理函数，使用可控 Promise。第一条路径输出 `B_disabled_before_A_response=true`、`B_disabled_after_A_response=false`，在 B 状态未确认前发出了 `/api/tasks/B/timer/start`；第二条路径输出 `A_button_after_old_GET=开始计时`，此前 start 已成功返回 `running=true`。没有访问真实计时接口。
- 建议：操作响应检查任务与弹窗代次后才能修改任何 UI，包括 disabled；查询与写操作共享状态代次，旧查询不能覆盖较新的操作结果；操作进行中也不能由轮询随意解除禁用。统一管理当前弹窗的加载、操作和运行状态，避免多个异步回调各自控制同一按钮。
- 此问题发生于单设备正常导航/轮询，与已接受的服务器跨设备同时开始计时无关。

### 2. [P2] 周回顾切换没有请求代次，迟到响应会切回旧周

- 位置：`src/main/resources/static/js/app.js:1348`、`:1354`、`:1364`、`:1367`。
- 触发：当前为上周（offset=-1），点击上一周发出 -2 请求，未返回时点击下一周发出 0 请求；0 先返回，-2 后返回。两个导航按钮在请求期间可用，回调没有判断是否仍是最新请求。
- 原因：`navWeek` 每次基于上一次已返回的 `state.reviewData.weekOffset` 计算目标，再无条件写入 `state.reviewData` 和渲染。`openReview` 的初次加载也没有代次保护，可以覆盖期间发起的导航结果。连续向同一方向点击还会基于同一旧 offset 重复请求同一周。
- 影响：已显示本周后又退回更早的周，完成明细和统计随之改变；复制回顾读取的也是被旧响应覆盖的数据。日历/列表已修好的代次保护尚未覆盖这里。
- 验证：执行提取的当前 `navWeek`，按新请求先返回、旧请求后返回控制完成顺序，输出 `review_after_new_then_old=-2`，最后一次导航目标是 0。探针只验证函数行为，没有运行真实浏览器。
- 建议：独立记录用户选择的目标周次，并为初次打开与翻周共用请求代次；成功和失败仅处理当前代次。请求期间禁用导航也能减少交错，但仍需处理关闭/重开后的旧结果，复制入口应对应当前已确认的数据。

### 3. [P3] 导入允许带逗号的分类名，分类出现后却无法筛选其任务

- 位置：`src/main/java/com/devstudio/kanban/service/BackupService.java:236`、`:238`、`:337`、`:338`；查询拆分为 `src/main/java/com/devstudio/kanban/dto/BoardQuery.java:37`、`:52`，匹配为 `src/main/java/com/devstudio/kanban/service/TaskService.java:755`。
- 触发：导入备份中某项任务的 `cat="A,B"`。导入成功，分类表与任务都保留 `A,B`；用户在筛选中选中这个分类。
- 原因：日常分类创建/更新通过 `CategoryService.cleanName` 替换逗号，以遵守筛选参数的 CSV 协议；导入只 trim/cut，绕过该规则。前端数组经 join 和 URL 编码后，服务端解码仍得到 `A,B`，再拆成两个分类 `A` 和 `B`，无法精确匹配任务上的完整分类名。URL 编码不能解决服务端解码后的分隔冲突。
- 影响：导入任务在全量列表可见，但选择其分类会漏掉任务。仅空间主可导入，标准当前版本导出的分类通常没有逗号，因此优先级 P3；手工备份、外部或历史数据可以触发。它是已有任务字段的导入校验不一致，不要求扩大 JSON 恢复范围。
- 验证：调用当前 `BackupService.importData`，内存 mapper 接收分类和任务，再通过当前 `BoardQuery.from` 与 `TaskService.match` 核对筛选。输出 `imported_category=A,B`、`imported_task_category=A,B`、`filter_categories=[A, B]`、`selected_category_matches=false`。
- 建议：导入补齐分类和任务赋值使用同一套分类名规范化规则，保证两者一致；同时处理规范化后名称碰撞与空名称。或者整体修改筛选传参协议，但不能只对前端名称做 URL 编码。

## 第六轮修复复核

- 循环关联：复用目标检查同一空间，不再读取目标标题写入日志；彻底删除和过期清理均通过 `deleteChildren` 调用 `clearRecurNext`，SQL 清除指向被删除 ID 的上游引用。文档已明确回收站内后续任务仍算存在，彻底删除后可重新生成，按此规则接受。
- SSE：无订阅时直接返回；成员查询失败记录日志后停止投递；过滤器额外捕获广播异常。当前服务探针确认无订阅时成员查询次数为 0，有订阅时模拟查询失败不会向调用方抛出；没有降级成全员广播。
- 计时：任务 ID 校验覆盖工时渲染，打开弹窗先禁用按钮；但按钮启用及查询/操作顺序仍有第 1 项中的遗漏，不能认定为全面修复。
