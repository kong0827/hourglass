# 沙漏 AI 能力规划：通用能力、差异化能力与落地顺序

> 状态：产品分析稿，未实施，不改变现有路线、许可与发布口径。
> 回答三个问题：沙漏应该集成哪些 AI 能力、哪些是通用能力、哪些值得做成差异化。
> 实现细节（接口、提示词、权限、限流）见 [AI 助手集成方案](AI助手集成方案-2026-11-11.md)，本文只谈产品判断。

---

## 0. 结论

三句话：

1. **通用能力决定“能不能用”，差异化能力决定“为什么是沙漏”。** 问答、建单、摘要、生成草稿会迅速变成所有项目管理工具的标配，做不好是短板，做好了也不是护城河。
2. **沙漏的差异化只做一件事：把系统里的记录编译成可交付的证据。** 每条结论都能点回源记录；不评分、不预测个人、不自动改数。可以叫**证据型 AI（Evidence-grounded AI）**。
3. **通用能力做薄，差异化能力跟随三个交付钩子分批落地。** 不设独立的“AI 产品线”，不建通用 Agent 平台，不做聊天入口的功能墙。

### 0.1 AI 的三个角色

| 角色 | 替用户省掉什么 | 性质 | 典型能力 |
| --- | --- | --- | --- |
| 记录助手 | 录入、整理、拆分的机械劳动 | 通用，入口 | 问答跳转、自然语言建单、文档拆任务、用例生成 |
| 口径解释者 | 翻记录、对数字、解释“为什么” | 通用入口 + 差异答案 | “这个版本到哪了”“为什么延期”“两个报表为什么不一样” |
| 证据整理者 | 拼周报、拼交付说明、拼证据包 | **差异化** | 交付说明、变更台账、发布就绪体检、客户简报、复盘底稿 |

前两个角色保证助手有人用；第三个角色决定用户为什么离不开沙漏。

### 0.2 一条边界

判断一个 AI 动作能不能做，只看一句：

> **这个动作如果失败或被误解，用户能不能一眼看出、能不能撤销？不能，就不让模型直接做。**

由此推出：所有写操作都是“草稿 → 预览 → 人工确认 → 服务端执行”；所有证据型输出都必须带引用；所有缺口都显示“未记录”，而不是让模型补全。

### 0.3 先做、后做、不做

| 判断 | 能力 |
| --- | --- |
| 现在做 | 助手入口（问答 + 精准跳转 + 单条建单）、统一“草稿→确认”交互、引用与 AI 标识、评测集 |
| 跟随 Gate 1 做 | 交付说明草稿、版本级变更台账、发布就绪只读清单、固定问题查询、周报事实底稿、发布说明草稿 |
| 跟随 Gate 2 做 | 证据包、跨项目变更台账、追踪链自由问答、风险叙述、客户版简报、记录质量纠偏、确认式批量操作 |
| 条件触发 | 语义搜索、CI/Git 事件核对、客户门户问答、本地模型、Agent 工作流 |
| 明确不做 | AI 评分/排名、自动改状态、自动发布、任意 SQL、跨系统写操作、生产力监控、替代评审签认 |

## 1. 参考：主流工具把 AI 放在哪

> 以下只观察公开产品页与更新日志，未做同任务实操；不引用未验证的菜单细节。

| 产品 | AI 主形态 | 值得学 | 不照搬 |
| --- | --- | --- | --- |
| Jira / Atlassian Rovo | 企业知识搜索 + 对话 + 可嵌入工作流的 Agent；官方主张“项目几乎能自己管理” | 工作项内联动作、Agent 可被流程触发、上下文即入口 | 跨工具知识图谱与企业搜索，需要大量连接器和组织数据 |
| Linear Agent | 内置助手，理解 roadmap / issue / 代码，可创建和更新 issue；支持技能与自动化，在应用内和 Slack/Teams 工作 | @ 提及的低摩擦入口、triage 自动化、把“技能”沉淀为可复用流程 | 自治修改代码/状态；依赖代码托管的深度集成 |
| Asana AI Teammates | 可像同事一样被“分配工作”的专用 Agent，提供多种预置角色；强调人类检查点、权限、审计与可逆动作 | 角色化 Agent + 人类检查点 + 可逆动作，这套信任设计值得直接借鉴 | Agent 市场与大规模自治，维护成本高，小团队无法监督 |
| 飞书项目 AI | 统一 AI 助手入口，也可作为流程中的 AI 节点；报告、风险洞察、创建需求、模板、周报与人力分析 | 把 AI 嵌进流程节点，而不是另开一个聊天页；周报/人力分析的成品化 | 复杂流程引擎与大组织配置 |
| 通用工作台 AI（ClickUp Brain / monday AI / Notion AI 等） | 连接工作区内容的问答、摘要、写作与搜索 | 摘要与写作的顺手程度、结果直接可用的交互 | 大而全的知识库/文档 OS，不是沙漏的定位 |

### 1.1 收敛出的通用经验

这八条已经是行业共识，沙漏应当遵守，但不应把它们当差异化：

1. **入口就地**：在用户正在看的对象上提供“问这个项目/这个版本”，而不是让用户复制内容去聊天框。
2. **动作结构化**：自然语言负责表达意图，真正执行走结构化草稿和表单，不让模型直接调接口。
3. **写操作有检查点**：生成 → 预览 → 确认 → 执行；可撤销、有审计。
4. **答案带来源**：摘要、状态、风险都要能点回原始记录或文档。
5. **权限继承**：模型能看到的内容，不能超过当前用户本来能看到的范围。
6. **失败可降级**：模型不可用、额度耗尽、JSON 不支持时，FAQ、模板和确定性规则仍然可用。
7. **成本可见**：显示本次消耗、模型与是否降级；批量任务有预算上限。
8. **评测集驱动**：用固定问题集和固定样例回归，而不是每次换模型后凭感觉。

### 1.2 沙漏不跟的三条路

- **不做企业知识搜索**：Rovo 的价值来自连接整个组织的文档与系统；沙漏的用户只有几十人，数据在项目内，做连接器的投入产出不成立。
- **不做自治 Agent**：Linear/Asana 的 Agent 可以连续执行多步操作；沙漏的证据链要求“谁确认、何时确认、依据哪条记录”，自治会破坏证据的可解释性。
- **不做 Agent 市场/模板商店**：2 名维护者无法维护几十个 Agent 的提示词、权限与回归；宁可做 6 个打磨过的场景动作。

**通用功能的半衰期很短。** 模型厂商每季度都会把摘要、写作、搜索做得更好；把护城河建在“会聊天”上，等于把命运交给上游。

## 2. 沙漏的约束决定了打法

| 约束 | 对 AI 能力选择的影响 |
| --- | --- |
| 自托管、数据敏感、小型项目制团队 | 出站必须可控：每人自配 Key、可关、可脱敏；长期提供本地模型选项；“证据不出内网”本身可以成为卖点 |
| 用户没有专职 PMO | AI 的输出必须是**成品文档/清单/简报**，不能只是聊天记录；否则用户还要自己拼 |
| 2 名维护者、单实例、无 Redis/MQ | 不引入向量数据库、编排框架、Agent 平台；复用现有 `AiClient`、SSE、审计与权限 |
| 全局 2 个 AI 并发、非流式、90/150 秒预算 | 优先做低频高价值任务；聊天做短请求与独立配额；批量任务排队、缓存、可取消 |
| 计划、完成、发布严格分开，有 revision 与不可变快照 | 事实必须由服务端查询后注入，模型只负责叙述；这也是竞品最难复制的数据基础 |
| 角色与项目级权限 | 查询前按 `viewerScope` 过滤；模型上下文里不出现无权数据；输出不越权 |
| 现有 AI 已覆盖拆任务、文档体检、用例、周报 | 不重复造功能，先把这些能力统一到同一套“生成→确认→引用”交互 |

### 2.1 一个 2×2：把投入放对位置

|  | 低风险（不改数/易撤回） | 高风险（改数/影响他人） |
| --- | --- | --- |
| **高频** | 问答、导航、建单、摘要、我的待办解释 → **做薄、做顺** | 批量改状态、批量改负责人、自动流转 → **只做确认式，不急** |
| **低频** | 润色、翻译、格式整理 → **少做，能用即可** | 交付说明、证据包、客户简报、复盘 → **差异化重点** |

沙漏的投入应该集中在右下角：低频、高价值、高风险但可人工确认的“出证”能力。高频低风险能力是入口，不是终点。

## 3. 能力地图：沿交付链路找机会

| 阶段 | 用户真正想完成的事 | 通用 AI（应该有） | 差异化机会（值得做深） | 现有基础 |
| --- | --- | --- | --- | --- |
| 需求池 / 评审 | 把想法变成可评审、可排期的条目 | 条目补全、摘要、相似需求提示、评审问题清单 | **承诺基线**：立项时冻结“承诺了什么”，后续可对照 | 需求池、WSJF、revision |
| 文档 / PRD | 沉淀方案，拆成可执行工作 | Word/Markdown 导入、拆任务、完成度体检、润色 | 文档与承诺/任务/测试的**覆盖缺口** | AI 拆任务、文档体检、Word 导入评估 |
| 工作项 / 排期 | 建单、排期、推进、解释偏差 | 自然语言建单、字段补全、相似项、批量草稿 | 计划 vs 实际的**偏差解释** | 看板/列表/日历/甘特、依赖 |
| 测试 / 缺陷 | 用例、缺陷、计划、回归 | 用例生成、失败转缺陷、截图转缺陷、回归建议 | 测试证据与**发布范围**的对应 | 测试五模式、计划快照 |
| 版本 / 发布 | 定范围、确认发布、写说明 | 发布说明草稿、范围摘要 | **发布就绪体检、证据包、承诺-实际对照** | 版本、发布计划、发布证据六表 |
| 回顾 / 报表 | 周报、复盘、向上/向外汇报 | 周报草稿、报表解读、异常摘要 | **事实底稿、变更台账、客户简报** | time_log、task_log、历史快照 |
| 个人 / 协作 | 安排待办、处理通知 | 今日计划、逾期解释、通知摘要 | 个人投入叙述（**不作为考核**） | 我的工作、计时 |
| 平台 / 帮助 | 上手、排障、理解口径 | 帮助问答、精准跳转、配置引导 | **口径解释**：为什么两个数不一样 | 6 份帮助文档、口径附录 |

这张表的用法：通用列是“必须有”，差异列是“值得投人”。不要在每个格子都加一个 AI 按钮。

## 4. 通用能力：做薄、做顺、统一交互

### 4.1 清单

| 编号 | 能力 | 做法 | 复用/新增 | 优先级 | 边界 |
| --- | --- | --- | --- | --- | --- |
| G1 | 产品问答与精准跳转 | 精选 FAQ 优先，长尾走帮助文档检索；链接白名单 | 新增助手编排 | P0 | 不编菜单名；答不上来给下一步 |
| G2 | 自然语言建工作项 | 抽取标题/类型/项目/负责人/日期；缺项用选择器；确认卡后落库 | 复用 `TaskCommandService` | P0 | 一次一条；权限与审计复用 |
| G3 | 文档 / PRD → 任务草稿 | 分节、抽取、勾选后创建；与 Word 导入方案合流 | 已有 | P0 | 草稿不落库；不整篇上传时先分节 |
| G4 | 文档完成度体检 | 对照模板与必填项给缺口清单 | 已有 | P0 | 不给“完成度分数”，只列缺什么 |
| G5 | 测试用例生成 | 从需求/文档生成，勾选后入库 | 已有 | P0 | 生成结果需人工确认 |
| G6 | 周报 / 月报草稿 | 从完成、待确认、进行中与工时事实生成；引用记录 | 已有，增强引用 | P1 | 不让模型编工时；异常需标注 |
| G7 | 发布说明草稿 | 从版本范围、已完成任务、缺陷修复生成 | 新增 | P1 | 完成≠发布，措辞必须区分 |
| G8 | 写作润色 / 结构化 | 段落润色、摘要、改写 | 已有 | P2 | 少投入，不追求差异化 |
| G9 | 粘贴会议记录/聊天 → 任务草稿 | 粘贴文本，抽取多条任务，逐条勾选 | 新增 | P2 | 不接外部 IM，不做自动监听 |
| G10 | 截图 / 日志 → 缺陷草稿 | 有视觉模型时读截图；否则粘贴文本 | 新增 | P2 | 需视觉模型；失败降级为文本 |
| G11 | 帮助中心内嵌问答 | 复用 G1，在帮助页提供“问一句” | 复用 | P1 | 与全局助手同一套答案 |
| G12 | 自然语言只读查询 | P1 固定问题；P2 组合查询；服务端预定义查询模板 | 新增 | P1/P2 | 不让模型写 SQL；查询前过滤权限 |
| G13 | 语义搜索 | 向量检索任务/文档/用例 | 新增 | P3 | 先看关键词搜索效果，避免运维成本 |
| G14 | 批量草稿 | 一次生成多条任务，逐条勾选 | 复用 G2/G3 | P2 | 不做无人确认的批量写 |

### 4.2 三条统一规则

1. **同一套交互语言**：所有 AI 写操作都是“生成草稿 → 卡片预览 → 确认 → 执行”；所有 AI 读操作都带“来源 / 推断 / 建议”标签。
2. **同一套错误语言**：额度耗尽、Key 无效、模型不支持 JSON、超时，都翻译成“发生了什么 + 去哪改 + 能不能重试”。
3. **同一套评测**：帮助问答 20 题、建单 5 个场景、证据任务 10 个样例、对抗样例 5 个；每次换模型或改提示词都跑一遍。

### 4.3 通用能力里最值得先做的三个

- **G1 + G2（助手入口）**：决定用户会不会用；也是后续所有场景动作的入口。
- **G3/G4（文档到任务）**：与现有文档工作流贴合，用户已经在文档里写 PRD，转化路径最短。
- **G6/G7（周报与发布说明）**：用户每周/每版本都要写，重复劳动最明显，最容易感知价值；但必须从“通用摘要”升级为“引用事实的底稿”，否则只是另一个写作工具。

## 5. 差异化能力：证据型 AI

### 5.1 为什么沙漏能做，别人难复制

1. **数据模型**：沙漏把计划、完成、实际发布分开记录，有 revision、工时事实、测试计划快照、不可变发布事件。多数工具的 AI 只能读到“当前状态”，无法还原“当时承诺了什么、后来改了什么”。
2. **交付语境**：沙漏的用户是项目制交付团队，最终要向外说明范围、变更与证据；通用工具优化的是内部协作，不产出“可交给客户/老板的说明”。
3. **自托管**：客户敏感数据可以不出内网；“AI 可以关、Key 可以自带、模型可以本地”本身是采购理由。
4. **角色缺口**：小团队没有 PMO，没人专职拼周报和交付说明；AI 必须产出成品，而不是再给一个看板。
5. **记录者受益飞轮**：认真记录的人，AI 替他生成周报、交付说明和证据包；记录越完整，输出越好；输出越好，越愿意记录。这是通用聊天工具没有的循环。

> 护城河不是提示词，是“证据数据模型 + 交付场景默认值 + 记录者受益的循环”。提示词会被抄走，数据模型和历史习惯不会。

### 5.2 能力清单

| 编号 | 能力 | 用户问题 | 产出 | 主要证据 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| D1 | 交付说明生成器 | “这个版本到底交付了什么？给我一份能发出去的说明” | 承诺 / 实际 / 变更 / 证据 / 未完成 / 下期建议 | 需求计划与 revision、任务、测试、发布快照 | P1 alpha，P2 GA |
| D2 | 承诺与变更台账 | “范围为什么变了？改了几次？谁影响的？” | 变更表 + 原因 + 影响 + 缺失原因提示 | 需求调期、版本变更、任务解绑、发布计划 revision | P1 版本级，P2 跨项目 |
| D3 | 发布就绪与证据缺口体检 | “这个版本能发了吗？还缺什么证据？” | 分级清单 + 深链 + 解释 | 版本范围、任务完成、测试计划、分支、发布记录 | P1 只读，P2 证据包 |
| D4 | 交付风险叙述 | “本周哪个项目有风险？为什么？” | 事实 + 可能原因 + 建议核查项 | 逾期、阻塞、停滞、负载、变更 | P2 |
| D5 | 客户 / 干系人简报 | “给客户一份本周进展，别带内部信息” | 脱敏、可外发的简报 | D1 + 外部可见字段 | P2/P3 |
| D6 | 追踪链问答 | “登录页改版这个承诺现在到哪了？” | 需求→任务→测试→分支→版本→发布的链路与缺口 | 全链路记录 | P1 固定问题，P2 自由问 |
| D7 | 复盘事实底稿 | “这个项目为什么延期？把事实按时间线列出来” | 时间线、计划 vs 实际、投入分布、阻塞 | 操作记录、工时、快照 | P2 |
| D8 | 记录质量与口径纠偏 | “为什么报表和发布说明对不上？” | 缺口/矛盾/异常清单 + 补录入口 | 审计、计时、状态、版本关联 | P1 提示，P2 批量 |

### 5.3 四个核心能力展开

#### D1 交付说明

一份可编辑的草稿，默认六段：

1. **本期承诺**：需求、目标版本、计划日期、验收口径。
2. **实际完成**：完成的任务/故事、修复的缺陷、通过的测试。
3. **变更**：时间、范围、原因、影响；引用 revision。
4. **发布与验证证据**：生产发布记录、制品与 SHA256、测试计划快照、分支合并状态。
5. **未完成与风险**：完成未发布、测试未过、范围未覆盖；显示“未记录”而不是推测。
6. **下期建议**：只列候选，不自动排期。

关键约束：

- 每条事实由服务端查询后注入，模型只组织语言；模型不生成 ID、日期、工时数字。
- 每条结论可点回工作项、需求、测试计划或发布记录。
- 缺失证据显式标“未记录”，并给补录入口。
- 导出前检查内部备注、个人信息与客户敏感字段；默认不自动发送。

竞品难点：通用 AI 能总结“本周完成了什么”，但很难回答“当时承诺了什么、变更了几次、发布证据在哪”，因为多数工具没有把这三件事分开存。

#### D2 承诺与变更台账

输出一张表：变更对象、原计划、现计划、变更时间、原因、发起人、影响的任务/版本、原因是否缺失。支持追问“这次延期是谁触发的”“哪些变更没有写原因”。

价值：项目制交付最常见的争议不是“做没做”，而是“什么时候答应的、为什么变了”。沙漏的 revision 已经是现成证据，AI 只是把它读出来。

边界：只读；不自动改计划；不评价变更好坏；原因缺失时提示补充，不替用户编原因。

#### D3 发布就绪与证据缺口体检

固定规则先判定，AI 只解释和排序：

- **范围**：任务完成但未绑版本、版本范围与计划不一致、计划中的任务被移出但无原因。
- **质量**：测试计划未完成、失败用例未转缺陷、无回归记录。
- **代码**：分支未合并、无制品或 SHA256、制品与版本不匹配。
- **发布**：无成功生产记录、只有 test/staging、rollback 或部分成功、发布证据字段缺失。
- **口径**：把“完成”当“已发布”、快照与当前统计混用。

输出 5–10 条，分为“阻断 / 警告 / 提示”，每条带深链。**不是发布门禁**：系统不阻止发布，只把缺口摆出来，决定权仍在人。

#### D6 追踪链问答

回答“这个承诺到哪了”，并把链路缺口摆出来：

> 需求「登录页改版」→ 已排期到 v2.3 → 4 个任务完成 3 个 → 测试计划 12/15 通过，1 个失败未转缺陷 → 分支已合并 → 版本尚无生产发布记录。

P1 先支持固定问题：版本范围、项目风险、我的逾期、某需求追踪。P2 再做自由组合查询。所有查询走服务端模板，模型只负责选模板和叙述，不写 SQL。

### 5.4 共同设计约束

1. **事实由服务端查，模型只叙述**：数字、日期、ID、状态一律来自查询结果。
2. **每条结论可点回**：没有引用的证据型结论不渲染。
3. **区分“记录 / 推断 / 建议”**：推断必须标明依据与不确定性。
4. **不评分、不排名、不预测个人**：与“不以无依据的 AI 评分替代判断”保持一致。
5. **缺口显示“未记录”**：不补全、不猜测、不用行业平均值填充。
6. **写操作确认、可撤销、有审计**：模型不直接调用写接口。
7. **外部版显式导出**：预览、脱敏、人工确认后才可发给客户。
8. **失败可降级**：模型不可用时，规则清单、模板和 FAQ 仍然可用。

### 5.5 支撑差异化的“飞轮能力”：D8 记录质量纠偏

这是最不显眼、但最重要的一项：

- 完成但无发布记录、进行中停滞、日期倒置、版本范围与任务不一致、重复需求、漏记工时。
- 输出“缺什么 + 点哪补”，不自动修改。
- 在周报、交付说明、发布体检里自然出现，让用户感受到“记录越完整，输出越省事”。

没有 D8，证据型 AI 会在脏数据上产出漂亮但不可信的文档；有了 D8，AI 反而推动记录质量，形成正向循环。

## 6. 优先级与路线

### 6.1 排序标准

按五项打分，不做伪精确的数字评分，只用高/中/低：

- **用户价值**：是否直接减少一次沟通或产出一个交付物。
- **差异化**：是否只有沙漏的数据模型能做。
- **数据就绪**：现有记录是否足够，是否需要先补字段/口径。
- **实现成本**：是否复用现有 AI 栈，是否需要新基础设施。
- **风险**：是否涉及写操作、权限、数据出网或对外发布。

### 6.2 分批

| 批次 | 时间参考 | 交付内容 | 依赖 | 成功信号 |
| --- | --- | --- | --- | --- |
| P0 地基 | 现在–4 周 | 助手 MVP（G1/G2）、统一 AI 动作与引用规范、AI 标识与审计、评测集、帮助锚点稳定化 | 现有 AI 栈 | 10 名内部用户试用；100 次真实提问；建单草稿采纳率 ≥50% |
| P1 钩子 | 至 Gate 1（约 2027-02） | D1 交付说明 alpha、D2 版本级变更台账、D3 只读体检、D6 固定问题、G6/G7/G11 | 交付说明 MVP、版本 revision | 3–5 家试点每周 ≥1 份 AI 起草的交付说明；制作 ≤30 分钟 |
| P2 证据 | 至 Gate 2（约 2027-05） | D3 证据包、D1 导出、D4 风险叙述、D5 客户简报、D7 复盘底稿、D8 批量纠偏、G9/G10、确认式批量操作 | 证据包、CI/Git 可选 | 证据完整度 ≥80%；AI 起草占比 ≥60%；修改比例 ≤30% |
| P3 外延 | 至 Gate 3（约 2027-11） | 客户门户问答、CI/Git 证据核对、语义搜索、本地模型、Agent 工作流（条件触发） | 门户、API、集成 | 外部接收人每周使用；≥2 家付费/续用 |

### 6.3 与产品三步走对齐

| 产品钩子 | AI 的角色 | 不做什么 |
| --- | --- | --- |
| Gate 1：交付说明 / 变更台账 | 把记录起草成说明和台账 | 不替 PM 定稿、不自动发客户 |
| Gate 2：发布就绪 / 证据包 / CI | 体检缺口、组织证据、解释偏差 | 不做发布门禁、不自动部署 |
| Gate 3：客户门户 / 决策简报 | 生成脱敏外部版、回答范围与进度 | 不暴露内部评论与个人数据 |

**AI 不单独设路线，跟随三个钩子。** 钩子是产品价值，AI 是放大器和降低制作成本的手段；反过来会把 AI 做成演示，钩子却没落地。

## 7. 产品形态与交互原则

### 7.1 三个入口

| 入口 | 形态 | 适合 |
| --- | --- | --- |
| 全局助手 | 右下角悬浮按钮，非模态面板；移动端全屏抽屉 | 问答、导航、建单、跨对象提问 |
| 场景动作 | 文档、测试、发布、回顾页上的“生成草稿/体检”按钮 | 已有明确对象和上下文，不需要聊天 |
| 环境摘要卡 | 项目驾驶舱、版本页、周回顾里的“本周变化/证据缺口”卡片 | 用户没提问，但需要知道“发生了什么” |

优先级：场景动作 > 环境摘要 > 全局助手。**用户不该为了用 AI 先打开一个聊天框。**

### 7.2 八条交互原则

1. **就地**：默认带上当前项目/版本/工作项作为上下文，不让用户重复描述。
2. **草稿**：先给可编辑草稿，不直接落库、不直接发送。
3. **引用**：每个事实带来源 chip，点开可看原文；没有来源的数字不显示。
4. **区分置信**：标注“来自记录”“来自帮助”“模型推断”“建议核查”。
5. **缺信息用选择器**：能点选就不追问；一次只问一个必填项。
6. **可撤销**：写操作有明确的确认与撤销路径；批量操作先看差异。
7. **成本可见**：显示本次 token、模型、是否降级；批量任务给预算提示。
8. **不假装**：不知道就说不知道，并给“去哪找/问谁/补哪条记录”。

### 7.3 移动端

- 助手改为全屏抽屉，保留顶部当前页面上下文；关闭回到原位置。
- 避让右下角「新建」FAB：打开助手时隐藏，关闭恢复；全屏视图两者都隐藏。
- 输入框跟随软键盘（`visualViewport`），发送中显示“停止”，不锁死页面。
- 草稿卡纵向压缩：只显示标题、项目、截止、负责人；其余折叠到“更多”。

### 7.4 标识与审计

- 所有 AI 生成内容打标：界面显示“AI 生成/起草”，审计记录来源（助手、文档、测试、发布）。
- AI 创建的工作项在审计里可区分“AI 助手起草 + 用户确认”。
- 不把 AI 标识做成免责声明墙；只在关键决策点提示“这份内容是草稿”。

## 8. 指标

北极星不变：**每周有效交付说明数（VDS/W）**。AI 指标只回答“是否降低了制作成本、是否值得信任”，不替代北极星。

| 维度 | 指标 | 建议观察值 |
| --- | --- | --- |
| 采纳 | 助手周活 / 空间活跃成员 | 30–40% |
| 采纳 | 提问后点击链接或采纳草稿的比例 | ≥25% / ≥50% |
| 价值 | 交付说明中 AI 起草占比 | ≥60% |
| 价值 | 人工修改比例 | ≤30% |
| 价值 | 交付说明制作时长中位数 | ≤30 分钟 |
| 价值 | 证据完整度提升 | +10pp |
| 信任 | 证据型答案引用覆盖率 | ≥95% |
| 信任 | 无依据结论比例（每周抽样 30 条） | <2% |
| 信任 | “答不上来”时给出下一步的比例 | 100% |
| 信任 | AI 写操作撤销/回退率 | <1% |
| 成本 | 每活跃用户每周 token、p95 延迟、429 率 | 按实例基线，429 <1% |

### 8.1 评测集

- 帮助问答 20 题（含“如何创建任务”“为什么看不到项目”“AI 设置在哪”）。
- 建单 5 个场景（信息完整、缺项目、缺负责人、相对日期、多任务）。
- 证据任务 10 个（交付说明、变更台账、发布体检、追踪链、风险叙述，各 2 个样例）。
- 对抗样例 5 个（无权项目、歧义项目、数据缺失、文档内提示注入、额度耗尽）。

通过标准：引用可解析、无权限泄露、不编造记录、失败有降级、输出可被人工在 5 分钟内改完。

## 9. 风险与反模式

| 风险 / 反模式 | 表现 | 对策 |
| --- | --- | --- |
| 万能聊天框 | 什么都问、什么都答，答案不可追溯，用户试两次就弃用 | 场景动作优先；范围限定；答不上来给下一步 |
| AI 功能墙 | 每个页面都加按钮，提示词与权限散落 | 统一动作协议；只做高价值场景；集中评测 |
| 幻觉证据 | 编造日期、工时、发布记录、任务 ID | 事实由服务端注入；引用必填；抽样审计 |
| 数据出网 | 自托管卖点被破坏，客户不敢用 | BYOK、出站开关、脱敏、分节上传、本地模型选项 |
| 评分诱惑 | 健康度分数、个人排名、AI 预测工期 | 只做事实叙述与规则清单；不评分、不预测个人 |
| 自治写操作 | Agent 自动改状态、自动发布 | 草稿→确认→执行；可撤销；审计 |
| 维护成本 | 2 人维护几十个提示词与 Agent | 复用 `AiClient`；不引入新基础设施；6 个场景打磨 |
| 记录质量下降 | 用户依赖 AI 编内容，记录更差 | D8 缺口提示；显示“未记录”；不自动补全 |
| 模型依赖 | 换模型后 JSON 失败、额度不足、体验崩塌 | Provider 无关；降级解析；FAQ/模板兜底；固定评测集 |
| 权限泄露 | 模型上下文混入无权项目数据 | 查询时过滤；上下文只放当前用户可见内容；权限回归测试 |

### 9.1 三个最容易走偏的方向

1. **把 AI 当新首页**：做一个“AI 工作台”，让用户先聊天再干活。沙漏的用户是来交付的，不是来聊天的。
2. **把摘要当交付物**：周报、发布说明只做“总结”，不做“承诺-变更-证据”的结构，最后还是要人工拼。
3. **把 Agent 当卖点**：在证据链产品里宣传“AI 自己干活”，会直接削弱“可追溯、可确认”的信任。

## 10. 需要拍板的六件事

| 决策 | 选项 | 建议 |
| --- | --- | --- |
| 主线 | 通用助手 vs 证据型 AI | **证据型 AI 为主线，助手是入口** |
| P0 范围 | 只做助手 MVP vs 助手 + 信任底座 + 评测 | **后者**；引用、标识、评测不能后补 |
| D1 节奏 | 等产品钩子 vs 与 Gate 1 同批 alpha | **同批 alpha**；AI 起草是交付说明的成本优势 |
| 模型策略 | 继续 BYOK vs 空间级共享 Key vs 本地模型 | **P0 继续 BYOK；P2 评估空间级；本地模型作为自托管选项** |
| 数据边界 | 默认发字段 vs 默认发文档正文 | **默认只发必要字段与片段；正文需显式开启；提供脱敏预览** |
| 只读查询 | 固定问题 vs 自然语言自由查询 | **P1 固定问题集；P2 组合查询；始终服务端模板，不让模型写 SQL** |

另外两个建议直接定下来，不必再讨论：

- **所有 AI 输出打标并记录来源**，否则证据型 AI 无法自证。
- **帮助文档章节锚点先稳定化**（当前是运行时 `section-N`），否则问答里的“查看手册”链接会漂。
