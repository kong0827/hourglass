## 0. 结论摘要

### 0.1 一句话结论

沙漏已经具备一套**少见地完整且自洽的“需求→文档→任务→版本→测试→工时→周回顾”数据闭环**，在 50 人以下自托管研发团队这个细分定位上，竞争力不在“功能数量”，而在**一条数据主线 + 自动化工时 + 周回顾 + 自托管**。当前最主要的短板不是“缺一个大功能”，而是**项目这个核心对象太薄、跨对象检索缺失、测试管理停在“用例清单”、以及若干高频交互的可靠性/上下文问题**。下一阶段应当“补核心对象的骨架、修高频路径的体验”，而不是向飞书项目/禅道的功能深度看齐。

### 0.2 七个核心问题的直接回答（详见第 16 章）

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 相比主流产品的核心竞争力 | **一体化轻闭环 + 自动工时/周回顾 + 自托管 + 低配置成本**。飞书项目强在流程与权限深度，禅道强在测试，Linear 强在交互速度；沙漏强在“一个团队一周内能真正用起来，且数据能回到管理者手里”。 |
| 2 | 真实功能缺口 | 项目负责人/起止/成员/里程碑/归档；跨对象统一搜索；测试模块树/测试计划/批量执行/导入导出/测试报告；任务默认归属与孤儿任务治理；文档编辑器首次加载可靠性；项目级角色与审计。 |
| 3 | 哪些竞品功能不需要 | 自定义工作项类型、字段级权限、复杂节点流/审批引擎、多租户 SaaS、实时协同表格、资源平衡/成本核算、预测型 AI 评分、插件市场、IM/会议套件。 |
| 4 | 哪些已有功能需要重新设计 | 项目详情（任务聚合页→项目驾驶舱）、任务新建/详情（全屏抽屉→720px 侧栏）、全局搜索（任务筛选器→跨对象直达）、测试用例（扁平卡片→用例库+测试计划）、导航命名（项目/需求/需求池/文档口径统一）。 |
| 5 | 哪些页面/交互明显不足 | 项目详情信息缺口、任务抽屉字段过载、搜索结果只跳列表、测试用例逐条执行、文档首次打开空白/误报未保存、弹层跨路由残留、顶部动作与筛选拥挤。 |
| 6 | 如何兼顾轻量与专业性 | 只补“对象骨架”和“闭环证据”，不补“配置能力”；用固定字段+折叠高级项替代自定义字段；用测试计划+模块树替代测试平台；用统一搜索替代导航重构；用默认值和模板替代流程配置。 |
| 7 | 下一阶段最值得投入 | **P0：项目实体与驾驶舱、统一搜索、测试计划与模块、文档编辑器可靠性、任务默认项目/弹层生命周期**；随后再做任务抽屉重构、通知聚合、项目模板与追溯矩阵。 |

### 0.3 最值得投入的五件事

1. **把“项目”从任务分组升级为可管理的对象**：负责人、计划起止、成员、当前版本、里程碑、归档。这是所有管理者视图的地基。
2. **做跨对象统一搜索（Cmd+K）**：项目、任务、文档、用例四类直达，复用现有权限与全文索引，不新建搜索页。
3. **把测试用例做成“能承接一次回归”的最小闭环**：模块树 + 测试计划 + 批量执行 + 导入导出 + 结果汇总，缺陷转出能力已经具备。
4. **修高频路径的“信任问题”**：文档编辑器首次加载空白/误报未保存、弹层跨路由残留、新建任务默认无项目。
5. **重构任务详情为 720px 侧栏**：首屏固定“做什么、谁做、何时做、到哪了”，高级字段折叠，评论/关注人右栏常驻。

### 0.4 明确不做（保护定位）

不做自定义工作项类型/字段级权限/复杂工作流设计器/审批引擎/多租户/实时协同编辑/资源平衡/预测型 AI 评分/插件市场/IM 套件。理由见第 13 章：这些能力会显著提高配置与维护成本，直接侵蚀“50 人以下、无专职 PMO、开箱即用”的核心优势。

## 1. 产品现状与定位

### 1.1 产品是什么

沙漏是一套**可自托管的中小型研发协作工作台**。它不是通用项目管理平台，也不是 IM/文档套件，而是围绕研发团队的一条主链路设计：

```
需求池（收集/评审/WSJF）
   → 项目（原“需求”，承载目标与版本）
   → 需求文档（需求/技术方案/验收/其他，树形 + 历史 + 评论 + 分享）
   → 工作项（任务/用户故事/缺陷/史诗，看板/列表/日历/甘特）
   → 版本（计划中/进行中/已发布）
   → 测试用例（执行结果 + 失败转缺陷）
   → 工时（自动计时 + 有效工时口径）
   → 周回顾 / 组合 / 风险 / 负载 / 报表
```

这套链路的最大特点是**同一套数据模型贯穿到底**：需求池的条目、项目的文档、任务、版本、测试用例、工时、周回顾不是拼接的模块，而是共享 `workspace → requirement → task/doc/test_case` 的同一套主键与权限。这一点在竞品中并不常见：飞书靠“空间/工作项/插件”组合，禅道靠“产品/项目/执行”多层级，Linear 则刻意只做 issue。

### 1.2 目标用户与核心场景

| 角色 | 核心诉求 | 沙漏当前支撑 | 主要摩擦 |
| --- | --- | --- | --- |
| 团队负责人/管理者 | 10 秒看懂项目是否健康、谁在做什么、什么时候能交付 | 组合视图、风险、负载、报表、周回顾、项目看板 | 项目本身没有负责人/起止/里程碑，健康度只能从任务反推 |
| 产品/需求负责人 | 收集需求、评审、写清需求与验收、拆任务 | 需求池 + WSJF + 文档树 + AI 拆任务 + 版本 | 需求到用例/缺陷的追溯链不完整；搜索找不到文档 |
| 研发负责人/开发 | 快速建任务、看依赖、更新进度、记工时 | 看板/列表/甘特、依赖、子任务、检查项、计时器、快捷键 | 新建任务默认无项目；任务详情字段过载；弹层残留 |
| 测试 | 管理用例、按计划执行、失败转缺陷、出结果 | 用例 CRUD、步骤、执行流水、失败转缺陷、最近结果 | 无模块树、无测试计划、无批量执行、无导入导出、无测试报告 |
| 空间管理员 | 管人、管权限、管数据、管集成 | 4 级空间角色、项目可见矩阵、备份导出/导入、邮件/Webhook、AI 配置 | 无审计日志、无组织/部门、无系统参数/公告、无存储与任务监控面板 |

### 1.4 技术架构与约束（决定了产品边界）

| 维度 | 现状 | 对产品的含义 |
| --- | --- | --- |
| 后端 | Spring Boot 2.7.18 / Java 8 / MyBatis / Spring Security | 稳定、可私有化；Java 8 限制了部分新语法与生态 |
| 数据库 | MySQL 8，utf8mb4，44 张表 | 单库单实例，事务简单；跨对象检索可用 LIKE/ngram，不宜上 ES |
| 前端 | 原生 JavaScript ES Modules，无框架、无构建 | 首屏轻、部署简单；但复杂交互（拖拽、编辑器、虚拟列表）维护成本高 |
| 实时 | SSE | 适合 50 人以下团队；断线重连与多标签页需验证 |
| 部署 | Nginx 静态资源 + 反向代理、systemd、单实例 | 刻意不支持集群/多租户；备份恢复是运维核心 |
| 存储 | 本地附件/文件，无对象存储 | 附件容量与清理需要管理面板 |
| AI | 每人配置模型与额度；结果需人工确认后落库 | 差异化亮点，但必须坚持“可解释、可撤销” |

> **结论**：架构选择与“轻量自托管”定位一致。不要为了对标 SaaS 竞品引入 Redis/MQ/ES/对象存储；否则部署复杂度会直接摧毁目标用户的使用意愿。

### 1.5 真实使用链路（实机走查）

1. **登录 → 我的工作**：首屏聚合待办、风险、团队概览；首次进入曾出现一次工作区菜单“加载中”卡住，刷新恢复（见 9.7 待验证）。
2. **项目 → 项目看板**：单项目页展示计划周期、预估/实际工时、偏差、任务分布、近 8 周、成员负载；但项目负责人、项目起止、成员、里程碑、当前版本均不在页面上（18-project-detail.png（截图 `18-project-detail.png`））。
3. **新建任务**：抽屉为全屏宽表单，“所属项目”首项为“（无项目）”，截止日期/预计工时在首屏之外（13-new-task.png（截图 `13-new-task.png`）、12-task-drawer.png（截图 `12-task-drawer.png`））。
4. **文档编辑**：首次打开出现空白画布，等待后内容出现；在一次加载未完成时切走，触发“有未保存的修改 221 字”的误报（19-doc-editor.png（截图 `19-doc-editor.png`）、19-doc-editor2.png（截图 `19-doc-editor2.png`））。
5. **全局搜索**：输入关键词后提示“「xx」的搜索结果在看板/列表中查看”，只能跳到任务列表，不能直达项目/文档/用例（15-search.png（截图 `15-search.png`））。
6. **测试用例 → 执行 → 转缺陷**：单条执行可用，失败转缺陷会把步骤与备注写入缺陷描述；但无法按测试计划批量执行（11-testcases.png（截图 `11-testcases.png`））。

## 2. 竞品选择与研究方法

### 2.1 选择逻辑

不以“名气大”为唯一标准，而是按**与本产品的竞争关系**选择样本：

- **同场景正面竞争**：飞书项目（一体化协作平台里的专业项目管理）、Teambition/Tower（轻量项目协作）。
- **能力上限参照**：飞书项目 + 禅道/PingCode（流程深度/测试深度），用于判断“哪些能力值得补、哪些不该补”。
- **体验标杆**：Linear（键盘与详情侧栏）、Asana（项目概览与时间线）、Notion（文档/知识库）、Trello（极简看板）。
- **平台边界参照**：企业微信（身份/连接平台，原生项目管理弱，项目能力主要靠生态），用于判断“哪些事应该集成而不是自建”。

### 2.2 样本矩阵

### 2.4 对比维度

每个模块统一按七维对比：**对象模型 → 功能覆盖 → 信息架构 → 交互路径 → 权限与治理 → 扩展性 → 视觉与可用性**。这样避免“竞品有 A 功能，所以沙漏也要有”的简单对标。

## 3. 竞品功能体系与设计拆解

### 3.1 飞书项目（Meego）

**定位**：面向中大型研发/交付团队的专业项目管理平台，强调“空间—工作项—流程—度量”的可配置性。

**功能体系（官方资料口径）**：

- **空间/业务线**：以空间隔离团队与流程，空间内配置工作项类型、字段、工作流、视图、权限。
- **工作项类型**：需求、任务、缺陷、版本、迭代等；支持自定义工作项类型与属性（企业版能力，具体范围待验证）。
- **节点流/工作流**：状态节点、流转条件、节点权限；支持按工作项类型配置不同流程。
- **字段与字段权限**：自定义字段、字段必填/默认值/可见范围；字段级权限是其专业性的重要来源。
- **视图**：表格、看板、甘特、日历、树形、思维导图等；支持筛选、分组、排序、列配置、视图共享。
- **度量**：内置图表/仪表盘，按工作项、人员、时间聚合；支持自定义度量。
- **测试管理**：官方提供测试用例/测试计划能力（部分以插件/应用形式启用），与缺陷联动；具体开通方式与版本差异需以租户为准（**C 待验证**）。
- **自动化**：状态变更、字段变更触发通知/动作（企业版能力，范围待验证）。
- **权限**：空间角色、项目角色、工作项/字段级权限；适合有 PMO/多团队治理的组织。

**信息架构**：空间 → 业务线/项目 → 工作项 → 详情；左侧导航以“空间/项目/视图”为主，详情多为右侧滑出或独立页。

**交互与设计**：信息密度高、配置入口多；优势是“任何流程都能配”，代价是首次使用需要专人配置与培训。其详情页通常采用“主信息 + 右侧属性/评论”的结构，值得借鉴的是**属性分组与折叠**，而不是字段级权限本身。

**对本产品的启示**：

- 必须借鉴：工作项详情的“核心字段优先 + 属性分组”、视图保存、度量口径说明。
- 谨慎借鉴：自定义字段/字段权限/节点流——沙漏目标团队没有 PMO，配置成本会大于收益。
- 不借鉴：以“空间/业务线”多层隔离替代简单的 workspace/project；沙漏的单空间多项目更轻。

### 3.2 飞书任务 / 飞书文档 / 多维表格 / 管理后台

**飞书任务**：定位个人与轻团队待办，强调“从聊天/文档中一键建任务”、清单、截止提醒、订阅关注、与我相关聚合。它不承担项目计划、版本、测试，是“任务入口”而非“项目管理”。启示：沙漏的“我的工作”应继续强化**聚合与一键处理**，而不是把任务页做成第二个项目页。

**飞书文档/知识库**：块编辑器、多人协同、评论/@、文档树/知识库、权限继承、版本历史、模板。启示：沙漏的文档树、历史、评论、分享已经覆盖核心；缺的是**模板**与**更可靠的编辑体验**，不需要实时协同。

**多维表格**：表格/看板/日历/甘特/表单视图、字段类型、关联/引用、自动化、仪表盘、高级权限。它是“用表格搭应用”的通用工具，能力强但学习成本高。启示：沙漏不应变成“可配置数据库”；但可以借鉴**视图保存、字段分组、表单化录入**三个轻量点。

**飞书管理后台**：组织架构/部门/用户组、角色、应用管理、安全合规、审计日志、SSO/SCIM、数据权限。启示：沙漏不需要组织树与 SCIM，但需要**审计日志、系统信息、备份/邮件/Webhook 的可观测性**，这是自托管产品的信任基础。

### 3.3 企业微信

**定位**：企业身份、通讯录与连接平台；原生能力集中在沟通与协同（消息、文档、微盘、会议、审批、汇报、待办、日程），**项目管理不是其原生核心能力**。

**原生 vs 生态（必须区分）**：

| 能力 | 是否原生 | 说明 |
| --- | --- | --- |
| 通讯录/组织架构 | ✅ 原生 | 企业成员、部门、标签 |
| 消息/群/应用消息 | ✅ 原生 | 触达能力强，适合通知 |
| 文档/微盘/会议 | ✅ 原生 | 协同办公，不是项目管理 |
| 审批/汇报/待办/日程 | ✅ 原生 | 轻量流程与个人待办 |
| 项目/任务/测试/版本 | ✗ 非原生 | 通过开放接口、应用市场第三方应用或自建应用实现 |
| 项目数据与度量 | ✗ 非原生 | 依赖第三方应用或自建 |

**启示**：

- 沙漏应把企业微信视为**身份与通知通道**（扫码登录/应用消息/群机器人），而不是功能对标对象。
- 不要因为企微有审批/汇报就自建审批引擎；沙漏的“版本/状态/评审”已经是轻量流程。
- 若未来做组织同步，优先做**通讯录只读同步/邀请链接**，不做复杂组织权限。

### 3.4 轻量工具：Teambition / Tower / Trello / Asana / Linear / Notion

| 产品 | 核心对象 | 优势 | 局限 | 对沙漏的可借鉴点 |
| --- | --- | --- | --- | --- |
| Teambition | 项目/任务/日程/文件 | 项目首页清晰、模板多、国内团队熟悉 | 测试/研发闭环弱 | 项目首页的“概览+动态+成员”结构；项目模板 |
| Tower | 项目/任务清单/看板/日历/讨论 | 轻、任务清单体验好 | 研发流程与度量弱 | 任务清单的快速录入与分组 |
| Trello | Board/List/Card | 极简、拖拽心智强、Butler 自动化 | 无项目组合/测试/文档 | 看板列的“一个动作只出现一次”；不要把卡片做成表单 |
| Asana | 项目/任务/子任务/里程碑/目标 | 项目概览、时间线、工作负载、规则 | 中量级、配置渐重 | 项目概览的“状态更新+里程碑+进度”；时间线 |
| Linear | Issue/Cycle/Project/View | 键盘优先、Cmd+K、Triage、极快 | 无原生测试管理；甘特/文档能力较轻；强意见流程 | Cmd+K、Triage（需求池）、侧栏详情、速度感 |
| Notion | Page/Database | 文档与数据库灵活、模板强 | 流程弱、易失控 | 文档树、模板、数据库视图（仅借鉴，不做低代码） |

**重点结论**：

- 轻量工具的“轻”不是功能少，而是**默认路径短、配置少、视觉噪音低**。沙漏目前在“功能完整度”上已超过 Trello/Tower，但在“默认路径的顺滑度”上还不如 Linear/Trello。
- Asana 的“项目概览 + 状态更新”非常适合沙漏补齐项目驾驶舱；Linear 的 Cmd+K/Triage 非常适合沙漏的搜索与需求池。

### 3.5 专业工具：禅道 / PingCode

**禅道**：

- 对象：产品 → 项目 → 执行；需求、任务、Bug、用例、测试单、测试计划、发布。
- 测试管理：用例库、模块树、测试计划、测试单、测试报告、评审、导入导出；这是其最强壁垒。
- 设计：信息密度高、界面偏传统；配置项多，学习成本高。
- 启示：沙漏测试模块应借鉴**“模块树 + 测试计划 + 批量执行 + 报告”**四件事，但不借鉴其多层级对象与重配置。

**PingCode**：

- 对象：需求/迭代/任务/缺陷/测试/知识库/工时/度量；一体化程度高。
- 测试：用例库、测试计划、评审、报告、与缺陷/需求联动；追溯能力较强。
- 启示：借鉴**“需求—用例—缺陷”追溯链**，用轻量关联面板实现，不做完整测试平台。

### 3.6 竞品共性结论（8 条）

1. **对象模型清晰**：用户知道“我在哪一层、这个对象属于谁”。沙漏的对象模型其实更简单，但命名把它变复杂了。
2. **详情不离开上下文**：Linear/Asana/飞书均以侧栏/抽屉查看详情；全屏表单只用于“新建/复杂编辑”。
3. **搜索是导航的替代品**：成熟产品都有跨对象搜索/命令面板；用户不再记“功能在哪”。
4. **视图可保存、可共享**：筛选/分组/列配置是高频动作，保存视图能显著降低重复劳动。
5. **测试与缺陷强关联**：用例失败→缺陷→修复→回归是测试管理的核心闭环，单独一个用例列表无法承接。
6. **项目首页回答“健康度”**：负责人、状态、时间、里程碑、风险、进度是标配；只有任务统计不够。
7. **渐进式披露**：核心字段首屏可见，高级字段折叠；配置能力藏在设置里。
8. **一致的视觉系统**：颜色、间距、层级、空状态、危险操作权重一致；这直接影响“专业感”。

## 4. 项目管理对标

### 4.1 本产品现状（代码 + 截图）

**数据模型**：`requirement` 表只有 `id / workspace_id / name / description / status / first_released_at / created_at / updated_at`（[01_schema_full.sql:422](../../sql/baseline/01_schema_full.sql#L422)）。没有负责人、计划起止、成员、当前版本、里程碑、归档字段。

**页面**：18-project-detail.png（截图 `18-project-detail.png`） 显示项目看板包含：计划周期（由任务日期推导）、预估工时合计、实际投入、工时偏差、任务分布、近 8 周新增/完成、成员负载。页面回答的是“任务完成了多少”，而不是“这个项目谁负责、何时交付、现在处于什么阶段、有什么风险”。

**入口**：项目详情路由 `project` 的标题是“项目看板”（[router.js:58](../../frontend/js/core/router.js#L58)），而左侧导航中的“项目”实际对应 `requirement`（历史命名），容易让用户以为有两个“项目”。

**已有优势**：

- 单项目看板与“全部项目”透视表共用一套口径，进度=Σ任务完成度÷任务数，口径可解释。
- 成员负载按“剩余预估 ÷（剩余工作日 × 6h）”计算，对 50 人以下团队足够。
- 组合视图、风险、报表已经能支撑管理者跨项目查看。

## 7. 测试用例管理对标

### 7.1 本产品现状

**不足（截图 + 代码确认）**：

1. **模块是自由文本**（`test_case.module`，注释明确“自由填写，筛选用”），没有模块树/层级，无法按“支付核心/退款”组织。

4. **没有导入/导出**：无法从 Excel/禅道迁移，也无法把用例交给外部。
5. **没有评审**：用例评审（产品/开发/测试三方）没有承载。
6. **没有测试报告**：只有计数，无法输出“本轮通过率/失败清单/缺陷关联”的报告。
7. **用例与任务/缺陷的追溯弱**：仅有 `latest_bug_task_id`，没有“用例覆盖了哪些需求/任务”的矩阵。

- **A 必须补齐**：模块树（或两级路径）、测试计划、批量执行、导入导出、失败证据（附件）。
- **B 值得优化**：测试报告、通过率趋势、用例与缺陷双向跳转。
- **C 可以考虑**：用例评审、需求覆盖矩阵。
- **D 不建议**：测试环境管理、自动化执行平台、测试数据生成、性能测试。

> **关键判断**：沙漏不需要成为 TestRail/禅道，但必须能承接“一次真实回归”。最小闭环 = 模块树 + 测试计划 + 批量执行 + 结果汇总 + 缺陷转出 + 报告导出。这六件事做完，测试模块就从“用例清单”升级为“质量证据”。

## 8. 管理与权限对标

### 8.1 本产品现状

**已实现**：

- 全局管理员：账号列表/创建/编辑/重置密码/删除（[AdminUserController:51-79](../../backend/src/main/java/com/hourglass/controller/AdminUserController.java#L51)）。
- 空间角色：owner/admin/member/viewer；项目可见范围：none/read（[ProjectAccessService:27-38](../../backend/src/main/java/com/hourglass/service/ProjectAccessService.java#L27)）；owner/admin 全量、viewer 全局只读、member 按 `project_member`。
- 设置 Tab：空间/成员与角色/项目可见范围/工作流/集成/数据/活动/账号（[index.html:1544-1552](../../frontend/index.html#L1544)）。
- 工作流：看板列、优先级档位显示名/颜色。
- 集成：邮件、Webhook、AI 模型配置；通知（应用内/SSE/邮件/Webhook）。
- 数据：导出、导入覆盖、备份、清空任务数据（危险操作有确认）。
- 活动：空间活动列表（非完整审计）。

**不足**：

1. **无组织/部门**：只有 workspace 成员，无法表达部门/小组；对 50 人以下团队可接受，但跨部门协作时权限解释成本高。
2. **无自定义角色/RBAC**：固定 4 级空间角色 + 项目可见性；够用，但不能表达“项目负责人/评审人/只读测试”等细分。
3. **无审计日志**：谁改了权限、谁导出了数据、谁重置了密码，无法追溯；自托管产品的合规短板。
4. **无系统参数/字典/公告**：状态/优先级可改显示名，但没有系统级配置页、公告、登录策略。
5. **无存储/任务监控面板**：附件容量、备份结果、邮件/Webhook 失败、SSE 连接数不可见；`HealthController` 有健康检查但无 UI。
6. **无 SSO/LDAP/开放 API**：只有 Webhook（通知出站），没有入站 API/Token；与外部系统集成能力有限（待验证是否有隐藏接口）。
7. **项目角色缺失**：`project_member` 只有 none/read，没有“项目负责人”；项目负责人权限只能靠空间角色，无法做到“某成员只负责某项目”。

### 9.1 方法与样本

- **证据**：截图存于 仅存本地的截图证据（不随公开仓库分发）；页面优化示意见 [`页面优化示意图.html`](../audit/页面优化示意图.html)。
- **限制**：竞品未做同等深度登录实测；部分企业版交互未验证；未做可用性实验室测试与埋点分析。

### 9.2 信息架构分析

**左侧导航分组（现状）**：我的工作 / 项目协作 / 工作项 / 洞察 / 度量 / 设置。

| 分组 | 入口 | 用户心智 | 问题 |
| --- | --- | --- | --- |
| 我的工作 | 我的工作、评审、周回顾 | 个人待办 | 清晰 |
| 项目协作 | 项目、组合、需求池、文档 | 项目与需求 | “项目”实际是 requirement，“需求池”是 demand，“文档”挂在项目下；三者关系需要学习 |
| 工作项 | 看板、列表、日历、甘特、分支 | 执行 | 清晰 |
| 洞察 | 分析、报表、风险、负载、阶段 | 管理 | “阶段”与“版本”容易混 |
| 度量 | 同上部分 | 数据 | 与“洞察”边界模糊 |
| 设置 | 空间/成员/可见范围/工作流/集成/数据/活动/账号 | 管理 | 信息架构合理 |

**核心问题：命名口径不统一。** 数据模型里 `requirement` 的中文注释是“项目（原需求）”，但 UI 同时出现“项目”“需求池”“需求文档”“项目看板”。用户第一次进入时无法判断：

- “项目”与“需求”是不是同一件事？
- “需求池”里的条目通过评审后去了哪里？
- “项目看板”是项目列表还是单项目？
- “文档”与“需求文档”有什么区别？

这不是文案小问题，而是**信息架构的根**。竞品中，飞书用“空间/工作项”明确分层，Linear 用 Issue/Project/Cycle 三个词各指一物；沙漏需要一次彻底的口径统一。

**建议口径（不改数据库表名，只改 UI 文案）**：

| 数据对象 | 建议 UI 名称 | 说明 |
| --- | --- | --- |
| `requirement` | **项目** | 交付容器；路由 `project` 标题改为“项目概览” |
| `demand` | **需求池** | 收集与评审；通过后“转项目”或“关联项目” |
| `requirement_doc` | **文档** | 不再叫“需求文档”，因为含技术方案/验收 |
| `project_version` | **版本** | 不叫“阶段”，避免与项目阶段混淆 |
| `task` | **工作项**（类型：任务/用户故事/缺陷/史诗） | 列表/看板标题统一为“工作项” |

### 9.3 关键用户路径逐步分析

#### 路径 A：管理者查看项目健康度

```
登录 → 我的工作 → 项目 → 选择项目 → 项目看板
```

- **步骤数**：4 步（可接受）。
- **信息获取**：能看到工时、偏差、任务分布、成员负载；**看不到负责人、计划起止、成员、里程碑、当前版本、风险摘要**。
- **业务体验**：管理者需要再去“组合/风险/负载”三个页面拼信息，无法在项目页完成判断。
- **结论**：项目页是“任务统计页”，不是“项目驾驶舱”。这是最高优先级的页面重构。

#### 路径 B：新建并分配任务

```
看板/列表 → 新建任务 → 填写标题/描述/类型/项目/版本/史诗/文档/分支/… → 保存
```

- **步骤数**：1 次点击 + 1 个长表单。
- **摩擦**：抽屉全屏宽；所属项目默认“（无项目）”；截止日期、预计工时在首屏之外；保存前需要滚动确认。
- **业务体验**：开发在站会/临时任务场景下追求“10 秒建完”，当前路径更像“填一份完整表单”。
- **结论**：保留完整字段，但把高频字段前置、低频字段折叠；默认当前项目。

#### 路径 C：写需求文档并分享

```
文档 → 选择项目 → 新建文档 → 选择类型/父级 → 编辑 → 保存 → 分享
```

- **摩擦**：首次打开编辑页空白；加载中切走会误报未保存；文档无模板；分享链接的权限说明不够显眼。
- **业务体验**：文档是需求的载体，编辑器的可靠性直接决定信任；一次误报就会让用户不敢在网页里写长文。
- **结论**：P0 修可靠性；P1 加模板与保存状态可视化。

#### 路径 D：测试执行与缺陷闭环

```
测试用例 → 找到用例 → 执行 → 失败 → 转缺陷 → 去任务看板处理
```

- **摩擦**：用例平铺，模块只能筛选不能树形组织；一次回归要逐条点；失败证据（截图/附件）无处放；没有“本轮测试结果”视图。
- **业务体验**：测试人员无法把“今天跑完 V1.2 回归”作为一件事管理，只能把用例当待办逐条做。
- **结论**：补“测试计划”对象，让测试活动有边界、有结果、有报告。

#### 路径 E：全局搜索定位

```
Cmd+K / 点击搜索 → 输入关键词 → 提示“去列表查看” → 进入任务列表 → 再筛选
```

- **摩擦**：只搜任务；结果不分组；不能直达详情；对项目/文档/用例无效。
- **业务体验**：用户越熟悉产品，越依赖搜索而不是导航；搜索弱会让“功能找不到”的感受放大。
- **结论**：复用现有索引做跨对象搜索，是投入产出比最高的体验改进之一。

#### 路径 F：切换页面时的上下文

```
打开任务抽屉 → 点击左侧“项目” → 抽屉仍在 → 再点“新建项目” → 两个弹层叠加
```

- **摩擦**：路由切换不关闭抽屉/弹层；Esc 逐层关闭，连续按也未必回到干净页面。
- **业务体验**：用户会误以为“操作没生效”或“页面坏了”；更严重的是未保存内容可能丢失。
- **结论**：路由切换统一清理浮层；有未保存内容时先确认再关闭。

### 9.4 视觉设计分析

**做得好的部分**：

- 设计令牌统一：`#F7F8FA` 背景、`#FFFFFF` 卡片、`#E4E7EC` 边框、`#101828/#475467/#98A2B3` 文字层级、`#2563EB` 主色，整体是克制的浅色专业风，接近 Linear/Notion/Jira 的混合气质。
- 信息密度适合桌面 1440px；表格、卡片、抽屉的圆角与阴影一致。
- 看板卡片、甘特条、状态标签的颜色语义清晰；空状态有引导。
- 移动端做了响应式与 PWA，最低可用性达标。

**需要优化的部分（与 `docs/ui-redesign-spec.md` 的 P1–P8 一致）**：

| 编号 | 问题 | 表现 | 影响 |
| --- | --- | --- | --- |
| V1 | 顶部动作堆叠 | 新建、筛选、视图、导出等按钮平铺 | 主次不清，找不到主动作 |
| V2 | 筛选器换行 | 多条件时折成两行，挤压内容 | 页面跳动，视觉噪音 |
| V3 | 卡片层级弱 | 卡片/面板/背景对比不足 | 信息分区靠猜 |
| V4 | 列表无列操作 | 列头不能排序/配置/固定 | 大列表效率低 |
| V5 | 装饰过重 | 渐变/阴影/彩色标签过多 | 专业感被稀释 |
| V6 | 状态不一致 | 空态/加载/错误样式不统一 | 用户不知道发生了什么 |
| V7 | 危险操作同权重 | 删除/清空与普通按钮同样式 | 误操作风险 |
| V8 | 任务详情居中弹窗/全屏 | 遮住上下文，字段过长 | 创建/编辑效率低 |

**视觉优化原则**：

1. **一个页面只有一个主行动**：主按钮实心蓝，其余为次级/幽灵按钮。
2. **筛选收进一行**：常用筛选外露，更多筛选进 Popover；已选条件用 Chip 展示。
3. **卡片用边框与留白分层**，不用重阴影。
4. **危险操作统一红色描边 + 二次确认 + 影响说明**。
5. **加载用骨架屏，错误用可重试的 EmptyState**，不用空白页。

### 9.6 值得保留的设计（不要重做）

1. **统一度量口径**：进度、工时偏差、负载都有明确公式与说明（如“剩余预估 ÷（剩余工作日 × 6h）”）。这是专业性的体现。
2. **自动计时 + 有效工时**：跳过周末、8h 封顶、计时器归属人，贴合研发实际；竞品很少做得这么细。
3. **周回顾**：自动总结完成/待确认/进行中，分区互斥；这是管理者的“周会材料”。
4. **甘特图**：依赖、基线、关键路径、分享，功能深度超出同量级产品。
5. **文档树 + 历史 + 评论 + 分享 + Word 导入**：需求沉淀的完整链路。
6. **需求池 + WSJF + 评审状态机**：从“收集”到“立项”的轻量治理。
7. **批量任务编辑**：6 种批量动作已实现，别被“列表只能单个改”的错觉误导。
8. **快捷键与保存视图**：Cmd+K 聚焦搜索、N 新建、G 跳转、? 帮助；任务视图可保存。
9. **权限矩阵简单可解释**：4 级空间角色 + 项目可见性，够用且容易培训。

**③ 竞品参考**

### 14.8 项目角色、审计与系统信息（P1/P2）

**① 当前问题**  
项目无负责人/角色；无审计日志；自托管缺少版本/备份/存储/邮件/Webhook 的统一可观测页。

**② 问题位置**  
`ProjectAccessService`、`AdminUserController`、设置页。

**③ 竞品参考**  
飞书后台审计、企微操作日志、Linear 企业版审计。

**④ 优化建议**  

- 项目负责人：字段 + 权限（编辑项目设置/成员/归档）；项目成员展示。
- 审计日志最小集：登录成功/失败、权限变更、数据导出、删除/清空、备份恢复；保留 90 天，可筛选/导出。

**⑤ 交互方案**  
审计日志只读表格 + 时间/操作人/动作/对象/结果筛选；系统信息页卡片式；危险操作二次确认写清影响范围。

**⑥ 页面方案**


**⑦ 优先级**：P1（负责人/审计）+ P2（系统信息）。  
**⑧ 预期收益**：责任明确；故障可定位；合规可解释。  
**⑨ 实施成本**：约 5–8 人日。  
**⑩ 验证指标与风险**：审计覆盖关键动作 100%；故障平均定位时间下降；风险：日志量——只记关键动作，不做全量请求日志。

## 16. 最终定位与发展建议

### 16.1 定位重述

> **沙漏是适合 50 人以下自托管研发团队的“需求到交付”轻量工作台：用一套数据模型把需求池、项目、文档、工作项、版本、测试、工时和周回顾串起来；不需要专职 PMO，不要求复杂配置，数据留在自己服务器。**

这个定位有三个关键词：

- **一套数据模型**：不是模块拼装，而是同一条主线；这是竞品最难复制的地方。
- **不需要 PMO**：默认流程可用，配置后置；这是与飞书项目/禅道的根本差异。
- **数据在自己服务器**：自托管、可备份、可审计；这是与 SaaS 的根本差异。

### 16.2 护城河（三层）

| 层 | 护城河 | 现状 | 如何加固 |
| --- | --- | --- | --- |
| 数据层 | 需求→文档→任务→版本→测试→工时→周回顾同源 | 强 | 补项目骨架与追溯，让主线“看得见” |
| 体验层 | 自动工时 + 周回顾 + 甘特 + 文档沉淀 | 强 | 修高频路径（搜索/详情/编辑器） |
| 部署层 | 自托管、单实例、无重依赖 | 强 | 审计/备份可观测，降低运维焦虑 |
| 智能层 | AI 拆任务/文档体检/周报草稿，人工确认 | 中 | 坚持可解释、可撤销，不做评分 |

### 16.3 发展策略：守正、补齐、差异化

1. **守正**：不要为了对标而增加配置能力；保持固定对象、默认流程、轻量部署。
2. **补齐**：项目骨架、统一搜索、测试计划、文档可靠性——这四件是“专业感”的来源。
3. **差异化**：把“自动工时 + 周回顾 + 自托管 + AI 辅助”讲成一个完整故事，而不是功能列表。
4. **克制**：每个新功能先问三个问题：目标团队是否每周用？是否能用现有对象表达？是否增加配置/维护成本？三个答案不理想就不做。

### 16.4 主要风险

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 功能蔓延 | 对标飞书/禅道，配置越来越多 | 用 A/B/C/D 与“三个问题”把关 |
| 体验债务 | 新功能叠在旧交互上，路径更长 | 每个版本留 20% 预算修体验 |
| 数据信任 | 编辑器/保存/权限出现误报 | 自动化 e2e + 明确状态 + 可恢复 |
| 自托管运维 | 备份/升级/邮件/Webhook 故障 | 系统信息页 + 审计 + 运维文档 |
| 竞品替代 | 飞书一体化免费/低价 | 强调自托管、数据主权、轻量闭环 |
| AI 过度承诺 | 用户期待自动决策 | 只做草稿与辅助，人工确认后落库 |

### 16.5 七个核心问题的详细回答

#### Q1：相比主流产品，沙漏的核心竞争力是什么？

**一句话：用一套数据模型，把研发团队从需求到周回顾的闭环做得比轻量工具完整、比专业平台轻。**

- 对 Trello/Tower/Teambition：沙漏多了需求池、文档、版本、测试、工时、周回顾、甘特依赖，且是同源数据。
- 对飞书项目/禅道/PingCode：沙漏少了配置与流程深度，但开箱即用、部署简单、学习成本低，适合没有 PMO 的 50 人以下团队。
- 对 Linear：沙漏多了文档、测试、工时、周回顾、甘特；Linear 更快更聚焦，但不覆盖交付闭环。
- 对 Notion：沙漏有明确的研发流程与度量，不要求用户自己搭数据库。

**真正难被复制的是“同源数据 + 自动工时 + 周回顾 + 自托管”的组合**，而不是某个单点功能。

#### Q2：真实功能缺口有哪些？

按影响排序：

1. 项目实体骨架（负责人/起止/成员/里程碑/归档）与项目驾驶舱。
2. 跨对象统一搜索。
3. 测试模块树/测试计划/批量执行/导入导出/报告。
4. 任务默认项目与孤儿任务治理。
5. 文档编辑器首次加载可靠性与脏状态。
6. 项目负责人权限、审计日志、系统信息页。
7. 通知聚合/深链、项目维度周报、项目模板。

这些缺口的共同点：**不是“缺一个炫技功能”，而是“核心对象的骨架或高频路径的可靠性”**。

#### Q3：哪些竞品功能不需要？为什么？

- **自定义工作项类型/字段/字段级权限**：目标团队没有 PMO 维护；配置越多，默认路径越差。
- **复杂节点流/审批引擎**：沙漏的看板列 + 状态 + 评审已足够；审批会把协作工具变成流程平台。
- **多租户/SaaS**：与自托管、数据隔离、单实例架构冲突。
- **实时协同编辑**：成本高、研发文档以异步为主；历史/评论/分享已够。
- **资源平衡/成本核算**：需要费率、资源日历、跨项目排期；50 人以下团队用不上。
- **预测型 AI 评分**：不可解释，容易误导；README 已明确非目标。
- **插件市场/低代码/IM 套件/测试自动化平台**：维护成本高，应该集成而非自建。
- **组织树/部门/SCIM**：workspace 成员 + 项目负责人足够。

#### Q4：哪些已有功能需要重新设计？

1. **项目详情**：任务聚合页 → 项目驾驶舱（负责人/起止/成员/里程碑/风险/Tab）。
2. **任务新建/详情**：全屏长表单 → 720px 侧栏 + 核心字段首屏 + 更多字段折叠。
3. **全局搜索**：任务筛选器 → 四类对象统一搜索 + 直达。
4. **测试用例**：扁平卡片 → 模块树 + 用例库 + 测试计划 + 批量执行。
5. **导航命名**：多词多义 → 术语表 + 关系说明 + 标题统一。
6. **顶部动作/筛选**：堆叠/换行 → 一个主行动 + 筛选一行 + 更多筛选 Popover。
7. **弹层生命周期**：跨路由残留 → 路由守卫统一清理 + 未保存确认。

#### Q5：哪些页面/交互存在明显不足？

- **项目详情**：缺负责人/起止/成员/里程碑/风险（P0）。
- **新建任务**：默认无项目、关键字段下沉（P0）。
- **文档编辑**：首次空白、误报未保存（P0）。
- **全局搜索**：只搜任务、结果跳列表（P0）。
- **测试用例**：无模块树/计划/批量/导入导出（P1）。
- **任务抽屉**：全屏、字段过载、评论在底部（P1）。
- **弹层**：跨路由残留、Esc 层级不清（P1）。
- **导航**：项目/需求/需求池/文档口径混乱（P1）。
- **看板/列表顶部**：动作堆叠、筛选换行（P1）。
- **移动端**：密度过高（P2）。

#### Q6：如何在保持轻量的前提下提升完整性与专业性？

**四条原则**：

1. **补对象骨架，不补配置能力**：项目负责人/起止/成员/里程碑是“对象骨架”；自定义字段/流程是“配置能力”。前者提升专业性，后者增加负担。
2. **用默认值代替配置**：默认当前项目、默认看板列、默认文档类型、默认测试模块；用户不改也能用。
3. **用“计划/版本/报告”承载专业流程**：测试计划、版本、周回顾都是“有边界的活动”，比流程设计器更轻。
4. **用统一搜索代替导航重构**：搜索是轻量的可发现性方案，不需要重排整个信息架构。

**判断标准**：一个新功能如果要求管理员先配置 30 分钟才能用，就不适合沙漏；如果打开就能用、只在需要时展开，就适合。

#### Q7：下一阶段最值得投入什么？

**按投入产出排序**：

1. **文档编辑器可靠性（2–4 人日）**：投入最小、信任收益最大。
2. **任务默认项目 + 孤儿任务（2–3 人日）**：数据完整性立竿见影。
3. **项目实体 + 驾驶舱（8–12 人日）**：管理者价值的核心。
4. **统一搜索（5–7 人日）**：全站效率杠杆。
5. **测试计划 + 模块树 + 批量 + 导入导出（10–15 人日）**：专业度与测试团队留存。
6. **任务侧栏 + 顶部动作 + 通知中心（Phase 2）**：体验打磨。

**不建议现在做**：项目模板、追溯矩阵、自动化、SSO、暗色模式——这些是 Phase 3 的“锦上添花”，不应抢占 P0 资源。

### 16.6 90 天行动建议

| 时间 | 重点 | 交付物 | 成功标准 |
| --- | --- | --- | --- |
| 第 1–2 周 | 止血 | 文档编辑器修复 + 任务默认项目 + 路由清理浮层 | 误报 0；默认项目率 ≥ 90% |
| 第 3–5 周 | 项目骨架 | 6 字段 + 驾驶舱首屏 + Tab | 信息完整率 ≥ 80% |

| 第 9–12 周 | 体验打磨 | 任务侧栏 + 顶部动作 + 通知中心 | 创建时长 −25%；通知点击 +20% |
