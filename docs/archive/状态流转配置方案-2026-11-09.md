# 状态流转配置方案（矩阵拦截，默认全放开）

- 日期：2026-11-09
- 状态：已实施（2026-11-09，后端编译与受影响单测通过；前端未做浏览器回归）
- 原型：`docs/preview/status-transition-preview.html`（单文件，可直接双击打开，含设置页、看板效果、规则说明三个视图和明暗主题）

## 1. 目标

在「空间设置 / 看板列」里配置状态流转矩阵，用来限制工作项能否从一列直接移到另一列。

做：

- 每个空间一份「来源列 × 目标列」矩阵，每格三态：允许 / 需填原因 / 禁止。
- 默认全部允许；只保存被改动过的格子，没配过就是允许。
- 阻止和提示统一在后端判定，所有移动入口口径一致。

不做：

- 不做条件、审批、状态历史、角色级流程引擎。
- 不改变列自己的计时与逾期规则（处理规则继续独立生效）。
- 不把阻塞变成状态；阻塞仍只是「进行中 / 待验证」上的任务标记。
- 不强制规定必须先配规则才能用；默认全放开，保持现有使用习惯。

## 2. 交互设计

### 2.1 设置页

「看板列」面板下方新增「状态流转」面板：

- 行 = 当前所在列，列 = 目标列；对角线显示「—」，因为同列内是排序，不是流转。
- 每格点一下按「允许 → 需填原因 → 禁止 → 允许」循环，颜色区分：中性灰 / 橙 / 红；改动即时保存，不需要整表提交。
- 图例常驻，右上角显示已设置的限制数量。
- 操作：`恢复默认`（清空全部显式规则，回到「全部允许 + 已完成重开需原因」）。
- 说明文字只讲结论：行是当前列、列是目标列，默认全部允许，只收紧需要的格子。

### 2.2 看板上的反馈

- 允许：直接移动，沿用现有行为（进入可计时列自动开表、进入已完成停表并归档）。
- 需填原因：弹窗要求填写原因，确认后才移动；原因写进活动记录。
- 禁止：本地直接提示「不能从 X 直接到 Y」，不发起请求；空间主 / 管理员确认后可强制移动。
- 拖拽过程中不做悬停禁用态，统一在落下时判定并回弹，避免拖拽样式与最终校验两套口径不一致。

### 2.3 文案

- 三态名称：允许 / 需填原因 / 禁止。
- 禁止提示：`不能从「进行中」直接到「已完成」，请先移到「待验证」`。
- 需原因标题：`移到「已完成」需要填写原因`。

## 3. 规则语义

| 规则 | 行为 | 典型场景 |
|---|---|---|
| 允许 | 直接移动 | 默认值、常规推进 |
| 需填原因 | 弹窗必填原因，写入活动记录后移动 | 退回、重开、跳过验证 |
| 禁止 | 拒绝移动，给出明确提示 | 必须按顺序走，如进行中不能直接完成 |

判定顺序：同一对「来源 → 目标」只有一条规则；未配置时按默认（`已完成 → 非已完成` 需原因，其余允许）。禁止优先于需原因，需原因优先于允许。

## 4. 覆盖入口与例外

必须走同一套判定（前端预判 + 后端强制校验）：

1. 看板拖拽移动。
2. 列表页勾选后批量改列（整批预校验，有一条不合法就整批不动）。
3. 列表行内菜单改列。
4. 卡片菜单「移动到」。
5. 任务抽屉里编辑改列。
6. 取消完成 / 重开（回到完成前所在列时同样判定）。
7. 「我的工作」里的完成按钮。
8. 键盘 ← / → 移列。

前端只负责提前弹原因或给出提示；即使前端缓存过期或绕过界面，后端仍会按同一规则拒绝，避免「拖拽拦住、别的入口能绕」。

不参与拦截（系统行为，放行）：

1. 删除看板列时系统把任务搬到保留列。
2. 导入、备份恢复、初始化种子。
3. 空间主 / 管理员的「强制移动」——保留逃生口，避免规则配错把人堵死。

## 5. 数据与兼容

- 每个空间保存一份规则集合，键是「来源列 + 目标列」，值是三态之一；没有记录时按默认：`已完成 → 非已完成` 为需原因，其余允许。
- 新建列默认对所有人允许；列改名不影响规则（按列 ID 关联）；删除列时清理相关规则。
- 已完成的「重开」默认需填原因，可在矩阵里改成允许或禁止；禁止时空间主 / 管理员仍可强制。
- 现有数据不需要迁移，上线即“全部允许”，行为与现在完全一致。
- 规则变更清空间元数据缓存，看板下一次请求生效。

## 6. 权限与错误码

- 配置权限：空间主 / 管理员；其他成员只读（矩阵禁用）。
- 强制移动：仅空间主 / 管理员；普通成员带 `force` 请求会被拒绝。
- 需要原因：返回 412，前端弹原因输入框，填完带原因重试。
- 禁止流转：返回 422，前端提示不可移动；空间主 / 管理员可确认后强制。
- 强制移动记入移动日志，detail 追加「（强制移动）」；有原因时追加「，原因：xxx」，不单独建审计表。

## 7. 验收标准

1. 新空间、新列默认全部允许，所有现有操作不受影响。
2. 设置「进行中 → 已完成 = 禁止」后，拖拽、批量、抽屉编辑三个入口都被拒绝，提示文案一致。
3. 设置「已完成 → 进行中 = 需填原因」后，取消完成必须填原因，活动记录能看到原因文本。
4. 规则只对配置的「来源 → 目标」生效，其他路径不受影响。
5. 删除列后相关规则自动清理；新建列默认允许。
6. 批量移动中有一条被禁止时，整批不产生任何变更。
7. 空间主/管理员强制移动可以越过规则，并留下审计记录。
8. 前端缓存过期时，后端返回 412/422，界面仍能补原因或强制，不出现“点了没反应”。

验证结果（2026-11-09）：

- 后端 `mvn -DskipTests compile`、`test-compile` 通过；`WorkspaceMetaCacheTest`、`TaskWorkflowServiceNotificationTest`、`WorkspaceServiceMemberCacheTest`、`PermissionRulesTest` 通过。
- 前端所有改动文件通过 ESM 语法检查。
- 未做浏览器端回归：矩阵点击、拖拽弹窗、批量整批失败、抽屉改列等交互需在页面上再走一遍。

## 8. 工作量与风险

| 项 | 估算 |
|---|---|
| 规则存储、读取、统一校验、接口 | 1 天 |
| 设置页矩阵交互 | 1 天 |
| 拖拽 / 批量 / 抽屉 / 重开的禁用态与原因弹窗 | 1.5–2 天 |
| 回归（计时、完成归档、批量、导入） | 1 天 |
| 合计 | 3–5 人日 |

主要风险：

1. 列是可自由配置的，矩阵随列数平方增长（6 列 30 个可配格子），规则配错时用户只看到“拖不过去”，所以禁止提示必须写清“为什么”和“下一步”。
2. 多个移动入口已统一收口到后端校验；新增移动入口时必须调用同一服务，否则会出现“拖拽拦住、新入口能绕过”。
3. 需填原因会打断拖拽节奏，建议只用在退回、重开这类低频操作上。

## 9. 已确认的决策

1. 强制移动：空间主和管理员都可以。
2. 批量移动：任一项被禁止或缺少原因时整批失败，不产生部分变更，错误信息带任务标题。
3. 「已完成」重开：默认「需填原因」，可通过矩阵改为允许或禁止。
4. 默认规则不落库：只有显式改动过的格子才存记录，恢复默认等于清空记录。
5. 与处理规则解耦：矩阵只决定“能不能流转”，列的计时 / 逾期仍由处理规则独立控制。
