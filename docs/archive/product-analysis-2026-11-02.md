# Hourglass 产品化分析报告（2026-11-02）

> **报告视角**：产品经理，面向"把现有工时看板打造成轻量项目管理工具"的决策。
> **对标对象**：Jira（国际标杆）、禅道（国内研发全流程）、PingCode（新一代国内敏捷工具）；辅助参考 Teambition、Worktile、Linear。
> **现状依据**：对仓库约 4.05 万行代码（Java 后端 2.1 万 / 前端 1.8 万）、19 张表、51 次提交的完整审查。
> **阅读对象**：产品决策者、后续负责落地的开发 / AI 实施者。

---

## 1. 现状盘点：我们有什么

### 1.1 项目基本面

| 项 | 值 |
|---|---|
| 定位 | 适合 50 人以下团队的工时驱动任务看板（Hourglass 工作台） |
| 技术栈 | Spring Boot 2.7.18 / Java 8 / MyBatis / MySQL 8；前端零框架零构建 + PWA |
| 部署 | 单 jar + systemd + Nginx，无 Redis / MQ / 对象存储 |
| 功能 | 看板、计时、日历、甘特（自研深水区）、周回顾、完成快照、我的任务、分支、AI 助手、SSE 通知、回收站 |
| 工程资产 | 9 轮代码审查记录、95K 字优化方案、21 个幂等迁移脚本、18 个测试类、一键部署/回滚脚本 |

### 1.2 产品主线（不要丢）

产品的核心主张：**任务管理不是目的，工时和回顾才是**。移动任务驱动计时，计时沉淀成周回顾和月度清单。已固化的口径包括：

| 口径 | 定义 |
|---|---|
| 有效工时 | 跳过周末 + 每人每天合计封顶 8 小时（跨任务、跨空间共享额度） |
| 计时归属 | 计时是"人"的属性，开始 B 自动停 A |
| 完成后接力 | 完成计时中任务后自动接续同列下一任务（不抢其它空间的计时） |
| 日历铺开 | 按实际结束日 = min(完成日, 截止日)，提前完成不占后续日期 |
| 周回顾三区 | 已完成 / 待确认完成 / 进行中互斥 |
| 任务清单 | 完成时落快照，历史统计不受改名 / 删除影响 |

### 1.3 差异化优势（对标竞品仅有的领先项）

| 优势 | 竞品对照 |
|---|---|
| 工时口径 | Jira 工时要买 Tempo 插件；禅道/PingCode 内置但无"每日封顶 + 跳周末"口径 |
| 自研甘特 | 依赖 FS/SS/FF/SF + 滞后、关键路径、基线偏差、SQL 区间分页 + 视口窗口化；Jira 高级路线图要加钱 |
| 周回顾 + AI 周报 | 竞品无原生"能直接发出去的周报"；完成快照表保证历史统计稳定 |
| 轻部署 | 单 jar + MySQL，私有化免费自部署；禅道次之，Jira/PingCode 私有化门槛高 |

**结论：这四项是产品立足点，任何新模块必须复用而不是另造一套。**

## 6. 分阶段路线图

### 阶段 0：模型定稿（2 周，纯设计不写代码）

1. 领域模型：组织 → 空间 → 项目 → 迭代 → 工作项（Epic/Story/Task/Bug）→ 子任务。
2. 命名归位：代码中 `Requirement` 表示"项目"、`RequirementDoc` 表示"需求"，前端混用 req/reqDoc——界面文案先统一为"项目/需求"，表名后改。
3. 兼容策略：`task` 表**加列不加表**（`type` / `sprint_id` / `status_id` / `project_id`），存量数据零迁移。
4. 权限矩阵与工作流规则的最小可用清单（防止做成"万能配置器"）。
5. 并行补 CI + 权限/工作流集成测试——当前 18 个测试类撑不起权限改造。

**里程碑 M0**：模型评审通过；`task` 表加列的迁移脚本通过幂等验证。

### 阶段 1：治理骨架（6 周）→ 交付"有规矩的看板"

| 周 | 交付 |
|---|---|
| W1–2 | 权限切面 + 四档空间角色；统计/回顾接口收口 |
| W3 | 工作项类型（含 Epic 汇总） |
| W4 | 自定义字段（schema 驱动） |
| W5–6 | 工作流引擎（流转规则/必填/后置动作）+ 项目组合总览页 |

**里程碑 M1 验收**：Viewer 只读；Dev 建 Bug 与建 Story 表单不同；"开发→测试"必填提测说明；总览页一屏看到所有项目红黄绿。

### 阶段 2：研发闭环（8 周）→ 交付"能跑完整迭代"

| 周 | 交付 |
|---|---|
| W7–8 | 需求池 + 评审状态 + 优先级评分 |
| W9–10 | Sprint（Backlog/容量/结转），容量复用 8h 工时口径 |
| W11–12 | 缺陷管理（专属字段 + 缺陷趋势） |
| W13 | 版本发布 + 自动发布说明 |
| W14 | 报表中心（燃尽/速度/累积流/交付周期，口径挂 `MetricsService`） |

**里程碑 M2 验收**：一个真实迭代从"需求评审→排期→执行→Bug 修复→发布→回顾"全流程在线上完成；站会用系统投屏，不再拼聊天记录。

### 阶段 3：协作体验（5 周）→ 交付"愿意天天用"

W15–19：@提及/关注/订阅、通知规则引擎、全文搜索、API Token + 入站 Webhook、Jira/禅道导入器、移动端可写。

**里程碑 M3 验收**：第三方脚本用 Token 创建任务成功；从 Jira 导入 500 条历史任务字段不丢；手机上能完成"改优先级+评论"。

### 阶段 4：平台化（按需启动）

SSO → 自动化引擎 → Git/CI 集成 → 多实例。**触发条件**：付费客户 ≥ 3 家或单空间成员 > 30 人时，多实例前置。

### 关键路径依赖图

```
权限矩阵 ──┬─→ 工作项类型 ─→ 缺陷管理 ─→ 缺陷趋势报表
           ├─→ 工作流 ────→ 迭代Sprint ─→ 燃尽/速度图 ─→ 报表中心
           └─→ 项目组合总览
自定义字段 ─→ 需求池评审（评分字段）
API Token ─→ DevOps 集成 / 自动化引擎
```

## 7. 技术路线建议：分层重写，不另起项目

### 7.1 现有资产复用率评估

| 资产 | 复用判断 | 复用率 |
|---|---|---|
| 工时口径 `WorkTime` | 直接保留，差异化核心 | 90% |
| 甘特后端计算（依赖/关键路径/基线/区间分页） | 保留算法，前端重写 | 后端 80% / 前端 20% |
| 周回顾 / 完成快照 | 直接保留 | 85% |
| AI 能力（拆分/体检/周报） | 直接保留 | 85% |
| 任务/项目/需求领域模型 | 需一次模型归位，不能原样扩展 | 50% |
| 权限层 | 必须重写 | 10% |
| 前端（零框架 1.8 万行） | 强表单/强状态场景撑不住，局部引 Vue3 + 组件库，旧页面灰度迁移 | 10–20% |
| 数据库（19 表零外键） | 保留数据，补约束与新表 | 70% |
| 部署/安全实践 | 保留经验，补 Docker/CI | 60% |
| 测试（18 类 / 4 万行） | 不足，是最大改造风险 | 20% |

### 7.2 三条路线对比

| 路线 | 6 周能做到 | 3–4 个月 | 主要风险 | 结论 |
|---|---|---|---|---|
| A. 原地增量 | 总览 + 部分字段 | 工作流/自定义字段让前后端迅速耦合 | 前端债务爆炸 | ✗ |
| B. 分层重写 | 新前端壳 + 治理骨架 | 可交付的小团队 PM | 双端并行期成本 | **✓ 推荐** |
| C. 全新项目 | 只能重做已有功能 | 才刚开始补迭代/缺陷 | 丢掉工时/甘特/回顾资产 | ✗ |

### 7.3 绞杀者模式改造顺序

| 阶段 | 动作 | 旧系统状态 |
|---|---|---|
| 0 | 补 CI + 关键路径集成测试；定领域模型与权限矩阵 | 不变 |
| 1 | 新建权限切面、工作项类型、自定义字段、工作流内核；旧 `task` 表加字段适配 | 看板仍用旧页面 |
| 2 | 新建 Vue3 前端壳，先替换"总览/项目/设置"，旧页面按路由逐步替换 | 新旧页面共存 |
| 3 | 迭代/缺陷/发布/报表建在新内核；旧甘特/回顾通过 API 复用 | 旧模块只读或隐藏 |
| 4 | 数据迁移与灰度：按空间切换，旧系统保留只读一个周期 | 双跑 |
| 5 | 下线旧前端与旧权限逻辑 | 完成 |

### 7.4 一次性升级项

| 项 | 现状 | 目标 | 原因 |
|---|---|---|---|
| Java / Spring Boot | 8 / 2.7 | 17 / 3.x | 2.7 已停止主流支持，建议阶段 2 结束安排升级窗口 |
| 会话/缓存 | 进程内 | Redis | 团队化后必须支持多实例 |
| 附件 | 本地目录 | 对象存储（可选） | 多实例与备份 |
| CI | 无 | GitHub Actions / GitLab CI | 每次改造的安全网 |
| 部署 | systemd | Docker Compose | 降低环境差异 |

| 模块 | 不做原因 |
|---|---|
| 测试用例管理 | 禅道强项但使用率低；用"缺陷 + 用例外链"覆盖，投入产出比差 |
| SaaS 多租户与计费 | 与私有化免费定位冲突，且单实例架构不支持 |
| 插件市场 | API 与协议稳定前是伪需求 |
| 复杂 BPM 审批引擎 | 工时审批用轻量审批（1 条规则配置）即可 |
| 全功能对齐 Jira | 对标其骨架（类型/工作流/Sprint），不对齐其重量（scheme/权限方案的组合爆炸） |

## 9. 风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | 零框架前端撑不住 schema 表单/工作流配置页 | 阶段 1 直接卡死 | 前端局部引 Vue3 + Element Plus，新页面新栈、旧页面灰度迁移（绞杀者模式），不做全量重写 |

| 7 | 备份不含附件二进制 | 换机/磁盘损坏丢附件 | 阶段 1 顺带把附件纳入备份脚本，README 显著提示 |

## 11. 一页纸结论

1. **守住**：工时口径、周回顾、甘特、AI 周报、轻部署——对标矩阵里仅有的三个 🟢，是产品立足点。
2. **先补骨架**：权限/类型/字段/工作流（P0，约 6 周）——不做这个，迭代和缺陷只是往混乱里加数据。
3. **再串闭环**：需求池→Sprint→缺陷→发布→报表（P1，约 8 周）——这是从"看板"到"项目管理工具"的分水岭。
4. **后做体验**：协作/搜索/API/导入（P2，约 5 周）——决定留存与采用门槛。
5. **按需平台化**：SSO/自动化/多实例——被真实规模需求触发再做，不预支。
6. **技术路线**：在现有项目上分层重写（保留后端领域与数据，前端与治理层新建，旧模块绞杀者式灰度替换），不另起项目。
7. **总预算**：P0+P1+P2 约 19 周（单人全职）；P0+P1 约 14 周即可达到"可交付的轻量 PM"。
