# 「已发布」状态：影响与工作量评估

- 日期：2026-11-09
- 交互原型：[published-status-preview.html](../preview/published-status-preview.html)（看板徽标、发布/撤回、身份权限、版本发布自动标记）
- 结论：**把「已发布」做成「已完成」上的单向发布标记（徽标），不是第四个看板状态。**  
  已确认：看板用徽标、发布日期必填且只可补录过去、所有空间默认启用、任务负责人与管理员/项目负责人可发布版本、普通成员可标注自己的任务但不能发布版本、版本首次发布自动标记、新增 `publish_source` 并在活动日志记录发布/撤回。历史已发布版本本期不回填，发布后才完成的任务也不补标（走补丁版本）。权限一律按 `owner_user_id` 严格判断，不用显示名兜底。含这些范围约 **7 人日，另留 0.5–1 人日缓冲**；独立第四状态约 9–13 人日，因为现在整个系统把 `done` 同时当成「完成」「终点」「归档触发」「展示列」四种语义。
- 直接建一个自定义列「已发布」最便宜（0.5–1 人日），但**不满足要求**：完成时间会被清空、完成快照会被删除、统计会把它算成未完成，而且「只能从已完成来」只是可改的配置，不是硬规则。

## 1. 现状：`done` 不是普通状态

任务状态存在 `task.board_column`，`done` 是系统列，不在 `board_column` 表里，由代码硬编码。它同时承担四件事：

| 语义 | 现在的实现 |
|---|---|
| 完成 | 进度按 100 计、完成数/趋势/版本完成数按 `done` 统计 |
| 终点 | 停表、不计逾期、不提醒、不计流程停留 |
| 归档触发 | 移入 `done` 写完成快照；离开 `done` 删完成快照 |
| 展示 | 看板最后一列「已完成」，列表/日历/甘特/分享页都有专属样式 |

硬编码范围（约数）：

- 后端 Java：46 处 `Consts.COL_DONE`，分布在 14 个文件。
- SQL：52 处 `'done'` 字面量，7 个 mapper；其中 `TaskMapper.xml` 约 40 处，其余在版本、需求、需求文档、分支、测试计划。
- 前端：56 处 `boardColumn ===/!== "done"`，分布在 18 个文件；另有 `COLUMNS`、`doneExtra`、`doneScope`、`toggleTaskDone` 等专属逻辑。

所以「加一个状态」不是加一个枚举值，而是要把「完成」和「终点」两个口径从 `done` 里拆出来，或者在 `done` 上增加一个子状态。

## 2. 三种做法对比

| | A. 发布标记（推荐） | B. 独立系统状态 | C. 自定义列 |
|---|---|---|---|
| 数据表示 | `task.published_at`，`board_column` 仍是 `done` | 新增系统列 `published` | 新建自定义列「已发布」 |
| 只能从已完成来 | 发布接口校验 `board_column='done'`，天然满足 | 需要服务端硬规则 + 矩阵默认值 | 矩阵可配，新建/导入可绕过 |
| 不计工时 | 不产生工时记录，天然满足 | 需要确保不可计时 | `ended` 可停表，但 `normal` 会自动开表 |
| 不计耗时 | `completed_at` 不动，天然满足 | 需要改移列逻辑，禁止清空 `completed_at` | 现状会把 `completed_at` 清空 |
| 完成记录 | 不动，天然保留 | 需要改归档逻辑，离开 `done` 不能删快照 | 现状会删除快照 |
| 统计口径 | 不变，发布只是徽标/筛选 | 所有「完成/未完成」口径都要改 | 会被算成「其他列/未完成」 |
| 看板形态 | 仍在「已完成」列，卡片带「已发布」徽标 | 新增一列「已发布」 | 新增一列「已发布」 |
| 发布权限 | 空间主/管理员 + 项目负责人（`requirement.owner_user_id`）+ 任何成员（自己的任务，按 `task.owner_user_id` 严格判断）；版本仅管理员/项目负责人/版本内任务负责人 | 同样需要定义并落到所有入口 | 沿用写权限，无法只给负责人 |
| 版本发布联动 | 版本首次发布时自动标记版本内「已完成且未发布」的任务；发布后完成的走补丁版本，不补标旧版本 | 需额外处理批量标记与统计口径 | 不支持，只能另写脚本 |
| 工作量 | **7 人日（另留 0.5–1 人日缓冲）**（含权限、来源字段、活动日志与版本自动标记） | **9–13 人日** | 0.5–1 人日，但不满足要求 |

## 3. 方案 A：把「已发布」做成「已完成」的子状态

这是最贴合「只是用来作为一个状态记录」的做法：任务在业务上仍然是完成状态，只是多了一个「已发布」标记和发布时间。

### 3.1 数据

```sql
ALTER TABLE task ADD COLUMN published_at DATE NULL COMMENT '发布日期（空=未发布；仅已完成任务可填）';
ALTER TABLE task ADD COLUMN publish_source VARCHAR(16) NULL COMMENT '发布来源：manual 手动 / version 随版本';
```

- 与 `completed_at` 并列，互不覆盖：`completed_at` 是完成时间，`published_at` 是发布时间。
- `publish_source` 与 `published_at` 同生同灭：发布时写入，撤回时清空；普通编辑不能改。
- 版本来源的版本名按当前 `version_task` 关联读取；任务被解绑后只显示「随版本自动标记」，不把版本名复制进任务表。
- 版本归属以 `version_task` 为唯一事实来源。`task.version_id` 字段如果继续保留，绑定/解绑必须在同一事务里同步更新两处；查询和自动标记只认 `version_task`，避免两个来源不一致。
- 可选索引：`KEY idx_ws_published (workspace_id, published_at)`，只在需要按发布日筛选/统计时加。
- 存量数据不回填；老任务保持 `NULL`，历史已发布版本本期也不补 `published_at`，版本页对这类版本显示「历史版本未记录发布状态」；后续需要时按 `released_at` 一次性回填。
- 如果不需要「发布日期」，只加 `is_published TINYINT(1)` 也可以，但建议直接存日期，后续报表不用再改表。

### 3.2 接口与不变量

新增两个动作，不经过看板拖拽：

- `POST /api/tasks/{id}/publish`
- `POST /api/tasks/{id}/unpublish`

规则：

1. `publish` 只允许 `board_column='done'` 且 `published_at IS NULL` 的任务；其他状态返回 400/422。
2. `publish` 必须带发布日期（`YYYY-MM-DD`，默认今天）；允许补录过去日期，但不能晚于今天，也不能早于完成日期。日期为空、未来日期或早于 `completed_at` 返回 400。
3. 任务发布权限：空间主/管理员可发布全部项目；项目负责人可发布自己负责的项目（`requirement.owner_user_id = 当前用户`，该字段为空时不再按创建人/任务负责人猜测，只有空间主/管理员可操作）；任何成员（包括普通成员）可发布/撤回自己负责的任务（`task.owner_user_id = 当前用户`），写权限严格按用户 ID 判断，不用显示名兜底。查看者返回 403。当前用户无法绑定到账号、或任务负责人 `owner_user_id` 为空时，操作入口显示「未绑定账号，无法操作」并拒绝写入。
4. `unpublish` 只允许 `published_at IS NOT NULL` 的任务；权限同上；清空发布日期与来源，任务仍保持 `done`。随版本自动标记的任务，任务负责人可撤回自己的，项目负责人/管理员可撤回项目内全部，版本状态不变。
5. 已发布任务如果要离开 `done`（取消完成/重开/改列），必须先 `unpublish`，否则拒绝并提示「请先撤回发布」。这样「已发布」永远依附于「已完成」。
6. 创建任务、普通编辑、批量改列都不能直接写 `published_at` / `publish_source`；只有发布接口和版本发布自动标记能写，且两者必须同时写、同时清。
7. 发布/撤回必须写任务活动日志（`task_log`）：手动发布记 `publish`、撤回记 `unpublish`、版本自动标记逐任务记 `publish` 且来源为 `version`，保留操作人、时间、日期与版本 ID。版本级再记一条汇总，便于版本动态展示；逐任务记录不能省，否则任务活动里看不到发布。自动标记只对本次实际更新成功的行写日志（见 3.4），避免并发/重试产生重复记录。
8. 备份导出/导入保留 `published_at` / `publish_source`；不合法数据（非 done 但有发布日期，或只有日期没有来源）导入时清空或拒绝，按现有导入策略选一种。
9. 发布日期校验：`DATE(completed_at) <= published_at <= 今天`。后端以服务端日期为准，前端只做同步的 `min`/`max` 提示，不能依赖前端。

### 3.3 权限：谁能发布、谁能撤回

| 角色 | 任务发布/撤回 | 版本发布 |
|---|---|---|
| 空间主 / 管理员 | 全部项目 | 全部项目 |
| 项目负责人 | 自己负责的项目 | 自己负责的项目 |
| 任务负责人（任何成员对自己负责的任务） | 自己的任务（`task.owner_user_id`） | 仅当该版本内有自己负责的任务 |
| 普通成员（对该版本无负责任务） | 自己的任务，可以标注/撤回 | 不可发布版本 |
| 查看者 | 不可 | 不可 |

- **普通成员也可以标注自己的任务已发布**，但仅限 `task.owner_user_id = 当前用户`；不能撤回别人的任务。
- 「项目负责人」本期只认 `requirement.owner_user_id`。该字段为空时，项目级发布/撤回权不开放，由空间主/管理员代操作；不按创建人、任务负责人或显示名推断。多负责人需要 `project_member.role='lead'`，放到二期。
- 任务负责人不是「项目负责人」，两者分开判断，避免把项目级权限误给到个人；所有写权限都按 `owner_user_id` 严格匹配，显示名只用于界面展示。
- 任务没有归属项目（`req_id` 为空）时，只有空间主/管理员可以发布。
- 前端按同一规则隐藏或禁用按钮；服务端仍必须校验，避免直接调接口绕过。用户未绑定账号或负责人字段为空时提示「未绑定账号，无法操作」。
- 版本发布权限不再直接沿用 `ProjectAccessService.assertWrite`。新规则是：空间主/管理员、项目负责人，或该版本内至少负责一项任务的成员。普通成员即使有项目写权限，只要版本内没有自己负责的任务，也不能发布版本；这条需要新增服务端校验。
- **已知副作用**：普通成员只要在该版本内有一项自己负责的任务，就会获得整个版本的发布权。当前已确认接受；如果后续要求「普通成员永远不能发版本」，需要引入独立的发布角色字段，而不是继续复用「版本内是否有负责任务」。
- 任务负责人发布版本会连带自动标记版本内其他人负责的任务，这个后果已确认接受；自动标记以版本发布操作人身份执行并写活动日志。
- 任务负责人可撤回自己的任务（包括随版本自动标记的），但不能撤回别人的；版本级撤回、批量操作仍由项目负责人/管理员执行。

### 3.4 版本发布后自动标记

触发点是版本**首次**从非 `released` 变为 `released`（`ProjectVersionService.publish` 中 `releasing=true` 的分支）：

```sql
UPDATE task t
JOIN version_task vt ON vt.task_id = t.id AND vt.workspace_id = t.workspace_id
SET t.published_at = #{releaseDate},
    t.publish_source = 'version'
WHERE t.workspace_id = #{workspaceId}
  AND vt.version_id = #{versionId}
  AND t.board_column = 'done'
  AND t.published_at IS NULL
  AND DATE(t.completed_at) <= #{releaseDate};
```

规则：

1. 只标记发布当时已经「已完成」且未发布的任务；版本发布后才完成的任务不会自动补标，也不提供批量「补标发布」入口。版本页对这类任务显示「未随本版本发布」并链接到任务，由用户决定手动发布（不改变本版本记录）或另开补丁版本；热修复用新的补丁版本承载，不把新任务塞回旧版本。
2. 发布日期取版本发布日期（`releasedAt` 的日期部分，缺失时取当天）；用 `DATE(completed_at) <= releaseDate` 兜住版本日期被补录到任务完成之前的情况。
3. 自动标记与手动发布写同一条 `published_at` 和 `publish_source`，来源记为 `version`；仍可逐项撤回（任务负责人撤回自己的，项目负责人/管理员撤回项目内全部），撤回不改变版本已发布状态。
4. 重复发布同一个版本（状态已经是 `released`）不会再次标记。
5. 自动标记和版本状态变更必须在同一事务里完成，SQL 使用条件更新（`published_at IS NULL` 且 `board_column='done'`），按实际影响行数取任务 ID 再批量写 `task_log`；只给真正被更新的行记录 `publish` 活动（来源 `version`、版本 ID、操作人=发布版本的人、日期），另写一条版本级汇总「版本 v2.4.0 发布，自动标记 N 项」。并发或重试不会产生重复日志，也不给每个任务单独发通知。
6. 标记后完成数、工时、耗时、完成快照都不变。现有版本通知统计的是版本内全部任务（不区分完成/未完成），本期把文案改为「你负责的 N 项任务在该版本中」，不再暗示这些任务都已发布；验收时也不要把它等同于新增徽标数。
7. 版本发布权限：空间主/管理员、项目负责人，或该版本内至少负责一项任务的成员；普通成员即使有项目写权限，只要版本内没有自己负责的任务也不能发布。自动标记以版本发布操作人身份执行。
8. 历史已发布版本不补标；版本页显示「历史版本未记录发布状态」，避免用户误以为这些版本的任务都漏了徽标。

### 3.5 编辑与移列的保留逻辑

这是最容易漏的地方：

- `TaskCommandService.update` 是用新 `Task` 覆盖更新，必须显式保留旧 `publishedAt` / `publishSource`，否则改标题/负责人就会把发布标记清掉。
- `TaskWorkflowService.move` 是加载原任务再改列，两个发布字段会自动保留；但如果目标不是 `done`，要在移列前检查并拒绝。
- `TaskMapper.update` 的 SQL 要加 `published_at = #{publishedAt}, publish_source = #{publishSource}`；`cols` 和所有显式列清单（如 `selectMyTasks`）都要带上这两个字段。
- 备份导入导出、任务复制、项目模板、批量创建都要显式处理：正常复制不带发布日期/来源；旧备份若带发布日期但任务不是 `done`，按 3.2 第 8 条清空或拒绝。
- 版本自动标记用一条批量 SQL（3.4）完成字段更新，按实际影响行批量写 `task_log`；不要逐个任务调用 `archive` 或逐条发通知。
- 版本归属只读 `version_task`。如果保留 `task.version_id`，绑定、解绑、批量导入都要在同一事务里同步两处；自动标记 SQL 也只 JOIN `version_task`，不要依赖 `task.version_id`。
- 版本发布与自动标记放在同一事务：先条件更新版本状态（避免并发重复发布），再条件更新任务字段并按影响行写日志；失败整体回滚。
- `TaskCompletionService.archive` 不需要改；如果希望任务删除后仍能查「是否发布、何时发布」，再给完成快照加 `published_at` / `publish_source` 两列（可选，不影响主流程）。

### 3.6 前端

最小闭环：

- 看板「已完成」卡片显示「已发布」徽标（日期 + 来源提示）；只有 `publishedAt` 非空时显示。
- 任务抽屉：已完成任务显示「标记发布」/「撤回发布」按钮和发布时间；其他状态不显示。
- 按钮可见性按 3.3 权限：任何成员只在自己负责的卡片上看到「标记发布」；普通成员也能操作自己的任务，但看不到版本发布按钮；无权限时禁用并说明原因，不要只在服务端报错。
- 发布弹窗：发布日期必填、默认今天；`min` 取该任务的完成日期，`max` 取今天；允许补录过去，选择未来日期或早于完成日期时前端提示、后端 400。确认后卡片即时出现徽标，无需刷新。
- 列表：状态列显示「已发布」，并提供「已发布 / 未发布」筛选；发布率只做展示，不改变完成统计口径。
- 来源展示：徽标/列表/抽屉按 `publish_source` 显示「手动标记」或「随版本自动标记」；版本名从当前版本关联读取，解绑后只显示来源、不显示旧版本名。
- 版本页：发布确认弹窗展示「将自动标记 N 项已完成任务」，发布完成后显示结果；已发布版本不重复提供发布入口。发布按钮只对空间主/管理员、项目负责人和版本内任务负责人展示，普通成员不展示。
- 版本页对发布后才完成的任务显示「未随本版本发布」并链接到任务；不提供批量「补标发布」按钮，热修复引导到新的补丁版本。
- 历史已发布版本（无 `published_at` 数据）显示「历史版本未记录发布状态」，不要显示成「0 项已发布」。
- 未绑定账号或负责人字段为空时，发布/撤回按钮禁用并提示「未绑定账号，无法操作」。权限判断只按用户 ID，不按显示名匹配。
- 任务活动日志：手动发布、撤回、版本自动标记都要能看到；版本自动标记逐任务记录，不能只留版本级汇总。
- 分享页、移动端卡片同步显示徽标；徽标组件在看板/列表/抽屉统一，避免文案和样式分叉。
- 「隐藏已完成」逻辑不用改，因为底层仍是 `done`。

如果希望看板上有独立的「已发布」视觉列，可以在 A 的基础上做**虚拟列**：底层仍是 `done`，看板按 `published_at` 把已完成任务分成「已完成 / 已发布」两栏。这样统计口径不变，但拖拽要从「移动列」改成「发布/撤回动作」，前端工作量会增加约 1–2 人日。

### 3.7 工时与耗时

- 工时：手动发布和版本自动标记都不写 `time_log`，不会增加工时；任务在 `done` 时计时已经停止。
- 耗时：`completed_at` 和完成快照的 `total_minutes` 都不动，现有「总耗时/交付周期」不受影响。
- 流程停留：发布不是列移动，不会产生 `task_log` 的 `move` 事件，不会被算成新的停留段。
- 如果以后想看「完成到发布用了多久」，单独用 `published_at - completed_at` 算，不要混进现有工时/耗时指标。

## 4. 方案 B：做成真正的第四个系统状态

如果产品上必须让「已发布」成为和「已完成」并列的状态、能拖进独立列，那就要按下面的范围改。

### 4.1 必须拆开的语义

| 语义 | `done` | `published` | 建议 |
|---|---|---|---|
| 完成/进度 | 是 | 是 | 两者都算完成，否则发布后项目进度会回退 |
| 终点 | 是 | 是 | 两者都不计时、不计逾期、不提醒 |
| 完成快照 | 进入时写，离开时删 | 进入时保留 | 从 `done` 到 `published` 不能删快照 |
| 工时 | 不计新增 | 不计新增 | 不可计时 |
| 完成耗时 | `completed_at` | 不改 `completed_at` | 发布不覆盖完成时间 |
| 流程停留 | 跳过 | 跳过 | 否则会多出一段「已发布停留」 |
| 版本/需求/分支完成数 | 计入 | 必须计入 | 否则发布后这些统计会掉 |
| 循环任务 | 进入时派生下一次 | 不派生 | 只在进入 `done` 时派生 |

一个具体例子：项目 10 项全部完成，进度 100%；如果发布 5 项后统计仍只认 `done`，项目进度会掉到 50%。这是 B 方案最容易被忽略、也最容易被用户当成 bug 的影响。

### 4.2 代码影响面

**后端**

- `Consts`、`TaskSupport`、`TaskCalc`：新增 `COL_PUBLISHED`，区分 `isCompleted` / `isTerminal` / `isPublished`。
- `TaskWorkflowService`：移列时保留 `completed_at`；进入 `published` 不删完成快照；停表；不派生循环任务；重开只允许 `done`。
- `TaskCommandService`：创建/编辑/批量入口禁止直接进 `published`；普通编辑要保留 `published_at`。
- `ColumnTransitionService`：默认规则改为「`done → published` 允许，其余到 `published` 禁止」；并且服务端硬校验，不能只靠矩阵配置。
- `TaskQueryService` / `TaskMapper`：看板增加 `published` 列及分页；所有 `board_column <> 'done'` 改为排除两个终点；所有 `= 'done'` 的完成统计评估是否包含 `published`。
- `FlowHealthService.addSegment`：跳过 `published`，否则「停留时长」会多一段。
- `ProjectVersionService`、`VersionPhaseService`、`DemandService`、`RequirementDocMapper`、`DevBranchMapper`、`EstimateService`、`AiReqDocService`：完成数/进度口径改为包含 `published`。
- `ManagerService`、`MobileService`、`NotificationService`、`BackupService`：`isDone` 改为「完成/终点」判断；备份导入导出支持新列。
- `Response`/`BoardResponse.ColumnDef`：增加 `published` 标记或列类型，前端据此区分。

**SQL**

约 50 处 `'done'` 需要逐条判断，重点包括：

- 未完成查询：`NOT IN ('done','published')`。
- 完成统计：`IN ('done','published')`。
- 逾期/提醒/我的工作：排除两个终点。
- 看板 fallback：`knownColumns` 必须包含 `published`，否则已发布任务会漏进第一个自定义列/待处理列。
- 版本任务排序、列表排序：`published` 排在 `done` 之后。
- 完成快照/趋势/按模块/按负责人：确认是否包含 `published`，避免数字突然下降。

**前端**

56 处 `boardColumn === "done"` 需要逐条判断是「完成」还是「精确的 done」；18 个文件，重点：

- 看板：新增固定列、列计数、分页、拖拽、折叠、空状态、移动端 tab、`doneExtra`/`doneScope` 的拆分。
- 任务抽屉：状态下拉、进度 100 的提示、取消完成/撤回发布。
- 列表/甘特/日历/项目/组合/版本/需求/需求文档/分支/评审/分析/分享页：状态标签、完成数、进度、隐藏已完成、筛选。
- `format.js` 的 `COLUMNS`/`syncColumns`/`isCustom`：`published` 不能被当成可改名/可删的自定义列。
- 设置页：矩阵包含 `published`，且相关格子要说明是固定规则；列管理不能创建同名「已发布」。

**兼容**

- 旧前端/PWA 缓存会把 `published` 当未知列或未完成状态；需要同时发布并 bump service worker 缓存版本。
- 旧备份导入新空间：`published` 要能识别；新备份导入旧版本会回落到待处理，需接受或提示。
- 回滚成本：B 回滚要把 `published` 任务迁回 `done`；A 回滚只需停用标记，成本低很多。

### 4.3 工作量（B）

| 工作包 | 内容 | 人日 |
|---|---|---|
| 状态模型与流转 | 常量/助手、硬规则、创建/编辑/批量/导入拦截 | 1.5–2 |
| 完成/计时/耗时/循环 | 保留完成时间与快照、停表、重开、撤回、循环 | 1–1.5 |
| SQL 与统计 | 7 个 mapper、约 50 处、看板分页、版本/需求/分支/分析 | 2.5–3.5 |
| 前端 | 4 固定列、拖拽、抽屉、18 个文件、56 处判断 | 2.5–3.5 |
| 兼容与数据 | 迁移、备份、PWA、文档 | 1–1.5 |

可选加项：按空间开关（默认关闭）+1–1.5 人日；版本发布自动标记 +1–2 人日；发布报表/快照字段 +0.5–1 人日。

## 5. 为什么 C（自定义列）不满足要求

建一个自定义列「已发布」、处理规则选 `ended`、流转矩阵把其他列到它的格子设为禁止，看起来 0.5–1 天就能完成，但现状代码会这样：

1. `TaskWorkflowService.move` 对任何非 `done` 目标执行 `completedAt = null`，并从 `task_completion_record` 删除记录。  
   结果：完成时间没了，完成记录/总耗时统计也没了。
2. 自定义列在统计里属于「其他列」，项目进度、版本完成数、需求完成数、分支完成数都会把它当未完成。
3. 创建/编辑/导入可以绕过矩阵直接写入该列；矩阵本身也允许管理员改回「允许」。
4. 如果处理规则误设为 `normal`，从 `done` 拖进去还会自动开始计时。
5. 流程停留、提醒、逾期扫描只跳过 `done`，已发布任务会被算成逾期/在制。

所以 C 只能作为「先看一眼」的临时方案，不能作为正式状态。

## 6. 「发布」概念已经很多，先定层级

系统里已经有四个「发布」：

- 版本发布：`ProjectVersion.status = released`，按版本批次发布。
- 分支发布：`DevBranch.status = released`，代码分支上线。
- 文档发布：需求文档 `published_at`，控制成员可见性。
- 需求时间线：`release` 阶段，展示从完成到发布。

再加「工作项已发布」就是第五个。建议在文案上区分：

- 工作项已发布 = 这一项工作是否已经上线/交付（最小单位）。
- 版本已发布 = 这一批工作项的上线批次。
- 分支已发布 = 代码通道的状态。
- 文档已发布 = 文档可见性。

另外，版本发布现在会给负责人发「你负责的 N 项任务已随该版本发布」，但不会改任务状态。已确认改为联动：

- 版本首次发布时，只自动标记「绑定该版本且已完成」的任务；版本发布后才完成的任务不补标，也不做批量补标入口；版本页显示「未随本版本发布」，热修复走新的补丁版本。
- 自动标记可逐项撤回（任务负责人撤回自己的，项目负责人/管理员撤回项目内全部），撤回不改变版本已发布状态。
- 版本通知文案改为「你负责的 N 项任务在该版本中」，只陈述归属，不暗示已发布。
- 分支发布、文档发布仍保持各自独立语义，不联动工作项状态。

## 7. 主要风险

1. **统计回退**：发布后项目/版本/需求进度下降，是 B 方案最大的用户感知风险。
2. **完成记录丢失**：B/C 如果没改归档逻辑，`total_minutes` 和完成记录会消失，历史报表无法解释。
3. **计时误开**：`published` 如果被当成普通列，移入会自动开始计时。
4. **入口不一致**：拖拽、批量、抽屉、键盘、移动端、导入必须走同一套校验，否则会出现「拖不进去但编辑能改」。
5. **旧客户端/PWA**：新状态在旧前端里可能显示为未完成；需要同步发版和缓存版本。
6. **权限与撤回**：谁能发布、谁能撤回、发布后能否重开，必须一开始定清楚，否则上线后靠强制移动补救。
7. **权限边界**：项目负责人按 `requirement.owner_user_id` 判断，任务发布按 `task.owner_user_id` 判断，版本发布还要判断「版本内是否有自己负责的任务」。写权限严格按用户 ID，不用显示名兜底；存量 `owner_user_id` 为空的任务和项目必须先回填，否则负责人会看到「未绑定账号」，项目负责人为空时只能由管理员代操作。重名用户不再影响权限判断。
8. **自动标记预期**：版本发布只处理当时已完成的任务；发布后才完成的任务不补标、也不提供批量补标，版本页显示「未随本版本发布」，需要用补丁版本承载，否则用户会以为「发布了却没标」。
9. **撤回与版本状态脱节**：逐项撤回不改变版本「已发布」状态，同时看版本状态和任务发布状态时需要在报表里说明。
10. **空间噪音**：本次所有空间默认启用，不做开关；徽标是惰性的，没人发布就不出现。如果后续要做独立列，再评估按空间开关。
11. **历史版本没有徽标**：本期不回填历史已发布版本，老任务会保持「未发布」。版本页显式标注「历史版本未记录发布状态」，发布说明里也要写清楚，避免被当成漏标。
12. **活动日志量**：版本发布自动标记会为每个任务写一条 `task_log`，大版本可能一次写入较多记录；只对实际更新行写日志并批量插入，确认任务动态/版本动态的展示不会刷屏。
13. **版本归属双来源**：`version_task` 与 `task.version_id` 同时存在时可能不一致；必须以 `version_task` 为准，保留 `task.version_id` 就要在同一事务同步，否则会出现「版本页有任务、自动标记却没标」。
14. **普通成员获得版本发布权**：「版本内至少负责一项任务」意味着普通成员可能获得整个版本的发布权。本期接受；如果产品后续收紧为「普通成员永远不能发版本」，需要独立角色字段，不能继续靠任务归属推断。

## 8. 建议的落地顺序

如果目标是「先让团队能记录哪些完成了、哪些真的上线了」：

1. **第一步（推荐）**：方案 A 全量——发布标记 + 来源字段 + 徽标 + 发布/撤回 + 权限 + 版本自动标记 + 发布日期 + 活动日志 + 列表筛选，约 7 人日，另留 0.5–1 人日缓冲。
2. **上线前数据准备**：回填 `task.owner_user_id` / `requirement.owner_user_id` 为空的历史数据；无法绑定的账户在界面上走「未绑定账号」提示，不用显示名兜底。
3. **第二步（可选）**：发布统计报表，1–1.5 人日。
4. **第三步（可选）**：看板虚拟「已发布」列，1–2 人日。

如果产品明确要求「已发布」是独立状态、可拖拽、可单独统计，再按方案 B 立项，按 9–13 人日排期。

## 9. 决策状态

已确认（2026-11-09）：

1. 看板不新增独立列，采用「已完成」卡片上的「已发布」徽标。
2. 任务发布/撤回权限：空间主/管理员可操作全部项目；项目负责人可操作自己负责的项目；任何成员（包括普通成员）可操作自己负责的任务；查看者不可。
3. 版本发布权限：空间主/管理员、项目负责人，或该版本内至少负责一项任务的成员；普通成员即使有项目写权限，只要版本内没有自己负责的任务也不能发布版本。任务负责人发布版本会连带标记版本内其他人的任务，后果已确认接受。
4. 记录发布日期：`published_at DATE`，发布时必填，默认当天；允许补录过去日期，不允许未来日期，且不能早于完成日期。
5. 新增 `publish_source`（`manual` / `version`），与 `published_at` 同生同灭；发布、撤回和版本自动标记都要写任务活动日志，版本自动标记逐任务记录。
6. 所有空间默认启用「发布」，不做空间开关。
7. 已发布任务必须先撤回发布，才能取消完成/移出「已完成」。
8. 历史已发布版本本期不回填；老任务保持未发布，版本页显示「历史版本未记录发布状态」，后续需要时再按 `released_at` 一次性补。
9. 任务负责人可以撤回自己的任务（包括随版本自动标记的），但不能撤回别人的。
10. 「项目负责人」只认 `requirement.owner_user_id`；该字段为空时不开放项目级发布权，由空间主/管理员代操作，不按创建人/任务负责人/显示名推断。多负责人需要 `project_member.role='lead'`，放到二期。
11. 版本发布后才完成的任务不补标，也不做批量「补标发布」入口；版本页显示「未随本版本发布」并链接任务，热修复走新的补丁版本。
12. 所有写权限严格按 `owner_user_id` 判断，不用显示名兜底；上线前回填为空的历史负责人数据，未绑定账号的操作入口提示「未绑定账号，无法操作」。
13. 版本归属以 `version_task` 为唯一事实来源；如果保留 `task.version_id`，绑定/解绑必须在同一事务同步。版本发布、自动标记、日志写入放在同一事务，条件更新并按实际影响行写日志，避免并发重复。
14. 版本通知文案改为「你负责的 N 项任务在该版本中」，不暗示都已发布；历史版本显示「历史版本未记录发布状态」。
15. 工作量按 7 人日排期，另留 0.5–1 人日缓冲。

本期不做（非阻塞）：

1. 项目多负责人 / 独立发布角色字段。
2. 版本页批量「补标发布」入口。
3. 历史版本发布状态回填。
