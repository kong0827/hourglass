## 发现

### 1. [P2] 保存任务的迟到成功响应会关闭另一个任务的编辑窗口

- 位置：`src/main/resources/static/js/app.js:1141`、`:1146`；任务打开与字段重新赋值为 `:1041`、`:1046`，关闭入口为 `:1172`–`:1174`。
- 触发：在任务 A 点击保存，请求还未完成时关闭弹窗；打开任务 B 并修改标题等字段；此时 A 保存成功返回。
- 原因：提交时请求 URL 与 payload 已属于 A，服务端没有写错任务，但新增/编辑的成功回调都无条件调用全局 `closeTaskForm()`，没有捕获并校验弹窗代次。保存期间只禁用保存按钮，关闭、取消、遮罩以及 Escape 仍允许离开，因此用户可以打开 B。
- 影响：B 的编辑窗口被 A 的保存回调关闭，尚未保存的编辑被打断。再次打开 B 时 `openTaskForm` 从任务数据重新填充字段，先前草稿会被覆盖。此处不声称 A 的内容被保存进 B；问题是旧操作干扰当前编辑与草稿丢失。
- 验证：提取当前 `taskForm` 提交处理函数，以可控 Promise 模拟 A 保存未完成、当前窗口变为 B 且标题为 `B_unsaved_draft`，再完成 A 请求。输出 `save_request=/api/tasks/A`、`modal_closed_by_A_response=B`、`B_modal_open_after_A_response=false`。字段重填和关闭入口另经源码核对；没有访问真实 API。
- 建议：为任务弹窗建立独立的打开/关闭代次，提交时捕获该代次，只有仍属于原弹窗时才关闭或修改当前表单状态。单纯比较任务 ID 不够，因为同一任务关闭再重开、以及两个新增窗口的 ID 为 null，也可能受到旧响应干扰。保存完成后的看板刷新可正常执行；当前窗口的按钮状态与错误提示应由它自己的操作负责。
- 这是单设备的正常导航问题，与已接受的多人覆盖策略或跨设备计时并发无关。

## 第七轮修复复核

1. 计时：当前 `workSeq` 在打开弹窗及开始/停止操作时递增，`workBusy` 阻止写操作期间的轮询，回调先检查任务和代次再更新按钮。原探针复测输出 `B_remains_disabled=true`、`A_after_old_GET=停止计时`，旧 A 响应不再提前启用 B，旧 GET 不再覆盖新的 start 结果。
2. 周回顾：初次打开与翻周共用 `reviewSeq`，`reviewTarget` 累计用户导航目标。连续两次向前翻周发出 -2、-3 请求，-3 先返回、-2 后返回时最终保持 -3，输出 `review_targets=-2,-3`、`review_after_old_response=-3`。
3. 导入分类：补齐分类表和任务赋值均调用 `normalizeCatName`。当前服务探针导入 `A,B` 后，分类和任务均为 `A B`；通过实际查询参数解析和任务匹配逻辑验证，输出 `selected_category_matches=true`。

此外核对了任务循环关联更新、空间与附件授权、保存视图结构校验、静态缓存、部署备份和提醒发送的相关实现，未新增仅凭猜测或已被接受的限制产生的发现。SSE 无订阅时跳过查询、有订阅时成员查询失败隔离的探针仍通过。
