# 第六轮代码审查（2026-10-14）

## 结论与范围

对第五轮修复后的当前代码继续检查功能完整性、交互连贯性、实现可行性、隐藏缺陷与逻辑边界，确认 3 项问题：1 项 P1、2 项 P2。第五轮报告中的六项问题均已看到对应修复；本轮没有重复将那些已覆盖的路径列为问题。

只新增审查报告，未修改业务代码。会话不踢线、任务最后写入生效且无冲突 UI、JSON 非全量恢复、文件与数据库无 outbox 补偿、同账号跨设备计时并发窗口，继续按照文档约定接受。仓库没有可用的已提交版本历史，不将所有本轮发现都断言为最近修改引入；第 2 项的异常入口来自新增 SSE 成员查询。

## 发现

### 1. [P1] 循环任务残留关联在 ID 复用后可泄露其他空间的私有标题

- 位置：`src/main/java/com/hourglass/kanban/service/TaskService.java:512`，特别是 `:514`–`:517`；清理路径为 `:436`，指定 ID 创建为 `:253`。
- 触发顺序：共享空间循环任务 P 已生成后续任务 K2，P 保留 `recurNextId=K2`；将 K2 放入回收站后彻底删除；另一账号在自己的个人空间以指定 ID K2 创建新任务；共享成员重新打开 P，再完成 P。
- 原因：彻底删除 K2 没有清除指向它的循环关联；创建接口允许复用已释放的 ID。再次完成 P 时，按全局 ID 查到任务就直接当作后续任务复用，没有核对空间或派生身份，且将查到的标题写入 P 的共享时间线。
- 影响：个人任务标题泄露到共享空间成员可读取的日志；P 也无法正确生成自己的下一次循环任务。同空间复用 ID 同样会把无关任务误认作后续任务。这是串行操作下的关联与授权问题，不依赖多人覆盖或计时并发。
- 验证：通过当前 `TaskService.purge/create/move` 执行上述序列，动态 mapper 使用内存假数据，输出 `recurrence_shared_log_contains_private_title=true`、`linked_target_workspace=PERSONAL`。没有调用真实数据库或读取真实私有任务。
- 建议：复用前至少验证目标属于同一空间，任何日志写入都不能先读取并传播越权目标标题；彻底删除、过期清理及覆盖导入应统一处理上游循环引用。还需避免同空间 ID 复用误认，采用不可复用的派生身份或可靠的关联清理规则，并明确后续任务已删除时是否重新生成。

### 2. [P2] 新增 SSE 成员查询异常会在业务处理成功后逃出请求过滤器

- 位置：`src/main/java/com/hourglass/kanban/service/SseService.java:71`；`src/main/java/com/hourglass/kanban/config/ChangeBroadcastFilter.java:28`、`:46`。
- 触发：带 workspace 的变更请求已经完成业务处理并返回成功状态，随后 SSE 广播查询空间成员遇到数据库连接池耗尽、临时连接故障等异常。
- 原因：新增的 `memberMapper.selectByWorkspace` 位于 emitter 发送异常捕获之外；过滤器先执行 `chain.doFilter`，再广播，广播调用也没有隔离异常。即使没有 SSE 订阅者，仍会查询成员并可能失败。
- 影响：已提交的写入之后，异常仍向 Servlet 调用链传播，可能干扰响应交付或连接完成；用户可能认为保存失败而重试，造成重复创建等后果。是否最终返回 HTTP 500 取决于响应是否已提交及容器处理，不能笼统断言所有部署都返回 500。
- 验证：使用当前 `ChangeBroadcastFilter`、当前 `SseService` 与模拟 Servlet 请求/响应及抛错成员 mapper，输出 `business_chain_completed=true`、`filter_exception_after_success=SIMULATED_MEMBER_LOOKUP_FAILURE`。成功状态设为 200；探针证明调用顺序及异常传播，未模拟真实网络响应提交。
- 建议：将广播作为独立的刷新通知，捕获并记录成员查询/广播失败，不让其改变成功业务请求的交付结果；没有订阅者时直接返回。查询失败应停止本次发送，不能降级成向所有账号广播。这是通知失败隔离，不要求实现已排除的 outbox 补偿。

### 3. [P2] 计时操作的迟到响应会覆盖另一个任务弹窗并改变下一次操作

- 位置：`src/main/resources/static/js/app.js:2451`–`:2460`；任务切换入口为 `:1041`，初始化计时状态为 `:2439`。
- 触发顺序：在任务 A 点击开始计时，请求未完成时关闭弹窗并打开未运行计时的任务 B；B 的计时查询先完成，随后 A 的开始响应返回。
- 原因：计时查询 `fetchTimer` 已检查 `editingId === taskId`，但开始/停止操作回调直接调用 `renderWork(d)`，没有记录请求所属任务或弹窗代次。关闭/打开任务不取消该请求，禁用计时按钮也不会禁止切换弹窗。
- 影响：B 弹窗显示 A 的累计工时及“停止计时”。再点击时用当前 B 的 ID 和被 A 污染的按钮状态，发出 `/api/tasks/B/timer/stop`，而不是用户期望的开始 B 计时；后续查询可能恢复显示，但此前已产生误操作。这与服务器同账号跨设备同时开始计时的约定无关。
- 验证：提取当前 `renderWork` 和原计时点击处理函数，以可控 Promise 模拟乱序响应，输出 `B_button_after_A_response=停止计时`、`B_work_after_A_response=计时中 · 已 3 分钟；累计 12`，请求顺序为 `/api/tasks/A/timer/start,/api/tasks/B/timer/stop`。无真实计时数据被修改。
- 建议：发送时捕获任务 ID 与弹窗代次，成功及失败回调只更新仍属于该操作的界面；按钮禁用状态也需按当前弹窗请求管理。任务打开时先确认计时状态，再允许用户操作，避免把默认按钮文案作为唯一运行状态来源。

## 第五轮修复复核

源码核对确认：显式角色写入统一调用管理员锁并按锁定结果保护最后管理员，省略角色时 mapper 跳过角色更新；密码入口新增 UTF-8 72 字节上限；推送改为解析顶层 JSON 对象与整数状态码；日历与列表的成功/失败回调加入请求代次；保存视图增加服务端结构校验与前端先校验后应用；SSE 订阅绑定用户，带空间广播按成员过滤。

这些结论是对修复实现的核对，不代表完成真实 MySQL 并发或浏览器端到端验收。SSE 授权修复的正常路径仍有效，第 2 项是其失败路径未被隔离。

## 验证与限制

- 当前项目 `mvn -o -DskipTests package` 成功，编译 100 个 Java 源文件；无测试源文件，命令跳过测试。
- 当前 app.js 通过 Node `vm.Script` 语法解析。
- Java 探针使用本轮编译的 `target/classes` 和项目依赖，复现循环关联越权日志与过滤器异常传播；Node 探针执行提取的当前函数，复现计时响应乱序。
- 没有执行真实 MySQL 事务/锁集成、浏览器端到端、实际 SSE 网络连接或第三方推送验收。模拟 mapper 不证明数据库运行时的所有行为，但相关分支与 SQL/服务调用结构已核对。
- 探针均使用构造数据并置于系统临时目录，未操作实际业务数据；业务代码保持不变。
