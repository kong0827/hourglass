## 1. 结论先行

1. **思路是否一致**：对象骨架（工作项、视图、版本、测试、权限、通知）与 Jira、TAPD、禅道、Linear 基本同构；战略分叉在于"第一公民"——它们是流程配置、研发模板或协作记录，沙漏是**交付证据**。因此沙漏不该向 Jira 的工作流引擎、禅道的对象层级、飞书的流程引擎看齐。
2. **更适合谁**：10–50 人、项目制或外包交付、有明确版本上线节奏、需要向客户或上级解释"承诺了什么、实际交付了什么、投入在哪"、且能承担自托管运维的团队。最适合兼岗 PM + 兼岗运维的结构。
3. **哪里可以完善**：A 类硬缺口已基本收敛（测试计划、批量执行、用例导入导出、项目删除保护、需求人工交付判定）。剩下的关键不是功能数量，而是四件事：**一页式交付说明缺失、版本范围变更没有过程证据、记录者本人拿不到收益、外部采用门槛偏高**。外加信息架构与发布质量两类"最后一公里"问题。

一句话：**把已有的交付链变成一份能直接发出去的说明，再让写记录的人也能用上这份说明。**

## 2. 对标结论：骨架同构，灵魂不同

### 2.1 各产品的"第一公民"

| 产品 | 第一公民 | 典型选择 | 与沙漏的关系 |
| --- | --- | --- | --- |
| Jira | 可配置流程 | 工作流、字段方案、权限方案组合 | 骨架同构；配置深度不跟 |
| 禅道 | 对象链 + 流程 | 产品-项目-执行三层、用例-测试单-报告 | 追溯同构；层级与概念数量不跟 |
| TAPD | 研发流程模板 | 需求-迭代-缺陷-用例-测试计划 | 链路最接近；SaaS 形态不同 |
| 飞书项目 | 流程引擎 + 协作 | 空间、工作项类型、节点流、度量 | 类型抽象同构；节点流不跟 |
| PingCode | 研发全流程商业套件 | 测试四件套、效能度量、私有化收费 | 测试及格线对齐；套件深度不跟 |
| Linear | 速度 | 键盘优先、默认值、视图即过滤 | 交互克制可学；无工时与测试链 |
| Notion / 多维表格 | 数据即文档 / 表驱动 | 行即页面、多视图、自动化 | 投影思路同构；流程语义不同 |
| Trello / Teambition | 看板心智 | 板-列-卡、执行者/参与者 | 轻量闭环同构；证据链不同 |
| **沙漏** | **交付证据** | 发布记录、完成快照、工时日志、周回顾 | — |

### 2.2 同构与分叉

| 维度 | 主流做法 | 沙漏选择 | 判断 |
| --- | --- | --- | --- |
| 工作项与视图 | 多类型 + 看板/列表/甘特/日历 | 四类型固定 + 五种投影 | 同构，保持 |
| 迭代 | Sprint / 迭代对象 | 无迭代，用版本承载批次 | 有意分叉，写清口径即可 |
| 工作流 | 可配状态机、节点流、审批 | 固定状态机 + 受控列 + 卡点 | 有意分叉，不补引擎 |
| 字段 | 自定义字段矩阵 | 固定字段 + 折叠 + 缺陷专属字段 | 有意分叉，不补矩阵 |
| 测试 | 用例库→评审→计划→执行→报告 | 用例→计划→批量执行→缺陷回链→覆盖矩阵 | 已到及格线，补趋势即可 |
| 工时 | 手填或第三方 | 状态驱动自动计时 + 补记 + 周回顾 | 差异化护城河 |
| 发布 | 流水线状态或版本标记 | 人工确认发布事实 + 快照 + 不可变记录 | 差异化护城河 |
| 协作 | 实时协同编辑、IM 套件 | 乐观锁 + 评论 + 通知 + webhook | 有意分叉，不补协同 |
| 部署 | SaaS 为主 | 单实例自托管，jar + MySQL | 差异化护城河 |
| 交付说明 | 靠人写周报/汇报材料 | **尚未产品化（本次补齐）** | 最大空白 |

## 3. 适合谁，不适合谁

### 3.1 适配判断

用两个轴看：**交付解释压力**（是否需要向外部或上级证明交付）与**流程配置需求**（是否需要为不同团队配不同流程）。

| | 配置需求低 | 配置需求高 |
| --- | --- | --- |
| **解释压力高** | **沙漏甜点区**：项目制、外包、IT 交付、内部系统团队 | Jira / 飞书项目 / 禅道企业版 |
| **解释压力低** | Linear / Trello / 多维表格 | 大型 PMO 平台 |

甜点区画像：10–50 人；有版本或验收节点；兼岗 PM；能接受自托管；关注"这个版本到底交付了什么"而不是"流程能不能任意配"。

### 3.2 三类角色各自要什么

| 角色 | 现在从沙漏拿到什么 | 还缺什么 |
| --- | --- | --- |
| 执行者 | 我的工作、计时、周回顾、阻塞记录 | 记录之后对自己有什么用的直接反馈 |
| 项目负责人 | 版本、发布、报表、负载、逾期 | 一份不改数字就能发出去的交付说明 |
| 管理员 | 权限、备份、通知、审计 | 升级不破坏、演示版本一致、容量边界清楚 |

### 3.3 不建议承接的团队

| 类型 | 原因 | 替代建议 |
| --- | --- | --- |
| 100 人以上多部门、强合规 | 单实例与固定流程撑不住组织复杂度 | Jira / 飞书项目 / 禅道企业版 |
| 需要多租户 SaaS 或按席位计费 | 与私有化免费定位冲突 | 商业 SaaS |
| 需要客户电子签认、计费率、结算锁账 | 属于合同与财务系统边界 | 专业财务/交付系统 |
| 需要任意工作流与字段矩阵 | 会把开箱即用换成配置负担 | Jira / PingCode |
| 纯个人任务管理 | 价值主要来自团队追溯 | Linear / 滴答清单 |

## 4. 完善项总览与分级

分级沿用既有口径：**A 必须补齐**（影响闭环/可用性/数据安全）、**B 值得优化**（已有但不好用）、**C 可以考虑**（增益非必需）、**D 不建议增加**。

| # | 事项 | 现状 | 级别 | 去向 |
| --- | --- | --- | --- | --- |
| 1 | 一页式交付说明 | 只有发布说明、AI 周报、文档样例 | A | WP1 |
| 2 | 版本范围变更账本 | 调期/改版本有日志，但无"基线 vs 实际"对照 | A | WP2 |
| 3 | 记录者收益 | 周回顾偏管理视角，个人交付清单缺 | A | WP3 |
| 4 | 外部采用门槛 | 无 SSO、无公开 API、无 Git 联动、无迁移导入 | A（分客群） | WP4 |
| 5 | 发布确认体验 | 已可用，但字段偏多、默认不友好 | B | WP5 |
| 6 | 项目级里程碑 | 仅工作项 is_milestone 标志 | B | WP6 |
| 7 | 信息架构与体验收敛 | 入口多、术语多义、抽屉密度高、搜索不直达 | B | WP7 |
| 8 | 测试计划增强 | 计划/批量执行已有，缺按版本圈选与趋势 | B | WP8 |
| 9 | AI 克制使用 | 有周报草稿与拆任务，缺交付场景 | C | WP9 |
| 10 | 运维可信 | 基线/增量曾漂移、演示版本滞后 | A（发布质量） | WP10 |
| 11 | 工作流引擎、自定义字段、多级任务、实时协同、插件市场 | 未做 | D | 不做 |

## 5. 设计原则：少填写、少介入

这不是交互风格偏好，而是产品的采用门槛。记录经济学失衡的根因是"成本落在记录者、收益落在管理者"，所以任何新功能先过这张检查表。

| # | 原则 | 落地表现 | 反例（不做） |
| --- | --- | --- | --- |
| 1 | 自动生成优先 | 能从版本、发布、测试、工时推导的，一律不填 | 让用户手写交付摘要 |
| 2 | 0 个必填字段 | 打开即有内容，可直接导出 | 生成前弹 5 项必填表单 |
| 3 | 只确认例外 | 只对缺失、冲突、对外口径要求确认 | 每个区块都要点"已读" |
| 4 | 默认值覆盖多数 | 客户版、最近成功发布、含未发布项 | 每次都要选模板与范围 |
| 5 | 数字只读，文字可改 | 统计值不可编辑，叙述可改写 | 允许手改通过率 |
| 6 | 最多三步 | 进入 → 确认 → 导出/分享 | 配置向导超过一屏 |
| 7 | 缺失即标注 | 显示"未提供/未验证"，不推断、不补造 | 自动编一段原因 |
| 8 | 一次配置全员受益 | 模板、语气、可见范围按空间记忆 | 每人重复设置 |
| 9 | 可回溯、可撤销 | 每个数字可点回原始记录；导出即快照 | 导出后还能改内容 |
| 10 | 高级项折叠 | 默认收起，摘要显示实际值 | 把工时明细摊在主界面 |

**交互验收线**：0 必填、自动字段占比 ≥ 80%、人工确认 ≤ 3 处、从入口到导出 ≤ 3 步、默认生成 ≤ 3 秒。

## 6. 交付物一：一页式交付说明（原型）

原型位置：[delivery-note-2026-11-13.html](audit/prototypes/delivery-note-2026-11-13.html)。单文件、离线可开，含深浅色与完整交互。

### 6.1 它解决什么

把"版本承诺、实际发布、质量验证、投入、遗留风险、证据"收成一页，给**不登录系统的人**看。它不替代发布记录，而是发布记录的对外表达层。

### 6.2 交互主线

| 步 | 用户动作 | 系统行为 | 设计约束 |
| --- | --- | --- | --- |
| 1 | 在版本页点"交付说明" | 读取最近一次成功发布，自动生成 6–8 个区块 | 无需选择，直接出内容 |
| 2 | 看顶部提示 | 显示"2 处文字待确认" | 只标例外，不标全部 |
| 3 | 点"一键确认 2 处" | 清除待确认状态，文字保持可改 | 确认不覆盖已改写内容 |
| 4 | 导出或分享 | 生成不可变快照，分享只读 | 导出即锁定 |

### 6.3 三种语气

| 语气 | 面向 | 包含 | 不包含 |
| --- | --- | --- | --- |
| 客户版（默认） | 客户、验收方 | 范围、变更、质量、后续计划、证据 | 工时明细、内部备注、人员负载 |
| 管理版 | 上级、PMO | 上述 + 投入与负载、风险责任人 | 内部备注 |
| 内部版 | 团队复盘 | 全部 + 内部备注、工时按成员 | — |

语气是**同一份数据的投影**，不是三份文档；切换不重新填任何内容。

### 6.4 默认与例外

| 项 | 默认 | 用户何时需要动 |
| --- | --- | --- |
| 发布记录 | 最近一次成功生产发布 | 从未确认发布 → 阻断客户版 |
| 范围 | 含未发布项（避免范围误读） | 只想给已发布清单时关闭 |
| 工时 | 客户版隐藏，管理/内部版显示 | 客户版需要时可打开 |
| 交付对象 | 项目客户名 | 首次生成时确认一次，之后记忆 |
| 补充说明 | 空 | 完全选填 |

### 6.5 数据来源

| 区块 | 来源 | 缺失时 |
| --- | --- | --- |
| 交付摘要 | 版本范围 + 发布记录 + 测试统计 | 显示"统计未完成" |
| 交付范围 | 版本任务关联 + 发布记录 | 未关联项标"未确认" |
| 变更说明 | 需求调期、任务改版本、发布偏离 | 标"无变更记录"，不编造 |
| 质量与验证 | 测试计划、执行结果、缺陷 | 标"未执行回归" |
| 投入与负载 | 工时日志（计时 + 补记） | 标"未记录工时" |
| 后续计划 | 未完成项、已知问题 | 标"未提供" |
| 证据与附件 | 发布记录、快照、测试报告、需求来源 | 发布未确认时显示"无可用快照" |

### 6.6 阻断与边界

- **客户版没有成功发布记录 → 不能生成、不能分享**，只能切内部版导出带"草稿"标注的文件。
- 分享链接是只读快照，内部备注永不进入分享。
- 数字只读；文字可编辑；导出后锁定，重新生成产生新快照。
- 不替代部署执行、流水线验证、客户验收签认，页脚固定声明。

### 6.7 验收标准

| # | 标准 | 判定 |
| --- | --- | --- |
| 1 | 0 个必填字段 | 打开即可导出 |
| 2 | 默认生成 ≤ 3 秒 | P95，典型项目 100 工作项内 |
| 3 | 待确认 ≤ 3 处 | 超出则说明生成规则有问题 |
| 4 | 每个数字可点回来源 | 抽查 5 个数字全部可追溯 |
| 5 | 客户版无发布即阻断 | 有明确原因与下一步 |
| 6 | 导出快照不可变 | 再次导出内容不随系统变化 |
| 7 | 分享链接不含内部信息 | 客户版/内部版交叉核对 |
| 8 | 全流程 ≤ 3 步 | 版本页 → 确认 → 导出 |

## 7. 实施路径：十个工作包

### 阶段一 · 补闭环（4–6 周）

| WP | 目标 | 主要改动 | 不做什么 | 人日 |
| --- | --- | --- | --- | --- |
| WP1 一页式交付说明 | 版本页一键生成、确认、导出、分享 | 聚合接口；快照模型；三种语气投影；PDF/MD/打印；只读分享 | 不做文档编辑器、不做在线协同 | 8–12 |
| WP2 版本范围变更账本 | 回答"最初承诺什么、现在是什么、为什么变" | 版本范围基线快照；调期/改版本/发布偏离自动归集；变更原因与确认人 | 不做审批流、不做变更单对象 | 5–7 |
| WP3 记录者收益 | 让写记录的人也用得上 | 个人周/月交付清单；"我参与了这个版本的哪些项"；一键生成个人周报；漏记与异常工时提醒 | 不做绩效评分、不做排行榜 | 4–6 |
| WP10 运维可信 | 升级与演示不再成为事故源 | 基线/增量一致性校验；升级兼容检查；备份恢复演练脚本；演示环境版本水印 | 不做高可用集群、不做自动升级 | 3–5 |

阶段一完成标志：任一有成功发布记录的版本，负责人可在 3 步内产出一份可直接发客户的 PDF；个人在周回顾里能直接导出自己的交付清单。

### 阶段二 · 降门槛（7–9 周）

| WP | 目标 | 主要改动 | 不做什么 | 人日 |
| --- | --- | --- | --- | --- |
| WP4a SSO | 让已有身份体系的客户不必再建账号 | OIDC 标准协议；企微/钉钉/飞书作为预设；首次登录自动匹配邮箱 | 不做 LDAP 全量目录同步、不做 SCIM | 5–8 |
| WP4b Git 联动 | 分支与提交能回到工作项 | Webhook 接收；分支命名约定识别；PR/MR 关联展示在版本与工作项 | 不执行部署、不接管流水线 | 8–12 |
| WP4c 迁移导入 | 降低从 Jira/禅道/表格迁入的成本 | CSV 模板导入工作项/需求/用例；字段映射页；导入预检与失败行回执 | 不做全自动双向同步 | 5–8 |
| WP4d 公开 API | 让客户能自己接报表与自动化 | Token 管理；工作项/版本/工时的只读接口；分页与限流 | 不做 GraphQL、不做写入全开放 | 5–7 |
| WP5 发布确认分层 | 把发布确认从表单变成一次确认 | 默认"快速确认"；制品/SHA/目标/偏离理由折叠；异常时才展开 | 不新增发布审批流 | 3–5 |
| WP6 项目级里程碑 | 让管理者看到项目节点而不只是任务 | 项目驾驶舱时间轴；工作项里程碑聚合；可选独立里程碑 | 不做项目集、不做资源平衡 | 5–7 |

阶段二完成标志：一家有 GitLab 与统一身份的项目制客户，可在不写代码的情况下完成账号接入、历史导入与分支关联；发布确认从 6 个字段降到 1 次点击。

### 阶段三 · 收敛体验（4–6 周）

| WP | 目标 | 主要改动 | 不做什么 | 人日 |
| --- | --- | --- | --- | --- |
| WP7 信息架构与体验收敛 | 降低"找不到、看不懂、填太多" | 一级入口归并；术语统一（项目/需求/工作项）；任务抽屉分层；搜索结果直达对象；无权限给禁用原因；分页显示"已加载 x/y"；并发写冲突提示 | 不做全站重写、不做新前端框架 | 8–12 |
| WP8 测试计划增强 | 让回归从"能用"到"顺手" | 按版本一键圈选用例；计划模板复用；通过率趋势 | 不做用例评审流配置、不做多级用例树 | 4–6 |
| WP9 AI 克制使用 | 在交付场景里省时间，不制造结论 | 交付说明文字草稿；范围变更解释；工时异常提示；全部标注"待确认" | 不做评分、预测、自动判定交付 | 3–5 |

阶段三完成标志：新用户在无培训情况下完成"建版本 → 圈用例 → 发布确认 → 导出交付说明"；帮助文档术语与界面一致。

## 9. 风险与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| 1 | 交付说明被当成"自动写周报"，内容失真 | 对外口径事故 | 数字只读、来源可点、缺失即标注、导出前必须确认例外 |
| 2 | 记录者仍觉得记录无收益 | 数据质量下降，交付说明失去依据 | WP3 优先于 WP4；个人清单必须能直接导出 |
| 3 | 版本范围基线只在启用后生效 | 老项目变更账本为空 | 首次打开时以当前范围建基线，明确标注"基线始于某日" |
| 4 | 部分发布、回滚、跨项目范围口径不清 | 同一版本两种说法 | 先定口径再开发：以发布记录的目标环境与范围为准；回滚单独记事件 |
| 5 | SSO/Git 集成带来安全与运维负担 | 部署事故、数据外发争议 | 默认关闭；最小权限；Webhook 只读；文档写明数据流向 |
| 6 | AI 生成内容被直接对外 | 合规与信任风险 | 所有 AI 文字默认"待确认"，不生成数字，不自动确认 |
| 7 | 定位偏窄，试点客户难找 | 规划空转 | 优先外包研发与 IT 交付；用现有客户做样板，不追求通用 |
| 8 | 许可与商业化预期错位 | 客户误以为生产免费 | README、官网、演示环境统一标注许可与支持边界 |

## 10. 明确不做

| 能力 | 不做理由 |
| --- | --- |
| 工作流引擎 / 节点流 / 审批中台 | 50 人团队用固定状态机 + 卡点足够；配置成本高于收益 |
| 自定义字段矩阵 | 用固定字段 + 折叠 + 类型专属字段替代 |
| 多级父子任务 / 项目集 | 检查清单 + 单层史诗已够；层级会推高录入与统计复杂度 |
| 实时协同编辑 | 架构级投入；乐观锁 + 冲突保留草稿是恰当替代 |
| 插件市场 / 开放生态 | API 与协议稳定前是伪需求 |
| 多租户 SaaS / 席位计费 | 与自托管私有化定位冲突 |
| 计费率、审核锁账、客户电子签认 | 属于合同与财务边界；交付说明只解释投入，不用于结算 |
| 预测型 AI 评分 / 自动判定交付 | 不可解释，且会削弱"人工确认事实"的产品主张 |
| IM / 邮件 / 网盘套件 | 用 webhook、邮件、附件做连接，不做替代品 |

## 11. 下一步

1. **评审原型**：用真实项目数据替换示例，重点看客户版是否能直接发出去、内部版是否愿意给团队看。
2. **定口径**：部分发布、回滚、跨项目范围、历史项目基线四条规则先写进手册，再进开发。
3. **技术预研**：交付说明聚合接口与快照模型，先做只读聚合，不碰现有发布记录结构。
4. **拆迭代**：WP1 拆成"自动生成 → 确认与锁定 → 导出与分享"三个可独立验收的迭代。
5. **选试点**：优先一个有 GitLab、有客户验收节点、能自托管的外包或 IT 交付团队，用其真实版本跑通一次对外交付。
