原型说明（与已落地实现一致）

要点做法理由
测试预估是独立字段 工作项「计划」区新增「测试预估（小时，可选）」，与开发「预计耗时」并存；不填按 0 计。 测试投入和开发投入是两笔账。混填会让开发剩余虚高，也说不清是谁的活。
只有测试身份有这份数字 测试剩余只统计「待测试 / 测试中」且本人为测试负责人的工作项；已完成、已取消的测试不再占用未来时间。 口径对齐「他接下来还要干什么」，而不是「他历史上测过什么」。
保守结算 测试剩余 = Σ max(0, 测试预估 − 测试窗口内已计)；窗口未开始的项已计按 0，进行中未收口的轮次也只用已计结算。 宁可把剩余算高，也不把还没发生的测试工时算成已完成，避免排期被低估。
并入个人总负载 总负载 =（开发剩余 + 测试剩余）÷（容量窗口工作日 × 每日容量），每日容量取本人计时设置。 一个人一周能投入的时间是一个池子，开发活和测试活共用同一份容量。
容量窗口纳入测试截止 窗口从今天算到在手工作项（含待测 / 在测）的最晚截止日，最少 5 个工作日、最多 22 个。 只有测试任务的人也有截止日，不能因为开发侧没活就按最短窗口算容量。
合计不重复计数 名册顶部「合计剩余」仍只算开发剩余，测试剩余在旁单独标注。 团队总量保持稳定可比；测试部分可在成员行与驾驶舱单独核对。
可追溯 成员工作台单列测试剩余与测试工作项；驾驶舱剩余列悬停显示「含测试剩余」，CSV 单列「测试剩余(小时)」。 合并成一个总负载后，仍要能拆开解释「为什么是这个数」。

已知边界（本方案不覆盖）

  • 测试预估未填按 0，不按开发预估比例折算——口径可解释优先。
  • 「测试窗口内已计」取计时记录；测试过程没有计时时，测试剩余会偏高。
  • 测试计划 / 用例执行工时不在本链路内，后续若接入需要另定折算口径。
  • 不新增「仅测试身份」的独立名册视图，测试身份并入成员行展示。
  • 驾驶舱成员表仍只列有开发工作项的成员，纯测试身份需从「成员负载」名册的成员卡片查看。
