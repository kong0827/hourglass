工时统计 · 按阶段

跟随当前筛选 · 7 条需求 · 服务端全量聚合，不受甘特分页影响

口径与逻辑复核

阶段时间轴按真实记录回放，不做计划推算；工时统计只使用已有的工作项预估与计时记录。下面是实施前需要一起确认的边界。

阶段时间轴

  • 已复核评审：创建 → 最后一次通过；待评审到今天，拒绝停在拒绝日；同日拒绝后重开按时间比较，不会误停。
  • 已复核排期：最后一次排期 / 调期；撤排后保留历史段；旧排期晚于最后通过时收成单点。
  • 已复核开发 / 测试 / 发布：真实开工、用例与测试窗口、成功生产发布条目；取消停在取消日。
  • 边界无工作项时，即使用例全部通过也不会出现「完成」点（当前要求 taskCount > 0），需要确认是否符合预期。
  • 语义按阶段分组是按需求「当前阶段」归组，不拆行；按阶段拆行把一条需求按 评审 / 排期 / 设计 / 开发 / 测试 / 完成 / 发布 展开成多行，只画该阶段。

工时归属 v1

  • 建议预估：关联工作项 estimate_minutes 合计，整体计入「开发」；工作项预估没有阶段字段。
  • 建议实际：time_log 已结束记录；落在工作项测试窗口内的归「测试」，其余归「开发」。
  • 边界测试窗口只保留最近一轮：task.test_started_at / test_finished_at 会被新一轮覆盖，早期轮次计时可能落入开发。
  • 可选若要在评审 / 设计 / 测试分别录入预估，需要新增「阶段预估」字段或子表，属于 v2。

维度可行性

  • 可行项目：demand.req_id；按项目可见性过滤，与列表一致。
  • 可行目标版本：demand.version_id，是排期目标版本，不等于实际生产发布版本；中途换版本会把工时归到当前目标版本。
  • 可行模块：demand.category_id，是需求模块；模块按项目维护，同名模块需带项目前缀；需求未填模块会落到「未指定」。
  • 后续负责人 / 人员：需求没有负责人字段；工时记录有计时人，但按人统计需要单独口径。

实施前确认

  • 口径测试工时按「最近一轮测试窗口」还是从 task_log 重建全部测试轮次？后者更准，SQL 更复杂。
  • 口径版本维度用「目标版本」还是「实际生产发布版本」？两者在换版本 / 回滚时会不一致。
  • 口径模块维度只认需求模块，还是需求未填时回退到工作项模块？回退会产生跨维度重复。
  • 范围阶段天数是否需要一并上线？它是自然日、阶段可重叠，不能与工时相加。
  • 形态「按阶段拆行」是否随 v1 上线？它最贴合「甘特按阶段看工时」，但行数和滚动明显增加。
  • 性能统计需服务端按全部匹配需求聚合，不能只算甘特已加载的 100 条。
