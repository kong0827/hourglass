登录模块需求说明

版本 2.32026-11-14孔祥劲关联需求：登录改造（K-88）

1. 概述

统一认证平台的登录模块承担全部子系统入口。本期改造目标：统一各子系统登录页视觉与交互口径，补齐失败反馈与安全防护短板，并将登录日志接入审计平台。

2. 用户故事

  • 作为系统用户，我希望登录失败时能立刻看到明确原因，而不是页面无响应。
  • 作为安全管理员，我希望连续失败达到阈值后出现验证码，防止暴力尝试。
  • 作为审计人员，我希望每次登录尝试（含失败）都留有可检索的日志。

3. 接口约定

字段类型说明
accountstring登录账号，工号或手机号，≤64 字符
passwordstring密码密文，RSA 加密传输
captchastring触发风控后必填，≤6 字符

4. 失败反馈

登录失败需要有提示。

5. 验收标准

  • 四类失败场景（密码错误、账号不存在、账号停用、验证码错误）均有对应文案，可通过/失败判定。
  • 连续失败 5 次后图形验证码出现，验证码错误不计入失败次数。
  • 登录日志含时间、账号、IP、结果，保留 180 天。

AI 链路：哪些环节保留、哪些换接口

          
后端 AI 服务是「纯文本进、建议文本出」，与编辑器无关，全部保留；只有最前端的「取选区」和最后一步「写回」要换成 Univer API。

          

            
1 · 取选区现状 window.getSelection() / SunEditor API → 换 Univer 选区与段落 API

            
2 · 请求后端纯文本 + 前后文 + 章节名，POST /api/ai/…，不变

            
3 · 生成建议AiSelectionService 提示词、限流、额度、审计，不变

            
4 · 预览确认对照弹窗、假设单列、用户点替换/插入，不变

            
5 · 写回正文现状 insertHTML 字符串注入 → 换 Univer 命令，天然可撤销、不产生脏标签

对现状的影响面

          
量级：保留（不动）· 小（改函数/适配层）· 中（模块级改造）· 大（涉及数据迁移与双轨）。

          

            

              
              
区域现状换 Univer 后动作 · 量级

              
            

          

        

        

          
需要拍板的决策点

          

            
1. Markdown 双格式是否保留：现状文档分「富文本 / Markdown」两种格式。换 Univer 后建议收敛为统一快照，Markdown 编辑模式退出或只作导入格式；否则双存储长期维护成本高。

            
2. .docx 导出与导入的转换层：开源核心不含 docx 服务。建议沿用现有客户端 docx 导出与导入预览链路，补「快照 ↔ docx」转换；转换不保真的部分（页眉页脚、文本框）沿用现有边界说明。

            
3. 迁移节奏：建议双轨灰度：新建文档走 Univer、存量文档保持 SunEditor 只读/编辑，按项目分批迁移 HTML → 快照；迁移脚本需带校验与回退。

            
4. 多人协同：开源核心只有前端协同能力，服务端要自建（Yjs/OT 持久化）或后续买商业版；建议本期不做，只把快照与 unitId 字段留好。
