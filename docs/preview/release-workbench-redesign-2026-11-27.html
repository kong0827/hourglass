#现状（证据）重设计后取舍
1一屏 23 字段 + 5 段说明文字；记录一次发布最少 7 个动作发布台 3 段：范围 / 事实（4 字段）/ 差异。计划页 4 必填 + 条件字段把"数据模型字段"降级为默认值，只在差异时出现
2就绪卡写「5/5 可提交」，主按钮却是灰的（两套判定不同源）一条动作条一个状态：待说明 N 项 / 可以记录。按钮永远可点，缺口逐项定位禁用按钮只隐藏问题，不解释问题
3失败原因藏在折叠的「高级与异常字段」，报错还要用户去展开结果切「失败」时失败框就地展开并标红必填条件必填就地出现，符合填写动线
4预检需手点，任何改动即作废（15+ 处失效调用）→ 反复"改一下点一次预览"输入停止 400ms 自动重算，右上角显示"检查已同步 · 18:32"预检从"动作"变成"状态"，去掉一次往返
5偏差原因一个 textarea 常驻最底部，红字在中部，结论在下部，视线三段折返逐条差异各带一个原因框，填完即绿；一致项折叠成一句原因与差异同屏，无需理解"哪个原因对应哪件事"
6计划表单 0 个必填标记，但状态=就绪时强制 4 项必填标 *；状态改为「标记就绪」动作，未满足时给清单并定位校验时机与用户意图对齐
7回滚是折叠区里 操作=回滚 的一个下拉值记录行上「回滚这次」按钮 → 发布台进入回滚态，范围/目标自动限定为原事件子集危险操作显式化，且少一次手工核对
8主 CTA 在 300px 右栏，窄屏堆到表单下方，按钮跑出视口底部常驻动作条，全宽固定，任何宽度都在视野内去掉右栏，同时消灭"找不到提交按钮"
9幂等键、查询原键、重试原完整请求、明确重置——四个内部概念直接给用户一条状态横幅："上一条请求状态未知，沙漏已保留，正在确认是否已记录" + 两个按钮用户要的是"我这次到底发出去了没"
10范围勾选 300px 高、无分页，200 项要先点 4 个筛选才能批量选按状态分组 + 组头批量选 + 三个快捷动作（全选已完成 / 恢复计划范围 / 只看差异）绝大多数场景是"发已完成的那批"
四条交互原则
智能默认时间=现在、范围=计划内已完成、环境/覆盖/目标键=继承计划。用户只改动与事实不同的部分，而不是从零填 14 个框。
差异驱动一致的东西不占用注意力：折叠成"其余 5 项与计划一致"。只有不一致才出现一行，并就地要一个原因。
状态常驻底部动作条承载唯一的就绪结论与主按钮；顶部徽标承载唯一的检查时间。不再出现"这里说就绪、那里说不行"。
术语瘦身幂等键、快照令牌、disposition、覆盖未知这类内部词退出界面，只保留业务侧真正会说的：计划、实际、差异、回滚。
落地边界（不改后端也能做）
  • 范围、事实、差异三段全部由现有 /release-preview 的返回字段驱动，无需新增接口；把"点按钮才调"改成防抖自动调即可。
  • 逐条差异原因仍写入现有的 deviationReason 单字段：前端按维度分段拼接（[环境] … [范围] …），后端零改动，历史展示按同样规则拆回。
  • 「标记就绪」复用现有 status=ready 保存路径，只是把校验时机从下拉切换改为按钮触发。
  • 回滚入口复用 operation=rollback + relatedReleaseId，由记录行按钮预填，不再要求用户理解下拉组合。
  • 需要后端配合的一项（可选）：差异原因按维度结构化存储，便于报表统计偏差分布；不做也能跑，只是统计要解析文本。
  • 发布记录时间线默认只看本版本：VersionRelease 已带 versionIds，现有 tab=history 就是版本维度查询，「全部版本」只是去掉过滤条件。
  • 已发布 / 终态版本进发布台不再提供「新建一批范围」，只提供登记回滚与重部署：与现有 contentLocked 判定一致，不新增状态。
  • 在发布台内切版本 = 换主语：范围勾选、计划摘要、来源态一并重置为该版本默认，回滚快照只在它自己的版本上下文里生效，不会残留上一版本已勾的项。
  • 原型数据边界：v0.9.4 展开了工作项与计划范围，v0.9.3 展开了发布快照项（供跨版本回滚演示），其余版本用占位与提示；真实页面按各版本范围加载，交互骨架不变。
