版本 / 模块 · 阶段投入　按阶段看预估与实际耗时；不需要起止时间，分钟按阶段归属直接相加，起止时间只影响“测试窗口归属”和可选的“停留天数”。下面的数字为演示数据。

版本

版本页现有统计按「工作项 → 版本绑定」汇总；项目模块面板按「工作项 → 模块」汇总。当前原型给这两处补上同源的阶段拆分，并明确哪些阶段有真实工时、哪些只有计数。

版本阶段投入

主指标沿用版本卡现有口径（工作项版本绑定）；阶段表逐行标注数据来源，需求口径只用于「进入 / 停留」两列。

阶段口径

版本卡里的「已投入 / 预估 / 剩余」来自工作项；「已排需求」来自目标版本指向该版本的需求。两者不是同一批对象，阶段表用「口径」列区分，避免把需求阶段的工作项工时和需求条数混算。

项目下的模块阶段投入

模块面板本来就是工作项口径（task.category_id）。展开某一行，看该模块的开发 / 测试工时；已完成与未开始用条数表达。

版本范围

展开行只放到「开发 / 测试 / 完成 / 未开始」四段：工作项没有评审、设计、发布的时间字段，模块维度也拿不到需求时间轴，硬拆会编造数据。
模块合计 + 未指定 = 项目合计，与现有模块面板同一套口径；阶段拆分只是在同一批工作项上多两个求和。

为什么没有起止时间也能算

阶段耗时是「分钟的和」，不是区间长度：每条计时记录只归一个阶段，相加即可，不需要阶段首尾日期。起止时间只在两处有用：判断一条计时是否落在测试窗口内，以及算出可选的平均停留天数。

三个口径别混用

  • 口径版本页现有统计是工作项按 task.version_ids 绑定；需求的目标版本是 demand.version_id，换版本后两者会分叉。
  • 口径模块面板按 task.category_id 归集；需求池的模块是 demand.category_id，同名模块也未必同批对象。
  • 建议卡片主指标不动，阶段表用「口径」标签逐行写清来源；需求口径只补「进入 / 停留」两列。
  • 建议「按日期落段」放进 v2 开关：需要需求阶段区间齐备，未落入任何区间的计时要单独列「未归类」。

工时归集规则（与已确认口径一致）

  • 开发工作项 estimate_minutes 全部计入开发；time_log 中不在测试窗口内的分钟计入开发。
  • 测试task.test_started_at / test_finished_at 窗口内的 time_log 计入测试；窗口只保留最近一轮。
  • 边界重开测试会覆盖窗口，早期轮次计时落回开发；需要更准就走 v2 的按日期落段。
  • 不造数评审 / 排期 / 设计 / 完成 / 发布没有计时来源，阶段表显示「—」，不给推算值。

实施落点

  • 复用做一个 StageEffort 归集器：输入工作项集合 + 计时记录 → 开发 / 测试分钟，门禁与权限沿用现有查询。
  • 版本/api/phase/stats 的每个版本行加 devMinutes / testMinutes，同一次快照内求和，不新增查询轮次。
  • 模块/api/manager/projects/{id} 的模块行加 devMinutes / testMinutes；合计 + 未指定仍等于项目合计。
  • 可选版本卡上的阶段条只需 2 段（开发 / 测试）；7 行明细放展开区，默认收起，避免卡片过高。

实施前确认

  • 范围版本卡的阶段表是否要「需求口径」的进入 / 停留两列？需要按目标版本 join 需求时间轴，多一次聚合。
  • 交互模块行展开阶段，默认收起还是默认展开？默认收起更接近现有模块面板，展开才看到工时构成。
  • 口径「按日期落段」是否进 v1？更准，但要处理并行阶段优先级和「未归类」桶。
  • 字段若评审 / 设计也要预估值，需要新增阶段预估字段或子表（v2），否则这些阶段只有条数。
