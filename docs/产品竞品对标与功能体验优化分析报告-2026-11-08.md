## 0. 结论摘要

### 0.1 一句话结论

沙漏在“50 人以下、自托管、无专职 PMO 的研发团队”这个定位上已经形成了**竞品中少见的一体化数据闭环**（需求池→评审→文档→工作项→版本→测试→工时→周回顾，全部挂在同一个项目键上，统计数字可回溯到具体任务和操作）；它当前的问题不是“缺大功能”，而是**四件“最后一公里”的事**：已经写进代码但没发布的项目对象升级（负责人/起止/归档）要落地验收、测试模块缺少能承接一次回归的最小计划闭环、任务详情与导航的信息密度/术语负担过重、以及一处会直接打断新部署的发布质量问题（基线 SQL 与增量脚本漂移）。下一阶段应“发布并打磨已有骨架，补齐测试闭环，收敛信息架构”，而不是向飞书项目/TAPD 的功能深度看齐。

### 0.2 七个核心问题速览（详见第 16 章）

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 核心竞争力 | 一条数据主线的全闭环 + 任务驱动的自动工时与周回顾（竞品普遍无）+ jar+MySQL 级私有化 + 零配置默认的克制 |
| 2 | 真正影响使用的缺失 | 测试计划与批量执行；项目档案发布验收与项目级里程碑；账号禁用与项目软删除；基线 SQL 漂移；任务复制；跨对象搜索的入口统一 |
| 3 | 竞品有但不必做 | 节点流/审批引擎、自定义字段矩阵、多级父子任务、实时协同编辑、插件市场、部门组织架构、细粒度权限位、项目集/资源平衡、IM/邮件套件 |
| 4 | 应重新设计的现有功能 | 任务详情抽屉（33 个可编辑字段单屏）、侧栏信息架构（20 个平级入口、三处周报/统计重叠）、术语（“项目/需求/任务-工作项”多义）、三种保存语义并存、测试用例逐条执行 |
| 5 | 页面与交互不足 | 项目详情信息薄、搜索结果不直达对象、分页“已加载 x/y"缺失、无权限静默隐藏、任务并发覆盖无提示、移动端破坏性手势 |
| 6 | 轻量与专业的平衡 | 只补“对象骨架 + 闭环证据 + 数据安全底线”，不补“配置能力”；用固定字段+折叠替代自定义字段，用测试计划替代测试平台，用保存视图替代报表设计器 |
| 7 | 下阶段最值得投入 | 第一阶段三件事：发布质量修复与项目档案验收、测试最小闭环（计划/批量执行/CSV 导入导出）、账号禁用与项目回收站 |

### 0.3 本轮审查新发现的两个“非体验”问题

1. **发布完整性（P0）**：`sql/baseline/01_schema_full.sql` 自称重放等效，但实际缺 `sql/50_project_profile.sql` 与 `sql/51_notification_ref.sql` 的列，而 HEAD 代码已依赖这些列（`Requirement.java`、`AppNotificationMapper.xml`）。**只按基线建库的全新部署会直接报错**。禅道 18.x 升级后“菜单找不到对象”是前车之鉴——私有化产品把“升级不破坏”视为生死线。
2. **演示环境滞后（P1）**：对外演示跑的是 v1.0.0，缺统一搜索与项目档案，潜在客户体验不到 HEAD 最强卖点。需要“发布即同步演示环境”的机制与版本水印提示。

### 0.4 明确不做（保护定位）

不做：多租户 SaaS、实时协同编辑、复杂工作流设计器/审批引擎、自定义字段矩阵、资源平衡与成本核算、预测型 AI 评分、插件市场、IM/会议/邮件套件、部门级组织架构、细粒度权限位开关。理由见第 13 章：这些能力会把“开箱即用、半天上手、一个人就能维护”的核心优势换成配置与维护负担。

## 1. 产品现状与核心定位分析

### 1.1 产品是什么

沙漏是一个**以工作项为执行主线的研发协作工作台**：需求池收集与评审（WSJF 打分）、文档沉淀方案、工作项推进（看板/列表/日历/甘特/分支五种投影）、版本绑定发布、测试用例与执行、任务驱动自动计时、周回顾与月度清单。所有对象通过统一的项目键 `req_id` 关联（`task/demand/requirement_doc/test_case/project_version/dev_branch` 六表同键，索引齐全，**已证实**），因此进度、工时、逾期、覆盖率等指标全部从日常操作自动产生，无需二次录入。

模块现状速览（HEAD）：

| 模块 | 核心对象 | 成熟度判断 |
| --- | --- | --- |
| 项目 | `requirement` 表（历史命名，UI 称“项目”） | ◐：档案字段已在 HEAD 但未发布、未验收 |
| 需求池 | `demand` + `demand_log` 评审留痕 + WSJF | ✅ 闭环完整，质量高 |
| 工作项 | `task`（story/task/bug/epic 四类型 + 缺陷专属 5 字段） | ✅ 覆盖面广；⚙ 录入密度过高 |
| 文档 | `requirement_doc` 树 + 历史快照 + 分享 + 批注 | ✅ 轻量文档管理已够用；⚙ Word 导入细节 |
| 测试 | `test_case` + `test_case_run` + 覆盖矩阵 | ◐ 缺测试计划/批量执行/导入导出 |
| 工时 | `time_log`（timer/manual）+ 工作时段裁剪 + 完成快照 | ✅ 差异化能力，竞品普遍缺失 |
| 版本 | `project_version` + `version_task` + 发布说明 | ✅ |
| 分支 | `dev_branch` 四状态跟踪 | ✅ 小而实用 |
| 洞察 | 分析/报表/负载/逾期/周回顾 | ✅ 面广；⚙ 入口分散 |
| 平台 | 权限三层/审计(HEAD)/通知四渠道/备份导出/健康检查 | ◐→✅ 随 v1.1 补齐审计 |

### 1.2 目标用户与核心场景

目标：**50 人以下研发团队**，有迭代节奏但没有专职 PMO；买不起/不想维护禅道或飞书项目的复杂度，又觉得纯任务看板（Trello 类）“管不了需求和度量”。三类真实角色：

- **执行者**：今天做什么、拖了什么、这周花了多少时间——由“我的工作/周回顾”承接。
- **技术管理者**：哪个项目要延期、谁超载、这个版本承诺了什么——由“项目总览/成员负载/逾期与阻塞/版本阶段”承接。
- **系统管理员（往往兼任）**：建账号、配看板列、查审计、做备份——由“设置”9 tab 承接。

三个高频场景：迭代推进（看板拖拽 + 自动计时）、版本承诺问答（需求→版本→发布说明一条链）、月底/周会汇报（周回顾自动总结 + AI 周报草稿 + 报表导出）。这三个场景在演示环境实测中全部可走通（**已证实**：项目列表、需求池评审看板、甘特、负载、周回顾均有真实演示数据渲染）。

### 1.3 技术架构与产品边界（决定了什么该做什么不该做）

单 jar + MySQL 8，无 Redis/MQ/对象存储；前端是**零构建原生 ES Module SPA**（无框架、`index.html` 2905 行静态骨架 + 21 个视图模块 + 19 个内核模块，**已证实**）。这套架构天然支撑“低运维私有化”，也天然不利于：多人实时协同（无 OT/CRDT 基础）、海量数据（依赖 MySQL 单库与 FULLTEXT ngram）、复杂权限引擎（权限是应用层 `ProjectAccessService` + URL 规则双层，够用且防探测做得好：读不到的资源返回 404 而非 403）。结论：**产品承诺的“不做清单”与架构约束一致，应继续坚持**。

### 1.4 工程质量观察（影响路线图可信度）

值得肯定的工程事实：权限双层校验、定时任务逐空间/逐任务异常隔离（提醒扫描 6 小时窗口 + 在飞去重）、并发保护（循环任务派生裁决、文档乐观锁 409 保留草稿）、留痕密度（task_log 字段级 diff + 审计日志含 IP）、前端 SSE 指数退避 + ETag + 深链接力 + 空/错/无权三态工厂 + token 化暗色主题。**后端成熟度高于前端产品化程度**：前端缺少组件抽象（字符串拼 HTML、同一卡片两套渲染），是后续 UI 迭代成本的结构性风险。

### 1.5 竞争力判断

| 竞争力来源 | 竞品对照 | 强度 |
| --- | --- | --- |
| 一体化数据主线（需求↔文档↔工作项↔版本↔用例↔工时↔回顾） | 飞书要靠 4 个产品拼；禅道/PingCode/TAPD 有类似链但重得多；Linear/Teambition 没有测试链与工时链 | **强，护城河** |
| 任务驱动自动工时（拖入进行中开表、完成停表、估时系数） | 六大调研竞品均无原生工时；禅道工时靠手填 | **强，差异化** |
| 周回顾 + AI 周报草稿（只读本页数据、不编造口径） | Linear/禅道/PingCode 均无结构化回顾 | **独有** |
| 私有化门槛（jar+MySQL） | 禅道一键包重、PingCode 私有化收费、飞书/TAPD 无自托管 | **强** |
| 零配置默认（P0-P3、四档角色、固定状态机、三套内置模板） | 对标 Linear Method“有主张的默认值” | **中强，需守住** |
| 覆盖矩阵（需求—用例—缺陷追溯） | 轻量工具中没有；TAPD/PingCode 有但重 | **中强，待计划闭环补强** |

## 2. 竞品选择及对标依据

### 2.1 选择逻辑

按“用户实际会被拿来比较的对象”选样，而非按知名度：(a) 客户是飞书/企微用户时，销售被问“为什么不直接用飞书”；(b) 客户是私有化用户时，绕不开禅道/PingCode/TAPD；(c) 产品自我要求“轻”和“快”，须对标交互标杆 Linear 与泛用模板 Notion/Trello；(d) 国内小团队常用 Teambition 作参照。

### 2.2 样本矩阵

| 产品 | 形态 | 目标规模 | 对沙漏的参照价值 | 口径提醒 |
| --- | --- | --- | --- | --- |
| 飞书项目（Meego） | SaaS（无自托管） | 中大型研发/交付组织 | 工作项类型抽象、节点流、人员排期、度量 | 复杂场景专用，是“不做”方向的镜子 |

## 3. 竞品功能体系与产品设计分析

### 3.1 飞书项目（Meego）

“流程引擎 + 项目空间”形态：空间 → 工作项类型（需求/缺陷/任务/版本）→ 节点流（节点带负责人、表单、准入/流转规则）。多视图（表格/看板/甘特/树形/全景）、人员排期（跨空间负载）、自动化规则、度量图表、轻应用与插件。权限从实例负责人到租户管理员五级，可细到字段级与节点级。它的存在证明两件事：**“工作项 + 类型”抽象是正确方向**（沙漏已对齐）；**节点流是为整车级合规设计的**，50 人团队用线性状态 + 流转校验即可——沙漏的“待处理→进行中→待测试→已完成 + 甘特依赖 + 阻塞卡点”就是它的合理子集。[快速了解](https://www.feishu.cn/hc/zh-CN/articles/184622406695)、[产品手册](https://project.feishu.cn/b/kahelpcenter)、[权限指南](https://www.feishu.cn/content/7rgg2vro)

### 3.2 飞书任务 / 文档 / 多维表格 / 管理后台

飞书任务：清单→分组→任务→子任务，负责人 + **关注人**（“不参与但知情”的最轻机制）、提醒、多视图（列表/看板/甘特/仪表盘）、全局 `#` 快捷呼起。飞书文档：知识空间→页面树→文档本体；权限两层（协作者 + 链接范围）；历史自动记录可还原；模板中心丰富。多维表格：表→记录→多视图投影 + 自动化（触发→动作，可建日程/任务/群）+ 行/列/视图级高级权限——它是“表驱动”轻项目管理的上限，也暴露其边界：**没有状态机与强制流转、追溯靠人肉关联字段、免费版单表 5000 行**（容量边界的诚实文案值得学习）。飞书管理后台：组织/角色/可见范围/**审计（按事件类型查询导出）**四件套，是企业采购的信任门槛——沙漏 HEAD 的 audit_log 已对齐最小实现。[任务](https://www.feishu.cn/product/task)、[知识库](https://www.feishu.cn/product/wiki)、[多维表格视图](https://www.feishu.cn/hc/zh-CN/articles/360049067931)、[自动化](https://www.feishu.cn/hc/zh-CN/articles/665088655709)、[管理员日志](https://www.feishu.cn/hc/zh-CN/articles/877442708521)

### 3.3 企业微信

设计哲学是“消息为中心 + 工作台应用为中心”。**原生**协作能力清单：文档/智能文档、智能表格（“一张表管项目、管业务、管客户”，最接近轻项目管理的原生件）、日程、待办（无子任务/依赖/甘特）、收集表、微盘、打卡/审批/汇报。**没有原生项目管理产品**：无工作项、迭代、缺陷、用例模型；项目管理全部由 ISV（Teambition 应用商店版、TAPD 企微关联等）补足。对沙漏的直接含义：企微用户的“项目管理预期”是被第三方养成的，而**企微群机器人 webhook 触达**是沙漏已具备的集成点（通知推送三渠道含企微/钉钉 webhook），应作为一等公民打磨而非藏在设置里。[官网](https://work.weixin.qq.com/)、[智能表格](https://work.weixin.qq.com/)、[待办 API](https://developer.work.weixin.qq.com/document/path/101530)、[服务商生态](https://open.work.weixin.qq.com/)

### 3.4 TAPD

与沙漏同构度最高的研发协作产品：需求（多级拆分）/计划/迭代/缺陷/任务/用例，双流程引擎（状态机 + 多阶段）、故事墙/甘特/燃尽、工作流可配（状态 + 流转规则 + **流转时补充字段 Appendfield**——状态变更即数据采集，低成本高杠杆）、报表（需求/缺陷/工时统计 + 定时邮件报告）。测试域是官方明确链路：**用例库 + 测试计划（从迭代/需求一键生成、关联用例与缺陷、批量执行、生成报告）**，但测试计划属企业版。TAPD 只有云端 SaaS、不主推私有部署——正是沙漏的差异化空间。[产品页](https://cloud.tencent.com/product/tapd)、[工作流设置](https://cloud.tencent.com/document/product/624/44313)、[测试计划](https://cloud.tencent.com/document/product/624/44299)、[FAQ 收费](https://cloud.tencent.com/document/product/624/34394)

### 3.5 禅道

同为私有化 + 开源 + 覆盖“需求-任务-bug-用例-发布”的对象链，是沙漏最直接的镜鉴。产品-项目-执行三层模型带来强追溯，也带来复杂度：**建 bug 先有产品、建用例先有需求**的对象链强制、九项可配必填、概念爆炸（版本/构建/套件/测试单/报告）——知乎长期差评“上手复杂”，有团队因学习成本放弃推广（[知乎](https://www.zhihu.com/question/36834488)）。测试域对象最全：用例库（含评审流、步骤分组）、测试套件、测试单（提测单）、测试执行、测试报告一键生成（[测试设置手册](https://www.zentao.net/book/zentaopms/1626.html)）。升级不兼容导致菜单丢失（[论坛案例](https://www.zentao.net/thread/293759.html)）是本报告 0.3 节发布质量问题的活教材。启示：**追溯关系应该用“关联字段”表达，而不是层级对象强制**；测试对象链到“计划-执行-报告”三级即可，套件/测试单两级砍掉。

### 3.6 PingCode

私有化研发管理商业标杆：需求-迭代-测试-度量-Wiki 五件套共享关联语义。测试管理是沙漏的及格线基准：**多级测试库、用例评审（必须先过评审才能进计划执行）、测试计划（关联迭代、批量筛选规划用例、执行记录历史与通过率、一键提 bug 自动回链）、33 项测试权限位**（权限位深度不必学）。[TestHub](https://pingcode.com/product/testhub)、[测试方案页](https://pingcode.com/solutions/test-manage)、[私有部署](https://docs.pingcode.com/blog/tool/67424.html)

### 3.7 Linear / Notion / Trello / Teambition

Linear：交互效率标杆——`C` 建 issue、快捷键覆盖每个操作、peek 详情、有主张的默认值、视图=过滤条件的保存（Option+V）、Issue 无字段矩阵膨胀。Notion：数据即文档（行本身就是页面）、九类视图投影、四级共享权限；代价是“搭系统要数天”且无工时/测试/研发语义。Trello：板-列-卡极小子集闭环、卡片行内编辑、拖拽即改状态；Power-Ups 市场是其能力外延方式（沙漏反面路线）。Teambition：**执行者（单选）+ 参与者（多选）二元角色**、项目模板一键复制结构、甘特只读预览分享链接、企业/项目两层权限且项目角色权限位可配（配得越细的教训见其“权限位合并”调整）；10 人以下免费、深度绑定钉钉。[Linear Method](https://linear.app/method)、[Notion views](https://www.notion.com/help/views-filters-and-sorts)、[Trello](https://trello.com/power-ups)、[Teambition 权限](https://support.teambition.com/help/docs/60c8649968465f00468fb3c2)

### 3.8 竞品共性结论（10 条）

1. 高频真需求收敛为一个子集：创建-指派-状态-截止 + 看板/列表 + 简单迭代 + 执行者/参与者 + 模板 + 缺陷回链 + 文档贴任务。几乎无人重度使用：工作流引擎、自定义字段矩阵、多租户组织、插件市场。
2. “表驱动”（多维表格/智能表格/Notion）能覆盖 70% 轻跟踪，但给不了**流程语义、追溯与度量**——沙漏应站“最小流程驱动”：固定状态机 + 校验 + 自动度量。
3. 视图=同一数据源的投影 + 过滤保存，是所有成熟产品的公共做法，沙漏已对齐（筛选在看板/列表/日历/甘特共享，`saved_view` 落库）——应做全做彻底。
4. 状态流转携带表单（TAPD Appendfield / 飞书项目节点表单）是数据采集最可靠的时机：完成时问一句“验收结论/实际工时”比事后补录有效。
5. 关注人机制（飞书任务/Linear subscribe）廉价高值，沙漏已有 `task_watch`——缺的是把“知情人”信息带到卡片与筛选上。
6. 权限层数控制在 2-3 层（全局/空间/项目），细粒度权限位是复杂度深渊（Teambition 合并权限位、飞书项目五级角色是为合规客户付的溢价）。
7. 审计日志是私有化采购信任门槛的最小实现（按事件/操作人/时间查询 + 导出），飞书后台与沙漏 HEAD 同构——应发布并展示。
8. 测试域及格线 = 用例库 →（简化）评审 → 计划/批量执行 → 通过率报告 → 缺陷互链；TAPD/PingCode/禅道三家殊途同归。
9. 触达通道决定留存：飞书靠 IM 内嵌、TAPD 靠企微关联推送；无私有 IM 的沙漏必须把 webhook/邮件/每日汇总推送做成默认好用（演示环境实测“服务端推送总开关：未开启”提示了配置引导仍有断点）。
10. 私有化产品的升级兼容与演示版本一致性是售前/售后生命线（禅道教训 + 本次实测 demo=v1.0.0）。

## 4. 项目管理功能对比

### 4.1 本产品现状（代码 + v1.0 实测）

项目实体落在 `requirement` 表（表名是历史包袱，UI 已全部称“项目”）。HEAD 已含负责人、目标、计划起止、归档（`sql/50`），`RequirementService` 做了负责人须为空间成员、起止日序校验，字段级修改写活动流；列表卡片/表格双模（表格 11 个可配列）、行内展开显示文档与工作项进度；删除为**硬删 + 大级联**（任务解绑保留，文档/版本/用例强删，附件与待发邮件清理，返回删除计数）。进度为实时聚合（任务 progress 均值，不冗余）。里程碑只是 `task.is_milestone` 标志位（甘特菱形、不占工期）。项目模板三套（blank/standard/test）**硬编码在 Java 类**，建项目时增量补齐结构。项目内权限只有 参与/只读/不可见 三档（`project_member.access`，pm/dev/qa 已停止写入、仅历史兼容读取——这是一次有意的复杂度收敛）。

v1.0 实测：新建项目表单只有名称/描述/状态 3 项（3 个控件），列表无负责人与起止列；项目总览（portfolio）渲染正常：3 个项目健康度、逾期任务数、本周完成、团队工时、超载标记与成员头像，可下钻。**负责人/起止/归档在演示环境不可见（待 v1.1 发布验收）。**

### 4.2 竞品做法（要点）

飞书项目：空间即项目，负责人/参与人/角色/准入分离，驾驶舱聚合风险；TAPD：项目含里程碑与迭代双容器，发布计划独立；禅道：项目是资源与里程碑容器，下挂执行；Teambition：项目主页 = 概览（任务概览 + 成员 + 公告）+ 应用开关；Linear：Project = 目标对象（lead、target date、status、priority、关联 issues 聚合、项目内文档）；多维表格：无“项目”对象，靠记录关联模拟。

项目模块的问题不是设计缺失而是**交付断在最后一公里**：档案字段、模板、归档都已在 HEAD，需要一次“发布 + 演示数据 + 回归 + 手册同步”的完整验收；随后补两件事——删除保护（A）和项目级里程碑区块 + 列表默认列升级（B）。**不要**引入项目层级（父项目/项目集）与可配状态流。

## 5. 任务管理功能对比

### 5.1 本产品现状

工作项 = `task` 四类型（任务/用户故事/缺陷/史诗）+ 缺陷专属字段（严重度/环境/复现步骤/发现版本/回归状态）；负责人单选（可绑定账号）+ 关注人表；优先级 P0-P3 固定档位；截止时间 + 开始日期 + 快捷按钮（今天/明天/一周后按工作日跳周末）；预计耗时 vs 实际计时；进度滑条 + 备注；循环任务（每日/周/月自动派生 + 接力）；阻塞卡点标记 + 依赖（FS/SS/FF/SF + lag，服务甘特）；评论 @提及；附件（图片/PDF/MD/ZIP/xlsx 在线编辑）；操作时间线字段级 diff；回收站 30 天；提醒 remind_at（可指定提醒负责人或+空间主）+ 5 分钟扫描 + 每日 09:00 汇总推送。看板内联新建支持快捷语法 `!P0 #项目 @负责人 +标签 %进度 ~每周 明天`；列表有 6 项批量操作与保存视图；跨空间“我的工作/团队”双视图按 access 标注可写性。**无**：任务复制接口、协作人（多人执行）、多级子任务（检查清单是清单不是工作项）。

v1.0 实测：任务抽屉打开一条真实任务，**33 个可编辑控件同屏**（基本信息/更多字段/缺陷信息/归属关系/时间与进度/检查清单/附件/工时/时间线 + 右栏人员/评论 10 区块）；看板四列拖拽、快捷筛选（逾期/今天/3 天/今日聚焦）渲染正常。

### 5.2 竞品做法（要点）

飞书任务：负责人 + 关注人 + 协作清单，全局 `#` 呼起；TAPD/禅道：多值参与人、缺陷独立对象与流转表单；Teambition：执行者(单) + 参与者(多)；Linear：创建即三字段（标题/类型/优先级默认），其余全折叠，peek 面板编辑，键盘全覆盖，无工时字段；多维表格/Notion：行即任务，视图即投影。

## 9. UI/UX 页面与交互体验深度分析

### 9.1 方法与证据限制

本轮视觉证据来自三个通道：① 前端代码（设计令牌、组件实现、渲染逻辑，**已证实**）；② 演示环境结构走查（可访问性树 + DOM 文本抽取，逐页读取真实渲染内容，**已证实**）；③ 交互路径推演（路由守卫、弹层生命周期、快捷键分层，代码级验证）。**限制**：本次内置浏览器视口不可用，未获得新截图；像素级排版（间距、对齐、密度观感）结论标注“高置信（代码/结构）+ 待验证（像素）”。

### 9.2 信息架构：入口平铺与术语多义是最大问题

20 个平级导航入口 + 5 个侧栏分组（`index.html:78-161`）。三组结构性混淆（**已证实**）：

1. **“项目”一词承载三页**：项目（projects，列表）/ 项目总览（portfolio，跨项目指标）/ 项目概览（project，单项目下钻）。用户无法预判点哪个。Linear/Teambition 都只留“项目列表 → 项目详情”两级。
2. **“需求”一词承载三物**：需求池（demand 原始需求）、需求文档（doc_type 值）、项目（表名 requirement，UI 已改名但“关联需求”文案在三处指向三种对象）。
3. **产出物重复入口**：分析（含流程体检）、报表中心、周回顾三处都能出“周报/统计/完成记录”；洞察与度量两个分组的语义边界模糊（版本是排期工具，与负载/逾期不同认知模型）。

侧栏在移动端被压成 5 tab + “更多视图”弹层，20 视图全部塞进弹层，发现成本高（**已证实**代码）。桌面端“我的工作/团队视图”“甘特”等重交互视图无移动形态——与 Linear 的“移动=查看+轻操作”路线一致，属合理取舍，但应把“完整版请在桌面使用”写成显性文案而非静默缺失。

### 9.4 页面结构问题清单（模块级）

- **项目页**：列表可用但默认列缺负责人/起止（v1.0 实测）；行内展开“文档+工作项+操作”三块混排，展开高度不可控。
- **任务抽屉**：10 区块 30+ 字段无分层导航；“更多字段”折叠只缓解不解决；右栏人员/评论与主区滚动关系易错位（代码证实两套 baseline 脏检查并存）。
- **文档编辑页**：工具栏齐全（富文本/MD/分屏），但“未保存”状态依赖角标；409 冲突文案好；Word 导入失败仅 toast，缺原因分类（待验证）。
- **测试用例页**：卡片流 + 统计头部有效；筛选器 6 组常驻顶栏，占用整行；缺“计划”维度入口（结构走查证实）。
- **设置页**：9 tab 信息量大但“工作流”tab 三块配置（列/分类/优先级）风格不一（列可拖、分类列表、优先级卡片）；“活动”与 HEAD“审计”语义相邻易混。
- **版本阶段页**：v1.0 实测切换项目后内容区样本极短（疑似依赖选择器状态，加载后仅回显筛选控件）——**待验证是否为渲染缺陷**。

### 9.5 交互与状态设计

做对的（不要重做）：空/错/无权限三态工厂统一且文案带上下文与下一步 CTA；看板首屏骨架屏；离线徽标 + SSE 断线提示条 + 60s 陈旧判定降级轮询；拖拽期间抑制实时广播防抖动；文档 409 保留草稿 + 二次确认；删除空间需输入名称确认；Esc 关闭优先级分层明确；`ds:before-route` 统一弹层卸载（HEAD 批次修复）。

仍有风险（代码级证实）：① 保存三语义并存且无视觉承诺统一；② 任务/用例并发写为后写覆盖（仅 SSE 软提醒）；③ 离线无写队列，恢复后刷新即丢草稿；④ 追加式分页无“已加载 x/y”显式反馈（60/200/500/100 四种页大小并存）；⑤ 权限不足的入口静默隐藏而非“禁用+原因”；⑥ 移动端看板左滑直接“完成”缺确认（对比需求池通过有确认，规则不一致）。

### 9.6 视觉设计

设计令牌集中于 `css/tokens.css`（色板/间距/圆角/阴影/P0-P3 语义色/布局尺寸），暗色全量覆盖、prefers-reduced-motion 降级、head 预写入防闪白——**体系是完整的，方向正确**（高置信）。风险点：① 无组件抽象，同一卡片两套（桌面/移动）字符串拼接渲染，视觉一致性靠人肉同步（已证实）；② SunEditor/Univer 第三方件靠外部补丁适配暗色，存在漂移面；③ 兼容别名 token 未清理，新页面可能取旧值；④ 像素级密度/对齐因缺截图待验证。视觉层面与竞品的真实差距不在“好看与否”，而在**信息密度控制**：禅道被嫌弃的是密度失控，不是配色；沙漏的任务抽屉正在局部重复这个错误。

### 9.7 体验问题分级（汇总，完整清单见第 11 章）

E1 高：任务抽屉字段密度；测试无计划容器；推送总开关静默未配置。E2 中：三组术语/入口混淆；搜索入口文案与范围；三种保存语义；分页无已加载反馈。E3 低：导出入口命名分散；设置卡片风格不一；移动端“更多视图”发现性。

## 14. 具体优化方案与页面改进建议

> 配套布局示意：[`docs/audit/优化方案示意图-2026-11-08.html`](./audit/优化方案示意图-2026-11-08.html)（浅色线框，含 14.2/14.3/14.4 优化前后对比）。

### 14.1 发布完整性与演示环境同步（优先级：高 ｜ 成本：低 ｜ 分类：A）

- **当前问题**：基线 SQL 缺 sql/50/51 列，全新部署即报错；演示环境停在 v1.0.0，客户体验不到统一搜索与项目档案。
- **问题位置**：`sql/baseline/01_schema_full.sql`、`deploy/`、演示服务器。
- **竞品参考**：禅道 18.x 升级菜单丢失是社区公认的信任灾难；多维表格对容量边界的诚实文案。
- **优化建议**：① 基线重放全部增量脚本并加 CI 校验“空库→基线→HEAD 冒烟”；② 发布 v1.1.0 时同步重部署演示环境并灌入含负责人/起止/归档/计划/搜索的演示数据；③ 页脚显示环境版本号（对演示环境），杜绝“看到的是旧版”。
- **交互/页面方案**：无 UI 改动（页脚版本水印除外）。
- **预期收益**：新部署成功率、售前演示完整度、升级信任。
- **实施成本**：低（半天脚本 + 半天部署演练）。

### 14.2 项目档案发布 + 项目详情升级为“项目驾驶舱”（高 ｜ 中 ｜ A/B）

- **当前问题**：项目对象薄（v1.0 实测表单仅 3 项）；HEAD 档案字段未验收；项目详情无“简报 + 里程碑 + 风险”结构；行内展开不可控。
- **问题位置**：`#/projects`、`#/project`、新建项目弹窗。
- **竞品参考**：Linear Project（lead/target date/status/关联 issues 聚合）、Teambition 项目概览、飞书项目驾驶舱（取其形不取其重）。
- **优化建议**：把 `#/project` 从“任务聚合页”定名为**项目驾驶舱**；侧栏“项目总览”改名**工作台-全局**或并入分析；“项目/项目总览/项目概览”收敛为**项目（列表）→ 项目（详情）**两级。
- **交互方案**：列表点项目名 → 驾驶舱；页内锚点 tab：概览/工作项/文档/测试/版本/里程碑；任何对象可从驾驶舱一跳达。
- **页面方案**（驾驶舱首屏）：

```
┌ 项目名 · 状态徽标 · 负责人 · 计划起止(进度条: 已过时间 vs 完成任务) ┐
│ [简报卡] 工作项 29 · 完成 18(69%) · 逾期 2 · 本周投入 21h · 距计划完工 −3d │
│ [里程碑条] ◆需求冻结 10-20 ✓  ◆联调 11-10 ●  ◆发布 11-20 ○ (横轴时间)      │
│ 左：风险信号(逾期5/阻塞2/超载1人 → 直达筛选)  右：成员负载迷你条形         │
│ Tab: 工作项 | 文档(带完成比) | 测试(覆盖矩阵摘要+通过率) | 版本 | 活动     │
└──────────────────────────────────────────────────────────────┘
```

- **优先级**：高；**收益**：管理者“一眼看清一个项目”的最小完整答案，兑现“数据回到管理者手里”主张；**成本**：中（后端聚合接口已有大半，主要在前端组页与术语收敛）。

### 14.3 测试最小闭环：测试计划 + 批量执行 + 导入导出（高 ｜ 中 ｜ A）

- **当前问题**：用例是清单不是流程；逐条执行；无法迁移存量用例。
- **问题位置**：`#/testcases`（新增第 4 个 tab，不新增一级入口，避免冗余）。
- **竞品参考**：TAPD 测试计划（从迭代一键生成、批量执行、报告）、PingCode 四件套、禅道裁剪版（砍套件/测试单）。
- **优化建议**：新增 `test_plan` 一表足矣：名称/项目/关联版本或需求/起止/状态（草稿→执行中→完成）/用例集（plan_case 关联表，圈选时按模块/优先级/需求过滤）；执行在计划内批量进行（勾选多行一次录入结果，备注与证据可选逐条补）；结果页给通过率/进度/缺陷数并可导出；CSV 模板导入导出复用 attachment 清洗与安全策略。
- **交互方案**：用例库圈选 →“加入计划”；计划详情：左用例列表（含每人执行进度）右汇总；失败转缺陷沿用现有链路；完成后一键“测试简报”（复用报表导出 PNG 通道）。
- **页面方案**：

```
┌ 测试计划 · V1.2 回归（执行中 11-05~11-19） · 关联: V1.2 · 覆盖需求 4 ┐
│ 汇总条: 68/120 已执行 · 通过 61 失败 5 阻塞 2 · 通过率 90% · 缺陷 5   │
│ [批量执行] 勾选→ 结果分段器(通过/失败/阻塞)+备注(选) → 一次提交        │
│ 列表列: 模块|用例|优先级|最近结果|执行人|耗时|操作(执行/转缺陷)         │
│ 右上: 导出报告 | 导入/导出用例(CSV) | 圈选用例                        │
└──────────────────────────────────────────────────────────┘
```

- **优先级**：高；**收益**：对有 QA 的团队从“能看”变“能用”，直接补上对标 TAPD/PingCode 的及格线；**成本**：中（1 表 + 1 关联表 + 1 页 + 2 接口；避免多级树/评审流则可控）。

### 14.4 任务抽屉信息分层 + 保存语义统一（高 ｜ 中 ｜ B）

- **当前问题**：33 控件一屏；必填 1 项但可见负担大；三种保存语义；“新建”复用“编辑”全量屏。
- **问题位置**：任务抽屉（`index.html:2189-2574`）、新建任务表单。
- **竞品参考**：Linear 创建仅三字段 + peek 折叠面板；飞书任务侧卡；Notion“按视图决定打开方式”。
- **优化建议**：① 抽屉首屏只留：标题/类型/负责人/截止 + 状态/进度 + 描述（7 面），其余分三组折叠：**关联**（项目/版本/史诗/分支/文档/依赖只读区）、**执行**（检查清单/附件/工时）、**更多字段**（提醒/循环/阻塞/分类/标签）；新建态只渲染首屏 + “需要更多字段?”一行。② 抽屉内普通字段改为**防抖自动保存 + 顶部“已保存 HH:mm”指示**，评论/附件保持即时，文档保持手动保存但把“未保存”状态做成呼吸灯式强提示——三种语义各有场景，但每种都要**可见**。③ 依赖区块只读展示“我依赖谁/谁等我 + 状态点”，编辑仍回甘特。
- **交互方案**：编辑任务 = 打开即改即存，Esc 关闭无“确认放弃”干扰（有未 flush 的字段时例外合并提示）；`C` 键从任意视图呼起同组件。
- **优先级**：高；**收益**：日频操作降负 + 消除误存/丢改的信任问题；**成本**：中（无接口改动，纯前端重组与 debounce 层）。

### 14.5 全局统一：术语表 + 搜索入口 + 导出收敛（中高 ｜ 低 ｜ B）

- **当前问题**：“项目/需求/任务-工作项”多义；顶栏搜索文案只提任务；导出六个入口命名各异。
- **问题位置**：导航、`index.html` 文案、分析/报表/回顾/列表/甘特/portfolio。
- **竞品参考**：Linear 全站统一 Issue/Project 两词；飞书“需求/缺陷/任务”命名纪律。
- **优化建议**：① 定术语表并全局执行：项目｜工作项（类型：任务/缺陷/故事/史诗，日常文案可称“任务”但导航与表单统一“工作项”）｜需求（仅指需求池对象）｜文档类型改为“PRD/技术方案/验收标准/其他”消除“需求文档”歧义。② 顶栏搜索 placeholder 改“搜索项目、工作项、文档、用例…（⌘K）”，与命令面板同端点同结果分组；补齐分支/版本纳入范围（C 期）。③ 导出统一为“导出…”下拉，选项与当前视图/口径联动，命名对齐（当前视图 CSV / 周报 / 甘特打印）。
- **优先级**：中高；**成本**：低（文案 + 一个下拉重构）；**收益**：认知成本与售前演示流畅度。

### 14.6 推送触达引导与“提醒链路自检”（中高 ｜ 低 ｜ B）

- **当前问题**：服务端推送总开关默认关，用户不知道“提醒没发出去”；配置分散在空间集成 + 个人偏好两层。
- **竞品参考**：TAPD 定时邮件报告、飞书自动化发消息卡片（触达是第一等公民）。
- **优化建议**：新空间创建后在“集成”页给三步引导（选渠道→发测试消息→开总开关）；加“自检”按钮（一键发样例并显示最近失败原因）；每日汇总卡片文案带“直达链接”。
- **优先级**：中高；**成本**：低；**收益**：逾期提醒链路从“配置了但没生效”变为可验证闭环。

### 14.7 列表与权限反馈的基础设施（中 ｜ 低 ｜ B）

- **当前问题**：追加分页无“已加载 x/y"；无权限静默隐藏；任务并发后写覆盖。
- **竞品参考**：Linear 列表尾部显式分页；Notion 权限 hover 说明。
- **优化建议**：① 四种页大小统一到一个 `< 已加载 x / y · 加载更多 >` 组件；② 无权限入口保留可见 + 禁用态 + tooltip“该项目对你是只读，联系管理员调整”，替代隐藏；③ 任务保存带版本戳（updated_at 比对），冲突时 toastAction“他人已更新，[查看差异并重新保存]”，复用文档 409 交互模式。
- **成本**：低中；**收益**：数据信任与操作确定性。

### 14.8 移动端规则一致性（中 ｜ 低 ｜ B/C）

- **当前问题**：看板左滑直接完成无确认，与需求池“通过需确认”不一致；“更多视图”发现性弱；重交互视图无显性说明。
- **优化建议**：破坏性/状态跃迁手势统一走 MOBILE_APPROVALS 表（已有机制，补 board 完成一态即可，保留 toast 撤销双保险）；“更多视图”按使用频度排序并在首页显示 2 个自定义 pin；甘特/批量操作页脚注“请在桌面端使用完整功能”。
- **成本**：低；**收益**：手机上“敢用”。

### 14.9 可以考虑的增强（C 类汇总，Phase 3）

用例两态评审 + 快照（复用文档 history）；项目“另存为结构模板”；空间文档虚拟根；自动化最小规则（触发：状态变更/逾期/指派 → 动作：通知/改列/建提醒，三选三）；周报邮件订阅；参与者（多值）显示；节假日日历。每项独立成卡、按反馈择机，**不打包成大版本**。

### 14.10 文档编辑器可靠性（随 v1.1 验收）

Word 导入图片抽为附件并在正文引用（解决 12MB 膨胀上限与复用问题）；导入失败给原因分类文案（格式不符/超限/解析失败）；首屏加载与“误报未保存”回归用例进浏览器测试清单（本轮无法在演示环境复现历史现象，标注待验证）。

## 16. 最终产品定位与发展建议（核心问题最终回答）

1. **核心竞争力在哪里？** 不在功能数量，在“**一条数据主线的全闭环 + 任务驱动自动工时 + 周回顾 + 零中间件私有化 + 零配置默认**”的组合。飞书/TAPD 证明闭环值得做但代价是全家桶或付费墙；禅道证明对象链强制会杀死小团队；Linear 证明轻的价值但不管测试与工时。沙漏恰好占住“50 人以下自托管研发协作”的真空带。
2. **真正影响使用的缺失？** 六项：测试计划闭环、项目档案的发布与验收、基线 SQL 漂移、账号禁用、项目删除保护、存量用例迁移。除第二项是“发布工程”问题外，其余都有明确低成本路径。
3. **竞品有但不必实现？** 工作流引擎、自定义字段、多级子任务、实时协同、插件市场、组织架构/LDAP、项目集与资源平衡、通用配置管理页、正式版本管理、IM/邮件套件、预测型 AI——每一项的详细理由见第 13 章，共同点是它们服务于“大组织的合规与配置自由”，而沙漏服务“小团队的即拿即用”。
4. **应重新设计的现有功能？** 任务详情抽屉（分层+自动保存）、项目详情（→驾驶舱）、信息架构（三“项目”入口收敛）、保存语义（可见承诺）、测试执行（→计划批量）。注意：全部是**重排与增容器**，不是推倒重做。
5. **页面与交互明显不足？** X1-X16 清单（第 11 章）；像素级审查待补一轮真机截图（第 9.1 节声明）。
6. **如何兼顾轻量与专业？** 只补三类东西：对象骨架（项目档案、测试计划）、闭环证据（覆盖矩阵、审计、通过率）、信任机制（并发冲突、删除保护、分页反馈）。判断标准一句话：**新功能的复杂度由产品内部消化，而不是转嫁给使用者**。
7. **下一阶段最值得投入？** 第一阶段的三件套：发布完整性 + 项目驾驶舱 + 测试计划闭环。它们分别回答“敢不敢买（稳定升级）、管理层看不看得见（项目答案）、QA 用不用得起来（测试流程）”——正是 50 人团队采购决策的三根支柱。

**最终主张**：沙漏不需要成为另一个飞书项目或禅道。把已经写进代码的骨架发布干净、把测试容器补上、把抽屉和导航的负担卸下来，它在自己的定位上就已经是功能完整、体验专业、操作简单的产品——剩下的差距应交给真实客户反馈逐项裁决，而不是交给竞品功能清单。
