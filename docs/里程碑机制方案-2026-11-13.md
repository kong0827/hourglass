# 里程碑机制方案

2026-11-13 · 交互原型见 [milestone-preview-2026-11-13.html](preview/milestone-preview-2026-11-13.html)

## 结论

把里程碑从「任务上的一个勾」升级为**项目级一等对象**：一条里程碑只表达一条达成条件，状态由条件或证据推导，不靠人工维护。

三种来源覆盖真实场景：**版本发布后**（生产成功才算）、**工作项完成后**（关联工作项全部完成）、**人工确认**（评审、验收等系统内没有完成信号的节点）。

**没有「任务里程碑」。** 工作项本身永远不是里程碑，只作为达成条件的证据；里程碑也不占工作项的数量、预估与燃尽。二者是「结果标记」与「执行单元」的关系，不是同一层级的两种任务。

不新增一级导航。里程碑落在项目概览、甘特和版本与发布三处，跟随项目出现。

## 现状的问题

| 现状 | 后果 |
| --- | --- |
| `task.isMilestone` 是工作项上的布尔标记 | 里程碑混进工作项计数、预估与燃尽，明明不是「一件事」却占一份工作量 |
| 只有单日节点和甘特菱形 | 说不清为什么算达成、证据是什么、为什么延期 |
| 与版本、发布记录没有关联 | 「完成不等于发布」这条主线在里程碑上断掉，上线仍靠口头确认 |
| 状态需要人记、人改 | 很快退化成第二套台账，和看板、发布记录对不上 |

## 对象模型

一条里程碑只需要这些字段：

| 字段 | 说明 |
| --- | --- |
| 名称 | 默认由来源生成，可改 |
| 项目 | 必填，跟随项目权限与可见性 |
| 达成方式 | 版本发布后 / 工作项完成后 / 人工确认，三选一，创建后不改 |
| 目标日期 | 计划口径，可改期；与达成时间分开 |
| 负责人 | 默认项目负责人，可换 |
| 关键标记 | 用于概览与周回顾提示，不影响判定 |
| 条件引用 | 版本 ID 或工作项 ID 集合；人工型为空 |
| 达成时间 / 来源 | 由系统写入，作为证据；人工型记录确认人 |
| 取消原因 | 取消时必填，保留历史 |

## 状态是算出来的

| 状态 | 判定 |
| --- | --- |
| 未达成 | 条件未满足，且未过目标日期 |
| 已达成 | 有达成时间与来源 |
| 已延期 | 条件未满足，且已过目标日期（天数实时计算） |
| 已取消 | 人工取消，不计入达成统计，记录保留 |
| 已达成（后回滚） | 发布型达成后发生回滚；达成历史保留，不撤销 |

三条硬规则：

1. **自动里程碑不接受手动标记。** 发布型只看 production 成功记录；工作项型只看完成状态。
2. **证据只写一次。** 发布型引用不可变发布记录；工作项型写入判定时间；人工型写入确认人、时间与一句备注。
3. **改期只改目标日期，不改条件。** 改期与取消都要原因，写入动态。

## 三种达成方式

| 方式 | 触发 | 证据 | 不适合 / 不算 |
| --- | --- | --- | --- |
| 版本发布后 | 版本 production 发布成功 | 发布记录（时间、执行人、制品 SHA256） | 测试环境、部分成功、失败、回滚都不算 |
| 工作项完成后 | 关联工作项全部完成 | 工作项完成状态与判定时间 | 只完成一部分不算；重开会回到未达成 |
| 人工确认 | 负责人一键确认 | 确认人、时间、可选备注 | 没有系统信号的评审、验收、对外承诺 |

原型里刻意保留了一个反例：V1.0 已部署到测试环境成功，里程碑仍是「未达成」——这正是产品「完成不等于发布」的口径。

## 与现有模块怎么咬合

| 位置 | 做法 |
| --- | --- |
| 项目概览 | 目标条下增加四个指标（已达成、进行中、已延期、距下个节点）和里程碑列表；延期与「尚无发布记录」合并成一条关注提示，不另起卡片 |
| 甘特 | 里程碑独立成轨，菱形落在目标日期；**不进入工作项计数、预估与燃尽**；点击打开详情 |
| 版本与发布 | 版本卡显示里程碑达成与发布次数；生产发布成功后自动达成；发布前检查只提示、不阻断，发布仍由有权限的人确认 |
| 周回顾 | 关键里程碑的达成与延期进入本周回顾，不再由人回忆 |
| 报表 | 里程碑按期率后置。先把口径跑顺，不急着造第二套指标 |
| 工作项 | 不受影响。里程碑独立于工作项，不占计数、预估与燃尽。存量 `task.isMilestone` 一次性映射为人工里程碑（沿用名称、负责人与目标日期），随后移除任务侧标记，不做只读双轨；历史甘特上仍以里程碑菱形显示，避免两套语义并存 |

## 交互：少填、少管

- **创建只填三项**：名称、目标日期、关联对象。达成方式点一下卡片，负责人默认项目负责人，关键标记默认勾选。
- **状态不可编辑**：没有「改成已达成」这种字段。人工型只有一个「标记达成」按钮。
- **下一步跟着类型走**：发布型给「去确认发布」，工作项型给「去完成剩余工作项」，人工型给「标记达成」。
- **默认值足够好**：发布型默认当前版本与版本结束日；工作项型默认未完成工作项与其中最晚结束日；人工型默认两周后。
- **更多设置折叠**：说明与提醒收在二级，不打断主流程。
- **取消不删除**：保留历史与原因，统计自动扣减。

## 借鉴与取舍

| 来源 | 借鉴了什么 | 本方案怎么落地 |
| --- | --- | --- |
| MS Project | 零工期任务表示里程碑 | 借语义，不借实现：不建零工期任务，避免污染工作项计数与燃尽 |
| Asana | 里程碑是一等对象、有独立视图 | 做一等对象，但不新增导航，挂在项目内三个已有视图 |
| Jira | 版本作为发布节点 | 直接复用现有版本与发布证据，不另造「发布」概念 |
| GitHub Milestones | 归组工作项、显示进度与到期 | 工作项型条件复用「进度 4/5」，但不把里程碑做成容器，工作项仍归属项目 |
| 禅道 / 飞书项目 | 阶段评审与人工确认 | 只保留「人工确认」这一种轻量补位，不做审批流 |

共同的取舍是：**不引入新的计划层级**。沙漏没有迭代，阶段由版本承载；里程碑只标记结果，不再长出一棵 WBS。

## 边界

不做：多层里程碑树、阶段计划、审批流、客户签认、里程碑工时或预算归集、跨项目里程碑视图、自定义规则引擎。

不替代：发布证据、部署执行、客户验收。里程碑只回答「这个结果到了没有、凭什么说到了」。

## 交互修复清单（2026-11-13 核验后）

核验结论：骨架 2–3 步可完成，问题集中在「自动建议值覆盖手填」与三处设计承诺未落地。以下只定义修法，原型代码未动。

### 第一批：P1

| 编号 | 现状 | 修法 | 验收 |
| --- | --- | --- | --- |
| A1 | 切换达成方式或增减工作项，会覆盖手填的名称与日期 | 草稿分别记录名称、日期是否被手填；只更新未手填的字段；名称清空视为未手填 | 手填名称与日期后切换类型、增减工作项，值不变；未手填时仍自动带默认 |
| A2 | 详情写「可附一句说明」，但「标记达成」一点即生效，没有备注入口 | 标记达成改为轻确认：显示确认人与日期，可填一句可选说明，确认后才写入 | 不填说明可一次确认；填写后证据与动态可见；Esc 不写入 |
| A3 | 负责人是只读块，与方案「默认项目负责人，可换」不一致 | 负责人改为可选，默认项目负责人并保留「默认」标记；仅在改人时多一步 | 可换人并写入详情；不改人时仍零输入 |
| A4 | 甘特工作项行有手型与悬停，点击无反应 | 工作项行/条打开工作项抽屉；里程碑行仍开里程碑详情 | 两类行各自到位，Esc 关闭，无假入口 |

### 第二批：P2（同一交互骨架内）

| 编号 | 修法 | 验收 |
| --- | --- | --- |
| B1 改期 | 保留默认顺延 7 天的快路径，但弹层显式显示「原日期 → 新日期（顺延 7 天）」，并提供「恢复原日期」；日期未变化时确认不可用 | 不会无声改期；恢复原日期后不能提交 |
| B2 撤销 | 撤销后 toast 提供 6 秒「撤销」；恢复达成并追加一条恢复日志 | 误点可恢复，证据链不断 |
| B3 零工作项 | 工作项型选 0 项时创建按钮置灰，选择区下就地提示；不再等点击后用 toast 拦截 | 无无效点击，提示贴着选择区 |
| B4 草稿 | 有手填内容时关闭新建抽屉先确认「放弃已填写内容？」；未手填直接关闭 | 误点遮罩不丢值；无内容时不打扰 |
| B5 折叠摘要 | 「更多设置」收起后显示已填内容，如「更多设置 · 已填说明」 | 收起后仍知道里面有值 |

### 暂不做（另批）

关注条两个问题拆成两个入口；里程碑空态；浮层焦点与 `aria-modal`；移动端 44px 触控目标。

### 不改的边界

三个必填项不变；不恢复任务里程碑；不新增页面或导航；发布型仍只认 production 成功记录。

## 待确认

1. **工作项型重开是否回退？** 当前按状态型处理：工作项重开，里程碑回到未达成并留痕。若团队更希望「一经达成就锁定」，改为事件型即可。
2. **已达成的人工里程碑能否撤销？** 当前可以撤销并留痕；发布型不可撤销，只能追加回滚记录。
3. **里程碑达成率是否进入项目列表？** 当前只在项目驾驶舱与版本页展示，避免项目列表多一列低密度指标。
