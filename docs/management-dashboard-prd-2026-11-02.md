## v0.2 修订说明

本版按 v0.1 评审结论重写核心规则，主要变化：

- **风险等级与数据质量拆分**：数据缺失不再把红色风险降级为灰色，只显示“数据质量”徽标；
- **完成/工时口径收口**：明确完成快照、任务表、工时表三个数据源的关系，以及回填、完成锁定、彻底删除的影响；
- **任务完成锁定（MGT-019）**：任务进入 done 后不可重开/移出，需要继续做时新建续做任务；完成快照正常流程只增不删；
- **只读权限闭环**：补管理读接口鉴权、接口分类、白名单、HTTP 403、管理员重叠、回滚安全；
- **数据初始化与维护权限**：删除“创建人回填”的错误前提，增加项目/任务字段批量补全（MGT-020 纳入 P0），并允许项目负责人维护自己项目的日期/优先级；
- **导出收紧**：`GET /api/export` 已是 owner-only；本版将 `GET /api/export/csv` 也收紧为 owner-only，exec 只能使用管理报表导出；
- **补充业务使用逻辑**：新增第 5.5 节，覆盖上线初始化、每周管理例程、风险闭环、人工覆盖、角色协作、状态流转和异常处理；
- **修正细节**：KPI 数量、示例日期、字段单位、导出格式、ETag、分页与排序等。

## 0. 一句话定义

在现有“空间 → 项目 → 需求 → 任务”数据之上，新增一个**供空间主和管理层查看的项目组合驾驶舱**：能在一屏内回答“哪些项目有风险、谁负责、进度是否落后、资源是否过载”，并支持下钻到项目和任务证据。

它不是新的项目管理引擎，不是 Jira 平替，也不是员工监控工具。

### 0.1 术语与边界

| 术语 | 本文含义 |
|---|---|
| 共享空间 | `workspace.type = shared`，可邀请成员，是管理层驾驶舱的唯一使用范围 |
| 个人空间 | `workspace.type = personal`，每个账号一个；**不出现管理入口**，也不参与跨空间组合 |
| 项目 | 数据库表 `requirement`，界面上叫“项目”；对应 `/api/reqs` |
| 需求 | 项目下的 `requirement_doc`，任务通过 `task.req_doc_id` 关联 |
| 任务 | `task` 表，看板列、负责人、起止、估时、进度、阻塞都在这里 |
| 空间主 | 空间成员角色 `owner`，拥有空间配置、成员、项目元数据、健康度覆盖权限 |
| 管理层 | 空间成员角色 `exec`（新增），只读查看管理驾驶舱和证据，不能写业务数据 |
| 项目负责人 | 项目上的 `manager_user_id`，不是空间角色；必须是共享空间的 owner/member，不能是 exec |
| 平台管理员 | `app_user.role = admin`，只负责账号运维；不是空间成员时看不到空间数据 |
| 管理口径 | 为管理层决策定义的口径，由服务端计算，前端只展示 |
| 执行口径 | 看板/项目页/分析页现有的任务视角口径，不直接作为管理决策依据 |
| 风险等级 | `riskLevel`：red / amber / green / unknown，表示项目当前风险 |
| 数据质量 | `dataQuality`：0–100，表示管理字段和任务字段的完整程度；**不决定风险等级** |
| 本周 | 周一 00:00 至下周一 00:00，时区 `Asia/Shanghai` |
| 有效任务 | `task.deleted_at IS NULL AND task.req_id = project.id` |
| 计划任务 | 非 backlog 的有效任务，加上 backlog 中已设置 `due_date` 的任务；用于截止日期覆盖率和临期风险 |
| 完成快照 | `task_completion_record`，任务完成时落一条；代表“当前有效完成” |
| 完成锁定 | 任务进入 done 后不可重开/移出完成列；需要继续做时新建续做任务 |
| 历史完成事件 | 若后续需要管理员纠错/多周期审计，新增事件表；**MVP 不提供**，见 3.11 |

> 本文历史说法中的“健康度”统一指 `riskLevel`；`dataQuality` 单独指数据质量。接口不再用 `health` 作为字段名。

## 1. 背景与目标

### 1.1 现状

当前系统已经具备完整的执行层能力：

- 空间 / 项目 / 需求文档 / 任务四层结构；
- 看板、列表、日历、甘特图；
- 有效工时、完成快照、流程体检、周回顾；
- 甘特依赖、基线、关键路径（前端计算）、按人 × 周负载；
- 项目页已有任务数、完成数、任务平均进度。

但管理层目前只能“自己拼信息”：

- 项目列表只有名称、描述、状态和任务平均进度，没有负责人、计划周期、风险等级；
- “分析”页偏执行视角，缺少项目组合、风险清单和资源冲突；
- 统计接口按单个空间取数，跨部门/跨空间没有组合视图；
- 空间成员只有 `owner/member`，没有“只看不改”的管理角色；
- 项目进度是任务进度的简单平均，不能直接作为管理决策依据；
- 任务进度依赖人工维护，团队不填时管理数字会失真；
- 完成快照 2026-10-21 才引入，存量完成没有回填，历史趋势天然不完整。

### 1.2 目标

**G1. 五分钟回答四个问题**

1. 现在哪些项目有风险，谁负责？
2. 本周完成了什么，投入了多少人天？
3. 谁过载、哪个项目本周估时最集中？
4. 哪些项目数据不完整，导致无法判断？

**G2. 让管理数据可被采信**

每个红黄绿都有明确规则、数据来源和可下钻的证据，不靠人工汇报口径。数据质量单独展示，不用“灰色”掩盖真实风险。

**G3. 不打扰现有协作**

除新增的“任务完成锁定”外，不改变任务看板、计时、需求编辑的现有习惯；完成后续做通过“新建续做任务”引导，不允许重开旧任务；管理视图只读，不新增填报负担；项目负责人可以在现有项目页补充自己项目的管理字段。

**G4. 权限边界清晰**

空间主、管理层、项目负责人、普通成员、平台管理员各自能做什么，由服务端保证；回滚旧版本时不会恢复管理层写权限。

### 1.3 非目标

本次明确不做：

- 对外商业化 ToB、多租户、计费、开放平台；
- SSO / LDAP / 企业组织架构；
- OKR、预算、采购、合同、审批流；
- 员工工时排行榜、个人绩效排名；
- AI 预测工期、自动重排计划；
- 项目级细粒度 RBAC（先做到空间级只读）；
- 独立风险工单/风险流转系统（风险清单只做视图，处理动作回到项目/任务）；
- 不可变完成事件表（MVP 用“当前有效完成”，P1 再评估）；
- 法定节假日日历（MVP 只跳周末，文档明示）。

### 1.4 上线判据

试点共享空间满足以下条件才算可用：

1. 项目负责人、开始日期、截止日期三项覆盖率均达到 80% 以上，任务负责人与计划任务截止日期覆盖率也达到 80% 以上；
2. 管理层能通过管理页定位到每条红色风险的具体任务证据；
3. `exec` 的所有写接口返回 403，管理读接口对 member 返回 403；
4. 管理总览与项目列表的高风险数量一致；
5. 管理页不出现“没有数据却显示绿色”的情况；
6. 已完成任务无法重开，续做任务可以正常创建；
7. 2,000 任务 / 50 项目下，管理总览 p95 < 500ms（本机或等效环境）。

## 2. 角色、权限与使用边界

### 2.1 角色定义

| 角色 | 所在层 | 说明 |
|---|---|---|
| `owner` | 空间成员 | 空间主，拥有空间配置、成员、项目元数据、健康度覆盖权限 |
| `exec` | 空间成员（新增） | 管理层/领导，只读查看管理驾驶舱、项目详情、风险、负载、导出 |
| `member` | 空间成员 | 项目成员，维持现有任务协作权限；默认看不到管理驾驶舱 |
| 项目负责人 | 项目字段 | 共享空间成员；可维护自己项目的日期/优先级，不能覆盖健康度 |
| `admin` | 平台账号 | 账号管理员，只负责账号运维；不因 `admin` 自动获得空间数据权限 |

> `admin` 与空间角色是两套体系。平台管理员如果不是空间成员，仍然看不到该空间的项目数据。
>
> 项目负责人不是空间角色，不参与 `workspace_member.role`；建议代码字段命名为 `manager_user_id`，避免和空间主 `owner` 混淆。

### 2.2 权限矩阵

| 能力 | owner | exec | 项目负责人（member） | 其他 member |
|---|---:|---:|---:|---:|
| 进入“管理”入口（仅共享空间） | 是 | 是 | 否 | 否 |
| 查看管理总览/项目组合/风险/负载 | 是 | 是 | 否 | 否 |
| 查看项目详情与任务证据 | 是 | 是 | 仅现有项目/任务页面 | 仅现有项目/任务页面 |
| 查看现有看板/列表/日历/甘特/分析（只读） | 是 | 是 | 是 | 是 |
| 导出管理报表 | 是 | 是 | 否 | 否 |
| 导出全量任务备份（`/api/export`，现状已 owner-only） | 是 | 否 | 否 | 否 |
| 导出任务 CSV（`/api/export/csv`） | 是 | 否 | 否 | 否 |
| 编辑任务 | 是 | 否 | 是 | 是 |
| 重开/移出已完成列 | 否 | 否 | 否 | 否 |
| 新建续做任务 | 是 | 否 | 是 | 是 |
| 编辑项目名称/描述 | 是 | 否 | 保持现状（是） | 保持现状（是） |
| 编辑项目状态 active/done/hold | 是 | 否 | 是（仅自己项目） | 否（需服务端收敛） |
| 编辑管理元数据（负责人/起止/优先级） | 是 | 否 | 是（仅自己项目，限日期/优先级） | 否 |
| 设置项目负责人 | 是 | 否 | 否 | 否 |
| 人工覆盖项目风险等级 | 是 | 否 | 否 | 否 |
| 分配/变更空间成员角色 | 是 | 否 | 否 | 否 |
| 修改空间配置/成员 | 是 | 否 | 否 | 否 |
| 修改自己的密码/资料/计时设置 | 是 | 是 | 是 | 是 |
| 切换空间/退出空间/标记通知已读 | 是 | 是 | 是 | 是 |
| 平台账号管理 | 仅 admin | 仅 admin | 仅 admin | 仅 admin |

> 现状补充：当前 `PUT /api/reqs/{id}` 允许任何空间成员修改名称/描述/状态。本版业务上把“项目状态”收敛到 owner/项目负责人；实现时必须在 `RequirementService.update` 校验，否则矩阵与现状不一致。若评审决定暂不收敛，则矩阵中的状态权限应改回“成员可改（现状）”。
>
> 项目负责人通过现有项目页的“项目资料”入口维护日期/优先级/状态，不经过管理驾驶舱；前端入口在 `js/views/projects.js`，后端复用 meta 接口并按 `manager_user_id` 校验。

**共享空间限制：**

- 管理入口和 `/api/management/**` 只在 `workspace.type = shared` 时可用；
- 个人空间即使当前用户是 `owner`，也不显示管理入口，接口返回 403；
- 每个账号都是自己个人空间的 owner，因此导航不能用“`myRole = owner`”作为管理入口的唯一条件，必须同时判断空间类型。

### 2.3 管理读接口也必须服务端鉴权

不能只保护写接口。以下接口必须由服务端校验“当前空间 + 角色”：

- `GET /api/management/overview`
- `GET /api/management/projects`
- `GET /api/management/projects/{id}`
- `GET /api/management/risks`
- `GET /api/management/workload`
- `GET /api/management/export`

规则：

- 当前空间必须是共享空间；
- 角色必须是 `owner` 或 `exec`；
- 项目必须属于当前空间，否则 404，不泄露其他空间是否存在；
- member 直接访问返回 403，前端显示“仅空间主和管理层可查看”，而不是整页报错。

实现建议：扩展现有 `@RequireRole`，增加 `EXEC`/`MANAGEMENT` 语义，或在 ManagementService 入口统一 `requireManagementView`；不要只靠前端隐藏入口。

### 2.4 写接口只读控制

`exec` 的写操作必须由服务端拒绝，不能只靠前端隐藏按钮。

#### 2.4.1 按接口分类，不能只看 HTTP 方法

本系统有大量“只读 POST”（通知已读、AI 审计/润色等），因此“所有非 GET 一律拒绝”会误伤正常使用。按下表分类：

| 类型 | 例子 | exec |
|---|---|---:|
| 空间业务写 | 任务/项目/需求/分支/附件/看板列/分类/AI 写入/导入/分享 | 拒绝 403 |
| 个人自助 | 登录、退出、改密码、改资料、改计时设置、切换空间、退出空间、通知已读 | 允许 |
| 全局自助 | 创建空间、接受邀请加入其他空间 | 允许（进入目标空间后按该空间角色判断） |
| 平台管理 | `/api/admin/**` | 按平台管理员权限判断，不受空间 exec 限制 |
| 只读 POST | 通知已读、AI 审计/润色等不写业务数据的接口 | 默认拒绝；逐接口白名单（当前仅通知已读），禁止“看方法放行” |
| GET/HEAD/OPTIONS | 所有读接口 | 允许，但管理读接口仍受 2.3 限制 |

#### 2.4.2 建议白名单

- `POST /api/auth/login`
- `POST /api/auth/logout`
- `POST /api/auth/password`
- `PUT /api/auth/profile`
- `PUT /api/auth/work-hours`
- `POST /api/workspaces/{id}/select`
- `POST /api/notifications/{id}/read`
- `POST /api/notifications/read-all`
- `POST /api/workspaces`（创建新空间）
- `POST /api/invite/{code}/join`（加入其他空间）
- `DELETE /api/workspaces/{id}/members/{userId}`（仅当 `userId` 是当前用户本人，退出空间）

其他业务写接口一律拒绝。白名单必须逐接口维护，新增接口默认拒绝。
AI 审计、润色、配置测试等 POST 默认不列入白名单；如果 exec 需要使用，再单独评估 AI 配额、审计和数据边界。

#### 2.4.3 过滤器实现要求

- 必须放在 Spring Security 认证链之后，确保 `SecurityContext` 已填充；
- 不能依赖前端隐藏，也不能依赖 `@CurrentWorkspace` 参数存在；
- 过滤器里拒绝时直接写 `ApiResult` JSON，HTTP 403，不能抛异常让容器返回 HTML；
- 空间解析优先取请求中的 `workspace` 参数；缺失时按 `lastWorkspaceId` 解析，但业务写接口应要求前端始终携带 `workspace`；
- 角色变更后主动失效 `WorkspaceMemberCache`；多实例部署最多延迟 60 秒；
- `/api/admin/**` 不受 exec 限制，否则“平台管理员 + 空间 exec”账号无法做账号运维；
- 角色回滚：旧版本没有只读过滤器，会把 `exec` 当普通成员。**回滚前必须先把 exec 改回 member**，或新版本用 feature flag 包住过滤器并保证旧版本不识别 exec。

#### 2.4.4 错误契约

- 未登录：HTTP 401，`{code:401,message:"未登录或登录已过期"}`；
- 无权限：HTTP 403，`{code:403,message:"仅空间主和管理层可查看"}`；
- 项目不存在/不属于当前空间：HTTP 404；
- 参数错误：HTTP 400；
- 导出失败：HTTP 400/500 + JSON，不返回 200 + 业务错误码。

现有 `SecurityConfig` 的 `accessDeniedHandler` 返回 HTTP 200 + code 403，新接口应统一改为 HTTP 403；至少管理接口必须如此。

### 2.5 隐私与使用边界

- 管理页不展示个人绩效排名，不提供“谁最闲/谁最忙”的文案；
- 管理页的个人负载明细仅 `owner/exec` 可见；
- **已知现状**：现有 `/api/gantt/load` 对所有空间成员开放，甘特负载面板也能被普通成员打开。这是既有能力，不在本期改动；因此不能对外宣称“整个系统的个人负载仅 owner/exec 可见”。若要统一隐私边界，P1 收紧甘特负载或对其脱敏；
- **现状与收紧**：`GET /api/export` 全量备份**已经**是 owner-only；`GET /api/export/csv` 任务 CSV 目前对所有成员开放，本版将其收紧为 **owner-only**；`exec` 只能使用 `/api/management/export` 导出管理字段；回滚旧版本会恢复 CSV 对成员开放的旧行为，需在发布/回滚说明中告知；
- 健康度覆盖原因、管理审计明细只对 `owner/exec` 可见；MVP 若复用空间活动流，只写通用事件，不写敏感原因；
- 管理报表导出不包含任务描述全文、附件内容、webhook/token；全量备份是 owner 专用能力，包含任务数据，不属于管理报表。

## 3. 核心指标口径

> 所有指标必须由服务端计算，前端只展示。口径变更必须同步本文档和 `docs/api.md`。

### 3.1 时间、时区与数据源

- 时区：`Asia/Shanghai`；服务端用 `LocalDate.now(ZoneId.of("Asia/Shanghai"))`；
- 本周：周一 00:00（含）至下周一 00:00（不含）；
- `task.completed_at` 与 `task_completion_record.completed_at` 都是 `DATE`，没有时分秒；
- `time_log` 按 `started_at` 归属周；跨周的计时会话整体归入开始周（现有行为，MVP 沿用）；
- 所有“今天”相关指标以服务端当天日期为准，前端不自行计算。

数据源：

| 数据 | 唯一来源 | 说明 |
|---|---|---|
| 任务状态/负责人/起止/估时/阻塞 | `task` | 有效任务排除软删除 |
| 当前有效完成 | `task_completion_record` | 任务进入 done 即锁定，不允许重开；见 3.11 |
| 完成趋势 | `task_completion_record` | 回填后使用；回填前显示“数据不可用”，不显示 0 |
| 工时 | `time_log.minutes` | 有效工时，已被每日上限和周末规则裁剪 |
| 活动/停滞 | `task.updated_at`、`task_log.created_at`、`task_comment.created_at`、`requirement.updated_at` | 管理字段变更不计入项目活动，见 3.9 |
| 项目元数据 | `requirement` | 负责人、起止、优先级、覆盖 |

### 3.2 项目范围

有效任务：

```sql
task.req_id = project.id
AND task.deleted_at IS NULL
```

规则：

- MVP 的项目完成率**包含 backlog 任务**，因为项目下任务通常已被视为承诺范围；
- 但“截止日期覆盖率”和“临期风险”只看**计划任务**：非 backlog 的有效任务 + backlog 中已设置 `due_date` 的任务；
- 未设置截止日期的 backlog 任务不应把整个项目判黄；它们只在数据质量里以“未排期”提示；
- 如果后续需要把 backlog 完全排除，增加项目级开关，不直接改全局口径。

### 3.3 项目实际完成率

**主口径：已完成估时加权完成率（推荐用于管理决策）**

```text
任务权重 = estimate_minutes > 0 ? estimate_minutes : 1
项目实际完成率 = Σ(已完成任务权重) / Σ(全部有效任务权重) × 100
```

规则：

- “已完成”只看 `board_column = 'done'`，不看 `progress`；
- 没有任务时返回 0，并标记 `noTasks = true`；
- 估时缺失的任务权重按 1，不能因此被忽略；
- 同时返回 `estimateCoverage`（有估时的任务数 / 有效任务数），低于 80% 时页面提示“估时覆盖不足，完成率可信度下降”。

**辅助口径：人工进度加权完成率**

```text
任务完成度 = done 列 ? 100 : clamp(progress, 0, 99)
项目人工进度 = Σ(任务权重 × 任务完成度) / Σ(任务权重)
```

规则：

- 未完成任务即使 `progress = 100`，也按 99 封顶，避免“项目显示 100% 但仍有未完成任务”；
- 该口径受人工维护影响，只作为辅助展示，不用于风险等级；
- 不使用“任务进度简单平均”作为管理口径。

### 3.4 项目计划完成率

按项目起止日期和工作日计算：

```text
项目总工作日 = [start_date, due_date] 内的工作日数（跳过周末）
已消耗工作日 = [start_date, min(today, due_date)] 内的工作日数
计划完成率 = 已消耗工作日 / 项目总工作日 × 100
```

边界：

- `today < start_date`：0%；
- `today > due_date`：100%；
- 起止缺失：`planAvailable = false`，不计算计划完成率；
- `due_date < start_date`：视为数据异常，`planAvailable = false`，数据质量标记；
- 法定节假日不建模，只跳周末；文档和页面都要明示这个限制。

### 3.5 进度偏差

```text
进度偏差（百分点） = 项目实际完成率 - 项目计划完成率
```

例：计划应完成 70%，实际完成 45%，偏差为 -25pp。偏差为负值时，前端同时显示数值和红色，不只靠颜色。

管理口径的“实际完成率”使用 3.3 的已完成估时加权（`doneWeightedPct`）；人工进度加权（`progressWeightedPct`）只作辅助展示，不参与偏差和风险判定。

### 3.6 风险等级

风险等级是**自动计算值**，人工只能做有限期覆盖。风险等级与数据质量是两个独立维度。

#### 3.6.1 状态处理

| 项目状态 | 风险等级 | 是否进入风险清单 | 是否计入逾期/停滞 |
|---|---|---:|---:|
| `active` | 按规则计算 | 是 | 是 |
| `done` 且有至少一个有效任务并全部完成 | green，标签“已完成” | 否 | 否 |
| `done` 但仍有未完成任务 | unknown，标签“已完成但有未完成任务” | 否（单独状态异常） | 否 |
| `done` 但无有效任务 | unknown，标签“已完成但无任务” | 否（单独状态异常） | 否 |
| `hold` | unknown，标签“已暂停” | 否 | 否 |

- `done` 项目如果仍有未完成任务，`statusIssue = done_with_open_tasks`：详情/列表显示“已完成但仍有 N 个未完成任务”，纳入总览的“状态异常”提示，但**不显示绿色**；
- `done` 项目如果没有任何有效任务，`statusIssue = done_without_tasks`，同样不显示绿色；
- `hold` 项目不参与健康度分布中的红/黄/绿统计，单独显示“暂停 N 个”；
- 设置 `done` 时自动清除人工覆盖；设置 `hold` 时保留覆盖但显示“已暂停”。

#### 3.6.2 判定优先级

1. `done` 但无有效任务：unknown，`statusIssue = done_without_tasks`；人工覆盖清除；不显示绿色；
2. `done` 且有至少一个有效任务并全部完成：green，标签“已完成”；人工覆盖自动清除；
3. `done` 但仍有未完成任务：unknown，`statusIssue = done_with_open_tasks`；人工覆盖清除；不显示绿色；
4. `hold`：unknown，标签“已暂停”；人工覆盖保留但**不展示、不参与统计**，恢复 active 后在有效期内继续生效；
5. 有效期内的**人工覆盖**：直接使用覆盖值，`healthSource = manual`，同时保留自动原因供查看；
6. 无有效任务：unknown，`noTasks = true`；
7. 自动规则：red > amber > green；
8. 起止日期缺失时 `planAvailable = false`，但任务级风险（逾期/阻塞）仍可把项目判红/黄；如果没有任何可计算的风险信号，则为 unknown，不显示绿色。

#### 3.6.3 自动规则

| 等级 | 条件（满足任一） |
|---|---|
| red · 高风险 | 已过截止日且仍有未完成任务；或进度偏差 ≤ -20pp；或存在 P0/P1 逾期任务；或逾期任务占比 ≥ 30% 且逾期任务数 ≥ 2；或存在 P0/P1 阻塞任务且阻塞 ≥ 3 天 |
| amber · 需关注 | 进度偏差在 (-20pp, -10pp]；或存在非 P0/P1 逾期任务；或存在任意优先级阻塞任务 ≥ 3 天；或剩余 7 天内到期、计划完成率 ≥ 80% 且实际完成率 < 计划完成率 × 80%；或活跃项目最近 14 天无活动；或存在 active 需求文档创建 7 天仍未拆出任务；或存在估时超支（实际/预估 ≥ 1.2 且任务未完成） |
| green · 正常 | 不满足 red/amber，且项目为 active、有有效任务、计划信息可计算 |
| unknown · 无法判断 | 无有效任务；或起止缺失且没有任何任务级风险信号；或项目暂停；或项目已完成但仍有未完成任务；或项目已完成但无任务 |

补充规则：

- 逾期任务占比 = 逾期任务数 / 有效任务数；
- 阻塞天数 = `today - blocked_at`；历史数据没有 `blocked_at` 时留空并从上线日开始计数，不用 `updated_at` 伪造；
- 任务截止日期覆盖率低于 80% 时，**不降低风险等级**，只在数据质量中提示；
- 负责人缺失时，**不降低风险等级**，只在数据质量中提示；
- 人工覆盖只允许 red/amber/green，不允许覆盖为 unknown；要恢复自动用“恢复自动”；
- 人工覆盖必须填写原因，保留 `health_updated_by/at` 和 `health_override_until`；
- 人工覆盖默认 30 天有效；到期自动回到自动计算；`done` 时自动清除；提供“恢复自动”按钮。

#### 3.6.4 为什么不再用数据质量降级

一个项目可能同时“有 3 个 P1 任务阻塞”且“缺负责人”。如果因为缺负责人显示灰色“未维护”，管理层会错过真实风险。因此：

- 风险等级只由风险规则决定；
- 数据质量单独显示“缺负责人/缺日期/任务未绑定账号”等徽标；
- 只有**无法计算**时才显示 unknown，而不是把已能计算出的红色藏起来。

### 3.7 风险类型与持续天数

| 类型 | 触发条件 | 严重度 | 持续天数 | 证据 |
|---|---|---|---|---|
| 项目逾期 | active 且 `today > due_date` 且仍有未完成任务 | red | 有：`today - due_date` | 截止日、未完成数 |
| 进度落后 | 偏差 ≤ -10pp | red（≤ -20pp）/ amber | 无 | 实际/计划/偏差 |
| 逾期占比过高 | 逾期任务占比 ≥ 30% 且逾期数 ≥ 2 | red | 无 | 逾期数/总数/占比 |
| 任务逾期 | `due_date < today` 且未完成 | red（P0/P1）/ amber（其他） | 有：任务逾期天数 | 任务名、截止日 |
| 任务阻塞 | `is_blocked = 1` 且未完成 | red（P0/P1 ≥ 3 天）/ amber（其他 ≥ 3 天；P0/P1 < 3 天） | 有：阻塞天数 | 任务名、阻塞原因、开始时间 |
| 临期低进度 | 剩余 0–7 天，计划完成率 ≥ 80%，实际 < 计划 × 80% | amber | 无 | 剩余天数、实际/计划 |
| 项目停滞 | active 且最近 14 天无活动 | amber | 有：无活动天数 | 最后活动时间 |
| 需求未拆解 | active 需求文档创建 ≥ 7 天且没有关联任务 | amber | 有：创建天数 | 需求标题、创建日 |
| 估时超支 | `actual / estimate ≥ 1.2` 且任务未完成 | amber | 无 | 实际/预估 |
| 人工覆盖 | 有效人工覆盖为 red/amber | 跟随覆盖值 | 无 | 覆盖原因、操作人、到期日 |

规则：

- 风险清单与风险等级使用同一套规则；不能出现“项目红但风险清单为空”；
- **只有有时间锚点的风险显示持续天数**：项目逾期、任务逾期、任务阻塞、项目停滞、需求未拆解；
- 偏差、覆盖率、估时超支没有历史起点，显示“当前值”，不编造天数；
- Top 风险排序：严重度（red > amber）→ 有持续天数的按天数降序 → 项目优先级（P0 > P1 > P2 > P3）→ 项目名；
- 每条风险必须有证据，不展示没有证据的推断；
- 数据质量提示不进入风险清单，单独在“数据质量”区块展示。

### 3.8 数据质量

数据质量是独立指标，**不决定风险等级**。

```text
数据质量 = 已满足的检查项 / 5 × 100
```

检查项：

1. 项目有负责人：`manager_user_id` 非空且对应当前共享空间 owner/member（不含 exec）；
2. 项目有开始日期；
3. 项目有截止日期；
4. 有效任务负责人覆盖率 ≥ 80%：`owner_user_id` 非空且对应当前共享空间 owner/member（不含 exec）的有效任务数 / 有效任务总数；
5. 计划任务截止日期覆盖率 ≥ 80%：有 `due_date` 的计划任务数 / 计划任务总数。

规则：

- 任务负责人覆盖必须用 `owner_user_id`，不能用 `owner` 文本；现有 `owner` 默认是“我”，文本口径几乎永远 100%，没有管理意义；
- `owner_user_id` 指向的账号已离开空间时，显示“历史负责人（已离开）”，**不计入覆盖率**；指向 exec 时显示“历史负责人（exec，只读）”，也不计入覆盖率；两种情况都需要 owner 重新指派；
- 计划任务定义见 3.2，未排期 backlog 不参与截止日期覆盖率；
- 没有任务时，检查项 4/5 视为未满足，数据质量最高 60；项目本身显示“无任务”；
- 估时覆盖率单独展示，不直接扣数据质量，因为估时不是所有团队都强制；
- 工作区汇总数据质量 = 所有项目已满足检查项总数 / (5 × 项目总数) × 100；没有项目时返回 `null`，页面显示“—”，不显示 0 或绿色；
- 单项目因为只有 5 个二元检查，取值只可能是 0/20/40/60/80/100；工作区汇总可以是任意 0–100（跨项目汇总）。示例中的“工作区 82 / 单项目 80”不矛盾；
- 数据质量只分三档展示：complete（100）、partial（60–99）、poor（< 60）；
- 数据质量低时，页面提示缺失项和“补全资料”入口，但不把红色风险降级。

### 3.9 逾期、阻塞、停滞

| 指标 | 口径 |
|---|---|
| 项目逾期 | active 且 `today > due_date` 且 `doneCount < taskCount` |
| 逾期任务 | `due_date < today` 且未完成、未删除；统一走 `TaskCalc.dueKind` |
| 阻塞任务 | `is_blocked = 1` 且未完成、未删除 |
| 项目停滞 | active 且最近 14 天无活动 |
| 最后活动时间 | `max(task.updated_at, task_log.created_at, task_comment.created_at, requirement_doc.updated_at, requirement.updated_at)`，但排除管理字段/健康覆盖造成的 `requirement.updated_at` 变化和纯文本编辑 |
| 本周完成 | `task_completion_record.completed_at` 在本周内；数据起始日之前显示“—”，不显示 0 |

最后活动时间说明：

- 评论不更新 `task.updated_at`，所以必须并入 `task_comment.created_at`；需求文档更新也不更新 `requirement.updated_at`，要并入 `requirement_doc.updated_at`；
- 健康度覆盖、负责人/日期维护会更新 `requirement.updated_at`，不能因此让停滞项目“复活”；
- 纯文本编辑（任务标题/描述/标签）也不应算作实质活动，避免“改个字就复活”；
- 建议服务端计算 `lastActivityAt` 时只统计任务状态/排期/进度/阻塞变化、评论、日志和项目名称/描述变更，排除管理字段和纯文本编辑；必要时落专门的活动视图。

### 3.10 资源负载

- 实际工时：`time_log.minutes` 汇总；这是**有效计入工时**，已被每日上限、工作时段、周末规则裁剪，不是物理在线时长；
- 预估工时：`task.estimate_minutes` 按任务排期分摊到周；只有截止日的任务按截止日所在周计入，并标记“未排期”；
- 周容量：MVP 用 `app_user.work_max_hours × 当周工作日 × 60` 计算，默认 8×5=40h；该字段本质是“每天最多计入几小时”，不是可用人力，页面标注为“周计入上限”；
- 负载率 = 预估工时 / 周容量；红色 ≥ 100%，黄色 85%–99%，正常 < 85%；
- 实际工时只作参考，不参与超载判定，因为实际值已被上限裁剪；
- 没有估时的任务不参与预估负载，但页面显示“估时覆盖不足”，不能把空白当 0；
- 团队汇总 = 有估时的成员预估工时之和 / 这些成员的容量之和；估时覆盖不足时显示警告；
- 默认按成员姓名排序，不按负载降序；不提供“谁最忙”文案；
- 个人明细仅 owner/exec 可见；现有甘特负载对成员的可见性见 2.5；
- 法定节假日、请假、兼职差异：MVP 只支持按账号每日上限推导，不建模节假日/请假；文档明示。

负载摘要中的“本周估时最集中项目” = 本周任务预估工时之和最大的项目，不叫“负载最高项目”，因为项目本身没有独立容量。

### 3.11 完成/工时历史口径

这是管理页最容易和现有页面数字对不上的地方，必须明确。

#### 3.11.1 完成

- `task_completion_record` 是**当前有效完成**：任务进入 done 时写入；正常流程不再删除；
- **任务完成后不可重开**：不允许移出 done、不允许调用 reopen、不允许通过编辑/移动/批量移动把列改回非 done；需要继续做时新建任务，见 4.2 MGT-019；
- 任务彻底删除后快照仍保留；任务软删除/恢复不影响完成记录；
- 2026-10-21 之前完成的存量任务没有快照，且 `sql/06` 默认不回填；
- 上线前必须执行一次性回填（从当前 done 任务生成快照），并记录 `dataStartDate`；
- `dataStartDate` 表示完成数据开始“完整可信”的日期；按实际情况记录（快照启用日或回填执行日），并在页面标注数据来源；回填能补充更早的、仍处于 done 的任务，这部分在趋势上标记为“回填数据”，不能和系统逐周记录混在一起；
- 管理页“本周完成”只统计 `dataStartDate` 之后的周；之前的周显示“—”，不能显示 0；
- 12 周趋势只渲染有数据的周，并在图例标注“完成数据自 YYYY-MM-DD 起”；
- 因为任务不可重开，完成快照在正常流程中只增不删，历史稳定性明显提高；P1 的完成事件表只用于管理员纠错、多周期审计等异常场景，不再是 MVP 的必需项；
- 现有分析页趋势仍读 `task.completed_at`，周回顾也读任务表，因此管理页完成数与它们可能不同；管理页必须标注数据源，P1 统一三处口径。

#### 3.11.2 工时

- 本周/12 周工时来自 `time_log`，按 `started_at` 归属周；
- `time_log` 会随任务彻底删除而删除；回收站保留 30 天，因此超过 30 天且被彻底删除的任务，其历史工时会消失；
- 管理页工时趋势需标注“仅统计仍存在的任务”；如果需要 12 周以上不可变工时，P1 做周工时归档；
- `time_log` 没有项目 ID 快照，项目工时按任务**当前** `req_id` 归属；任务换项目后，历史工时归属会变。文档明示；P1 在 `time_log` 增 `req_id` 或落项目周聚合；
- 人天换算：固定 8 小时 = 1 人天，仅用于展示；不按个人 `work_max_hours` 变化，避免同一报表口径漂移。

### 3.12 管理总览 KPI

顶部固定 7 个 KPI（不受周期选择器影响，全部标注“本周”）：

1. 项目总数（全部状态）；
2. 进行中项目数（active）；
3. 高风险项目数（active 中 riskLevel = red）；
4. 逾期项目数（active 中项目逾期）；
5. 本周完成任务数（完成快照，数据起始日之后）；
6. 本周投入工时（小时；人天 = 分钟 / 480）；
7. 工作区数据质量（0–100；无项目显示“—”）。

下方 5 个区块：

- 风险分布：active 项目的 red/amber/green/unknown 数量与占比；另起一行显示 done/hold 数量；
- 状态异常：`statusIssue` 非空（`done_with_open_tasks` / `done_without_tasks`）的项目数量，点击跳转项目列表并筛选“状态异常”；
- 12 周趋势：新增任务 vs 完成任务；完成数据从 `dataStartDate` 开始，缺失周不画 0；
- Top 风险：最多 5 条，按 3.7 排序；
- 负载摘要：本周超载人数、估时覆盖率、本周估时最集中项目、未排期任务提醒。

### 3.13 计算示例（验收用）

**示例项目 X 的输入（仅用于验证公式，不代表 7.3 的项目 A）：**

- 有效任务 10 个，估时合计 10,000 分钟；
- 5 个任务在 done 列，done 任务估时合计 6,000 分钟；
- 人工进度加权结果 65%（仅辅助）；
- 项目开始 2026-10-01，截止 2026-11-16，今天 2026-11-02，计划完成率 70%（23/33 个工作日）；
- 项目负责人、开始日期、截止日期已维护；
- 任务负责人账号覆盖 8/10 = 80%；计划任务 6 个，其中有截止日期 5 个 = 83%。

**计算：**

```text
doneWeightedPct = 6,000 / 10,000 × 100 = 60%
variancePct = 60 - 70 = -10pp
riskLevel = amber（-20pp < variance ≤ -10pp；-10pp 属于 amber）
dataQuality = 5/5 × 100 = 100
```

**边界验证：**

- 如果其中一个 P0 任务阻塞 4 天 → `riskLevel = red`，`dataQuality` 仍为 100；
- 如果项目负责人缺失 → `dataQuality = 80`，`riskLevel` 仍按 60%/70%/-10pp 计算为 amber，**不降级为 unknown**；
- 如果截止日期缺失 → `planAvailable = false`，`variancePct = null`；没有任务级风险时 `riskLevel = unknown`，有 P1 阻塞 4 天时仍为 red；
- 如果 done 任务估时合计 10,000、全部任务估时合计 10,000 → 100%，不是 99%；
- 如果未完成任务 `progress = 100` → 人工进度按 99，doneWeighted 不变；
- 如果本周估时 3,000 分钟、容量 2,400 分钟 → `estimatedPct = 125%`，红色超载；
- 如果 3 个任务未绑定 `owner_user_id`，任务负责人覆盖 7/10 = 70% → 数据质量 80（仅该项未满足），风险不变。

### 4.2 关键需求说明

#### MGT-001 新增 `exec` 角色

- `workspace_member.role` 取值扩展为 `owner/member/exec`；
- 现有邀请链接加入后仍为 `member`，由空间主在成员列表中改为 `exec`；
- 新增 `PUT /api/workspaces/{id}/members/{userId}/role`，仅 owner；
- 角色变更只允许 `member ↔ exec`；不允许把 owner 改为 exec，也不允许把 member/exec 改为 owner；空间主转让不在本期范围；
- 成员被设为 exec 前，如果仍是项目负责人或任务负责人，必须先转交；否则返回 409，避免“exec + 负责人”权限冲突；
- exec 不能被设置为任务负责人或项目负责人；历史数据中已经是的，按 exec 只读处理，需 owner 转交；
- `exec` 可以切换空间、退出空间、改密码、改资料、改计时设置、标记通知已读；
- `exec` 不能创建/编辑/移动/删除任何业务数据；
- `exec` 不是空间成员时，不因其他空间角色获得权限。

**验收：**

1. owner 把成员改为 exec 后，该成员刷新页面出现“管理”入口；
2. 该成员直接调用 `POST /api/tasks`、`PUT /api/tasks/{id}`、`DELETE /api/tasks/{id}` 均返回 403；
3. 该成员调用 `GET /api/management/overview` 返回 200；
4. 该成员调用 `POST /api/notifications/{id}/read`、`PUT /api/auth/work-hours` 正常；
5. 角色变更后 60 秒内不需要重新登录即可生效；
6. 个人空间不出现管理入口，接口返回 403；
7. 项目负责人或任务负责人直接改为 exec 返回 409；先转交后可以改；
8. 把 exec 设为任务负责人/项目负责人返回 400。

- 支持“未指定负责人”“缺日期”筛选；
- 支持批量设置负责人、批量设置日期；
- 建议值只能作为建议：项目负责人候选取任务负责人众数/最近任务负责人；开始/截止候选取任务最早开始/最晚截止；**必须人工确认**，不能自动写入；
- 现有 `requirement` 表没有 `created_by`，创建项目也没有审计，因此**无法回填“项目创建人”**；不要承诺这个能力；
- 批量操作写审计；失败要逐条返回，不整批静默失败。

验收：

- 试点空间可以通过列表在一个下午补齐大部分负责人/日期；
- 建议值不清空已有字段；
- 批量设置不覆盖比当前值更完整的数据，除非用户确认；
- 无权限用户不能批量修改。

#### MGT-016 健康覆盖生命周期（P0）

- 字段：`health_override`、`health_note`、`health_updated_by`、`health_updated_at`、`health_override_until`；
- 默认 30 天；到期自动回自动；
- done 时自动清除；
- 恢复自动按钮；
- 覆盖原因 ≥ 5 字；
- 覆盖不改变数据质量；
- 覆盖必须显示“人工”，自动原因仍可查看。

#### MGT-017 项目状态生命周期（P0）

- active：参与风险、逾期、停滞、负载、健康分布；
- done 且有至少一个有效任务并全部完成：风险 green，标签“已完成”，不进入风险清单/逾期/停滞；
- done 但仍有未完成任务：风险 unknown，`statusIssue = done_with_open_tasks`，标签“已完成但有未完成任务”，不显示绿色，纳入总览“状态异常”提示；
- done 但无有效任务：风险 unknown，`statusIssue = done_without_tasks`，标签“已完成但无任务”，不显示绿色；
- hold：风险 unknown，标签“已暂停”，不进入风险清单/逾期/停滞；
- 状态变更由 owner/项目负责人执行；其他成员保持现有项目名称/描述编辑，但管理页不提供状态编辑；
- 状态变更写审计；done 时清除人工覆盖。

验收：

- done 且有至少一个有效任务并全部完成 → green；
- done 但仍有未完成任务 → unknown + `statusIssue=done_with_open_tasks`，不显示绿色；
- done 但无有效任务 → unknown + `statusIssue=done_without_tasks`，不显示绿色；
- hold → unknown，且不进入风险/逾期/停滞。

#### MGT-018 成员移除/账号删除校验（P0）

- 移除成员前检查其是否是项目负责人；是则阻止，要求先转交或由 owner 清空；
- 任务负责人被移除不阻断（保留历史归属），任务显示“历史负责人（已离开）”，数据质量下降，owner 应重新指派；
- 清空负责人时写审计，数据质量下降；
- 平台管理员删除账号时同样处理；
- 不允许把项目负责人设置为非共享空间成员或 exec。

#### MGT-019 已完成任务禁止重开（P0）

**业务规则：**

- 任务一旦进入 `done`，该任务即“完成锁定”；
- 不允许移出 done、不允许调用 reopen、不允许通过编辑/移动/批量移动把列改回非 done；
- 需要继续做时，员工应**新建一个续做任务**，而不是重开旧任务；
- 旧任务和旧完成快照保留；旧工时记录在任务未彻底删除前保留；新任务使用新 ID、progress=0，完成时生成新的完成快照；
- 项目状态仍可按 5.5.8 从 done 重新打开，但“项目重新打开”不等于“任务重开”。

**服务端拦截：**

以下路径从 done 离开时统一返回 `409`，响应体 `{code:409,message:"已完成任务不可重开，请新建续做任务"}`：

- `POST /api/tasks/{id}/reopen`
- `PUT /api/tasks/{id}`：变更 `boardColumn` 且原列为 done
- `POST /api/tasks/{id}/move`
- `POST /api/tasks/bulk-move`：只要包含一个 done → 非 done，整批拒绝，不做部分成功
- 其他未来新增的“改列/改状态”接口

**前端：**

- 看板/列表/日历/甘特不允许把 done 任务拖出完成列；
- 任务抽屉隐藏“重新打开”；
- 点击完成任务的“新建续做任务”时，预填原项目、原关联需求、原标题（可编辑），新任务 progress=0，并在描述中自动引用原任务 ID/标题；
- 完成列和已完成任务显示“已完成，不可重开；如需继续请新建任务”。

**完成锁定范围：**

- 锁定：看板列（不能离开 done）、进度、估时、负责人、优先级、项目/需求关联、完成时间；未列出的任务字段默认也锁定；
- 允许：标题、描述、标签、评论、附件；
- 标题/描述修改不回写完成快照，管理完成数据以快照为准；
- 如果评审希望已完成任务完全只读，实施时把标题/描述也锁定即可。

**历史数据：**

- 新规则从上线日起生效，不回滚历史上已重开的任务；
- 回填只覆盖当前仍为 done 的任务；
- 若发现历史完成记录异常，由运维/管理员走受控修复，不开放普通用户重开。

**验收：**

1. done 任务调用 reopen 返回 409，完成快照仍在；
2. done 任务通过 PUT/move/bulk-move 离开 done 全部返回 409；
3. 前端无法把 done 任务拖出完成列，任务抽屉无“重新打开”；
4. “新建续做任务”生成新 ID、progress=0，旧任务和快照不变；
5. 批量移动中只要有一个 done 任务，整批拒绝且没有部分成功；
6. 历史已重开的任务不受影响，数据不回滚；
7. done 任务修改 progress/估时/负责人/优先级/项目关联/完成时间返回 409；修改标题/描述/标签允许且完成快照不变。

#### MGT-020 任务字段批量维护（P0）

- 数据质量下钻后，列出“未绑定 `owner_user_id` 的任务”和“计划任务缺截止日期”的任务；
- 支持按项目/负责人筛选，批量绑定共享空间 owner/member（不含 exec）、批量补截止日期；
- 不自动猜测负责人；建议值必须人工确认；
- 批量操作逐条返回失败原因，写审计；
- 不改变任务完成锁定规则：done 任务仍按 MGT-019 锁定。

验收：

- 试点空间可以把任务负责人覆盖率从低值批量补到 80% 以上；
- 批量操作不影响已完成任务的锁定字段；
- 批量失败不静默。

### 5.5 业务使用逻辑

本节回答“谁在什么时候怎么用”，避免页面做出来却没人用。

#### 5.5.1 上线初始化（owner，一次性）

1. 选定一个共享空间作为试点；
2. 在项目列表筛“未指定负责人”“缺日期”，批量补齐；
3. 负责人建议值来自任务负责人众数/最近任务负责人，必须人工确认；
4. 日期建议值来自任务最早开始/最晚截止，必须人工确认；
5. 邀请管理层账号，设为 `exec`；
6. 查看数据质量分布，目标 ≥ 80%；
7. 连续两周观察阈值是否合理，再决定是否推广到其他共享空间。

禁止：自动猜测负责人、自动从创建人回填（现有表没有创建人）、把数据质量低直接覆盖成绿色。

#### 5.5.2 每周管理例程（exec，5–10 分钟）

1. 周一上午打开管理驾驶舱；
2. 先看 7 个 KPI 和风险分布，再看 Top 风险；
3. 对每条红色风险：打开项目详情 → 找到任务证据 → 确认负责人和下一步动作；
4. 如果数据缺失：通知 owner/项目负责人补全，不直接覆盖；
5. 如果风险已知且暂时接受：由 owner 做有限期覆盖并写原因；
6. 导出本周筛选结果用于例会；
7. 下周同一时间复查；管理页不新建风险工单，处理动作回到项目/任务。

验收：每条红色风险都有证据；会议纪要中的数字与页面一致。

#### 5.5.3 风险处理闭环

```
风险清单 → 项目详情 → 任务证据 → 处理动作 → 下次刷新自动复算
```

- 处理动作包括：重新指派、调整排期、拆任务、解除阻塞、转交项目负责人；
- `exec` 只能看，不能改；需要 owner/项目负责人执行；
- 风险不会“手动关闭”，只能通过数据变化或有限期覆盖消失；
- 覆盖到期后风险自动重新出现，避免“盖住就忘”。

#### 5.5.4 人工覆盖流程

1. owner 打开项目详情；
2. 选择 red/amber/green，填写原因（≥ 5 字）；
3. 系统默认 30 天有效，显示到期日；
4. 页面显示“人工”标识，自动原因仍可展开；
5. 到期自动恢复；owner 可随时“恢复自动”；
6. 项目改为 done 时自动清除覆盖；
7. 覆盖不改变数据质量，不隐藏缺失项。

#### 5.5.5 角色协作

| 角色 | 日常动作 |
|---|---|
| owner | 维护成员/角色、项目负责人/日期/优先级、人工覆盖、导出、处理成员移出 |
| exec | 每周看板、风险下钻、导出；发现数据问题转给 owner/项目负责人 |
| 项目负责人（member） | 维护自己项目的日期/优先级、推进任务、处理逾期/阻塞 |
| 其他 member | 执行任务；通过现有页面反馈进度；看不到管理驾驶舱 |
| admin | 账号创建/重置/禁用；不因平台角色获得空间数据权限 |

#### 5.5.6 数据质量治理

- owner 每周看一次“缺负责人/缺日期/任务未绑定账号”；
- 优先补项目负责人和截止日期，因为它们影响计划完成率和风险判断；
- 任务负责人覆盖率低于 80% 时，补 `owner_user_id`，不是改显示名；由 MGT-020（P0）提供批量绑定，不要求逐个打开任务；
- 数据质量低但确实有风险的项目，仍然显示风险，只加“数据不完整”徽标；
- 目标：试点空间数据质量 ≥ 80%，不追求 100%。

#### 5.5.7 报表与周报

- 例会前按风险/负责人/状态筛选后导出 CSV；
- 导出文件只含管理字段，不含任务描述全文；
- 周报（P1）复用现有推送渠道，收件人 owner/exec；
- 周报不包含个人绩效排名，只包含项目风险、完成、工时总量。

#### 5.5.8 状态流转

- active → hold：项目暂停，风险显示“已暂停”，不进入风险清单；人工覆盖保留但暂不展示；
- active → done：全部有效任务完成时显示“已完成”；仍有未完成任务时显示“已完成但有未完成任务”，`riskLevel = unknown` + `statusIssue = done_with_open_tasks`；没有有效任务时显示“已完成但无任务”，`statusIssue = done_without_tasks`；两者都不显示绿色；
- done/hold → active：重新纳入风险计算；hold 恢复时未过期的人工覆盖继续生效；
- 状态变更由 owner/项目负责人执行并写审计；
- done 时清除人工覆盖，避免完成项目长期显示人工红色。

#### 5.5.9 异常、权限与空态

- 无权限：显示说明和“返回看板”，不显示 500；
- 个人空间：显示“管理驾驶舱仅共享空间可用”；
- 无项目：显示空态，不显示 0 值 KPI；
- 数据不足：显示“数据暂不可用”，不显示绿色；
- 接口失败：错误块 + 重试；
- 角色变更：刷新页面后生效；多实例最多 60 秒；
- 数据起始日之前：趋势显示“数据自某日起”，不画 0；
- 已完成任务不可重开：详情/趋势卡片显示“已完成任务不可重开，如需继续请新建任务”；
- 任务彻底删除：详情/趋势卡片显示完成快照保留、工时随删除消失的口径说明。

#### 5.5.10 明确不做的使用方式

- 不做个人绩效排名、工时排行榜、在线监控；
- 不做 AI 预测工期或自动重排；
- 不把风险清单做成工单系统；
- 不让 exec 写任何业务数据；
- 不自动猜测负责人/日期；
- 不把数据质量低当作绿色或灰色的理由。

#### 5.5.11 关键状态机

**项目状态：**

```text
active --暂停--> hold --恢复--> active
active --完成--> done --项目重新打开--> active
hold   --完成--> done
```

| 当前 | 动作 | 目标 | 业务效果 |
|---|---|---|---|
| active | 暂停 | hold | 风险显示“已暂停”，移出风险清单/逾期/停滞；人工覆盖保留但暂不展示 |
| active | 完成 | done | 风险显示“已完成”，移出风险清单；清除人工覆盖；仍有未完成任务时提示 |
| hold | 恢复 | active | 重新参与风险/逾期/停滞；未过期的人工覆盖恢复生效 |
| hold | 完成 | done | 同 active → done |
| done | 项目重新打开 | active | 项目重新参与风险计算；不恢复已清除的人工覆盖；**不等于任务重开** |

**人工覆盖：**

```text
无覆盖 --覆盖(red/amber/green + 原因 + 30天)--> 人工生效
人工生效 --到期--> 自动
人工生效 --恢复自动--> 自动
人工生效 --项目 done--> 自动（清除）
人工生效 --项目 hold--> 暂停展示；恢复 active 且未到期时继续生效
```

**任务阻塞：**

```text
未阻塞 --标记阻塞（写原因）--> 阻塞（blocked_at=now，source=real）
阻塞   --修改原因--> 阻塞（blocked_at 不变）
阻塞   --解除阻塞--> 未阻塞（blocked_at=null）
```

**任务完成（完成锁定）：**

```text
未完成 --移入 done--> 已完成（写入快照，任务锁定）
已完成 --尝试移出 done / reopen / move--> 拒绝 409（提示新建任务）
已完成 --新建续做任务--> 新任务（新 ID，progress=0，旧任务和快照保留）
已完成 --任务彻底删除--> 快照保留
```

- “完成锁定”只针对任务本身；项目状态仍可按 5.5.8 从 done 重新打开；
- 已完成任务允许查看、评论、附件、标签，以及修改标题/描述；列、进度、估时、负责人、优先级、项目/需求关联、完成时间锁定；
- 若确实需要更正历史完成记录，只能由运维/管理员通过受控的数据修复流程处理，不对普通用户开放。

**数据质量：**

```text
缺失 --补负责人/日期/绑定账号/补截止日--> 提升
提升 --删除负责人/成员移出/清空日期--> 下降
数据质量变化不直接改变 riskLevel；只在“无法计算”时把 risk 置为 unknown
```

#### 5.5.12 业务动作矩阵

| 动作 | 谁 | 前置条件 | 结果 | 审计 |
|---|---|---|---|---|
| 完成任务（移入 done） | owner/项目负责人/member | 有任务编辑权限 | 写完成快照；任务锁定 | 是 |
| 重开/移出 done | 无（正常流程） | — | 409，提示“新建续做任务” | 拒绝原因可记 |
| 新建续做任务 | owner/项目负责人/member | 项目属于当前空间 | 新任务 ID、progress=0；旧任务和快照保留 | 是 |
| 设置项目负责人 | owner | 目标是共享空间成员 | 更新 `manager_user_id`；数据质量可能提升 | 是 |
| 维护开始/截止/优先级 | owner/项目负责人 | 项目属于当前空间；负责人只能改自己项目 | 更新元数据；风险/计划完成率下次刷新复算 | 是 |
| 设置 done/hold | owner/项目负责人 | 项目属于当前空间 | done 清除覆盖；hold 保留但隐藏 | 是 |
| 人工覆盖风险 | owner | 原因 ≥ 5 字；覆盖值 red/amber/green | 写 `health_override*`；默认 30 天 | 是（通用事件） |
| 恢复自动 | owner | 存在人工覆盖 | 清空覆盖字段 | 是 |
| 批量补全 | owner | 选中项目属于当前空间 | 逐条更新；逐条返回失败 | 是 |
| 导出报表 | owner/exec | 当前筛选条件 | 生成 CSV；不缓存 | 是（通用事件） |
| 变更成员角色 | owner | 目标不是 owner | 更新 role；失效成员缓存 | 是 |
| 移出成员 | owner/目标本人 | 目标不是 owner；目标不是项目负责人 | 删除成员关系；本人退出 | 是 |
| 回填完成快照 | owner/运维 | 已备份 | 从当前 done 任务生成快照 | 是（运维日志） |

#### 5.5.13 完成后续做流程（MGT-019）

1. 员工在已完成任务上看到“新建续做任务”；
2. 点击后预填原项目、原关联需求、原标题，标题可修改；
3. 新任务使用新 ID，`progress = 0`，不复制完成状态、工时、阻塞、完成快照；
4. 新任务描述自动写入“续做自 #原任务ID 原任务标题”，便于追溯；
5. 旧任务保持完成，完成快照和管理统计不变；
6. 管理页会看到两条任务：旧任务计入完成，新任务计入进行中；项目完成率不会被反复重开影响；
7. 如果只是补充说明、附件或评论，直接在旧任务下操作，不新建任务。

边界：

- MVP 不强制父子关系；后续若需要“续做链”，再增加 `parent_task_id`，不在本期；
- “新建续做任务”不能做成“复制任务全部字段”，否则工时、完成状态、阻塞状态会污染新任务；
- 续做任务仍需遵守项目/需求的归属校验和负责人成员校验。

## 6. 数据模型改造

### 6.1 `requirement` 增加管理字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `manager_user_id` | `VARCHAR(32) NULL` | 项目负责人账号 ID；必须是共享空间成员 |
| `start_date` | `DATE NULL` | 项目开始日期 |
| `due_date` | `DATE NULL` | 项目截止日期 |
| `priority` | `VARCHAR(4) NOT NULL DEFAULT 'P2'` | 项目优先级 P0–P3 |
| `health_override` | `VARCHAR(8) NULL` | red/amber/green；空=自动 |
| `health_note` | `VARCHAR(200) NULL` | 人工覆盖原因 |
| `health_updated_by` | `VARCHAR(32) NULL` | 操作人 |
| `health_updated_at` | `DATETIME NULL` | 操作时间 |
| `health_override_until` | `DATETIME NULL` | 覆盖到期时间；空=不过期（仅历史数据） |
| `created_by` | `VARCHAR(32) NULL` | 未来新建项目的创建人；**存量无法回填** |

说明：

- 不改表名，不把 `requirement` 重命名为 `project`；
- 新字段中 `priority` 不是可空字段，文档不要写“所有新字段全部可空”；
- `created_by` 只用于未来项目，现有项目没有创建人记录；
- 项目负责人字段建议叫 `manager_user_id`，不要叫 `owner_user_id`，避免和空间主混淆；
- `health_override_until` 为空只用于历史数据，新建覆盖必须填。

### 6.1.1 `task` 增加阻塞开始时间

现有 `task` 只有 `is_blocked` 和 `blocked_reason`，没有“从哪天开始阻塞”。

| 字段 | 类型 | 说明 |
|---|---|---|
| `blocked_at` | `DATETIME NULL` | 进入阻塞状态的时间；解除阻塞时置空 |
| `blocked_at_source` | `VARCHAR(8) NULL` | `real` / `estimated`；历史估算值标记 |

写入规则：

- `is_blocked` 从 false 变 true 时写入 `now()`，`source = real`；
- 已阻塞状态下只改原因，不重置 `blocked_at`；
- 从 true 变 false 时置空；
- 历史数据**不要**用 `updated_at` 回填；留空并从上线日开始计数，或人工确认后标 `estimated`；
- `Task` 实体的 `blocked` 字段与数据库 `is_blocked` 的映射保持不变；
- 备份/导入、CSV 导出、任务详情、TaskMapper 都要同步该字段。

### 6.2 任务负责人覆盖

- 数据质量的任务负责人覆盖率必须用 `owner_user_id`；
- `owner` 文本只用于显示和历史兼容，不用作管理口径；
- 负责人账号必须是共享空间 owner/member，不能是 exec；历史非成员任务允许保存，但不能新指派给非成员；历史非成员负责人显示“已离开”，不计入数据质量覆盖率；历史 exec 负责人按只读处理，也不计入覆盖率，需 owner 转交；
- 项目负责人必须是共享空间 owner/member，不能是 exec；移出成员前必须转交。

### 6.3 角色

`workspace_member.role` 新增取值 `exec`，字段长度已足够，无需改列。

需要同步修改：

- `WorkspaceService` 的角色校验；
- `WorkspaceMemberCache` 的 `myRole` 传递与主动失效；
- 成员列表前端显示“管理层”；
- 邀请加入后默认 `member`，由 owner 改角色；
- 旧版本回滚前把 exec 改回 member，或加 feature flag。

### 6.4 索引

现有 `idx_ws_req (workspace_id, req_id)` 可支撑大部分项目聚合。建议补一条覆盖软删除的复合索引：

```sql
ALTER TABLE task
  ADD KEY idx_ws_req_active (workspace_id, req_id, deleted_at, board_column);
```

说明：

- 上线前用 `EXPLAIN` 验证是否真的被使用；如果 MySQL 选择现有 `idx_ws_req`，不要盲目加；
- 加列/加索引都要沿用现有迁移脚本的 `information_schema + PREPARE` 幂等写法；
- 项目列表按负责人/状态筛选时，项目量只有 50–200，不强制加索引；
- 如果后续项目数上千，再评估 `(workspace_id, status)`、`(workspace_id, manager_user_id)`。

### 6.5 审计

MVP 复用 `task_log` 的配置哨兵机制：

```text
task_id = 'MGT'
action = 'management'
detail = '调整项目A健康度'   -- 只写通用事件
```

敏感原因（如“供应商延期”）只放 `health_note`，不进入空间活动流。`health_note` 只能通过管理接口读取。

审计事件：

- 修改项目负责人/起止日期/优先级；
- 人工覆盖/恢复健康度；
- 变更成员角色；
- 导出管理报表；
- 批量补全/状态变更；
- 成员移出导致负责人清空。

P1 再评估独立 `management_audit` 表，支持查询和敏感明细。

### 6.6 备份/恢复

`BackupData.BackupReq` 当前只有 `id/name/desc/status/createdAt`，必须增加：

- `managerUserId`、`startDate`、`dueDate`、`priority`；
- `healthOverride`、`healthNote`、`healthUpdatedBy`、`healthUpdatedAt`、`healthOverrideUntil`；
- `createdBy`（如果有）。

同时：

- 备份版本号递增，旧备份导入时新字段为空；
- 导入时要校验负责人仍是空间成员，否则置空并标记数据质量；
- 恢复后数据质量可能下降，页面要能提示；
- `task.blocked_at` / `blocked_at_source` 同步进 `BackupTask`；
- 管理审计不进业务备份，避免敏感信息扩散。

### 6.7 完成/工时历史策略

- 上线前执行一次完成快照回填（从当前 done 任务生成），并记录 `dataStartDate`；
- 回填使用任务当前 `completed_at`，不伪造历史时分秒；
- 回填只覆盖仍存在的 done 任务，无法恢复已删除/历史上曾重开过的完成；
- 从本版起任务完成后不可重开；`TaskCompletionService.remove` 只保留给历史数据修复/导入等受控场景，不作为普通业务路径；
- 正常流程下完成快照只增不删；管理页明确提示“任务完成即锁定，如需继续请新建续做任务”；
- P1 的完成事件表（append-only）只用于管理员纠错、多周期审计等异常场景，不再是 MVP 的必需项；
- `time_log` 保留现状；管理页标注“任务彻底删除后工时会消失”，P1 再做周归档。

### 6.8 自动风险不落库

- 自动风险等级和 `statusIssue` 不落库，每次按规则计算，避免状态过期；
- 只落人工覆盖字段；
- 响应返回 `riskLevel`、`statusIssue`、`healthSource`（auto/manual）、`riskReasons`、`dataQuality`、`missingFields`、`healthOverrideUntil`；
- 因为风险不落库，列表必须先算全部项目再排序分页（项目量可控），或后续落每日快照；
- 后续如果要做风险历史趋势，增加按日快照表，不在 MVP 范围。

## 7. 接口设计

所有接口前缀 `/api/management`，统一使用 `@CurrentWorkspace` 解析空间，沿用 `ApiResult`；CSV 导出除外。

### 7.1 鉴权与错误

- 管理读接口：共享空间 owner/exec；
- 管理写接口：共享空间 owner；
- 导出：共享空间 owner/exec；
- member：403；
- 个人空间：403；
- 项目不存在/不属于当前空间：404；
- 错误体：`{code, message}`，HTTP 状态与 code 对齐；

### 7.6 导出格式

- `Content-Type: text/csv; charset=UTF-8`；
- UTF-8 BOM；
- 第一行列头；
- 文件名 `管理报表-项目组合-YYYY-MM-DD.csv`；

- 不含任务描述全文、附件、webhook/token；
- 不缓存（`Cache-Control: no-store`）。

### 7.7 分页、排序与性能

- 项目列表：先取工作区内全部项目 + 聚合事实（50–200 个量级），内存计算风险并排序，再切片；默认 20，最大 100；
- 风险清单：默认 100，最大 500；按项目分组返回；
- 负载：区间最大 26 周；任务上限沿用 20,000；
- 查询次数固定，不随项目数线性增加：项目 1 次、任务聚合 1 次、完成趋势 1 次、工时聚合 1 次、阻塞/风险明细 1 次（只查 red/amber）、负责人姓名批量 1 次；目标 ≤ 6 次；
- 不允许“先 selectAll 再逐项目查”的 N+1；
- 目标：2,000 任务 / 50 项目 p95 < 500ms；20,000 任务 / 200 项目 p95 < 1.5s；
- 测量方法：造 200 项目/20,000 任务数据，连续 10 次取 p95，记录 `EXPLAIN` 和慢查询日志。

### 7.8 ETag

可选复用 `WorkspaceVersionService`，但必须：

- ETag 包含空间、版本、查询串、**当天日期**、**当前角色**；
- 跨过 00:00 后健康度/计划完成率会变化，不能返回旧 304；
- 写操作成功 bump 版本；管理读接口只在同一天、同角色、同查询串下复用；
- 导出不使用 ETag。

### 7.9 对现有任务接口的影响（MGT-019）

这是本版对现有行为的**有意变更**，需要在发布说明中单列：

- `POST /api/tasks/{id}/reopen`：保留路由，但对 done 任务返回 409；
- `PUT /api/tasks/{id}`：如果原 `boardColumn = done` 且请求要改成非 done，返回 409；
- `PUT /api/tasks/{id}`：如果原 `boardColumn = done` 且请求修改了 `progress`、`estimateMinutes`、`ownerUserId`、`priority`、`reqId`、`reqDocId`、`completedAt`，返回 409（标题/描述/标签仍允许修改，但不回写完成快照）；
- `PUT /api/tasks/{id}`：done 任务未传 `boardColumn` 时按 done 处理，不能因为默认值落到 backlog；这条用于防止“只想改标题却把任务重开”；
- `POST /api/tasks/{id}/move`：从 done 移到非 done，返回 409；在 done 列内排序允许；
- `POST /api/tasks/bulk-move`：批次中只要有一个 done → 非 done，整批 409，不做部分成功；全部在 done 内排序允许；
- `DELETE /api/tasks/{id}`：允许；软删除/彻底删除都不删除完成快照；
- `POST /api/tasks/{id}/restore`：允许；恢复后仍是 done，不触发重开；
- `POST /api/tasks`：允许；新建续做任务走普通创建，不复制完成状态/工时/阻塞。

**实现注意（容易踩坑）：**

`TaskSaveRequest` 当前带默认值：`priority = P2`、`boardColumn = backlog`、`progress = 0`；`owner`/`category` 缺失时服务层还会填默认负责人/第一个分类。done 任务如果直接复用这个 DTO，会出现“只改标题却把优先级改成 P2、列改成 backlog、进度改成 0、负责人改成当前用户”的隐式修改。

因此 done 任务更新必须：

- 以数据库旧任务为底稿合并缺省字段；未显式提交的字段沿用旧值；
- 使用无默认值的专用 DTO（如 `DoneTaskPatch`），或在 Service 中逐字段比较 `old` 与 `req`；
- 只有锁定字段**实际值发生变化**时才 409，字段出现但值相同应允许保存；
- 409 校验必须在计时停表、完成快照、循环派生等任何副作用**之前**执行，避免“报错了但计时/快照已经变了”；
- done 任务只接受 `title`、`description`、`tags` 的变化；其他字段按锁定处理，建议专用 DTO 只暴露这三个字段；
- 标题/描述/标签可以更新，但不回写完成快照。

前端必须同步：

- 看板/列表/日历/甘特的 done 任务不可拖出完成列；
- 任务抽屉隐藏“重新打开”；
- done 任务提供“新建续做任务”，预填项目/需求/标题，描述引用原任务。

错误文案统一为：“已完成任务不可重开，请新建续做任务。”

### 8.2 风险纯函数

`ProjectRiskService.compute(ProjectFacts facts, LocalDate today)`：

```java

    String statusIssue;    // null / done_with_open_tasks / done_without_tasks

```

必须覆盖的单元测试：

1. 缺负责人 + 无其他风险 → 风险按自动规则（可能是 green/unknown），数据质量 80，不是灰；
2. 缺负责人 + P1 阻塞 4 天 → 仍为 red，数据质量下降；
3. 已逾期且未完成 → red；
4. 偏差 -25pp → red；
5. 偏差 -15pp → amber；
6. 逾期任务占比 10% → amber（非 P0/P1）；
7. 逾期任务占比 35% 且逾期数 ≥ 2 → red；
8. P0 阻塞 4 天 → red；
9. 任意阻塞 2 天 → 不因阻塞进 red；P0/P1 2 天 → amber；
10. 14 天无活动 → amber；
11. 截止日期覆盖率 60% → 风险不变，数据质量下降；
12. 人工覆盖红且未到期 → manual + 原因；
13. 人工覆盖过期 → 自动结果；
14. done 且有至少一个有效任务并全部完成 → green，即使缺字段；仍需显示数据质量；
15. hold → unknown；
16. 无任务 → unknown + noTasks；
17. 未完成但 progress=100 → 人工进度按 99；
18. 起止缺失但有逾期任务 → red + planAvailable=false；
19. due = today → 计划 100%，不逾期；
20. 跨周/跨月边界；
21. hold + 有效人工覆盖 → 仍显示 unknown，覆盖隐藏；恢复 active 且未过期 → 恢复 manual；
22. done + 有效人工覆盖 → green，覆盖被清除；
23. done + `POST /reopen` → 409，完成快照仍存在；
24. done + `PUT` 改列 / `move` / `bulk-move` 离开 done → 409；批量中混入一个 done 时整批拒绝且无部分成功；
25. done + 新建续做任务 → 新 ID、progress=0，旧任务和旧快照不变；
26. done + 软删除/彻底删除/恢复 → 完成快照保留；恢复后仍是 done，不触发重开；
27. done + 修改 progress/estimate/ownerUserId/priority/reqId/reqDocId/completedAt → 409；修改标题/描述/标签允许，完成快照不变；
28. done + PUT 只改标题且未传 boardColumn → 仍为 done，不落到 backlog，完成快照不变；
29. done + PUT 提交完整对象但锁定字段值都与旧值相同 → 允许保存；只有实际值变化才 409；缺省字段必须从旧任务合并，不能被 `TaskSaveRequest` 默认值覆盖；
30. done 但仍有未完成任务 → riskLevel=unknown、statusIssue=done_with_open_tasks，不显示绿色；done 但无任务 → unknown、statusIssue=done_without_tasks；done 且全部任务完成 → green；
31. 拒绝 done 重开/移出时，计时状态、完成快照、循环派生均未发生变化（409 必须在副作用之前）；
32. 把 exec 设为项目负责人 → 400；把仍是项目负责人的 member 改为 exec → 409，转交后可改；
33. 历史数据中 exec 同时是项目负责人 → 仍按 exec 只读，meta 编辑返回 403，项目负责人检查项不通过，提示 owner 转交；
34. 把 exec 设为任务负责人 → 400；历史任务负责人是 exec → 任务仍只读、不计入覆盖率，提示 owner 转交；
35. 任务负责人账号已离开空间 → 显示“历史负责人（已离开）”，不计入任务负责人覆盖率，数据质量下降；
36. 角色变更只允许 member ↔ exec；member/exec → owner、owner → exec 均返回 400。

## 9. 非功能需求

### 9.1 安全

- 管理读接口 owner/exec，管理写接口 owner；
- `exec` 写接口由服务端强制 403；
- 管理接口不返回 webhook/token/附件内容；
- 管理报表导出不含任务描述全文；现有全量任务备份收紧为 owner-only，并视为敏感数据；
- CSV 公式注入防护；
- 健康覆盖原因、审计敏感明细仅 owner/exec；
- 角色变更、覆盖、批量补全、导出留痕；
- 公开甘特分享链接不能替代管理驾驶舱：整空间 token、30 天有效、无法按项目/人撤销、无访问审计，只适合演示；
- nginx 80 端口如进入正式使用，至少应在内网/专线访问；HTTPS 和 SSO 放到后续企业级阶段。

### 9.2 隐私

- 不做个人绩效排名；
- 管理页个人负载仅 owner/exec；
- 现有甘特负载对成员可见是既有现状，P1 再统一；
- 周报不含个人排名；
- 管理报表导出只给 owner/exec；现有全量任务备份只给 owner；
- 审计原因不进入所有成员可见的活动流。

### 9.3 性能

- 首屏骨架屏 < 300ms 出现；
- 2,000 任务/50 项目 p95 < 500ms；
- 20,000 任务/200 项目 p95 < 1.5s；
- 查询次数固定 ≤ 6；
- 不对 `task` 做全表扫描；
- 负载任务上限沿用 20,000，区间最大 26 周；
- 管理页默认不做 SSE 实时刷新，手动刷新即可；
- 管理接口不阻塞任务写接口。

### 9.4 可用性

- 管理页失败不影响看板/任务；
- 空数据、缺字段、无权限、数据起始日都有明确文案；
- 已完成任务有“不可重开”的明确提示和“新建续做任务”入口；
- 颜色不是唯一信息载体；
- 移动端可用，不要求大屏适配；
- 趋势/工时卡片底部有口径说明。

### 9.5 兼容与回滚

- `/api/board`、`/api/reqs` 的字段契约不变；`/api/tasks` 字段契约不变，但 **MGT-019 会改变 done 任务离开完成的响应（409）**，属于行为变更，发布说明必须单列；
- `GET /api/export` 已是 owner-only；本版将 `GET /api/export/csv` 收紧为 owner-only，属于行为变更；回滚旧版本会恢复 CSV 对成员开放；
- 不改任务表字段语义（新增 `blocked_at` 除外）；
- 新字段中 `priority` 非空，其余可空；旧数据可渐进补齐；
- 修改静态资源后提升 `sw.js` 的 `CACHE_NAME`；
- 同步更新 `docs/api.md`、`docs/ui-redesign-spec.md`、README；
- 回滚旧 jar 前必须把 `exec` 改回 `member`，否则旧版本会恢复写权限；
- **回滚旧版本会恢复“任务可重开”的旧行为**，回滚说明必须明确告知；如不希望恢复，需保留新版本或加 feature flag；
- 回滚 SQL 只删除新增列/索引，不修改现有数据；先备份。

## 12. 风险与评审知会

### 12.1 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 项目负责人/日期不完整 | 大量项目 unknown，领导觉得“没用” | 上线前批量补全；数据质量单独展示；不伪造绿色 |
| 进度口径不统一 | 管理层与项目经理数字对不上 | 文档固化公式；管理页标注“管理口径”；项目页标注“执行口径”；P1 统一 |
| 完成/工时历史不完整 | 趋势开头为 0、清理后数字回退 | 回填 + 数据起始日；任务完成锁定；P1 工时归档 |
| 完成锁定改变现有习惯 | 员工想重开时受阻 | UI 引导新建续做任务；发布说明；客服口径 |
| 负载容量不准 | 误判过载/空闲 | 读取账号配置；实际值标注“计入工时”；估时覆盖提示 |
| 只读角色实现不彻底 | 领导误操作或绕过前端 | 管理读鉴权 + 接口分类 + 白名单 + 逐接口 403 测试 |
| 回滚旧版本 | exec 恢复写权限 | 回滚前改回 member；feature flag；演练 |
| 管理页变成“监控工具” | 团队抵触、数据失真 | 不做工时排行榜；以项目交付为主；明确使用边界 |
| 审计泄露 | 健康原因、角色变更被所有成员看到 | 通用活动事件 + 敏感原因只在管理接口；P1 独立审计表 |
| 个人负载隐私不一致 | 现有甘特负载已对成员可见 | 文档声明现状；P1 收紧或脱敏 |
| 跨空间范围不清 | 越权或看不全 | MVP 单共享空间；P1 只聚合共享空间、按最高角色 |
| CSV 注入 | Excel 打开执行公式 | 前缀转义 + 正确引用 |
| 数据质量降级风险 | 红色被灰色掩盖 | 本版已拆分，风险与数据质量独立 |

### 12.2 已确认的默认决策

以下按 v0.2 建议确认执行：

1. **健康度与数据质量冲突**：风险优先，数据质量单独展示，不降级；
2. **人工覆盖有效期**：默认 30 天，到期自动恢复，done 时自动清除；
3. **完成后续做**：任务完成后不可重开；新建续做任务默认带原项目/关联需求/原标题，描述引用原任务，不强制父子关系；
4. **负责人权限**：项目负责人和任务负责人必须是共享空间 owner/member（不能是 exec）；项目负责人可编辑自己项目的日期/优先级；健康覆盖仍仅 owner；
5. **个人负载可见性**：管理页仅 owner/exec；现有甘特负载的成员可见性是既有现状，P1 再收紧或脱敏；
6. **周期选择器范围**：KPI/风险/列表固定当前状态，负载跟随周期；
7. **跨空间**：只聚合共享空间，个人空间排除；
8. **周报渠道**：先复用 webhook/serverchan/pushplus；邮件/企业微信作为后续新增集成，不在 MVP 承诺；
9. **导出元数据**：首行保持列头，元数据放响应头/文件名；需要随文件携带时另附说明文件（P1）；
10. **管理入口**：仅共享空间 owner/exec，个人空间不提供；
11. **风险持续天数**：只给项目逾期、任务逾期、任务阻塞、项目停滞、需求未拆解等有时间锚点的风险；偏差/覆盖率/估时超支只显示当前值；
12. **完成状态一致性**：done 但仍有未完成任务时 `riskLevel = unknown` + `statusIssue = done_with_open_tasks`；done 但无任务时 `statusIssue = done_without_tasks`；两者都不显示绿色，纳入总览“状态异常”；已确认 MVP 不硬阻断状态修改，P1 再评估是否阻断；
13. **导出权限**：`GET /api/export` 已是 owner-only；本版将 `GET /api/export/csv` 收紧为 owner-only；exec 只能使用管理报表导出；
14. **MGT-020 纳入 P0**：任务负责人/截止日期批量维护进入 MVP，保证数据质量目标可落地。

### 12.3 需要评审知会的限制

- 2026-10-21 前的完成数据没有快照，回填只能覆盖当前仍为 done 的任务；历史趋势可能不完整；
- `time_log` 随任务彻底删除而删除，管理页的 12 周工时趋势只覆盖仍存在的任务；
- 现有甘特负载对成员可见，与管理页“个人负载仅 owner/exec”不是同一个边界；
- `GET /api/export` 已是 owner-only；本版将 `GET /api/export/csv` 收紧为 owner-only，回滚会恢复 CSV 对成员开放；
- 项目状态权限若从“成员可改”收敛到 owner/项目负责人，需要改服务端；否则按现状保留；
- 回滚旧版本会恢复“任务可重开”、exec 写权限和 `GET /api/export/csv` 对成员开放，回滚前必须改回 member 并知会用户；
- MGT-020 已纳入 P0，工作量 3 人日；如果不做，任务负责人覆盖率目标需要降低或接受逐个编辑；
- 本版明细 33 人日，建议按 36 人日排期（含约 10% 缓冲）。

## 14. 附录：与现有实现的对齐说明

以下事实已在当前代码中核实：

- 甘特图已支持依赖、基线、关键路径（前端计算）、按人 × 周负载；管理页应复用数据和交互，不要重做；
- 任务已有 `isMilestone`、`blocked/blockedReason`、`estimateMinutes`、`progress`；没有 `blocked_at`；
- 项目已有任务数/完成数/平均进度，但平均进度是执行口径，不作为管理口径；
- 当前代码允许任务重开/移出 done，并会在离开 done 时删除完成快照；本版要求改为完成锁定，所有离开 done 的路径返回 409；2026-10-21 前存量未回填，回填只覆盖当前仍为 done 的任务；
- `time_log` 没有项目 ID 快照，任务彻底删除会删除工时；管理页需明示；
- 现有 `/api/share/gantt` 是整空间、30 天、公开 token 的只读分享，适合演示，不适合作为领导正式入口；
- 当前部署为 nginx 80 端口，若管理驾驶舱进入正式使用，至少应在内网/专线内访问，HTTPS 与 SSO 放到后续企业级阶段；
- 现有 `/api/gantt/load` 对所有空间成员开放，管理页个人负载的隐私边界需单独声明；
- `SecurityConfig` 当前拒绝响应是 HTTP 200 + code 403，新管理接口应统一为 HTTP 403；
- 现有分析页趋势、周回顾、完成记录页的完成口径不完全一致，管理页必须标注数据源；
- 现有 `PUT /api/reqs/{id}` 允许任何成员修改项目状态；若本版要收敛状态权限，必须改服务端，否则矩阵与现状不一致；
- 现有 `TaskCommandService` 的任务负责人校验只看“是否空间成员”，不区分 owner/member/exec；本版需增加“不能是 exec”的角色校验；
- 现有 `GET /api/export` 已经是 owner-only；`GET /api/export/csv` 对空间成员开放，本版收紧为 owner-only，属于行为变更，发布说明需单列。
