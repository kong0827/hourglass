# 沙漏 · 内部接口契约

> 本文说明当前前端使用的会话认证接口，不是对外 Token / SDK 的承诺。开放 API Token、SSO 与 Git / CI 联动目前尚未提供；系统安全审计已有最小实现。产品主张是让投入可解释、让交付可追溯，不替代部署、财务结算或客户验收。

基准地址：`http://<服务器地址>:8080`（部署后走 nginx 时换成对外地址）

## 统一返回约定

- 成功：`{"code": 0, "message": "ok", "data": ...}`
- 业务错误：HTTP 200，`code` 非 0（400 参数问题 / 404 不存在 / 409 冲突 / 500 内部错误），`message` 为中文提示
- 校验失败：`code=400`，`message` 为具体字段提示（如「请填写任务标题」）
- 链路追踪：所有响应带 `X-Trace-Id` 响应头。每个请求生成 traceId 写入日志 MDC（日志格式 `%X{traceId}`）并回写该响应头，接口报错时用它反查后端日志；允许上游透传同名请求头（限 8–64 位 `[A-Za-z0-9_-]`，不合法则服务端重新生成）。AI / GitLab 外部调用日志只记模型、目标主机、耗时与 token，不落 Key 与完整地址

## 认证

除 `/api/health` 外所有接口需要登录态（会话 Cookie，有效期 30 天）：

- `POST /api/auth/login`（表单参数 `username`、`password`）→ 成功 `{"code":0,"message":"ok"}`，失败 HTTP 200 + `{"code":401,"message":"用户名或密码错误"}`
- `POST /api/auth/logout` → 退出登录
- `POST /api/auth/password`（body `{"oldPassword":"...","newPassword":"..."}`）→ 修改自己的密码（校验旧密码）
- 会话说明：登录状态 30 天有效；**管理员重置密码后，该用户已登录的会话保持有效直到过期**（无会话注册表，不会踢线）
- 未登录访问接口返回 HTTP 401 + `{"code":401,...}`；页面访问未登录跳转 `/login.html`
- 写操作（POST/PUT/DELETE）需携带 CSRF 头 `X-XSRF-TOKEN`（值取自 Cookie `XSRF-TOKEN`，前端已封装自动处理；Apifox 调试时先 GET 一次任意接口拿到 Cookie）

## 多用户与空间

- 账号由管理员创建下发（不开放注册）；共享空间可生成邀请链接，把**已有账号**拉入空间协作；管理员只管账号
- **空间模型**：每个账号自动有一个「我的看板」个人空间；任何人可新建共享空间并当空间主，成员**只能通过邀请链接加入**（对方打开链接并确认后才成为成员）；`POST /api/workspaces/{id}/members` 按登录名直接加人**仅平台管理员可用**，普通空间主调用返回 403，避免不经同意就把人拉进空间。共享空间支持**多位空间主**，权限完全等权；任何时刻至少保留一位空间主
- 所有业务接口都接受 `workspace` 查询参数（空间ID）；不传时用"上次使用的空间"，再退回个人空间。前端切换空间后自动携带
- **数据按空间隔离**：任务/子任务/项目/附件/工时/操作日志/标签/看板列属于空间；分类属于项目；保存的筛选视图属于"人+空间"
- **权限**：除查看者外的成员可做日常操作（增改删任务、拖拽、子任务、标签、计时、附件、回收站恢复）；**仅空间主**可做：改空间名 / 推送配置、删空间、删看板列、清空任务数据、导入覆盖；多位空间主等权。**空间主或管理员**可移成员、调整成员角色（空间主可调整任一角色并授予/撤销空间主；管理员只能处理成员 / 查看者，不能授予管理员或空间主；至少保留一位空间主）、生成 / 撤销邀请；**分类维护**：新建、改名、排序与换上级要求项目写权限；删除分类允许空间主、管理员或项目负责人；**项目集增删改**仅空间主或管理员；**分支创建 / 编辑 / 改状态 / 删除**按所属项目写权限判定，空间级公共分支由空间内非查看者维护。按登录名直接加人仅平台管理员可用。跨空间访问一律 404，权限不足返回 403
- **审计**：操作时间线记录操作人（`actorName`），历史数据显示为空
- 账号接口：
  - `GET /api/auth/me` → `{id, username, displayName, role, lastWorkspaceId, workStartHour, workEndHour, workMaxHours}`
  - `PUT /api/auth/work-hours`，body `{"startHour":9,"endHour":18,"maxHours":8}` → 修改自己的计时设置（`0 ≤ startHour ≤ 23`、`1 ≤ endHour ≤ 24`、`endHour > startHour`、`1 ≤ maxHours ≤ 24`）；只影响之后的计时折算，已记录工时不重算
  - `PUT /api/auth/profile`，body `{"displayName":"..."}` → 修改自己的显示名（负责人默认值与成员列表随之更新；**其参与空间中「负责人=旧显示名」的任务同步改为新名**，含回收站任务；操作时间线保留历史记录）
  - 管理员专属（`/api/admin/users`，见下方原章节）：新增/改显示名与角色/重置密码/删除（需先清空其个人空间数据、不是任何共享空间的唯一空间主、不能删自己、至少留一名管理员）
- 空间接口：
  - `GET /api/workspaces` → 我参与的空间（含 `type` personal/shared、`myRole`、`memberCount`）
  - `POST /api/workspaces`，body `{"name":"项目组看板"}` → 新建共享空间（创建者为空间主）
  - `POST /api/workspaces/{id}/select` → 记住"上次使用的空间"
  - `PUT /api/workspaces/{id}`，body 可按需提交 `{"name":"..."}` 或推送字段（仅空间主；个人空间名称不可改）。PATCH 语义：`name` 不传=保持原值；`notifyChannel`/`notifyEnabled` 不传=保持原值；`notifyWebhook` 不传=保持原值、传空串=清除；`notifyToken` 留空=保持原值，`clearToken:true` 才清除已保存 Token
  - `DELETE /api/workspaces/{id}`（仅空间主；存在发布证据时禁止破坏性删除，无证据时连带清理数据且不可恢复；个人空间不可删）
  - `GET /api/workspaces/{id}/members` → 成员（含显示名/登录名/空间权限角色/公司 `companyName`/默认岗位 `jobTitle`）
  - `POST /api/workspaces/{id}/members`，body `{"username":"xiaoming"}`（仅空间主）
  - `DELETE /api/workspaces/{id}/members/{userId}` → 空间主移除成员；成员自己调用即退出。多空间主等权：有其他空间主时可退出或被移除，最后一位空间主必须先移交或删除空间
  - `PUT /api/workspaces/{id}/members/{userId}/role`，body `{"role":"owner|admin|member|viewer"}` → 调整角色（仅空间主可授予/撤销空间主，管理员只能处理成员 / 查看者；降级最后一位空间主返回 400）。角色变化不改项目授权模式、不删已有授权：按项目分配的成员升为管理员再改回成员时，沿用此前分配，缺失的「不可见」种子行会自动补齐，不会因往返而扩大可见范围
  - `PUT /api/workspaces/{id}/members/{userId}/company`，body `{"companyName":"蓝海银行"}` → 标注成员公司（空间主 / 管理员可改任意成员；非查看者可改自己；最多 64 字，空串表示清除）。公司是空间级展示标签，只影响成员列表、花名册、负责人分组与评论展示，不改变任何权限。个人空间不展示公司与岗位，本人修改会被拒绝
  - `PUT /api/workspaces/{id}/members/{userId}/job-title`，body `{"jobTitle":"全栈工程师"}` → 空间默认岗位（空间主 / 管理员可改任意成员；非查看者可改自己；最多 32 字，空串清除）。项目无主角色覆盖时继承，不改变权限；活动流与空间审计在同一事务内留痕，个人空间本人修改会被拒绝
  - `GET /api/workspaces/{id}/member-label-options` → `{roleTitles,companyNames}`（内置、空间配置及已使用标签去重；项目角色标签只取当前账号可见项目，避免泄露不可见项目）；`PUT` 同路径、同结构整体保存自定义候选（空间主 / 管理员，每类最多 100 项；32 / 64 字）；不改已有标签
  - 邀请链接（共享空间协作入口，见 §29）：`POST/GET /api/workspaces/{id}/invites`、`DELETE /api/workspaces/{id}/invites/{inviteId}`（均限空间主 / 管理员）
  - 项目级授权（共享空间，限空间主 / 管理员）：
    - `GET /api/workspaces/{id}/project-access` → `{myRole, members, projects, grants}`，成员 × 项目的全量矩阵与现有显式授权
    - `PUT /api/workspaces/{id}/project-access`，body `{"userId":"u1","projectId":"p1","access":"write|read|none|"}` → 单格保存；`access` 为空表示恢复该成员的默认口径（存量成员回到可参与，按项目分配的成员回到不可见）。存量成员（`all` 模式）保存 `write` 时不落冗余行，等同恢复默认；审计与通知按「生效权限」比较，未真正变化不写记录
    - `PUT /api/workspaces/{id}/members/{userId}/project-access`，body `{"grants":[{"projectId":"p1","access":"write"},{"projectId":"p2","access":"read"}]}` → 一次性提交该成员全部项目权限，整批在同一事务内保存（任一格失败全部回滚）；按生效权限比较，仅当有实际变化时写一条审计与一条通知，无变化则两者都不写
  - 项目花名册与角色标注（共享空间，仅展示，不参与鉴权）：
    - `GET /api/workspaces/{id}/projects/{projectId}/members` → `{members:[{userId,displayName,username,companyName,jobTitle,roleTitle,effectiveRoleTitle,roleSource,secondaryRoleTitles,access,source,canEditRole}], canEditRole}`；空间查看者、不可见成员不返回；`roleTitle` 是项目主角色覆盖，空时继承 `jobTitle`，`roleSource` 为 project/workspace/unset；`access` 为生效权限（write/read），`source` 为可见来源。调用者须能看到该项目
    - `PUT /api/workspaces/{id}/projects/{projectId}/member-roles/{userId}`，body `{"roleTitle":"后端开发","secondaryRoleTitles":["测试"]}` → 主角色最多 32 字，空串恢复继承；兼岗最多 5 个、每个 32 字，省略兼岗字段保留原值、`[]` 清除。仅空间主 / 管理员或项目负责人可写；目标须非查看者且能看到该项目；不改变权限
    - `PUT /api/workspaces/{id}/projects/{projectId}/member-roles`，body `{"userIds":["u1","u2"],"roleTitle":"全栈工程师"}` → `{updated}`；最多 200 名，任一目标无效整批回滚；省略兼岗保留原值
    - `POST /api/workspaces/{id}/projects/{projectId}/member-roles/copy`，body `{"sourceProjectId":"p2","overwrite":false}` → `{copied,skipped}`；来源须同空间且调用者可见，目标可维护；只复制两边均可见的非查看者，以来源有效主角色快照保存，默认跳过已有显式主角色或兼岗；不复制权限
    - 工作项新指派或更换项目时，负责人账号须为非查看者且能看到目标项目（只读参与者仍可指派）；负责人及项目都未变时保留历史绑定，避免无关编辑清掉账号。前端候选与此花名册同源，加载失败关闭候选；跨项目批量分配只显示共同可指派成员
- 分类接口（原「模块」，`category` 是项目级目录树，可分层；工作项、需求池条目与测试用例共用一套节点）：
  - `GET /api/categories` → 空间内全部项目的目录节点 `[{id,projectId,parentId,name,color,sortOrder}]`，`parentId` 空串＝顶级；`?project={项目ID}` 只返回该项目的清单
  - `POST /api/categories?project={项目ID}`，body `{"name":"客户跟进","parentId":"","color":"#7a5c86"}`；层级不限（仅禁止成环），同级重名返回 409
  - `PUT /api/categories/{id}`（改名 / 换父节点：`parentId` 省略保留原值，空串移到顶级；改名只改字典，任务/需求关联存目录 ID 不回刷，展示名经字典实时解析，用例的 `module` 展示快照同步改名；目录只能属于建它的项目）
  - `DELETE /api/categories/{id}?targetId={目录ID}`（仍有子目录或被子目录 / 动态分组规则引用时拒绝；其下工作项、需求与用例迁到指定目录，targetId 缺省取项目内其他节点）
  - 分类维护权限：`POST` / `PUT` / `PUT order` 要求所属项目写权限（项目可参与成员即可）；`DELETE` 仅空间主、空间管理员或该项目负责人（`requirement.owner_user_id`）；查看者与只读成员 403（只读可查）
  - `PUT /api/categories/order?project={项目ID}&parentId={父ID}`，body `{"ids":[...]}`（ids 必须恰好是该父级下的全部节点；旧调用不传 `parentId` 时保持整项目排序口径）
- 项目集接口（空间级可选归组，只读汇总，不参与鉴权；`sql/106`）：
  - `GET /api/project-sets` → `[{id,workspaceId,name,description,ownerUserId,ownerName,status,plannedStart,plannedEnd,archivedAt,color,sortOrder,projectCount,taskCount,doneCount,progressPct,createdAt,updatedAt}]`；汇总只统计当前查看者可见的项目；无可见项目的集只对空间主 / 管理员返回
  - `POST /api/project-sets`，body `{"name":"流程引擎","description":"","ownerUserId":"u1","status":"active","plannedStart":null,"plannedEnd":null,"color":"#8a8578"}`；名称必填且同空间唯一，负责人须为空间成员；仅空间主 / 管理员
  - `PUT /api/project-sets/{id}`，同上字段并带 `updatedAt` 做并发校验；冲突返回 409；仅空间主 / 管理员
  - `DELETE /api/project-sets/{id}` → 只把项目 `set_id` 置空（回到未分组），不删除项目、工作项、需求与历史；仅空间主 / 管理员
  - `PUT /api/project-sets/order`，body `{"ids":["PS2","PS1",...]}`（ids 必须恰好是空间内全部项目集；数量或成员对不上返回 409 让前端刷新）；只改 `sort_order`，不动 `updated_at`；仅空间主 / 管理员
  - `PUT /api/reqs/{id}/set?setId={项目集ID}` → 换项目集；`setId` 为空串表示移出项目集（未分组）。只改归组，不改项目权限、工作项与版本；要求对该项目有写权限，项目集须属于当前空间
  - 项目归属：项目保存接口的 `setId` 为项目集 ID，省略保留原值、空串解除归组；服务端校验项目集属于当前空间。项目列表与进度接口返回 `setId` / `setName` / `containerKind`（`containerKind` 非空表示拆分产生的公共容器）
  - 项目集不改变项目可见性、项目角色或发布权限；项目之间仍按原规则隔离
- 优先级显示配置（每空间固定 P0/P1/P2/P3 四档，只改显示名与颜色，不改变存储、筛选、排序和导出 code）：
  - `GET /api/priorities` → 固定顺序返回四档 `[{workspaceId,code,name,color,...}]`；未配置的档位返回内置默认「紧急/高/中/低」，不写库
  - `PUT /api/priorities/{code}`，body `{"name":"高","color":"#F79009"}` → 修改单档显示配置；查看者 403
  - `DELETE /api/priorities` → 清除当前空间的自定义配置，四档全部恢复内置默认；查看者 403
- 任务/需求挂分类：`categoryId` 必须属于所属项目的分类。任务保存时 `null`（未提供）自动落到项目第一个分类，`""` 表示明确「未指定」不再回落；不属于该项目时校验失败。未挂项目的任务分类恒为「未指定」（存空串）。需求的 `null` 为「未指定」。新建项目时后端自动预置默认分类「其他」

## 管理视图成员标签筛选

`GET /api/manager/workload` 支持可选 `reqId`、`roleTitle`、`companyName`；`GET /api/manager/reports` 在此基础上另支持 `versionId`。负载另支持可选 `from`、`to`（`yyyy-MM-dd`，任一缺失即退回自然周口径；起终点反了自动交换，超过 92 天从终点往前截断）：传入后响应带 `rangeFrom`/`rangeTo`/`rangeWorkdays`，每个成员补 `rangeMinutes`（该区间内的实际计时），供「本周 / 上周 / 近 30 天 / 本月」切换；`weekMinutes`/`dayMinutes`/`lastWeekMinutes` 等周口径字段不受影响。按任务所属项目的有效主角色 / 兼岗、负责人公司和计划交付版本筛选；计时按关联任务范围裁剪，任务、计时、下钻与导出同源。响应带 `filterOptions:{roleTitles,companyNames,versions}`（当前可见项目范围内、尚未按标签筛掉的候选，workload 不下压 `versionId`）和 `scope:{reqId,roleTitle,companyName,versionId}`。`__unset__` 表示未设置；真实同名标签及以 `__label__:` 开头的标签在筛选值前加一层 `__label__:`，前端显示时仅解码一层。无关联任务的计时只在无筛选时保留。历史纯文本负责人只有姓名唯一时才解析账号，歧义不归到任一同名成员。成员另带测试身份字段 `testWaiting`/`testDoing`/`testWeekMinutes`/`testTaskRefs`：按工作项「测试负责人」统计待测试 / 测试中项数、本周该成员在自测工作项上的计时，以及这些在手测试项的 `{reqId,column}` 引用。测试剩余 `testRemainingMinutes` = 这些在手测试项的 `max(0, 测试预估 − 测试窗口内已计工时)` 之和（见 §14 的 `test_estimate_minutes`）；成员的 `remainingMinutes` 仍是开发剩余（名册顶部「合计剩余」用它，避免开发与测试重复累加同一项工时），`loadRemainingMinutes` = 开发剩余 + 测试剩余，负载百分比与容量窗口按 `loadRemainingMinutes` 计算（容量窗口的最晚截止日也包含在手测试项）。名册不按「是否有在手工作项」收口：空间内除系统管理员账号（`app_user.role=admin`）外，所有成员都占一行，没有在途项时剩余与负载为 0；按角色 / 公司筛选时只列命中的成员。每个成员另带 `capacityMinutesPerDay`，容量 = 容量窗口工作日数 × 本人计时设置的「每天最多计入小时数」（未设置按 480 分钟）；容量窗口从今天数到该成员未完成工作项的最晚截止日、只数工作日，无截止日按 5 天、最少 1 天，上限取响应顶层的 `maxWorkdays`（默认 22，配置项 `app.workload.max-workdays`），因此同一页不同成员的每日容量与窗口可以不同；项目详情与逾期风险里的成员负载用同一口径，成员 `projects[]` 另带 `testTaskCount`/`testRemainingMinutes` 且 `remainingMinutes` 已并入测试剩余。

## 通用查询参数（看板 / 已完成列表）

| 参数 | 说明 |
|---|---|
| q | 关键词，匹配标题/描述/进度备注（不区分大小写） |
| owners / pris / cats / reqs / tags | 逗号分隔多选；pris 取值 P0,P1,P2,P3；cats 取分类 ID（`categoryId`）；reqs 支持特殊值 `__none`（未归类）；tags 为标签名 |

## 4. POST /api/tasks

新增任务。`id` 选填（撤销删除/导入时指定），不填服务端生成。Task 使用 `versionIds` 数组：省略 / null 保留现有集合（新建默认空集合），`[]` 显式解绑，非空数组显式设置同项目版本集合，不根据需求目标隐式改绑。实际改关联须原因与权限，详见末尾闭环契约；Demand / TestPlan 仍是单目标 `versionId`。

```json
{"title":"重构权限校验中间件","description":"","priority":"P1","categoryId":"Gxxx",
 "boardColumn":"doing","dueDate":"2026-10-20","reqId":"Rxxx","progress":40,"note":"已确权方案"}
```

`dueDate` 格式 `yyyy-MM-dd`；`progress` 0-100；返回保存后的任务对象。新建与更新响应重新读取实际落库的 `versionIds` / `versionNames` 数组和 `tags`，以最终项目 / 负责人重算可写权限；`publishedAt/publishedReleaseId/publishSource/everPublished/publicationState/publicationTargets` 只读，优先由成功 production 记录推导，publishSource=record，无人工 canPublish / canUnpublish 操作入口；历史迁移补录走独立的 `publication-judgement` 接口，并额外返回只读投影 `manualPublished/manualPublishedAt/manualJudgeName/manualJudgeReason`。撤销删除恢复时可在 body 中带 `completedAt`（分钟级 `yyyy-MM-ddTHH:mm`；纯日期 `yyyy-MM-dd` 仍接受，按当天 00:00 落库）保留原完成时间、带 `subtasks: [{title, done}]` 一并重建检查清单。ID 只接受字母/数字/下划线/中划线（≤32 位），不合法会当作未提供重新生成；指定 ID 已被占用的返回 409；覆盖导入会保留附件/日志等子记录，指定这类"仍有历史子记录"的 ID 同样返回 409，防止旧记录误挂到新任务。

## 5. PUT /api/tasks/{id}

更新任务字段（与新增同结构，title 必填）；`versionIds` 数组省略 / null 保留、`[]` 解除，实际改变关联须 `versionChangeReason` 与管理者或该任务负责人可写权限，且不得改成功事实冻结的关联。列变更自动处理完成日期，并**同时写入一条 `action=move` 移动日志**；其他字段变更写 `action=update`。发布不锁任务完成 / 回退 / 计时，不要求先撤徽标；正式徽标只读，人工标记走独立接口，详见末尾闭环契约。

## 6. POST /api/tasks/{id}/move

拖拽移动。

```json
{"column":"done","beforeId":"Kxxx"}
```

`beforeId` 为空字符串/不传 = 移到列尾；同列内也用它调整顺序。`autoTimer=false` 时移入非待处理/非完成列不自动计时；`autoResume=false` 时移到已完成不自动接力下一条。返回：

```json
{"code":0,"data":{"task":{...},"from":"doing","to":"done","autoTimerStarted":false,"autoTimerTask":null}}
```

同列内移动（只调顺序）不会把停留时长切成碎段。内置列为 `backlog/doing/test/testing/done`（待处理 / 进行中 / 待测试 / 测试中 / 已完成）；进入 `test` 写提测时间，进入 `testing` 自动写开始时间（新一轮重置并清空结束时间），离开 `testing` 写结束时间，测试通过和退回都算这一轮结束。`testing` 退回 `backlog/doing` 默认需填 `reason`，缺少返回 412；三个测试时间均由服务端维护，客户端只读。

缺陷工作项（`itemType=bug`）的 `regressionStatus`（`pending` 待回归 / `passed` 通过 / `failed` 不通过）由服务端随列流转维护，`POST/PUT /api/tasks`、`move`、`bulk-move`、`reopen` 同一口径：进入 `test/testing` 记 `pending`（开发已提交修复）；进入 `done` 记 `passed`；从 `test/testing/done` 退回 `backlog/doing` 记 `failed`；列内移动保持原值。`POST/PUT` 显式传入与旧值相同的回归状态视为未修改，仍按流转推导；显式改为 `passed` 但目标列不是 `done`、或进入 `done` 时回归状态不是 `passed`，返回 400。缺陷关闭口径 = 完成列且回归通过。

### 6.1 POST /api/tasks/bulk-move

列表页批量改列，body `{"ids":["K1","K2"],"column":"done","autoTimer":false,"autoResume":false}`。逐项走 move 语义（移动日志、完成归档、循环派生一致）；批量默认不自动开始/接力计时。最多 500 项，任一项失败整批回滚。

### 6.2 POST /api/tasks/{id}/reopen

取消完成：按最近一次移入 done 的 `from_column` 回到**完成前所在列**；该列已删除时依次回退到 `doing`、第一个非完成列、`backlog`。不自动开始计时。返回结构同 move。

### 6.3 GET /api/tasks/canceled

已取消列表（默认视图不显示已取消，只从这个入口进）。可选 `reason`（`not_do` 不做 / `dup` 重复 / `deferred` 延期 / `design` 设计如此，其他值视为不限）与 `offset` / `limit` 分页（`limit` 缺省 100，服务端夹到 1..100）。返回：

```json
{"code":0,"data":{"items":[{...任务}],"total":7,"matched":3,"hasMore":false,
  "reasons":[{"name":"not_do","count":3},{"name":"dup","count":2}]}}
```

`total` 为全部已取消条数（不受原因筛选影响），`matched` 为当前原因筛选后的条数；`reasons` 为原因计数（`name` = 原因码），直接下发给筛选 chip，前端不再按当前页统计。

### 6.4 POST /api/tasks/{id}/cancel

取消工作项，进入终态「已取消」（`board_column=canceled`，不占看板列、不参与排序、不走流转矩阵）。body `{"reason":"not_do","note":"客户砍了该模块"}`：`reason` 四选一必填，`note` 说明必填（≤250 字）。已完成（`done`）的工作项不能直接取消，须先取消完成；已是已取消状态的返回 400。取消后不计逾期、退出完成率分母、退出需求完成分母，进度保留原值；从可计时列取消与移列同一口径（停表 + 接力同列下一条）。写 `action=cancel` 审计（from/to + 终态字段快照）并通知关注者。返回结构同 move（`to` 恒为 `canceled`）。

### 6.5 POST /api/tasks/{id}/uncancel

恢复已取消的工作项。body `{"note":"客户又要求做了"}`，说明必填（≤250 字）。回到 `cancel_from` 记录的取消前所在列；该列已删除（或为 `done`/`canceled`）时回第一个开列。清空 `cancel_reason/cancel_from/canceled_at` 三列并重新取列内排序号，取消期间他人改过的其他字段保留；恢复后照常计入逾期与完成率分母，需求完成判定重新刷新。只有已取消的工作项可以恢复，否则 400。写 `action=restore` 审计。返回结构同 move。

## 14. GET /api/export

导出当前空间的**任务备份**（v14）。结构与旧版前端 `hourglass-backup.json` **兼容（超集）**：包含 tasks/reqs/columns；v4 起额外包含任务评论（comments）、任务 `deletedAt`（回收站）与任务的 `reqDocId`/`branchId`/`estimateMinutes`/`blocked`/`blockedReason`/`ownerUserId`/`remindTarget` 字段；v5 起额外包含任务 `isMilestone`、甘特依赖（`deps`）、基线（`baseline` + `baselineAt`）；v6 起额外包含 `reqDocs`（需求文档，含正文）与 `branches`（分支池，不含分支操作时间线）；v12 起额外包含模块字典 `categories`（含所属项目，任务 `cat` 与需求池 `categoryId` 存模块 ID）；v13 起额外包含任务终态「已取消」三字段 `cancelReason`/`cancelFrom`/`canceledAt`；v14 期间新增任务可选字段 `testEstimateMinutes`（测试预估，分钟；旧备份缺省为空，导入按空处理）。旧版页面仍可直接导入读取；导入旧备份（无模块字典）时，任务/需求的模块值回落所属项目的默认模块。

导入 JSON 任务备份，按下述覆盖语义处理；**已有发布证据时禁止破坏性覆盖，建议导入新空间**。JSON 任务备份不是正式发布凭证，不从旧 released 状态、首版统计折算或任务完成状态构造发布记录 / 徽标；正式证据须从数据库备份恢复：

```json
{"v":14,"tasks":[{"id":"Kxxx","title":"...","desc":"...","pri":"P1","owner":"我","cat":"Gxxx",
  "col":"doing","due":"2026-10-20","progress":40,"note":"","reqId":"Rxxx","reqDocId":"Dxxx",
  "branchId":"Bxxx","estimateMinutes":240,"testEstimateMinutes":null,"blocked":false,"isMilestone":false,"completedAt":null,
  "cancelReason":null,"cancelFrom":null,"canceledAt":null}],
 "reqs":[{"id":"Rxxx","name":"...","desc":"","status":"active","createdAt":"2026-10-01"}],
 "categories":[{"id":"Gxxx","projectId":"Rxxx","name":"后端","color":"#3b82f6","sortOrder":1}],
 "comments":[{"taskId":"Kxxx","authorId":"Uxxx","authorName":"我","content":"...","createdAt":"2026-10-02T10:00:00"}],
 "deps":[{"from":"K1","to":"K2","type":"FS","lag":0}],
 "baseline":[{"taskId":"K1","start":"2026-10-01","due":"2026-10-08"}],
 "baselineAt":"2026-10-28T18:00:00",
 "reqDocs":[{"id":"Dxxx","reqId":"Rxxx","title":"...","content":"<p>...</p>","status":"draft","owner":"我"}],
 "branches":[{"id":"Bxxx","reqId":null,"name":"feature/login","status":"dev","owner":"我","targetBranch":"main"}]}
```

返回 `{"tasks": 42, "reqs": 5, "comments": 18, "reqDocs": 3, "branches": 2, "versions": 2, "demands": 4, "testCases": 12, "docComments": 6}`。

**覆盖语义（重要）**：导入清空并重建"任务类数据"——任务、回收站（保留原删除时间）、项目、子任务、标签、工时、**任务评论**、**甘特依赖与基线**与**完成归档**（完成归档按导入后的任务与工时重建，历史快照里的旧项目名/负责人名以备份数据为准）；v6 备份还会覆盖 **需求文档与分支**（含正文/状态/负责人，分支操作时间线清空）；**v10 备份还会覆盖测试用例、执行流水与文档评论**；**v12 备份还会按 ID 补齐模块字典**（不清空现有模块：备份模块的 ID 落库时已存在则映射复用，不存在则插入；模块映射缺失或不属于该任务/需求的项目时，模块值回落该项目默认模块）；旧备份没有对应字段时保留现状，不误删现有数据。**保留**附件文件与记录、操作时间线、保存视图、看板列、模块与优先级显示设置。跨空间复制导入时任务/项目/需求文档/分支 ID 冲突会自动重新生成并同步迁移引用（依赖端点按任务 ID 映射回指，自环/重复/成环边会被跳过）；看板列按备份补齐（跳过保留列 id=done 与超过 16 位的 id）、任务列按"列 id → 列名"两级映射落位。工时的计时人随备份恢复（`timeLogs[].userId`）；计时人不在目标空间（跨空间导入）时，该条工时归导入者。仅空间主可执行。导入会清除当前空间的只读分享令牌（旧链接立即失效），需要重新生成。

**旧备份兼容**：v3 及更早备份没有 comments 字段，v4 及更早没有依赖/基线字段，v5 及更早没有需求文档/分支字段，v10 之前没有测试用例/执行流水/文档评论，v12 之前没有模块字典（任务/需求的模块值回落所属项目默认模块），v13 起任务新增终态三字段 `cancelReason`（取消原因码 not_do/dup/deferred/design）/ `cancelFrom`（取消前所在列）/ `canceledAt`（取消时间），旧备份没有该组字段时按空值处理；对应字段缺失时保留空间现有数据，不执行清空；新增任务字段缺失时按空值处理。

**需求池备份（`BackupData.BackupDemand` / `demands[]`）**：`plannedStart`、`plannedEnd` 为可空的 `yyyy-MM-dd` 字符串，与 `expectDate` 独立；导出保留实际计划日期，旧备份缺字段 / null / 空白按空值处理，不从任务或版本日期推导，允许只填一端。主状态导出为 `review/pass/plan/done/closed`，关闭条目同时保留 `closeReason`（`rej/cancel/dup`）与 `closeStage`（`review/pass/plan/done`）；旧备份的 `rej/canceled` 导入时归一为 `closed`，旧 `rej` 自动保留评审不通过与关闭前待评审，旧 `canceled` 缺少关闭前阶段时按备份中的目标 / 计划字段兜底。原始无目标的 `plan` 保留 `plan` 状态与计划起止，`done` 也按备份原样保留、不重新判定；显式非空目标 `versionId` 按版本 ID 重映射后必须仍属于需求项目，映射失效返回 400 并回滚，不静默改状态或清空引用。所有非空计划日期的格式及 `plannedStart ≤ plannedEnd` 在任何覆盖删除前校验；非法日期或倒置区间返回 400，原空间数据不被删除。导入不自动重排关联任务，也不生成派生交付证据。

字段兜底：旧列 id（todo/review）自动映射、非法枚举取默认值、超长字段截断、无效项目/需求/分支引用置空、无效模块引用置空或回落项目默认模块；`subtasks`/`tags`/`recurType`/`remindAt`/`remindSent`/`timeLogs`（含计时人 userId）/`createdAt`/`columns` 导入时自动恢复，旧版备份（无这些字段）依旧兼容。

**导出不含**：附件文件本身（磁盘文件，随服务器备份目录 tar 保留，见 `deploy/backup.sh`）、操作时间线日志（导入时不会被删除）、完成归档快照（导入时按任务与工时重建）、分支操作时间线。需求文档历史快照与需求流转日志不在备份里，但覆盖导入时**保留现有记录**；同空间导入通常复用文档/需求 ID，跨空间导入可能留下无法对应的历史记录。测试计划不在备份里，导入时保留；同空间导入会复用测试用例原 ID，跨空间用例重新生成 ID 时计划圈选可能悬空。

## 19. POST /api/notify/test

立即对当前空间执行一次提醒推送（手动测试用，**仅空间主**）。需先在「空间设置」中配置该空间的推送 webhook。

```json
{"code":0,"data":{"sent":true,"content":"【开发工坊】任务提醒 2026-10-14\n逾期 2 项：..."}}
```

无逾期与今日到期任务时返回 `{"sent":false,"reason":"当前无逾期或今日到期任务，静默跳过"}`；手动测试（force）模式下即使为空也会发送一条测试消息。渠道由 `NOTIFY_TYPE` 决定：`webhook`（企微/钉钉，报文 `msgtype:text`）/ `serverchan`（Server酱，URL 里带 key，报文 `title/desp`）/ `pushplus`（报文 `token/title/content`，token 配 `NOTIFY_TOKEN`）。**pushplus 渠道下统一 token 只发送到官方固定端点（`https://www.pushplus.plus/send`），空间设置里的地址仅作为"启用推送"开关**；其余渠道的空间地址保存与发送时都会校验（仅 http/https，拒绝本机/内网地址），服务端不跟随重定向。推送结果以渠道**明确返回的成功码**为准（`errcode=0` / `code=0` / pushplus `code=200`）；HTML 错误页、空响应、跳转等无法确认成功的响应按失败处理，任务级提醒会保留在原 6 小时窗口内重试。超过 6 小时重试窗口仍未发出的提醒会被标记为已处理并在任务时间线记「提醒时间已过（超过 6 小时重试窗口），未推送」；未配置 webhook 的空间同样参与过期处理（记「提醒时间已过，空间未配置推送渠道，未推送」），不会永久静默挂起。

## 22. 看板列配置

## 26. 工时计时

- `GET /api/tasks/{id}/timer` → `{"running":false,"startedAt":null,"elapsedMinutes":0,"totalMinutes":45,"myTotalMinutes":30}`（`running/elapsedMinutes` 为"当前登录人"在该任务的计时状态；`totalMinutes` 为该任务全部成员的累计）
- `POST /api/tasks/{id}/timer/start` / `POST /api/tasks/{id}/timer/stop`（开始/停止仅作用于"我自己"；任务整体结算见下）
- `GET /api/tasks/{id}/timer/records` → 该任务的工时记录（已结束的计时 + 手工补记，按时间倒序最多 50 条）：`[{id,userId,userName,origin,minutes,date,startedAt,endedAt,note,mine}]`，`origin` 为 `timer`/`manual`；`startedAt/endedAt` 为计时原始起止时间，补记则使用所选日期的占位时间；仅 `timer` 的 `minutes` 按工作日、个人工作时段与每日剩余额度裁剪，`manual` 不套用这些裁剪规则
- `POST /api/tasks/{id}/timer/manual?forUserId=&date=yyyy-MM-dd&minutes=&note=` → 手工补记一条实际工时（忘开表、加班等）。项目可写者可补**任何人**（`forUserId` 空则补自己，非空须为空间成员）；补记不经过工作时段/8 小时上限的计时裁剪，只做范围校验（1 分钟 ~ 24 小时、日期不晚于今天），`started_at=ended_at=所选日期 12:00`，落库 `origin=manual`；日期落在当天仍占用该用户的计时日额度
- `DELETE /api/tasks/{id}/timer/records/{logId}` → **作废**一条已结束的工时记录（计时记录与手工补记都可作废；运行中的计时须先停止）。权限与补记一致：项目可写者。记录物理删除，任务时间线留下"作废计时记录 / 删除补记工时"的审计文字
- 作废后所有统计直接读 `time_log` 自动按实际工时重算；任务若已有完成快照，服务端同步重算 `total_minutes / first_started_at / last_ended_at`（历史快照用 `sql/46_refresh_completion_minutes.sql` 一次性对齐）
- 计时按**人**归属（`time_log.user_id` = 计时人）：开始新计时只自动停止"我自己"其他任务上已可见的运行中计时，不影响他人；单次计时按「每个工作日的工作时段 + 每人每天上限（默认 8 小时）」折算，忘停表时不会把夜间与周末计入，也不会超过当天剩余额度；任务完成（移入已完成）或删除时自动停止并结算**该任务上全部成员**的计时；统计报表的工时只统计"我"在当前空间的记录
- 备份往返：`BackupTimeLog` 含 `origin`/`note`；旧备份缺 `origin` 的按 `timer` 回填

## 29. 邀请链接（共享空间协作）

账号仍由管理员创建下发（**不提供自助注册**）；邀请链接用于把**已有账号**的同事拉进共享空间：对方打开 `/join.html?code=XXXXXXXXXX` 后，已登录则一键加入；未登录先登录（登录后自动回到该页完成加入）。个人空间不可邀请。

- 生成：`POST /api/workspaces/{id}/invites`（空间主 / 管理员）→ `{id, expiresAt, grantCount}`；邀请码为 10 位大写字母数字（去掉易混淆字符），有效期 **7 天**。body 可选 `{"grants":[{"projectId":"p1","access":"write"}]}` 预分配新成员的项目权限；`access` 只接受 `write` / `read`，重复与 `none` 会被忽略，未列出的项目加入后不可见
- 列表：`GET /api/workspaces/{id}/invites`（空间主 / 管理员）→ `PageResult<{id, workspaceId, createdBy, expiresAt, usedCount, createdAt, writeGrantCount, readGrantCount}>`；后两项为该邀请预分配的「可参与 / 只读」项目数
- 撤销：`DELETE /api/workspaces/{id}/invites/{inviteId}`（空间主 / 管理员）；与加入共用邀请行锁，撤销与加入并发时二者只有一个成功，已撤销的邀请加入返回 404。删除空间时邀请与预分配一并清理，删除项目时清理指向该项目的预分配
- 查看（公开）：`GET /api/invite/{code}` → `{workspaceName, inviterName, expiresAt, writeGrantCount, readGrantCount, alreadyMember}`；带登录态访问且已是该空间成员时，额外返回 `workspaceId` 供直接进入（未登录或非成员不返回空间 ID）。无效/已撤销 404，过期 400
- 加入（需登录）：`POST /api/invite/{code}/join` → `{workspaceId, workspaceName, already, grantCount}`；`already=true` 表示原本就是成员（幂等，不再计数，也不会覆盖其现有项目权限）；首次加入时在同一事务内写入成员身份与邀请预分配，项目已删除的预分配自动跳过。并发加入按「邀请行锁 → 用户行锁」顺序串行化，同一用户重复提交只计一次
- `usedCount` 在每次成功加入时 +1；邀请码大小写不敏感（统一转大写查询）；多用途链接对每位新加入者应用同一组预分配
- 安全：仅 `GET /api/invite/{code}` 为公开接口（放行见 SecurityConfig），`/join` 需登录；建议在 nginx 对邀请路径同样启用限速（与登录接口共用注释块）

## 30. GET /api/flow-health?days=90

流程体检：从 `task_log` 的跨列移动记录反推流程健康度。`days` 取 1-730，默认 90。只读，不改任何业务数据。

```json
{"code":0,"data":{
  "rangeDays":90,"since":"2026-07-24","generatedAt":"2026-10-22 16:58",
```

**口径**（改这里之前先看 `FlowHealthService` 的类注释）：

- **列停留**：任务进入某列到离开该列的时间。`avgSeconds`/`medianSeconds`/`p90Seconds` **只统计已经离开该列的段**（`segments`），当前仍停在该列的单独给 `ongoingCount`/`ongoingMaxSeconds`，不混进历史均值。
- **`share` 的分母只含已结束的停留**，但包含「已被删除的列」那段时间；「已完成」列是终点，不计入停留（`segments` 恒为 0）。
- **回退** = 目标列在 `board_column.sort_order` 里比来源列更靠前。`totalMoves` 只含跨列移动（列内排序不算）。
- **一次通过率** = 时间窗内完成的任务里，窗内没发生过回退的比例（窗口口径，不是任务全生命周期）。
- **需求开工延迟** = `requirement_doc.created_at` → 首个关联任务 `created_at` 的平均小时数。
- **时长单位全部是秒**，由前端格式化。

**数据来源与兼容**：`task_log.from_column`/`to_column` 是 `09_task_flow.sql` 新增的结构化字段，`POST /api/tasks/{id}/move` 写入；历史数据在该脚本里按 `detail` 文本「从「X」移动到「Y」」回填，列改名过的会回填不上（`from/to` 留 NULL，计入 `coverage.moveEvents` 但不算 `usableMoves`）。Service 侧另有基于 `detail` 的兜底解析。

## 31. AI 辅助需求（团队共享额度 / 个人额度）

三件事：**配自己的 AI**、**把需求拆成任务草稿**、**检查需求做完了没**；另有测试用例与周报草稿。
AI 来源分两层：平台管理员可配置团队 AI（`ai_shared_setting` 的 `platform / 0` 行），成员默认使用团队额度；成员也可以在账号级保留自己的 Key，显式选择后走个人额度。空间级共享（`workspace / <workspaceId>`）为 P1 预留，当前没有写入入口。

### 31.1 配置

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/ai/config?workspace=` | 我的配置与解析后的来源（**key 只回掩码**） |
| PUT | `/api/ai/config?workspace=` | 保存个人配置与来源偏好（`apiKey` 空=不改，`clearKey=true`=删除） |
| POST | `/api/ai/config/test?workspace=` | 对**解析后的来源**发一次极小请求，验证 key/地址/模型 |

`workspace` 可省略；带上时参与空间级共享 AI 的解析（P1 预留），省略只解析平台团队 AI 与个人配置。

```json
{"code":0,"data":{
  "provider":"deepseek","baseUrl":"https://api.deepseek.com/v1","model":"deepseek-chat",
  "hasKey":true,"apiKeyMasked":"sk-****a1b2","enabled":true,"keyBroken":false,
  "prefer":"auto","source":"team","sourceName":"团队 AI","allowPersonal":true,
  "team":{"available":true,"scope":"platform","provider":"deepseek","model":"deepseek-chat",
          "status":"由平台管理员提供，费用由团队承担"},
  "status":"已就绪：调用走团队额度",
  "presets":[{"id":"deepseek","name":"DeepSeek","baseUrl":"...","model":"deepseek-chat","keyHint":"..."}]
}}
```

- `prefer`：`auto`（默认，团队优先）或 `personal`（显式使用个人 Key）；PUT 时空 / `auto` 清除偏好。
- `source`：`team` / `workspace` / `personal` / `none`，是**本次解析结果**；`sourceName` 为可直接展示的名称。
- `team.available=false` 表示当前没有可用的共享配置（未启用、缺 Key、配置不完整或 Key 无法解密）；`status` 说明原因与联系人，不会把不可用的团队配置显示成「已就绪」，也不会因此改写 `source` 为个人。
- `allowPersonal=false` 时个人 Key 不参与解析，即使已保存；管理员重新打开后原 Key 仍可用。
- 解析顺序：可用空间共享 → 可用平台团队 AI → 个人配置；显式 `prefer=personal` 且允许个人时优先个人。**共享配置已启用但不可用（缺 Key / Key 解不开）时直接报错并提示联系平台管理员，不静默回落到个人 Key。**
- `POST /api/ai/config/test` 忽略个人总开关（未启用也能先测通），但遵循来源偏好：选了个人就测个人，避免测的和用的不是同一套。响应额外带 `source` / `sourceLabel`。
- `GET /api/ai/assistant/bootstrap` 额外返回 `aiSource` / `aiSourceName`，供悬浮助手说明当前使用哪一层额度；`AiUsage` 额外带 `sourceLabel`（`团队额度` / `我的额度`）。

**安全口径**（不要改）：

- Key 用 AES-GCM 加密后入库（`v1:` 前缀 + Base64(IV‖密文)），密钥来自 `app.ai.crypto-key`（部署用环境变量 `AI_CRYPTO_KEY` 覆盖）。个人与团队 Key 共用同一套加密。
- 接口**永不回传明文**，只有 `apiKeyMasked`（`sk-****a1b2`，短 key 全遮）。
- 换过部署密钥 → `keyBroken=true`、`hasKey=false`，提示重新填写。**这是设计行为，不是故障**。
- 所有 AI 调用只从 `CurrentUser.id()` 取配置；**没有跨账号兜底**：团队配置不可用时直接报错，不会借用他人的个人 Key。

**内置厂商**（全部 OpenAI 兼容，`baseUrl` 可改，可走中转/代理）：
DeepSeek、通义千问、月之暗面 Kimi、智谱 GLM、腾讯混元、OpenAI、本地 Ollama、自定义。
加新厂商只需改 `AiProviders`。

**错误口径**（AI 相关接口一致）：

| 情况 | HTTP | `message` 要点 |
| --- | --- | --- |
| 配置不完整、自定义地址不合法 | 400 | 指出缺哪一项或地址问题 |
| 上游返回 4xx/5xx | 502 | 按状态码翻译；上游原文附在括号里 |
| 账户额度用尽（`insufficient_quota`、欠费、余额不足） | 502 | 明确「额度不足」，提示充值或关闭「仅使用免费额度」 |
| Key 无效或权限不足（401/403，且非额度问题） | 502 | 提示到「个人设置 → AI 设置」检查 Key |
| 上游超时 / 首轮过慢放弃重试 | 504 | 提示检查网络或换更快的模型 |
| 同时超过 2 个上游请求 | 429 | 「AI 正忙」 |

上游错误只记一条 WARN（含厂商状态码、模型名、上游 message），不写 Key；不再走通用异常分支记 ERROR 或返回「服务内部错误」。

### 31.2 拆分与体检

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/ai/reqdoc/{id}/split?maxTasks=8` | 拆成任务**草稿**（不落库） |
| POST | `/api/ai/reqdoc/{id}/audit` | 完成度体检 |
| POST | `/api/ai/reqdoc/{id}/tasks` | 把勾选的草稿创建成任务 |
| POST | `/api/ai/reqdoc/{id}/selection` | 选区处理：`{action: rewrite/shorten/expand/explain, selection, before, after, instruction?, section?, format?}`，只回建议不写正文 |
| POST | `/api/ai/reqdoc/{id}/selection/tasks` | 把选中一段文字提为工作项草稿（不落库；勾选确认后走创建接口） |

`split` 返回 `{reqDocId, reqDocTitle, docChars, tasks:[{title,description,priority,dependsOnIndex,reason}], usage}`。
`usage` 为 `{model, promptTokens, completionTokens, totalTokens, jsonMode, jsonFallback}`：`jsonMode` 表示本次是否以 JSON 模式请求成功；`jsonFallback=true` 表示请求了 JSON 模式但模型不支持、已去掉 `response_format` 降级重试（纯文本接口如周报本就不走 JSON 模式，此时两者均为 false）。所有 AI 接口的 `usage` 同此结构。
喂给模型的是**已保存的正文**（转纯文本，保留段落/列表/表格行），超过 12000 字会截断并在 prompt 里注明；
同项目已有任务标题作为 few-shot 参考命名风格。

`audit` 返回 `{coverage, verdict, summary, nextStep, totalPoints, donePoints, doingPoints, todoPoints, missingPoints, points:[{point,covered,status,taskTitle,note}], tasks, usage}`。

**分工是刻意的**：AI 只负责"把需求拆成可验证的功能点"和"给每个点找覆盖它的任务"；
`coverage` 与 `verdict` **由服务端按规则算**，不让模型打分：

```
coverage = round((done×1 + doing×0.6 + todo×0.3 + missing×0) / total × 100)
verdict  = coverage>=95 且 missing==0 → done
         | coverage>=70 → mostly
         | coverage>=30 → partial
         | 否则 → not_started
```

理由：模型直接给的分"看起来合理但没法解释"，也无法保证"有缺失就不会说做完了"。

`tasks` 请求体：`{"tasks":[{title,description,priority,dependsOnIndex,draftIndex}]}`，`draftIndex` 为该草稿在 `split` 结果中的下标（缺省按提交顺序）。
逐条创建到文档所属项目的 `backlog` 列并关联本文档，单条失败不影响其它条，返回 `{created, skipped, linked, failed:[{title,reason}]}`；
与**本项目**已有任务同名会跳过（避免重复建；文档未归属项目时按可见范围去重）。
`dependsOnIndex` 指向的前置草稿也被选中并创建成功时，自动建一条 FS 依赖（`linked` 计数）；依赖按甘特同一套规则校验（两端可写、不成环、未超上限），连线失败不影响已创建的任务。

**注意**：这些接口是长请求（模型生成通常 20-60 秒），nginx 的 `proxy_read_timeout` 必须大于 120 秒，否则前端拿到 504。

### 31.3 测试用例生成

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/ai/testcases/generate` | 从需求文档或需求池条目生成用例**草稿**（不落库） |
| POST | `/api/ai/testcases/apply` | 把勾选的用例草稿创建成正式用例 |

### 31.4 周报润色

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/ai/review/polish?workspace=` | 把某一周的回顾数据写成一份可直接发出去的周报（只读，不落库） |

请求体：`{weekOffset: 0, note: "周三线上排查了支付超时"}`

- `weekOffset`：`0` 本周、`-1` 上周……不传按 `0`；服务端夹到 `[-52, 0]`。
- `note`（选填，≤200 字）：任务里体现不出来的事（线上排查、口头对齐、临时支持）。留空也行。

返回：

```json
{"code":0,"data":{
  "weekOffset":0,"label":"本周","weekStart":"2026-10-19","weekEnd":"2026-10-25",
  "report":"## 本周完成\n- 重构权限校验中间件，四个入口统一走鉴权\n…",
  "source":{"completed":3,"progress":2,"pendingDone":0,"truncated":false,"chars":1240,"withNote":true},
  "usage":{"model":"deepseek-chat","promptTokens":1580,"completionTokens":320,"totalTokens":1900,"jsonMode":false}
}}
```

**口径（与 31.2 同一条原则）**：数字不交给模型。完成数、按期率、延期、工时、逾期、P0 未关闭全部由
`ReviewService` 先算好、拼成"事实清单"塞进提示词，并明确要求模型只能引用、不得加总；
`source` 里的计数也是服务端给的，用来在界面上说明"这份周报基于多少条事实"。

- `report` 是**纯 Markdown 文本**（不带 ``` 围栏，服务端会剥掉围栏与"好的，以下是…"这类开场）：
  终点是粘进 IM/邮件，给 HTML 只会满屏标签。固定四节：本周完成 / 进行中 / 风险与阻塞 / 下周计划。
- 这一周**没有任何记录**时直接 400（"这一周没有任何工作记录，没有素材可写"），不调模型 —— 省额度也更诚实。
- 任务太多时只喂前 30 条完成 + 15 条进行中，并在 `source.truncated=true` 里说明。
- 同样是长请求（10-30 秒），前端按钮置灰 + 骨架屏；`ChangeBroadcastFilter` 不会广播（没有写操作）。

### 31.5 产品内助手

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/ai/assistant/bootstrap?workspace=` | 启动信息：模型状态、空间角色、可写项目与建议问题 |
| POST | `/api/ai/assistant/chat?workspace=` | 问答、入口建议、固定模板查询，或生成待确认草稿 |
| POST | `/api/ai/assistant/tasks/confirm?workspace=` | 确认执行草稿（建工作项 / 从需求拆分 / 提需求 / 需求流转 / 工作项移列） |

`chat` 请求体：`{messages:[{role:"user|assistant",content:"..."}], context:{view:"board",projectId:"P1",taskId?,demandId?}, draft?}`。

`chat` 返回 `intent`：`answer` / `query` / `create_task` / `create_demand` / `demand_action` / `move_task` / `clarify` / `navigate`。草稿类返回 `draft` 与 `requestId`，缺项放在 `missing`（候选只来自服务端可见集合）。

`confirm` 请求体：`{requestId, reqId?, title?, severity?, priority?, itemKind?, source?, expectDate?, demandId?, demandAction?, note?, versionId?, plannedStart?, plannedEnd?, taskId?, targetColumn?}`；返回 `{kind:"task|demand", taskId?, demandId?, title, href, statusName, message}`。

- 空间由服务端解析并校验成员身份；项目按当前用户可见范围重新过滤，前端传入的 `projectId` 不在可见集合时直接丢弃，不报「存在但无权」。
- 模型只拿可见项目的 id / 名称与内置 FAQ 摘录；需求与工作项由服务端在可见范围内按标题解析，标题与候选只下发前端、不进提示词。返回链接必须命中服务端白名单（站内 `#/` 与 `help.html#/`），草稿 `reqId` 必须命中「可见且可写」集合。
- 草稿只缓存在服务端内存 30 分钟，`requestId` 只对创建它的用户与空间有效（他人凭据 404）；确认时按目标最新状态与当前权限复核，再走 `TaskCommandService.create` / `DemandService` / `TaskWorkflowService.move`，留痕与页面点击一致，另记 `ai_assistant_exec` 系统审计（成功与拒绝都记）。
- 需求流转权限与页面同口径：通过 / 拒绝 / 撤回评审 / 重新打开需要项目写权限；排期 / 调期 / 撤排 / 关闭 / 恢复需要空间主、管理员或项目负责人。拒绝、调期、撤排、关闭、恢复必须填原因。工作项移列永不强制（`force=false`），越过流转规则直接返回服务端错误。
- 从需求拆分（`create_task` 且 `draft.fromDemand=true`）：只认可见、所在项目可写且未关闭、未完成的需求；项目固定为需求所在项目（确认时传入其他 `reqId` 返回 400），模块与计划日期按需求补齐，已排期需求的版本由任务服务自动继承。
- 固定模板查询（`intent=query`）：服务端按关键词确定性路由，不调用模型、不消耗额度；需是疑问句，或以「我 / 我的 / 我手上的」开头、以工作项 / 任务 / 待办 / 缺陷结尾的名词短语（如「我逾期的工作项」），带写动作、团队范围或操作咨询的一律不走模板。`queryType` 为 `overdue` / `today` / `soon`（今天起 3 天内）/ `blocked` / `open`，只查当前空间里本人负责的未完成工作项（账号绑定优先，历史数据按显示名兜底），逐项复核项目可见性；返回 `tasks[]`（`id,title,projectName,columnName,dueDate,blocked,href`，最多 20 条）、`total`、`hasMore`。`answer` 只含数量，不含标题。
- 无可写项目短路：当前空间里没有任何可写项目时，同时出现工作对象（工作项 / 任务 / 需求 / 缺陷）和写动词（新建、提、拆分、移到、通过、驳回、调期等）的请求直接返回 `intent=answer` 与「没有可写的项目」说明，不调用模型、不解析目标需求或工作项，未配置模型的查看者也不会被引去配置 AI。
- 每个用户 10 分钟最多 20 次对话；常见问题命中内置 FAQ 时不调用模型。模型或 FAQ 不可用时，前端退化为帮助中心入口。

### ⚠️ 为什么不用 `start_date` 算工期

**开始日期是"什么时候接到的"，不是"什么时候动手"。** 一个任务可能今天创建、下周才真正开工，
`[开始, 完成]` 之间的跨度里大部分是排队等待 —— 拿它算效率只会得出"我干活很慢"的错误结论。

唯一的可比基准是两个数：

| | 来源 | 说明 |
| --- | --- | --- |
| **预估** | `task.estimate_minutes` | 人自己填的，单位分钟（表单用小时，0.5 步进） |
| **实际** | `time_log.minutes` 累计 | 自动计时按工作日、个人时段及每日剩余额度折算；手工补记不按这些规则裁剪，需核对来源与记录 |

`start_date` / `due_date` 仍然只用于日历排布与逾期判断，**不参与任何效率计算**。

### 口径

- **系数 = Σ实际 / Σ预估**（不是"平均每个任务的比值"）。后者会让"预估 0.5h 实际 2h"（4 倍）的小任务
  和"预估 40h 实际 60h"（1.5 倍）的大任务等权重，结论会被小事带偏。
- **只统计已完成任务**：进行中的实际值还不完整，算进去会显得"总是高估"。
- **偏差分档**：实际/预估 `< 0.85` 高估 / `0.85~1.15` 准确 / `> 1.15` 低估。
- **预警只看进行中**（非 `backlog`、非 `done`）且 `实际/预估 ≥ 0.8`：`≥ 1.0` 记 `danger`（已超），否则 `warn`（接近）。
  `backlog` 里的任务还没开工（实际 0），预警没有意义。
- `estimate_minutes` 为 `null` 或 `0` 一律视为"没估"，不参与任何统计；保存时也统一存 `NULL`。

### 34.4 GET /api/manager/investment

「报表 → 投入结构」的聚合接口，按周期统计人力、工时与资源分布，只读、不新增表或录入项。

| 参数 | 说明 |
| --- | --- |
| `from` / `to` | 必填，`yyyy-MM-dd` 闭区间；前端季度取自然季度，年度取当年 1-1 至 12-31 |
| `reqId` / `roleTitle` / `companyName` | 可选筛选；`__unset__` 表示未设公司 / 未设角色；筛选只缩小统计范围，不改变归集口径 |

归集口径：

- **实际**：取已结束且分钟数 > 0 的计时，按 `time_log.started_at` 的发生日期归期；跨期的整段计时落在发生那一天。
- **测试窗口内 / 外**：计时日期落在工作项「提测 → 测试结束」窗口（含首尾两天，只取最近一轮）内的分钟计入 `testMinutes`（窗口内），其余计入 `devMinutes`（窗口外）；无测试窗口时全部计入窗口外。窗口外包含需求评审、设计、开发、运维等全部其余计时，不是「开发工时」。
- **预估**：工作项预估按计划开始日（无计划开始日取创建日）整条归期，不做按天摊分；跨期工作项只计入起始期。
- **人力**：本期有结束计时的计时人 + 本期有预估的负责人，按人去重；未指派负责人的预估计入工时，但不计入人力数。

返回 `{range, scope, totals, months, rows, filterOptions}`：

- `range`：`{from,to,days}`；`scope` 回显生效筛选。
- `totals`：`{key,name,users,projects,tasks,estimateMinutes,actualMinutes,devMinutes,testMinutes}`。
- `months[]`：覆盖区间内每个自然月，字段同 `totals`，无记录月份也返回 0 值槽。
- `rows`：`{project[],member[],company[],role[],position[]}`，字段同 `totals`；成员行额外带 `companyName`、`roleTitle`（主角色，兼岗可命中筛选；一人跨多公司 / 多角色时为「多个公司 / 多个角色」）；`key` 为 `u:<userId>` / `n:<负责人文本>` / `x:unassigned` 等分组键。
- `position` 行按空间成员岗位（`workspace_member.job_title`）归组，不受项目角色覆盖；未填岗位时回落项目主角色，都没有则归入「未设岗位」。同一个人只归一处。
- `filterOptions`：`{companyNames[],roleTitles[]}`，在筛选前采集，供下拉保留可选项。

## 已接受的现状口径（按设计如此，非缺陷）

以下行为是当前版本有意保留的设计边界，使用/验收时按此预期判断：

1. **会话与权限快照**：登录会话 30 天有效，角色写在会话里。管理员**重置密码/调整角色/删除账号不会踢掉旧会话**（无会话注册表）；但 `/api/admin/**` 每次请求按数据库当前角色复核，被降权或删除的管理员立即无法再调用管理接口；`/api/auth/me` 也读取数据库实时角色。普通接口的权限变化在下次登录（或会话过期）后完全生效。
2. **任务并发写为"最后写入生效"**：多人同时编辑同一任务不做版本校验/冲突提示，后提交的整体覆盖先提交的（实现范围约定，界面无冲突弹窗）。
3. **JSON 导入导出不做全量恢复**：导出包含需求文档正文、分支与其他工作数据，但不含附件二进制、操作时间线或完整正式发布证据；导入覆盖工作数据（任务/项目/评论/需求文档/分支等），保留附件文件/记录与时间线（保留的附件/日志按"空间+任务ID"关联，同空间原样导回会重新挂回原任务）。
4. **文件与数据库无两阶段一致性**：附件删除为"先删文件、后删记录"（或相反顺序的单边提交），极端故障下可能出现孤儿文件或失效引用；失败会写服务端告警日志，不做补偿任务。
5. **同账号计时串行化**：开始和停止计时在事务内锁定账号行，同一账号跨任务、跨设备的计时操作串行执行，避免重复运行记录和重复结算；不同账号之间互不影响。

`recurType`（daily/weekly/monthly/null）、`recurNextId`（循环任务派生的下一次任务ID：把已完成任务移回未完成再重新完成时复用该任务，不会重复生成；**彻底删除派生的下一次任务会清除该关联**，此后再次完成会重新生成；回收站中的派生任务视为仍存在）、`remindAt`（yyyy-MM-ddTHH:mm）、`tags`（字符串数组）、`totalMinutes`（累计工时）、`subtaskTotal/subtaskDone`、`deletedAt`（回收站中非空）。任务保存接口 `POST/PUT /api/tasks` 同步接受 `recurType`（空字符串=清除循环）、`remindAt`（null=清除）、`tags`（最多 8 个、每个 ≤16 字）。

2. **改名不再无差别改写"负责人文本"**（复评 R-2）：`owner_user_id = 该用户` 的任务无条件同步；`owner_user_id` 为空的历史任务，仅在"该空间内没有另一个同名在册成员"时才同步。同名串号的口子封住，且未回填数据也不会显示旧名。
3. **每日汇总也写应用内通知**（复评 R-3）：`dailyPush` 从"只遍历配了 webhook 的空间"改为遍历**全部启用**的空间；汇总按负责人分组落应用内通知（type=`task_due`）。因此**没配群机器人时汇总不再完全静默**。外部渠道行为不变（未配地址就不发外网）。
4. **提醒扫描按空间/按任务隔离异常**（复评 R-4）：任一空间或任一任务出错只跳过该条，不再中断整轮扫描（原实现一个 try 包住所有空间）。
5. **任务级联删除补齐评论与通知**（第九轮 #1/#2）：彻底删除任务（`DELETE /api/tasks/{id}/purge`、回收站每日自动清理）、清空空间、覆盖导入三处，都会一并删除 `task_comment` 与 `app_notification` 中该任务的记录。
   - 修正的后果：此前 `countChildRefs` 把评论计入，导致**已彻底删除的任务 ID 被永久锁死**（既不能新建同 ID，同 ID 还原还会把旧评论挂到新任务上）。
   - 导入口径：评论与通知**跟随任务删除**，与"操作时间线保留"有意区分 —— 时间线是审计记录，评论/通知会把内容直接展示给用户，留着就是可见的数据错乱。
6. **看板兜底列**（第九轮 #3）：空间的 `board_column` 为空（手工改库 / 异常恢复）时，未完成任务归入 `backlog`，而不是被静默丢弃（原实现响应里只剩「已完成」一列）。

8. **ID 生成**（第九轮 #6）：`Ids.gen` 的随机后缀由 `Math.random()` 4 位改为 `ThreadLocalRandom` 8 位（同毫秒组合数从 ~1.7×10⁶ 升到 ~2.8×10¹²），ID 仍 ≤32 字符。
9. **启动兜底的事务语义**（第九轮 #7）：`ensureDefaults` 改为通过自身代理调用 `ensureDefaultsFor`，实现**每个空间一个独立事务**（此前 `@Transactional` 因同类自调用而失效，等于每个 mapper 各自提交）。
10. **删除看板列的审计文案**（第九轮 #9）：活动流里写列名而不是列 ID（不再出现「其下任务已移入「C1a2b3c4」」）。
11. **删除零调用死代码**（第九轮 #8）：移除 `TimeLogMapper.sumSinceByWorkspaceUserFrom`（与 `sumSinceByWorkspaceUser` 完全重复且全项目零调用）。

`GET /api/review` 的 `progressTasks` 原来只判断 `progressOf(t) > 0`，而 `TaskCalc.progressOf` 对**已完成列的任务一律返回 100** —— 于是已完成的任务会同时出现在「本周完成」和「推进中」两个区块里，读起来就是同一件事写了两遍。

## 附录 · 2026-10-20 计时与周回顾（v1.4 增量）

### 1. 计时：拖列自动开关 + 有效工时口径

| 变化 | 说明 |
| --- | --- |
| **移入「进行中」自动开始计时** | `POST /api/tasks/{id}/move` 目标列不是 `backlog` 也不是 `done` 时，为**操作人**自动开始计时；若本人已有别的任务在计时，按原有"个人同一时刻只计一个任务"的规则先停掉它。响应新增 `autoTimerStarted: boolean`，前端据此提示「已开始计时」。 |
| **移入「已完成」自动结束** | 原有行为保留：关闭**该任务上所有人**的运行中计时。删除 / 移入回收站同样关闭。 |
| `TaskMoveRequest.autoTimer`（**新增**） | 可选布尔。不传 = 自动计时（拖拽、键盘移列、列表/日历的"移动到"）；传 `false` = 不自动（**取消完成**回退到进行中时用，避免"纠正状态"顺手开表）。 |
| **有效工时口径**（全新） | 停表时不再用"实际经过时间、上限 12 小时"，改为按 `WorkTime.effectiveMinutes()` 计算：① **跳过周六 / 周日**（整段落在周末记 0）；② **每人每天最多计入 8 小时**，并扣减当天已记录的工时（跨任务、跨空间都算）。运行中的 `elapsedMinutes` 也用同一口径。 |
| 时间线文案 | 停表日志改为「本次计入 N 分钟」，被裁剪时补一句「已按每天 8 小时 / 跳过周末裁剪，实际经过 M 分钟」。 |

**口径说明（容易踩的点）**：跨天计时按天切分、每天各自封顶 8 小时。例如周五 18:00 开表、周一 09:00 停表 → 周五记 6 小时 + 周末 0 + 周一封顶 8 小时 = 14 小时。这是"每天 8 小时"的字面实现；如果希望"跨天只算开始当天"，属于另一种口径，需要再确认。

> **v3.1 修订（2026-10-23）：按「工作时段」而不是自然日切段。**
> 原实现从每天 00:00 切，所以忘停表过夜时，凌晨一过就开始重新累计（用户实测报障）。
> 现在只计**工作时段**内的时长：默认 **09:00–18:00**，每个账号可在「个人设置 → 计时设置」自己调

### 2. 周回顾：`progressTasks` 改为按所在列

`GET /api/review` 的 `progressTasks`（前端「进行中」面板）口径改为：

### 5. 补丁（v1.5）：历史周期的「进行中」按周收敛

**问题**（用户实测反馈）：切到「上一周」时，「进行中」面板仍然列出**当前**进行中的任务 —— 包括这一周才创建 / 才拖进进行中的任务，等于把本周的工作算进了上周。

**原因**：`progressTasks` 是"当前状态"，与周期无关。

**修法**：`GET /api/review` 在 `weekOffset < 0`（历史周期）时，对 `progressTasks` 再做一次收敛：

> 只保留「**该周期内有日志活动**」（`task_log.created_at` 落在周期内）**且**「周期结束时任务已存在」（`created_at <= 周期结束日`）的任务。

- **本周（`weekOffset == 0`）不收敛** —— 「进行中」就该是"我现在在做的事"，不受"本周有没有动过"限制；
- 没有状态快照，用日志近似还原。因此「上周开工、这周一直没碰」的任务在本周视图里仍然出现（符合直觉），在更早的周期里则按"那一周动过"判断；
- 新增 `TaskLogMapper.selectActiveTaskIds(workspaceId, from, to)`（`DISTINCT task_id`，排除 `CFG` 哨兵事件）；
- `ReviewResponse` 结构不变。

**仍存在的局限**：进度数字仍是当前值；"上周拖进进行中、本周已完成"的任务只会出现在「本周完成」里，不会同时出现在上周的「进行中」。

### 6. 补丁（v1.6）：日历里提前完成的任务不再往后铺

**问题**（用户实测）：任务 5 号开始、25 号截止，12 号就做完了，但日历从 13 号到 25 号仍然每天显示它。

**原因**：日历区间是 `[start_date, due_date]`，没有考虑 `completed_at`。

**修法**：引入"**实际结束日**"概念：

> `实际结束日 = (已完成 && completed_at < due_date) ? completed_at : due_date`

| 位置 | 处理 |
| --- | --- |
| `GET /api/calendar` | 用实际结束日判断"与本月是否有交集"，提前完成的任务不再因为 `due_date` 在未来而被返回 |
| 前端 `calRangeOf(t)` | 日历格子铺开、右侧当日列表的区间判断都用同一个函数；已完成任务的 chip 带 `done` 样式（划线），悬停提示显示「已完成 10-12」而不是「进行中，截止 10-25」 |

`CalendarResponse` 结构不变。

#### 7.1 完成 / 暂停后自动接力计时

**问题**（用户实测）：正在计时的任务被拖进「已完成」或「待测试」后，表停了，但「进行中」列还有别的任务，却没有任何一个在计时 —— 得手动再去点一次。

**规则**：以下场景停表后，调 `TimeLogService.resumeInColumn(userId, workspaceId, 原列, 刚停表任务)`：

- `move` / `update` 把任务改到「已完成」
- `move` / `update` 把任务移到不可计时列（待测试 / 等待接续 / 执行结束）
- 用户手动点「停止计时」

| 条件 | 行为 |
| --- | --- |
| 我当前**还有**运行中的计时（比如别的空间的任务） | **不接力** —— 不能把别的任务抢掉 |
| 刚停表的任务不来自「进行中」列 | **不接力**（只允许进行中列接力） |
| 进行中列还有其他任务 | 按 `sort_order` 取**第一个负责人是当前账号、可写且未阻塞**的任务开始计时（复用 `start()`，含"个人同时只计一个"） |
| 进行中列没有属于当前账号的可接力任务 | 不接力，绝不把计时开到别人的任务上 |

`POST /api/tasks/{id}/move` 与 `POST /api/tasks/{id}/timer/stop` 响应新增 `autoTimerTask`（接力上的任务名，没有则为 `null`），前端在完成/停表提示后追加「· 已接着开始「X」的计时」。

**注意**：接力**只接当前账号自己的任务**，并且只在「进行中」列发生；不会把计时开到他人的任务上。这是对 spec G.5 的修正口径。

#### 7.2 每天 8 小时是「整天合计」，不是「每个任务各 8 小时」

**确认：已经是整天合计口径**，代码在 `WorkTime.effectiveMinutes()`：

```java
int used = usedMinutesOn.applyAsInt(day);          // 当天已记录的工时
int quota = Math.max(0, MAX_MINUTES_PER_DAY - used); // 480 - used
total += (int) Math.min(minutes, quota);
```

而 `usedMinutesOn` → `sumMinutesByUserOnDate` 的 SQL 是：

```sql
SELECT COALESCE(SUM(minutes), 0) FROM time_log
WHERE user_id = #{userId} AND ended_at IS NOT NULL AND DATE(started_at) = #{date}
```

**只有 `user_id` 和日期**，不限 `task_id`、不限 `workspace_id` —— 所以同一天多个任务共用 480 分钟额度，跨空间也算在一起。

实测（`WorkTime` 单测）：同一天三个任务各 200 分钟 → 记 200 + 200 + **80** = 480；额度满后再计 → 0；换一天重新有 8 小时。

## 附录 · 2026-10-26 分支管理（v3.2 增量）

### 1. 分支池：空间级公共分支 + 可选项目归属

分支池按空间维护，同时支持两种归属（`sql/31_branch_project.sql` 增量迁移）：

- `dev_branch.req_id` 为空 = **空间级公共分支**（历史数据默认落在这一档，行为与升级前一致）；
- `dev_branch.req_id` 非空 = **项目级分支**，直接归属 `requirement.id` 对应的项目。

不在分支上强制项目：主干、发布、跨项目的 feature 本来就会共用，强行切分会逼人重复建分支。
建任务时「所属分支」按当前项目过滤：直接归属该项目的分支 + 空间级公共分支（再按任务推导归属兜底），
避免不同项目的同名分支混在下拉里。表：`dev_branch` / `dev_branch_log`。

### 2. 状态与时间口径（两套，各管一件事）

状态：`dev`(开发中) → `testing`(待测试) → `merging`(待合并) → `released`(已发布)。
**允许任意方向切换**：现实里「待测试被打回开发中」很常见，强行单向只会逼人删分支重建、把历史丢掉。

| 记录位置 | 记什么 | 用途 |
| --- | --- | --- |
| `dev_branch.dev_at / test_at / merge_at / released_at` | **首次**进入该状态的时间（`COALESCE` 写入，回退不覆盖） | 算停留时长、发布周期（`released_at - created_at`） |
| `dev_branch_log` | **每一次**变更：动作、从哪到哪、谁、什么时候、附带说明 | 详情抽屉的操作记录；回答「谁把它退回了开发中」 |

新建时按初始状态盖上第一个时间点（默认 `dev` → `dev_at` = 创建时间），其余留空。
状态没变时不写日志（点错一次不该多一条噪音）。

### 3. 接口

| 接口 | 说明 |
| --- | --- |
| `GET /api/branches` | 分支列表。`?project=` 时返回「直接归属该项目 + 空间级公共分支」：公共分支按任务推导归属过滤，尚未关联任何任务的公共分支对所有项目可见；附带 `taskCount` / `doneCount`（排除回收站任务、只统计可见项目）与 `projects` 推导标签；排序 `FIELD(status)` + `updated_at DESC` |
| `GET /api/branches/{id}` | 详情（同一个实体） |
| `GET /api/branches/{id}/logs` | 状态变更时间线，倒序 |
| `GET /api/branches/{id}/tasks` | 挂在分支上的未删除任务（未完成在前） |
| `POST /api/branches` | 新建。body：`{name, status?, reqId?, targetBranch?, owner?, ownerUserId?, note?}`；`reqId` 空 = 空间级公共分支 |
| `PUT /api/branches/{id}` | 改基础信息（名字 / 所属项目 / 负责人 / 目标分支 / 备注）。**`status` 字段被忽略**；`reqId` 传空串表示退回空间级公共分支，不传（`null`）表示不改 |
| `POST /api/branches/{id}/status` | 改状态。body：`{status, note?}`。唯一会写时间点与时间线的入口 |
| `DELETE /api/branches/{id}` | 删除：先解绑任务（`task.branch_id = NULL`，任务保留），再删时间线与分支 |

校验口径：

- 分支名 `^[\p{L}\p{N}._/-]{1,80}$`（字母含中文、数字、点、下划线、中划线、斜杠；空格与 `@{}~^:?*[\` 本来 git 也不接受），同一归属维度内**唯一**（同项目不允许同名，不同项目允许；空间级公共分支之间不允许同名）；
- `reqId` 非空时必须是**本空间**的项目，否则 400「所属项目不存在」；
- `targetBranch` ≤80、`note` ≤200；
- 不填负责人 = 当前用户（与需求模块一致）。

> 为什么把「改状态」单独开一个接口：如果允许 `PUT` 顺手改 `status`，就会出现「改了状态但没走时间线/时间点」的
> 数据，统计和追溯立刻对不上。编辑弹窗里因此**不显示状态字段**。

### 4. 任务侧

`TaskSaveRequest` 新增 `branchId`（选填）；`task` 表加 `branch_id` + 索引（`sql/14`）。
保存时校验「分支存在且同空间」，否则 400「所选分支不存在」。连带处理：

- 删除分支 → 关联任务解绑（任务本身保留）；

- 清空空间数据（`WorkspaceService.wipeData`）→ 分支与时间线一起清掉。

### 5. 前端

- 侧栏新增「分支」（`data-view="branches"`，2026-11-08 起归入「交付」分组）；未读数不单独做角标，四档状态计数在页面顶部展示；

## 附录 · 2026-11-15 仓库只读同步（sql/98）

`project_repo` 保存项目与 GitLab 仓库的绑定，`dev_branch_alias` 保存人工别名。沙漏只读拉取分支与已合并 MR，不回写 GitLab、不触发流水线；同步结果写入 `dev_branch` 的远程事实字段（`remote_state` / `remote_head_sha` / `remote_head_at` / `merged` / `merged_into` / `merged_at` / `merge_evidence` / `last_seen_at`），不覆盖人工状态时间点。

### 1. 仓库绑定（/api/repos）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/repos?workspace=` | 空间内可见仓库，含 `tokenConfigured`（不返回令牌）、`lastSyncAt/Status/Error/Summary`、`openBranchCount`、`pendingBranchCount` |
| POST | `/api/repos` | 新建绑定；body `{reqId,name,repoUrl,projectRef,defaultTarget,importPolicy,syncEnabled,token}` |
| PUT | `/api/repos/{id}` | 修改绑定；`token` 留空表示不修改，`clearToken=true` 删除令牌；已有同步分支时不能改 `reqId` / `repoUrl` / `projectRef` |
| POST | `/api/repos/{id}/sync-now` | 立即同步一次；失败会把错误写回 `lastSyncError` 并返回错误，不影响其它仓库 |
| POST | `/api/repos/{id}/enabled` | query `enabled=true/false`，启停每 10 分钟的定时同步；暂停后仍可手动同步 |

- 写操作只允许空间主（`requireOwner`，管理员不含）；`sync-now` 同样只允许空间主。
- 已有同步分支时不能改 `reqId` / `repoUrl` / `projectRef`；当前没有删除绑定的接口，只能暂停定时同步。
- `projectRef` 为数字 ID 或 `group/project`；`importPolicy` 只接受 `recent90` / `all` / `manual`。
- 同一空间内 `repoUrl + projectRef` 唯一；`repoUrl` 默认拒绝内网与云元数据地址，自建内网 GitLab 需在部署层开启 `app.git.allow-private`（环境变量 `GIT_ALLOW_PRIVATE`）。
- 令牌用 AI 同一套 AES-GCM 加密保存，更换令牌不会在 GitLab 侧自动吊销旧令牌。

### 2. 分支生命周期与待确认

- `dev_branch.outcome`：`open` / `done` / `canceled` / `ignored` / `pending`，与开发状态 `status` 正交；`source` 区分 `manual` / `git`。
- `pendingReason`：远程分支消失（`disappeared`）、关闭后远程又有新提交（`closed_new_commit`）、分支名冲突（`name_conflict`）或需要人工确认。
- `GET /api/branches/pending` 按仓库分组返回待确认队列，筛选参数与分支列表一致。
- `POST /api/branches/{id}/outcome`，body `{decision:"done"|"canceled"|"ignored"|"",reason,note}`；`decision` 空串表示撤销人工判定并按远程事实重算。
- `POST /api/branches/outcomes/batch`，body `{ids,decision,reason,note}`；逐条校验项目写权限，单条失败不中断整批，返回逐条结果。

### 1. 任务分页（SQL 区间分页）

`GET /api/gantt`（登录）

参数：与 `/api/tasks/list` 相同的 `workspace/q/owners/pris/cats/reqs/tags/due/focus/blocked/noDue`，
另加：

| 参数 | 说明 |
|---|---|
| `from` / `to` | `yyyy-MM-dd`，按「与区间有交集」在 SQL 层过滤已排期任务；不传=全部排期任务 |
| `includeDone` | 默认 `true`；传 `false` 时 SQL 直接排除已完成列 |
| `offset` / `limit` | 稳定分页；`limit` 默认 300，上限 2000（前端按 500/页自动加载） |

返回：

```json
{ "items": [{...任务}], "total": 415, "offset": 0, "limit": 500, "hasMore": true,
  "unscheduledCount": 3,
  "unscheduled": [{...任务}],
  "deps": [{ "id": "D...", "fromTaskId": "K1", "toTaskId": "K2", "depType": "FS", "lagDays": 0 }],
```

  `deps` / `baseline` / `baselineAt` 与 `unscheduled` 都只随第一页（`offset=0`）返回。

  由生成列 `task.gantt_start / gantt_end` 承载（`sql/16`），走 `idx_gantt_range`。
- 排序稳定：`gantt_start, gantt_end, id`。
- `q` 在 SQL 中覆盖：标题/描述/备注/模块子串匹配（`LOCATE`，避免 `%`/`_` 被当通配符）+ 项目名 / 标签名 / 附件文件名 EXISTS，与看板 `match()` 对齐。
- `due` 的 over/today/soon、`focus`、`blocked`、`noDue`、负责人/优先级/模块/项目/标签同样在 SQL 层过滤。
- 前端：月视图把 `from/to` 下推并翻月重新查询；「适配全部」不带区间，按 500/页加载排期任务。
- 任务 `isMilestone` 为兼容字段：`POST/PUT /api/tasks` 仍可传，旧客户端更新时未传则保留原值，日期在服务端归一为单日；新前端不再写入该字段，项目里程碑改用 `/api/milestones`。

### 1. 权限与身份

所有写操作均要求项目可写；viewer、项目 read / none 无权。管理者为 workspace owner/admin 或项目 `ownerUserId` 对应账号且可写，身份不按 `displayName` / `owner` 文本识别。

| 操作 | 权限 |
| --- | --- |
| 需求 pass / rej / unpass / reopen | 项目写权限；空间主 / 管理员可管理空间内项目，普通成员按项目授权 |
| 需求 plan / replan / unplan / cancel / restore、发布计划维护 | 管理者 |
| 发布管理、版本 release-preview / release（含 redeploy / rollback） | 仅管理者，服务器提交时重新检查；任务负责人无整版本权，计划 ownerUserId 元数据不赋权 |

### 2. 需求排期

`DemandSaveRequest` 创建 / 编辑使用 `reqId,title,description,source,itemKind,categoryId,priority,expectDate,plannedStart,plannedEnd,acceptText,wsjfBusiness,wsjfUrgency,wsjfRisk,wsjfEffort,revision`。目标版本可暂不指定，保存 DTO **不含 versionId**，排期 / 调期通过动作设置或清空目标。编辑带 revision；创建由服务端初始化 0。`plannedStart/plannedEnd` 为日期，与 `expectDate` 独立；两端都填时开始不得晚于结束。`status=review` 时全部字段生效；`pass/plan` 只应用 `description,source,categoryId,acceptText` 与 WSJF 四项，`title,reqId,itemKind,priority,expectDate,plannedStart,plannedEnd` 一律保持库内原值；`done` 额外放行 `title,priority`，版本与计划日期仍由排期维护、完成状态也不可经编辑改变；`closed/rej/canceled` 返回 400，需先恢复。

`POST /api/demands/{id}/{action}` 返回 `Demand`：

| action | 状态与 body |
| --- | --- |
| plan | pass → plan，`{versionId,plannedStart,plannedEnd,priority,expectDate,note,revision}`；当前 revision 必填，versionId 可为 null（暂不指定目标版本）；选定目标时须同项目且未发布 |
| replan | plan → plan，同上；versionId 可为 null 以清空目标，仍属调期并保留 plan；note 原因与当前 revision 必填；计划日期省略 / null 可清空，绝不改旧任务 |
| unplan | plan → pass，`{note,revision}` 必填，清目标版本与计划起止 |
| cancel | review/pass/plan → closed，`{note,revision}` 必填；已完成需求不能直接关闭；可选 `closeReason=cancel`（中途取消，缺省）或 `dup`（重复需求），服务端记录 `closeStage=关闭前主状态`；保留需求、目标版本、计划起止与历史，不关闭 / 删除任务；目标引用仍参与版本删除保护 |
| restore | closed → review/pass，`{note,revision}` 必填；`closeStage=review` 回到待评审，其余回到已通过；回到已通过时清目标版本与计划起止，需重新排期 |
| pass | review → pass；可带 `{note,revision}`，提供 revision 时校验 |
| rej | review → closed，写 `closeReason=rej,closeStage=review`；`{note,revision}` 中拒绝原因必填 |
| unpass | pass → review；可带 `{note,revision}` |
| reopen | closed 且 `closeReason=rej` → review；可带 `{note,revision}`；中途取消与重复需求不能走此入口 |
| complete / auto_reopen | 只由完成判定服务写入：plan ⇄ done；不由 HTTP 动作端点直接触发，日志动作名为 `complete` / `auto_reopen` |

`DemandActionRequest` 原因说明字段是 **note**，不是 reason；日期为 `yyyy-MM-dd`，priority 为 P0/P1/P2/P3，revision ≥ 0。plan / replan 允许 versionId=null，当前 revision 必填；选定目标时须同项目且未发布；清空目标仍调期，须 note 原因；冲突返回 409，刷新后重试。需求调期 / 撤排 / 关闭 / 恢复不自动改任务版本、日期或状态；同一需求关联的多个任务可以跨版本。

### 3. 任务当前计划版本与只读发布字段

仅 Task 与版本改为 M:N；`TaskSaveRequest.versionIds` 保存 `version_task` 的当前计划集合，目标须同项目，**不是实际发布证据**。Demand / TestPlan 保留单目标 `versionId`，不扩展成数组。保存仍带 `versionChangeReason` 与 `oldUpdatedAt` 防并发覆盖。

| versionIds 输入 | 保存语义 |
| --- | --- |
| 省略 / null | 保留现有集合；新建默认空集合，不根据 demandId 或需求目标隐式改绑 |
| `[]` | 显式解绑；实际变更须原因与管理者或该任务负责人可写权限 |
| 非空数组 | 显式设置同项目版本集合；实际变更须原因与相应权限，不以空串代替数组 |

任务读取与 POST / PUT 保存响应返回实际落库的 `versionIds` / `versionNames` 数组及 `tags`；按最终项目 / 负责人重新判断可写权限。版本成功事实形成后内容关联冻结，不能以回滚或撤标解锁；**任务完成、回退、计时不受发布锁定**，按原流转与权限规则执行。冻结关联与历史证据不得因改项目 / 需求 / 版本或删除而破坏。

只读任务字段：`publishedAt,publishedReleaseId,publishSource,everPublished,publicationState,publicationTargets`；发布来源固定 `record`，仅成功 `production` deploy / redeploy 记录参与生产发布推导。`publicationState` 取 `unpublished / effective / partial / rolled_back / unknown`，表示未发布、有效、部分有效、引用范围已回滚或证据未知；结合目标覆盖理解，不把 unknown 当 full。test/staging 成功或 failed 事件不代表生产发布。badge 不是 `boardColumn` 新值；正式字段不授权人工写入或撤标，旧 `canPublish/canUnpublish` 不得作为人工发布入口，历史迁移补录只能走 `publication-judgement` 接口。

`DELETE /api/versions/{id}` 不会自动解绑：已发布或有实际尝试（含失败）、有任务绑定（含回收站）、需求目标引用（含 closed）或关联里程碑（含已取消）返回 422。无证据版本先按权限有因调整引用；回收站任务先恢复，已关闭需求按 `closeStage` 有因恢复，回到已通过时会清目标。删除不得清除历史证据，也不存在「先撤徽标即可删除」的路径。

**发布日程**：`GET /api/release-plans` 只读汇总，`status=open` 表示草稿 + 就绪，`all` 或缺省表示全部；`from/to` 为计划时间区间（含首尾日）。归档项目不进入结果，普通成员按项目可见范围过滤，owner/admin/viewer 全量可见；返回行含 `projectName,projectNames,versionName,versionNames,versionCount,versionStatus,plannedAt,environment,coverage,status,ownerName,plannedTaskCount`，不含计划任务明细。跨版本 / 跨项目计划在 `projectNames` / `versionNames` 列出全部成员，`projectName` / `versionName` 为主版本展示值。

**Plan 字段**：`id,revision,versionId,versionIds,plannedAt,ownerUserId,status,notes,risks,reason,plannedTaskIds,environment,targetKeys,coverage`。`versionIds` 为计划覆盖的版本集合，可跨版本 / 跨项目（≤50），当前版本必须包含；`versionId` 保留为主 / 展示版本。写入须覆盖全部版本所属项目的管理权限；历史计划若没有关联行，按 `versionId` 单版本处理。可写状态为 `draft / ready / canceled`，`completed` 仅由全部包含版本的成功生产事实产生并且只读。ready 需计划时间、负责人与至少 1 个工作项；调整 ready 或取消需 reason，更新必须匹配所选计划 revision。notes ≤2000、risks ≤1000、reason ≤500。环境为 `production / staging / test`；`targetKeys` 是数组，覆盖为 `full / partial / unknown`。完成计划不可修改；后续另建计划，紧急无计划事实必须填写 deviationReason，不能倒改完成计划。

**时间语义**：Plan.plannedAt 为 LocalDateTime 本地墙钟，前端不先转 UTC 再丢偏移；显示补齐零秒不导致 planDirty 误报，未改变时保留原值。ActualContext.occurredAt 为带 offset 的实际时刻，服务规范化 UTC；date-only 信息仅显示日期、不伪造时间。预检的「完成日晚于实际时间」警告把 occurredAt 换算到服务器时区后再取日，与工作项的本地完成日同口径，避免跨零点误报。

**三范围**：版本内容关联、计划 `plannedTaskIds`、实际 `actualTaskIds` 独立保存；计划范围取所选版本内容并集，实际范围始终只属于当前版本，也不以计划自动替代实际事实。一个版本生产只成功部署一次：已有成功生产事件时不得更换制品，补丁须新建 hotfix 版本；同一制品可 redeploy，可对成功事件 rollback。计划完成要求其全部关联版本都有关联同一计划的成功生产 deploy / redeploy，test/staging、rollback 与部分成功不完成计划；无关联行的历史计划按单版本处理。UI 明列 selected / omitted 两组及未选理由。

**ActualContext 字段与约束**：

| 字段 | 语义 |
| --- | --- |
| `planId` | 可选；紧急无计划必须 `deviationReason`，有计划则明确选定，不静默取最新 |
| `occurredAt` | 实际发生时间，带 UTC offset 的 ISO 8601（如 `2026-11-10T14:30:00+08:00`）；与服务器写入时间 `recordedAt` 分开，不再以仅日期 publishedOn 代替 context |
| `environment` | `production / staging / test` |
| `targetKeys` | 显式目标数组，与环境共同限定有效引用范围 |
| `coverage` | `full / partial / unknown`，未知不得冒充全量 |
| `artifactRef` / `artifactDigest` | 制品引用 / 64 位十六进制 SHA256，不用普通版本名代替制品证据 |
| `operation` | `deploy / redeploy / rollback` |
| `relatedReleaseId` | 关联实际事件；redeploy / rollback 明确所关联记录，rollback 仅撤销该记录在指定目标的引用范围 |
| `executorUserId` | 实际执行人元数据，不赋权，不替代提交者 releasedBy |
| `actualTaskIds` | 必须显式提供的唯一任务 ID 数组，最多 500 项；不自动选全部、不静默丢弃不符合普通计划条件的事实 |
| `deviationReason` | 紧急无计划、未完成事实及其他偏离须说明；未完成事实必须管理权限与该理由 |

预览显式接收实际 context，分别呈现版本内容、计划范围和实际范围，显示计划未选 `not_selected`、候选及 warnings。已发布不能自动排除（可能 redeploy）；未完成、完成时间晚于事件、需求关闭、跨范围等应显示偏离警告，不静默缩减 actualTaskIds。首版统计折算不生成事实。范围与覆盖未知必须明确呈现，不用候选百分比推断 100% 验收。

确认在同一 context 外另带 `result=success / failed`、`notes`、`failureReason`、`idempotencyKey`（非空 ≤64）、预览返回的 `planRevision` 与 `scopeToken`（非空 ≤64）；无计划时也沿用预览返回值，不自行伪造 revision。notes ≤2000；failed 必填 failureReason（≤1000）。失败只追加不可变尝试与范围快照 / 日志，不产生生产发布或完成计划；成功按显式实际范围原子写记录 / 条目 / 快照，仅当计划全部包含版本均已有成功生产部署 / 重部署且关联同一计划时才完成计划。实际版本必须属于计划包含的版本；`planRevision` 与 `scopeToken` 覆盖版本集合。发布管理权限提交时重新检查，`releasedBy` / `recordedAt` 由服务器确定，客户端不得冒充。

rollback 本身是一条新事件：按 environment/targetKeys 与 relatedReleaseId 撤销所引用范围，失败回滚不撤销；原记录、快照及 everPublished 历史保留，不抹后续不同成功、不解锁版本内容关联。任务 publicationState/publicationTargets 从成功生产事件及有效引用推导，不能只用最后一条事件或版本 released 字段判断。

**工作项动态的发布节点**：成功且非回滚的确认，给本次每个实际工作项写一条 `task_log`（`action=release`），`detail` 为「随版本「X」发布到生产 / 预发布 / 测试 · 发布时间 `yyyy-MM-dd HH:mm` · 执行人 Y」，时间由 UTC 按服务器时区还原到本地分钟；`change_data` 存 `releaseId,releaseNo,versionId,versionName,environment,operation,occurredAt,executorUserId,executorName`（`occurredAt` 为 ISO UTC）供回查发布记录。失败与回滚不写节点，同幂等键重放返回原记录也不重复写。节点只进工作项时间线与活动流（`entity_type=task`，活动台账「工作项」动作筛选含 `release`），不参与 publicationState 推导。

`scopeToken + planRevision + idempotencyKey` 防竞态：所选计划、范围、任务 / 需求或权限变化需复核、冲突后重新预览；同键同 body 重试返回持久化原 `VersionRelease`，同键不同内容返回 409，不重复落证据。**响应未知不等于失败**：sessionStorage 保留完整原 body/key，刷新 / 重开先 GET release-records?key=... 查询；查询失败不清请求、不生成新键、不盲重试。查到并核对一致记录后不重复创建；查询成功且无记录才允许显式重试原完整 body/key，明确拒绝也须先查询再显式重置、重新预览。最终 Chrome 恢复 27 断言 / 3 场景覆盖响应丢失、请求丢失及之后页面刷新 + 查询失败。

记录返回本次实际 context、result、planId/planRevision、server recordedAt/releasedBy、idempotencyKey、版本 / 计划 / 实际范围快照及 items；任务标题 / 负责人、需求与目标、完成时间、工时等历史信息读快照，不从当前对象补齐而漂移。记录、成功说明与快照 CSV 按事件读取；release-history 只查询，不提供发布历史 JSON 导出。

`GET /api/versions/stats` 将当前 taskCount/doneCount/workMinutes 与版本 / 计划 / 每次实际快照、覆盖和当前有效目标分开；实际交付与当次未选范围不等于当前剩余。M:N 关联和多事件不得放大全局工时。无正式记录显示 `no_release_record` / 未知证据，不把缺少证据当零交付或 full。需求关闭不抹实际快照，零任务不能 100% 验收。`uniqueProductionTaskCount/effectiveProductionTaskCount` 分别表示生产曾交付去重数和当前生效数，与事件处理项次分开展示，不推断待交付数。移动端关闭按钮保持 sticky 可达；具体验证时点与 SW 版本见更新日志发布记录。

需求排期到版本不会自动改写其名下工作项的版本：首次排期成功后前端弹出一次「带入工作项」确认，调期不批量迁移；确认走 `POST /api/demands/{id}/version-tasks`，逐条写 `version_change` 审计并在 after 快照标 `inheritanceSource=demand-batch`、`demandId`，任一任务冲突整批回滚，成功后递增版本 `revision`。候选为空时不弹确认；内容已冻结的版本候选恒为空、写入直接拒绝。版本页「管理工作项」的「按需求」分组与已排需求行内「补录工作项」是后续遗漏的兜底入口。

`limit` 服务端收敛到 `1–100`，`offset` 最小为 0；统计与筛选项由 SQL 聚合，不得先取全量明细再在客户端统计。工作页的 `statusCounts/stageCounts` 是清除工作筛选后的当前项目范围计数，用于页签；`page/metrics/versions` 响应当前筛选。`versions[]` 为 `{versionId,versionName,cnt}`，`__none` 表示未指定版本且排最后，其余按自然版本号倒序，数字段按数值比较（如 `V1.10` 在 `V1.2` 前）。

已排期与已完成需求额外返回字段 `deliveryStage,deliveryStageSource,taskCount,taskDone,caseCount,casePassed,devStart,deliveredAt,deliveryEvidenceMissing`，以及人工判定摘要 `manualDeliveryStage,manualDeliveryEffectiveOn,manualDeliveryReason,manualDeliveryJudgedBy,manualDeliveryJudgedAt`。阶段不是主状态；`waiting/active` 只在 `plan` 出现，`donePending/delivered` 只在 `done` 出现，其他主状态为空；自动派生之外只允许管理者在已完成需求上补录终态：

| deliveryStage | 来源与条件 |
| --- | --- |
| `delivered` | `done` 上优先来自真实发布：存在该需求 `result=success + environment=production + operation≠rollback + coverage=full + disposition=published` 且未被后续回滚按工作项撤销的发布条目（`deliveryStageSource=release`）；否则来自生效的人工「已交付」判定（`manual`） |
| `donePending` | `done` 上自动派生（`derived`）：已完成但没有生产发布记录；也接受人工判定（`manual`） |
| `active` | `plan` 上已有真实开工但尚未完成；真实开工取首次移出 backlog、首次计时、直接创建在执行列的最早日期，不读计划 `task.start_date` |
| `waiting` | 已排期但尚无真实开工 |

真实发布证据始终优先于人工判定；`deliveredAt` 有真实发布时取真实发布时间，没有时才取人工「已交付」的 `effectiveOn`。人工判定与需求当前目标版本绑定（`version_id` 做 null-safe 等值），换版本后旧判定不参与派生；修改判定先撤销旧记录再追加新记录，历史保留；撤销后恢复自动派生。只有 `status=done` 且 `canJudgeDelivery=true`（空间主、管理员或项目负责人）的用户可以写判定，写入使用项目锁、需求当前读与 `revision` CAS，冲突返回 409。

指向已发布版本但没有有效发布记录且没有生效人工「已交付」判定时，`deliveryEvidenceMissing=true`，只提示补证据，不能据版本状态或计划日期显示已交付。升级时先执行幂等迁移 `sql/72_demand_closed_delivery_stage.sql`，再按需执行 `sql/73_backfill_historical_delivery_evidence.sql`：已有成功生产条目的需求直接派生已交付；仅有 `released + released_at` 的历史版本可补一条明确标记为历史导入的发布证据；没有 `released_at` 时不读取 `target_date/updated_at` 猜测交付，保留已排期并输出人工补录清单。两个脚本均不补造工作项、用例或完成时间。主状态 `done` 由幂等迁移 `sql/105_demand_done_status.sql` 回填：发布证据优先（成功正式生产发布或生效人工判定直接置 `done`），其余按「至少 1 个未删除工作项全部完成 + 关联用例最新执行全部通过（0 条视为通过）」判定，不满足的保持 `plan`；随后所有改变工作项、用例、发布证据的写路径（含版本实际发布确认与回滚）都在同一事务内调用 `DemandCompletionService` 重新判定；发布证据只认成功、生产、非回滚、全量覆盖且未被后续回滚撤销的条目，失败、部分成功与回滚会让已完成需求按剩余证据回到 `plan` 或保持 `done` 并转「待发布」。人工判定表由幂等迁移 `sql/76_demand_delivery_judgement.sql` 创建；需求删除、项目删除、空间清空与备份覆盖导入都会一并清理该表记录。

## 附录 · 2026-11-13 版本终态、承诺基线、里程碑与版本报表（增量）

### 1. 版本关闭 / 取消

- `POST /api/versions/{id}/close` 与 `POST /api/versions/{id}/cancel`，请求体 `{reason}`，原因必填且 ≤500 字；分别写入 `status=closed` / `status=canceled`、`ended_at` 与 `end_reason`。
- 权限：项目写权限即可（项目负责人不必拥有发布权限）；已发布（`released`）或已结束的版本拒绝；仍有草稿 / 就绪发布计划时返回 422，需先完成或取消计划。
- 关闭与取消是终态：不能再加入发布计划、不能新增或调整工作项；历史、日志与工作项关联保留。`/api/versions/overview` 的已发布 / 进行中 / 计划中计数只统计 `released` / `active` / `planned`，关闭与取消不计入节奏，但仍出现在版本列表与筛选里（`sql/78_version_end_state.sql`）。

### 2. 承诺基线

- `POST /api/versions/{id}/start` 首次把版本从计划中置为进行中时，只写一次 `commitment_at`，并把当时绑定的工作项、标题与预估写入 `version_commitment_task`（`sql/79_version_commitment.sql`）。
- 基线不随后续增删工作项或修改预估回写；版本统计按「当前绑定 − 基线」给出新增 / 移除 / 完成，旧版本没有快照时字段为空，不根据当前数据倒推。
- 删除版本、删除项目、清空空间与任务数据整体清空时一并清理基线记录。

- JSON 任务备份（v12）不搬运里程碑定义、条件与日志；需要保留里程碑时使用完整数据库备份。覆盖导入会清理现有里程碑。

### 2. 阶段工时拆分（测试窗口内 / 外）

- 实际工时按测试窗口拆分：`testMinutes`（窗口内）为 `test_started_at` 与 `test_finished_at` 都存在时，计时记录日期落在两者自然日闭区间内的分钟数；其余计入 `devMinutes`（窗口外）。测试开始或结束缺失时不计测试分钟，因此测试分钟不会超过实际工时，且 `devMinutes + testMinutes = workMinutes`。窗口外包含需求评审、设计、开发、运维等，不应当作「开发工时」展示。

## 附录 · 2026-11-10 项目授权：新成员默认不参与 / 邀请预分配

### 1. 行为口径

- `workspace_member.project_access_mode` 区分两种成员口径：
  - `all`：默认参与。改动前的存量成员全部保留该值，升级后行为不变；没有 `project_member` 记录的项目仍然可见可写。
  - `assigned`：按项目分配。新成员通过邀请加入、或由平台管理员按登录名直接加入时使用；没有显式 `write` / `read` 的项目一律不可见。
- 新成员加入时默认不参与任何项目。邀请链接可在生成时预分配项目权限（只接受 `write` / `read`），加入时在同一事务内落库；已被撤销 / 已删除的项目授权自动跳过。

- 三档权限口径：`write` = 可参与（可查看、可编辑），`read` = 只读，`none` = 不可见。存量兼容码值 `pm` / `dev` / `qa` 继续归一到默认参与，不改变历史数据。
- 单格保存的 `access` 传空表示恢复该成员的默认口径：`all` 成员回到默认参与，`assigned` 成员回到不可见。
- 分配项目时，只有实际变化的单元格计入审计摘要与通知；批量提交一次只写一条配置记录、一条审计、一条系统通知。

## 附录 · 文档可见范围（2026-11-15）

照用例分组的口径给文档加一层文档级可见范围，三档：`team` 团队共享（默认，等同升级前行为）、`members` 指定成员、`personal` 仅自己。只约束已发布文档；草稿仍按 `published_at IS NULL` → 仅作者 + 空间 owner/admin 可见，与可见范围无关。

### 1. 判定口径

- 已发布可见 = 项目可见范围 ∩ 文档可见范围：`published_at IS NULL OR visibility='team' OR owner_user_id=当前用户 OR EXISTS(doc_visibility_member)`；`visibility` 为 NULL 时按 `team` 处理。
- 负责人始终可见；空间管理员同样受约束，不在名单里就是看不到，与用例分组一致。
- 列表、全局检索、项目文档计数、需求池关联文档共用 `RequirementDocMapper.visibilityWhere` 片段；详情、评论、历史、任务走 `getVisible` 服务校验，同一口径。列表 SQL 用子查询回 `member_count`。

### 2. 接口

| 接口 | 说明 |
| --- | --- |
| `PUT /api/req-docs/{id}/visibility` | 单独调整可见范围，不碰正文与乐观锁。body：`{visibility, memberIds}`；收窄守卫、名单校验与编辑路径共用 |
| `POST` / `PUT /api/req-docs` | body 增加 `visibility?` 与 `memberIds?`；`members` 档必须带名单 |
| `GET /api/req-docs/{id}` | 回显 `visibility`、`memberIds`、`memberCount`；列表回显 `visibility` 与 `memberCount` |

- 名单：≤50 人、去重、至少 1 人；主动提交名单时每位成员都必须真的看得到该项目，否则 400「所选成员里有人看不到本项目，请先在成员管理里授权」。编辑器保存正文不带 `memberIds` 时原样沿用旧名单、不重复校验，避免名单成员后来被移出项目反而阻断正文保存。
- 收窄守卫：把团队共享改成指定成员 / 仅自己，只能由文档负责人操作，否则 400「团队共享文档收窄可见范围需由文档负责人操作，避免其他成员突然看不到」。
- 非 `team` 档会撤销该文档的公开分享链接；`POST /api/req-docs/{id}/share` 仅 `team` 档可生成，其他档 400「仅团队共享文档可生成公开分享链接，请先调整可见范围」。
- 档位变化写入动态流：`可见范围：团队共享 → 指定成员`；同档位只换名单不记一条。

### 3. 数据库

- 迁移 `sql/99_doc_visibility.sql`（幂等）：`requirement_doc.visibility varchar(8) NOT NULL DEFAULT 'team'`；新增 `doc_visibility_member(doc_id, user_id, workspace_id, created_at)`，主键 `(doc_id, user_id)`，索引 `(workspace_id, user_id)`。**无回填**，存量文档默认 `team`。
- 清理点：删文档、删项目、删空间与备份覆盖导入都删 `doc_visibility_member`（TaskCascade 注册表已同步）。成员被移出空间不清名单行，与用例分组一致：重新加入后按名单恢复可见。
- 当时完整基线为 75 张表（新增 `doc_visibility_member` 与 `requirement_doc.visibility`；102 后为 76 张表）。

### 4. 边界

- 可见范围只收窄「谁能看」，不改变写权限：能在项目里编辑文档的人仍可编辑看得到的文档。改档位与名单走与编辑相同的门控（项目可写 + 文档负责人或空间管理员），其中把团队共享收窄成非团队档额外要求负责人本人，避免管理员误锁他人。
- 公开分享链接仍按 token 只读，非团队档不生成、不保留；改回团队共享不会自动恢复旧 token，需要重新生成。
- 管理员在指定成员 / 仅自己档下同样看不到未列入的文档；要恢复访问，由负责人把名单加上或改回团队共享。

- 前端「成员负载」页面卡片显示合并后的剩余与容量，测试行展示测试剩余；成员工作台、导出 CSV 与项目驾驶舱成员表同步新增测试剩余列。工作项抽屉「计划」区新增「测试预估（小时）」输入，测试卡显示该值。
