# 沙漏 · 内部接口契约

> 本文说明当前前端使用的会话认证接口，不是对外 Token / SDK 的承诺。开放 API Token、SSO 与 Git / CI 联动目前尚未提供；系统安全审计已有最小实现。产品主张是让投入可解释、让交付可追溯，不替代部署、财务结算或客户验收。

基准地址：`http://<服务器地址>:8080`（部署后走 nginx 时换成对外地址）

## 统一返回约定

- 成功：`{"code": 0, "message": "ok", "data": ...}`
- 业务错误：HTTP 200，`code` 非 0（400 参数问题 / 404 不存在 / 409 冲突 / 500 内部错误），`message` 为中文提示
- 校验失败：`code=400`，`message` 为具体字段提示（如「请填写任务标题」）

## 认证

除 `/api/health` 外所有接口需要登录态（会话 Cookie，有效期 30 天）：

- `POST /api/auth/login`（表单参数 `username`、`password`）→ 成功 `{"code":0,"message":"ok"}`，失败 HTTP 200 + `{"code":401,"message":"用户名或密码错误"}`
- `POST /api/auth/logout` → 退出登录
- `POST /api/auth/password`（body `{"oldPassword":"...","newPassword":"..."}`）→ 修改自己的密码（校验旧密码）
- 会话说明：登录状态 30 天有效；**管理员重置密码后，该用户已登录的会话保持有效直到过期**（无会话注册表，不会踢线）
- 未登录访问接口返回 HTTP 401 + `{"code":401,...}`；页面访问未登录跳转 `/login.html`
- 写操作（POST/PUT/DELETE）需携带 CSRF 头 `X-XSRF-TOKEN`（值取自 Cookie `XSRF-TOKEN`，前端已封装自动处理；Apifox 调试时先 GET 一次任意接口拿到 Cookie）

## 多用户与空间

- 账号由管理员创建下发（不开放注册）；共享空间可生成邀请链接，把**已有账号**拉入空间协作；管理员只管账号
- **空间模型**：每个账号自动有一个「我的看板」个人空间；任何人可新建共享空间并当空间主，成员**只能通过邀请链接加入**（对方打开链接并确认后才成为成员）；`POST /api/workspaces/{id}/members` 按登录名直接加人**仅平台管理员可用**，普通空间主调用返回 403，避免不经同意就把人拉进空间
- 所有业务接口都接受 `workspace` 查询参数（空间ID）；不传时用"上次使用的空间"，再退回个人空间。前端切换空间后自动携带
- **数据按空间隔离**：任务/子任务/项目/附件/工时/操作日志/标签/看板列/模块属于空间；保存的筛选视图属于"人+空间"
- **权限**：除查看者外的成员可做日常操作（增改删任务、拖拽、子任务、标签、计时、附件、回收站恢复）；**仅空间主**可做：改空间名 / 推送配置、删空间、删看板列、清空任务数据、导入覆盖；**空间主或管理员**可移成员、调整成员角色（管理员只能处理成员 / 查看者，不能授予管理员）、生成 / 撤销邀请；**删除模块**允许空间主、管理员或项目负责人；**分支创建 / 编辑 / 改状态 / 删除**按所属项目写权限判定，空间级公共分支由空间内非查看者维护。按登录名直接加人仅平台管理员可用。跨空间访问一律 404，权限不足返回 403
- **审计**：操作时间线记录操作人（`actorName`），历史数据显示为空
- 账号接口：
  - `GET /api/auth/me` → `{id, username, displayName, role, lastWorkspaceId, workStartHour, workEndHour, workMaxHours}`
  - `PUT /api/auth/work-hours`，body `{"startHour":9,"endHour":18,"maxHours":8}` → 修改自己的计时设置（`0 ≤ startHour ≤ 23`、`1 ≤ endHour ≤ 24`、`endHour > startHour`、`1 ≤ maxHours ≤ 24`）；只影响之后的计时折算，已记录工时不重算
  - `PUT /api/auth/profile`，body `{"displayName":"..."}` → 修改自己的显示名（负责人默认值与成员列表随之更新；**其参与空间中「负责人=旧显示名」的任务同步改为新名**，含回收站任务；操作时间线保留历史记录）
  - 管理员专属（`/api/admin/users`，见下方原章节）：新增/改显示名与角色/重置密码/删除（需先清空其个人空间数据、非共享空间主、不能删自己、至少留一名管理员）
- 空间接口：
  - `GET /api/workspaces` → 我参与的空间（含 `type` personal/shared、`myRole`、`memberCount`）
  - `POST /api/workspaces`，body `{"name":"项目组看板"}` → 新建共享空间（创建者为空间主）
  - `POST /api/workspaces/{id}/select` → 记住"上次使用的空间"
  - `PUT /api/workspaces/{id}`，body 可按需提交 `{"name":"..."}` 或推送字段（仅空间主；个人空间名称不可改）。PATCH 语义：`name` 不传=保持原值；`notifyChannel`/`notifyEnabled` 不传=保持原值；`notifyWebhook` 不传=保持原值、传空串=清除；`notifyToken` 留空=保持原值，`clearToken:true` 才清除已保存 Token
  - `DELETE /api/workspaces/{id}`（仅空间主；存在发布证据时禁止破坏性删除，无证据时连带清理数据且不可恢复；个人空间不可删）
  - `GET /api/workspaces/{id}/members` → 成员（含显示名/登录名/角色/公司 `companyName`）
  - `POST /api/workspaces/{id}/members`，body `{"username":"xiaoming"}`（仅空间主）
  - `DELETE /api/workspaces/{id}/members/{userId}` → 空间主移除成员；成员自己调用即退出；空间主不能退出自己的空间（可直接删空间）
  - `PUT /api/workspaces/{id}/members/{userId}/role`，body `{"role":"admin|member|viewer"}` → 调整角色（管理员只能处理成员 / 查看者）。角色变化不改项目授权模式、不删已有授权：按项目分配的成员升为管理员再改回成员时，沿用此前分配，缺失的「不可见」种子行会自动补齐，不会因往返而扩大可见范围
  - `PUT /api/workspaces/{id}/members/{userId}/company`，body `{"companyName":"蓝海银行"}` → 标注成员公司（空间主 / 管理员；最多 64 字，空串表示清除）。公司是空间级展示标签，只影响成员列表、花名册、负责人分组与评论展示，不改变任何权限
  - 邀请链接（共享空间协作入口，见 §29）：`POST/GET /api/workspaces/{id}/invites`、`DELETE /api/workspaces/{id}/invites/{inviteId}`（均限空间主 / 管理员）
  - 项目级授权（共享空间，限空间主 / 管理员）：
    - `GET /api/workspaces/{id}/project-access` → `{myRole, members, projects, grants}`，成员 × 项目的全量矩阵与现有显式授权
    - `PUT /api/workspaces/{id}/project-access`，body `{"userId":"u1","projectId":"p1","access":"write|read|none|"}` → 单格保存；`access` 为空表示恢复该成员的默认口径（存量成员回到可参与，按项目分配的成员回到不可见）。存量成员（`all` 模式）保存 `write` 时不落冗余行，等同恢复默认；审计与通知按「生效权限」比较，未真正变化不写记录
    - `PUT /api/workspaces/{id}/members/{userId}/project-access`，body `{"grants":[{"projectId":"p1","access":"write"},{"projectId":"p2","access":"read"}]}` → 一次性提交该成员全部项目权限，整批在同一事务内保存（任一格失败全部回滚）；按生效权限比较，仅当有实际变化时写一条审计与一条通知，无变化则两者都不写
  - 项目花名册与角色标注（共享空间，仅展示，不参与鉴权）：
    - `GET /api/workspaces/{id}/projects/{projectId}/members` → `{members:[{userId,displayName,username,companyName,roleTitle,access,source,canEditRole}], canEditRole}`；空间查看者、显式不可见成员不返回；`access` 为生效权限（write/read），`source` 为可见来源（项目负责人/空间主/空间管理员/空间默认参与/项目授权）。调用者须为空间成员且能看到该项目
    - `PUT /api/workspaces/{id}/projects/{projectId}/member-roles/{userId}`，body `{"roleTitle":"后端开发"}` → 标注该成员在本项目的唯一主角色（最多 32 字，空串表示清除）。仅空间主 / 管理员或项目负责人可写；目标须非查看者且当前能看到该项目；角色只用于展示、筛选与负责人下拉，不改变项目权限
- 模块接口（模块按项目配置：每项目一套清单，跨项目视图用全量字典按名称展示）：
  - `GET /api/categories` → 空间内全部项目的模块 `[{id,projectId,name,color,sortOrder}]`；`?project={项目ID}` 只返回该项目的清单
  - `POST /api/categories?project={项目ID}`，body `{"name":"客户跟进","color":"#7a5c86"}`
  - `PUT /api/categories/{id}`（改名只改字典，任务/需求关联存模块 ID 不回刷，展示名经字典实时解析；模块只能属于建它的项目）
  - `DELETE /api/categories/{id}?targetId={模块ID}`（其下任务与需求迁到指定模块，targetId 缺省迁到项目内最靠前的其他模块，至少保留一个）
  - 模块维护权限：`POST` / `PUT` / `DELETE` / `PUT order` 均要求空间主、空间管理员，或该项目负责人（`requirement.owner_user_id`）且拥有该项目写权限；查看者与普通成员 403（只读可查）
  - `PUT /api/categories/order?project={项目ID}`，body `{"ids":[...]}`（ids 必须恰好是该项目的全部模块）
- 优先级显示配置（每空间固定 P0/P1/P2/P3 四档，只改显示名与颜色，不改变存储、筛选、排序和导出 code）：
  - `GET /api/priorities` → 固定顺序返回四档 `[{workspaceId,code,name,color,...}]`；未配置的档位返回内置默认「紧急/高/中/低」，不写库
  - `PUT /api/priorities/{code}`，body `{"name":"高","color":"#F79009"}` → 修改单档显示配置；查看者 403
  - `DELETE /api/priorities` → 清除当前空间的自定义配置，四档全部恢复内置默认；查看者 403
- 任务/需求挂模块：`categoryId` 必须属于所属项目的模块；不传/不属于该项目时，任务自动落到项目第一个模块，需求为「未指定」。未挂项目的任务模块恒为「未指定」（存空串）。新建项目时后端自动预置默认模块「其他」

## 通用查询参数（看板 / 已完成列表）

| 参数 | 说明 |
|---|---|
| q | 关键词，匹配标题/描述/进度备注（不区分大小写） |
| owners / pris / cats / reqs / tags | 逗号分隔多选；pris 取值 P0,P1,P2,P3；cats 取模块 ID（`categoryId`）；reqs 支持特殊值 `__none`（未归类）；tags 为标签名 |
| due | 截止维度：over（逾期）/ today（今天）/ soon（3 天内，含今天） |
| focus | true = 今日聚焦（逾期 + 今天到期 + 进行中的 P0） |
| doneScope | 已完成列范围：week（默认，本周）/ all |
| doneLimit / doneOffset | 分页，默认 20 / 0，limit 上限 200 |

## 2. GET /api/board

看板聚合：三列数据、提醒计数、筛选元数据（负责人/优先级/模块/项目计数）。完成列返回第一页。

```json
{"code":0,"data":{
  "columns":{
    "backlog":{"items":[],"matched":0,"total":0,"allTotal":0,"hasMore":false},
    "doing":{"items":[],"matched":0,"total":0,"allTotal":0,"hasMore":false},
    "done":{"items":[],"matched":0,"total":0,"allTotal":12,"hasMore":false}
  },
  "counts":{"over":0,"today":1,"soon":2},
  "meta":{"owners":[{"name":"我","count":9}],"pris":[{"name":"P0","count":1}],
          "cats":[],"reqs":[{"id":"R...","name":"资金小程序","status":"active","count":3}],"unassigned":4}
}}
```

`matched`=筛选后条数；`total`=筛选前当前范围内条数；`allTotal`=全部历史条数（「仅本周 ⇄」提示用）。

## 3. GET /api/tasks/done

已完成列「加载更多」。参数同上（含 doneOffset）。响应为单个列对象：`{"items":[...],"matched":40,"total":40,"allTotal":40,"hasMore":true}`。

## 4. POST /api/tasks

新增任务。`id` 选填（撤销删除/导入时指定），不填服务端生成。Task 使用 `versionIds` 数组：省略 / null 保留现有集合（新建默认空集合），`[]` 显式解绑，非空数组显式设置同项目版本集合，不根据需求目标隐式改绑。实际改关联须原因与权限，详见末尾闭环契约；Demand / TestPlan 仍是单目标 `versionId`。

```json
{"title":"重构权限校验中间件","description":"","priority":"P1","categoryId":"Gxxx",
 "boardColumn":"doing","dueDate":"2026-10-20","reqId":"Rxxx","progress":40,"note":"已确权方案"}
```

`dueDate` 格式 `yyyy-MM-dd`；`progress` 0-100；返回保存后的任务对象。新建与更新响应重新读取实际落库的 `versionIds` / `versionNames` 数组和 `tags`，以最终项目 / 负责人重算可写权限；`publishedAt/publishedReleaseId/publishSource/everPublished/publicationState/publicationTargets` 只读，由成功 production 记录推导，publishSource=record，无人工 canPublish / canUnpublish 操作入口。撤销删除恢复时可在 body 中带 `completedAt`（yyyy-MM-dd）保留原完成日期、带 `subtasks: [{title, done}]` 一并重建检查清单。ID 只接受字母/数字/下划线/中划线（≤32 位），不合法会当作未提供重新生成；指定 ID 已被占用的返回 409；覆盖导入会保留附件/日志等子记录，指定这类"仍有历史子记录"的 ID 同样返回 409，防止旧记录误挂到新任务。

## 5. PUT /api/tasks/{id}

更新任务字段（与新增同结构，title 必填）；`versionIds` 数组省略 / null 保留、`[]` 解除，实际改变关联须 `versionChangeReason` 与管理者或该任务负责人可写权限，且不得改成功事实冻结的关联。列变更自动处理完成日期，并**同时写入一条 `action=move` 移动日志**；其他字段变更写 `action=update`。发布不锁任务完成 / 回退 / 计时，不要求先撤徽标；徽标只读，详见末尾闭环契约。

## 6. POST /api/tasks/{id}/move

拖拽移动。

```json
{"column":"done","beforeId":"Kxxx"}
```

`beforeId` 为空字符串/不传 = 移到列尾；同列内也用它调整顺序。`autoTimer=false` 时移入非待处理/非完成列不自动计时；`autoResume=false` 时移到已完成不自动接力下一条。返回：

```json
{"code":0,"data":{"task":{...},"from":"doing","to":"done","autoTimerStarted":false,"autoTimerTask":null}}
```

同列内移动（只调顺序）不会把停留时长切成碎段。内置列为 `backlog/doing/test/testing/done`（待处理 / 进行中 / 待测试 / 测试中 / 已完成）；进入 `testing` 自动写 `testStartedAt`（新一轮重置并清空结束日），离开 `testing` 写 `testFinishedAt`，测试通过和退回都算这一轮结束。`testing` 退回 `backlog/doing` 默认需填 `reason`，缺少返回 412；两个测试时间由服务端维护，客户端只读。

缺陷工作项（`itemType=bug`）的 `regressionStatus`（`pending` 待回归 / `passed` 通过 / `failed` 不通过）由服务端随列流转维护，`POST/PUT /api/tasks`、`move`、`bulk-move`、`reopen` 同一口径：进入 `test/testing` 记 `pending`（开发已提交修复）；进入 `done` 记 `passed`；从 `test/testing/done` 退回 `backlog/doing` 记 `failed`；列内移动保持原值。`POST/PUT` 显式传入与旧值相同的回归状态视为未修改，仍按流转推导；显式改为 `passed` 但目标列不是 `done`、或进入 `done` 时回归状态不是 `passed`，返回 400。缺陷关闭口径 = 完成列且回归通过。

### 6.1 POST /api/tasks/bulk-move

列表页批量改列，body `{"ids":["K1","K2"],"column":"done","autoTimer":false,"autoResume":false}`。逐项走 move 语义（移动日志、完成归档、循环派生一致）；批量默认不自动开始/接力计时。最多 500 项，任一项失败整批回滚。

### 6.2 POST /api/tasks/{id}/reopen

取消完成：按最近一次移入 done 的 `from_column` 回到**完成前所在列**；该列已删除时依次回退到 `doing`、第一个非完成列、`backlog`。不自动开始计时。返回结构同 move。

## 7. DELETE /api/tasks/{id}

删除任务：软删除进回收站（30 天自动清理）；发布徽标只读，不以人工撤标解锁删除，成功事实冻结的内容关联和历史证据受保护，不得级联清除。撤销/恢复用 `POST /api/tasks/{id}/restore`，详见第 20 节。

## 13. GET /api/review?weekOffset=-1

工作回顾。`weekOffset` 不传时自动选最近一个有完成记录的周；0=本周，-1=上周。返回：

```json
{"code":0,"data":{
  "weekOffset":-1,"weekStart":"2026-10-06","weekEnd":"2026-10-12","label":"上周",
  "completed":[{...任务}],
  "stats":{"done":5,"withDue":5,"onTime":4,"onTimeRate":80,"members":1,"late":1},
  "members":[{"name":"我","count":5}],
  "catDist":[{"name":"后端","count":3}],
  "progressTasks":[{...}],
  "reqDist":[{...同 /api/reqs}],
  "counts":{"over":1,"today":0,"soon":2},
  "openP0":2,"doing":3,"backlog":5
}}
```

完成率口径：按期率分母为「设置有截止日期的完成项」（withDue）；无截止日期的完成项既不计入按期也不计入延期（`late = withDue - onTime`）。

## 14. GET /api/export

导出当前空间的**任务备份**（v12）。结构与旧版前端 `hourglass-backup.json` **兼容（超集）**：包含 tasks/reqs/columns；v4 起额外包含任务评论（comments）、任务 `deletedAt`（回收站）与任务的 `reqDocId`/`branchId`/`estimateMinutes`/`blocked`/`blockedReason`/`ownerUserId`/`remindTarget` 字段；v5 起额外包含任务 `isMilestone`、甘特依赖（`deps`）、基线（`baseline` + `baselineAt`）；v6 起额外包含 `reqDocs`（需求文档，含正文）与 `branches`（分支池，不含分支操作时间线）；v12 起额外包含模块字典 `categories`（含所属项目，任务 `cat` 与需求池 `categoryId` 存模块 ID）。旧版页面仍可直接导入读取；导入旧备份（无模块字典）时，任务/需求的模块值回落所属项目的默认模块。

**交付工作数据**：任务 versionIds 数组、version.startDate、需求期望 / 计划日期及 canceled 随 JSON 搬运，引用按项目映射；Demand / TestPlan 仍为单目标 versionId。**不含 / 不转移**正式发布证据（完整计划、实际记录 / 条目 / 快照 / 日志及由其推导的徽标）、附件文件、操作时间线、保存视图、模块/优先级显示设置与看板列设置（模块字典随 v12 导出）。JSON 不是全量数据库备份；正式证据只用完整数据库备份恢复。

## 15. POST /api/import

导入 JSON 任务备份，按下述覆盖语义处理；**已有发布证据时禁止破坏性覆盖，建议导入新空间**。JSON 任务备份不是正式发布凭证，不从旧 released 状态、首版统计折算或任务完成状态构造发布记录 / 徽标；正式证据须从数据库备份恢复：

```json
{"v":12,"tasks":[{"id":"Kxxx","title":"...","desc":"...","pri":"P1","owner":"我","cat":"Gxxx",
  "col":"doing","due":"2026-10-20","progress":40,"note":"","reqId":"Rxxx","reqDocId":"Dxxx",
  "branchId":"Bxxx","estimateMinutes":240,"blocked":false,"isMilestone":false,"completedAt":null}],
 "reqs":[{"id":"Rxxx","name":"...","desc":"","status":"active","createdAt":"2026-10-01"}],
 "categories":[{"id":"Gxxx","projectId":"Rxxx","name":"后端","color":"#3b82f6","sortOrder":1}],
 "comments":[{"taskId":"Kxxx","authorId":"Uxxx","authorName":"我","content":"...","createdAt":"2026-10-02T10:00:00"}],
 "deps":[{"from":"K1","to":"K2","type":"FS","lag":0}],
 "baseline":[{"taskId":"K1","start":"2026-10-01","due":"2026-10-08"}],
 "baselineAt":"2026-10-28T18:00:00",
 "reqDocs":[{"id":"Dxxx","reqId":"Rxxx","title":"...","content":"<p>...</p>","status":"draft","owner":"我"}],
 "branches":[{"id":"Bxxx","reqId":null,"name":"feature/login","status":"dev","owner":"我","targetBranch":"main"}]}
```

返回 `{"tasks": 42, "reqs": 5, "comments": 18, "reqDocs": 3, "branches": 2, "versions": 2, "demands": 4, "testCases": 12, "docComments": 6}`。

**覆盖语义（重要）**：导入清空并重建"任务类数据"——任务、回收站（保留原删除时间）、项目、子任务、标签、工时、**任务评论**、**甘特依赖与基线**与**完成归档**（完成归档按导入后的任务与工时重建，历史快照里的旧项目名/负责人名以备份数据为准）；v6 备份还会覆盖 **需求文档与分支**（含正文/状态/负责人，分支操作时间线清空）；**v10 备份还会覆盖测试用例、执行流水与文档评论**；**v12 备份还会按 ID 补齐模块字典**（不清空现有模块：备份模块的 ID 落库时已存在则映射复用，不存在则插入；模块映射缺失或不属于该任务/需求的项目时，模块值回落该项目默认模块）；旧备份没有对应字段时保留现状，不误删现有数据。**保留**附件文件与记录、操作时间线、保存视图、看板列、模块与优先级显示设置。跨空间复制导入时任务/项目/需求文档/分支 ID 冲突会自动重新生成并同步迁移引用（依赖端点按任务 ID 映射回指，自环/重复/成环边会被跳过）；看板列按备份补齐（跳过保留列 id=done 与超过 16 位的 id）、任务列按"列 id → 列名"两级映射落位。工时的计时人随备份恢复（`timeLogs[].userId`）；计时人不在目标空间（跨空间导入）时，该条工时归导入者。仅空间主可执行。导入会清除当前空间的只读分享令牌（旧链接立即失效），需要重新生成。

**旧备份兼容**：v3 及更早备份没有 comments 字段，v4 及更早没有依赖/基线字段，v5 及更早没有需求文档/分支字段，v10 之前没有测试用例/执行流水/文档评论，v12 之前没有模块字典（任务/需求的模块值回落所属项目默认模块）；对应字段缺失时保留空间现有数据，不执行清空；新增任务字段缺失时按空值处理。

**需求池备份（`BackupData.BackupDemand` / `demands[]`）**：`plannedStart`、`plannedEnd` 为可空的 `yyyy-MM-dd` 字符串，与 `expectDate` 独立；导出保留实际计划日期，旧备份缺字段 / null / 空白按空值处理，不从任务或版本日期推导，允许只填一端。导入保留 `canceled` 状态；原始无目标的 `plan` 保留 `plan` 状态与计划起止；原始显式非空目标 `versionId` 按版本 ID 重映射后校验同项目，目标丢失 / 映射无效时置空，仅此类 `plan` 按原规则回到 `pass` 并清空计划起止，不把已取消需求恢复为已通过，也不自动重排关联任务。所有非空计划日期的格式及 `plannedStart ≤ plannedEnd` 在任何覆盖删除前校验；非法日期或倒置区间返回 400，目标映射失败也不能跳过日期校验，原空间数据不被删除。

字段兜底：旧列 id（todo/review）自动映射、非法枚举取默认值、超长字段截断、无效项目/需求/分支引用置空、无效模块引用置空或回落项目默认模块；`subtasks`/`tags`/`recurType`/`remindAt`/`remindSent`/`timeLogs`（含计时人 userId）/`createdAt`/`columns` 导入时自动恢复，旧版备份（无这些字段）依旧兼容。

**导出不含**：附件文件本身（磁盘文件，随服务器备份目录 tar 保留，见 `deploy/backup.sh`）、操作时间线日志（导入时不会被删除）、完成归档快照（导入时按任务与工时重建）、分支操作时间线。需求文档历史快照与需求流转日志不在备份里，但覆盖导入时**保留现有记录**；同空间导入通常复用文档/需求 ID，跨空间导入可能留下无法对应的历史记录。测试计划不在备份里，导入时保留；同空间导入会复用测试用例原 ID，跨空间用例重新生成 ID 时计划圈选可能悬空。

## 19. POST /api/notify/test

立即对当前空间执行一次提醒推送（手动测试用，**仅空间主**）。需先在「空间设置」中配置该空间的推送 webhook。

```json
{"code":0,"data":{"sent":true,"content":"【开发工坊】任务提醒 2026-10-14\n逾期 2 项：..."}}
```

无逾期与今日到期任务时返回 `{"sent":false,"reason":"当前无逾期或今日到期任务，静默跳过"}`；手动测试（force）模式下即使为空也会发送一条测试消息。渠道由 `NOTIFY_TYPE` 决定：`webhook`（企微/钉钉，报文 `msgtype:text`）/ `serverchan`（Server酱，URL 里带 key，报文 `title/desp`）/ `pushplus`（报文 `token/title/content`，token 配 `NOTIFY_TOKEN`）。**pushplus 渠道下统一 token 只发送到官方固定端点（`https://www.pushplus.plus/send`），空间设置里的地址仅作为"启用推送"开关**；其余渠道的空间地址保存与发送时都会校验（仅 http/https，拒绝本机/内网地址），服务端不跟随重定向。推送结果以渠道**明确返回的成功码**为准（`errcode=0` / `code=0` / pushplus `code=200`）；HTML 错误页、空响应、跳转等无法确认成功的响应按失败处理，任务级提醒会保留在原 6 小时窗口内重试。超过 6 小时重试窗口仍未发出的提醒会被标记为已处理并在任务时间线记「提醒时间已过（超过 6 小时重试窗口），未推送」；未配置 webhook 的空间同样参与过期处理（记「提醒时间已过，空间未配置推送渠道，未推送」），不会永久静默挂起。

## 26. 工时计时

- `GET /api/tasks/{id}/timer` → `{"running":false,"startedAt":null,"elapsedMinutes":0,"totalMinutes":45,"myTotalMinutes":30}`（`running/elapsedMinutes` 为"当前登录人"在该任务的计时状态；`totalMinutes` 为该任务全部成员的累计）
- `POST /api/tasks/{id}/timer/start` / `POST /api/tasks/{id}/timer/stop`（开始/停止仅作用于"我自己"；任务整体结算见下）
- `GET /api/tasks/{id}/timer/records` → 该任务的工时记录（已结束的计时 + 手工补记，按时间倒序最多 50 条）：`[{id,userId,userName,origin,minutes,date,startedAt,endedAt,note,mine}]`，`origin` 为 `timer`/`manual`；`startedAt/endedAt` 为计时原始起止时间，补记则使用所选日期的占位时间；仅 `timer` 的 `minutes` 按工作日、个人工作时段与每日剩余额度裁剪，`manual` 不套用这些裁剪规则
- `POST /api/tasks/{id}/timer/manual?forUserId=&date=yyyy-MM-dd&minutes=&note=` → 手工补记一条实际工时（忘开表、加班等）。项目可写者可补**任何人**（`forUserId` 空则补自己，非空须为空间成员）；补记不经过工作时段/8 小时上限的计时裁剪，只做范围校验（1 分钟 ~ 24 小时、日期不晚于今天），`started_at=ended_at=所选日期 12:00`，落库 `origin=manual`；日期落在当天仍占用该用户的计时日额度
- `DELETE /api/tasks/{id}/timer/records/{logId}` → **作废**一条已结束的工时记录（计时记录与手工补记都可作废；运行中的计时须先停止）。权限与补记一致：项目可写者。记录物理删除，任务时间线留下"作废计时记录 / 删除补记工时"的审计文字
- 作废后所有统计直接读 `time_log` 自动按实际工时重算；任务若已有完成快照，服务端同步重算 `total_minutes / first_started_at / last_ended_at`（历史快照用 `sql/46_refresh_completion_minutes.sql` 一次性对齐）
- 计时按**人**归属（`time_log.user_id` = 计时人）：开始新计时只自动停止"我自己"其他任务上已可见的运行中计时，不影响他人；单次计时按「每个工作日的工作时段 + 每人每天上限（默认 8 小时）」折算，忘停表时不会把夜间与周末计入，也不会超过当天剩余额度；任务完成（移入已完成）或删除时自动停止并结算**该任务上全部成员**的计时；统计报表的工时只统计"我"在当前空间的记录
- 备份往返：`BackupTimeLog` 含 `origin`/`note`；旧备份缺 `origin` 的按 `timer` 回填

## 29. 邀请链接（共享空间协作）

账号仍由管理员创建下发（**不提供自助注册**）；邀请链接用于把**已有账号**的同事拉进共享空间：对方打开 `/join.html?code=XXXXXXXXXX` 后，已登录则一键加入；未登录先登录（登录后自动回到该页完成加入）。个人空间不可邀请。

- 生成：`POST /api/workspaces/{id}/invites`（空间主 / 管理员）→ `{id, expiresAt, grantCount}`；邀请码为 10 位大写字母数字（去掉易混淆字符），有效期 **7 天**。body 可选 `{"grants":[{"projectId":"p1","access":"write"}]}` 预分配新成员的项目权限；`access` 只接受 `write` / `read`，重复与 `none` 会被忽略，未列出的项目加入后不可见
- 列表：`GET /api/workspaces/{id}/invites`（空间主 / 管理员）→ `PageResult<{id, workspaceId, createdBy, expiresAt, usedCount, createdAt, writeGrantCount, readGrantCount}>`；后两项为该邀请预分配的「可参与 / 只读」项目数
- 撤销：`DELETE /api/workspaces/{id}/invites/{inviteId}`（空间主 / 管理员）；与加入共用邀请行锁，撤销与加入并发时二者只有一个成功，已撤销的邀请加入返回 404。删除空间时邀请与预分配一并清理，删除项目时清理指向该项目的预分配
- 查看（公开）：`GET /api/invite/{code}` → `{workspaceName, inviterName, expiresAt, writeGrantCount, readGrantCount, alreadyMember}`；带登录态访问且已是该空间成员时，额外返回 `workspaceId` 供直接进入（未登录或非成员不返回空间 ID）。无效/已撤销 404，过期 400
- 加入（需登录）：`POST /api/invite/{code}/join` → `{workspaceId, workspaceName, already, grantCount}`；`already=true` 表示原本就是成员（幂等，不再计数，也不会覆盖其现有项目权限）；首次加入时在同一事务内写入成员身份与邀请预分配，项目已删除的预分配自动跳过。并发加入按「邀请行锁 → 用户行锁」顺序串行化，同一用户重复提交只计一次
- `usedCount` 在每次成功加入时 +1；邀请码大小写不敏感（统一转大写查询）；多用途链接对每位新加入者应用同一组预分配
- 安全：仅 `GET /api/invite/{code}` 为公开接口（放行见 SecurityConfig），`/join` 需登录；建议在 nginx 对邀请路径同样启用限速（与登录接口共用注释块）

**内置厂商**（全部 OpenAI 兼容，`baseUrl` 可改，可走中转/代理）：

| 情况 | HTTP | `message` 要点 |
| --- | --- | --- |
| 配置不完整、自定义地址不合法 | 400 | 指出缺哪一项或地址问题 |
| 上游返回 4xx/5xx | 502 | 按状态码翻译；上游原文附在括号里 |

### 31.2 拆分与体检

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/ai/reqdoc/{id}/split?maxTasks=8` | 拆成任务**草稿**（不落库） |
| POST | `/api/ai/reqdoc/{id}/audit` | 完成度体检 |
| POST | `/api/ai/reqdoc/{id}/tasks` | 把勾选的草稿创建成任务 |

`split` 返回 `{reqDocId, reqDocTitle, docChars, tasks:[{title,description,priority,dependsOnIndex,reason}], usage}`。
喂给模型的是**已保存的正文**（转纯文本，保留段落/列表/表格行），超过 12000 字会截断并在 prompt 里注明；
同项目已有任务标题作为 few-shot 参考命名风格。

`audit` 返回 `{coverage, verdict, summary, nextStep, totalPoints, donePoints, doingPoints, todoPoints, missingPoints, points:[{point,covered,status,taskTitle,note}], tasks, usage}`。

**分工是刻意的**：AI 只负责"把需求拆成可验证的功能点"和"给每个点找覆盖它的任务"；
`coverage` 与 `verdict` **由服务端按规则算**，不让模型打分：

```
coverage = round((done×1 + doing×0.6 + todo×0.3 + missing×0) / total × 100)
verdict  = coverage>=95 且 missing==0 → done
         | coverage>=70 → mostly
         | coverage>=30 → partial
         | 否则 → not_started
```

理由：模型直接给的分"看起来合理但没法解释"，也无法保证"有缺失就不会说做完了"。

`tasks` 逐条创建，单条失败不影响其它条，返回 `{created, skipped, failed:[{title,reason}]}`；
与已有任务**同名会跳过**（避免重复建）。

**注意**：这些接口是长请求（模型生成通常 20-60 秒），nginx 的 `proxy_read_timeout` 必须大于 120 秒，否则前端拿到 504。

### ⚠️ 为什么不用 `start_date` 算工期

**开始日期是"什么时候接到的"，不是"什么时候动手"。** 一个任务可能今天创建、下周才真正开工，
`[开始, 完成]` 之间的跨度里大部分是排队等待 —— 拿它算效率只会得出"我干活很慢"的错误结论。

唯一的可比基准是两个数：

| | 来源 | 说明 |
| --- | --- | --- |
| **预估** | `task.estimate_minutes` | 人自己填的，单位分钟（表单用小时，0.5 步进） |
| **实际** | `time_log.minutes` 累计 | 自动计时按工作日、个人时段及每日剩余额度折算；手工补记不按这些规则裁剪，需核对来源与记录 |

`start_date` / `due_date` 仍然只用于日历排布与逾期判断，**不参与任何效率计算**。

### 口径

- **系数 = Σ实际 / Σ预估**（不是"平均每个任务的比值"）。后者会让"预估 0.5h 实际 2h"（4 倍）的小任务
  和"预估 40h 实际 60h"（1.5 倍）的大任务等权重，结论会被小事带偏。
- **只统计已完成任务**：进行中的实际值还不完整，算进去会显得"总是高估"。
- **偏差分档**：实际/预估 `< 0.85` 高估 / `0.85~1.15` 准确 / `> 1.15` 低估。
- **预警只看进行中**（非 `backlog`、非 `done`）且 `实际/预估 ≥ 0.8`：`≥ 1.0` 记 `danger`（已超），否则 `warn`（接近）。
  `backlog` 里的任务还没开工（实际 0），预警没有意义。
- `estimate_minutes` 为 `null` 或 `0` 一律视为"没估"，不参与任何统计；保存时也统一存 `NULL`。

## 已接受的现状口径（按设计如此，非缺陷）

以下行为是当前版本有意保留的设计边界，使用/验收时按此预期判断：

1. **会话与权限快照**：登录会话 30 天有效，角色写在会话里。管理员**重置密码/调整角色/删除账号不会踢掉旧会话**（无会话注册表）；但 `/api/admin/**` 每次请求按数据库当前角色复核，被降权或删除的管理员立即无法再调用管理接口；`/api/auth/me` 也读取数据库实时角色。普通接口的权限变化在下次登录（或会话过期）后完全生效。
2. **任务并发写为"最后写入生效"**：多人同时编辑同一任务不做版本校验/冲突提示，后提交的整体覆盖先提交的（实现范围约定，界面无冲突弹窗）。
3. **JSON 导入导出不做全量恢复**：导出包含需求文档正文、分支与其他工作数据，但不含附件二进制、操作时间线或完整正式发布证据；导入覆盖工作数据（任务/项目/评论/需求文档/分支等），保留附件文件/记录与时间线（保留的附件/日志按"空间+任务ID"关联，同空间原样导回会重新挂回原任务）。
4. **文件与数据库无两阶段一致性**：附件删除为"先删文件、后删记录"（或相反顺序的单边提交），极端故障下可能出现孤儿文件或失效引用；失败会写服务端告警日志，不做补偿任务。
5. **同账号计时串行化**：开始和停止计时在事务内锁定账号行，同一账号跨任务、跨设备的计时操作串行执行，避免重复运行记录和重复结算；不同账号之间互不影响。

4. **提醒扫描按空间/按任务隔离异常**（复评 R-4）：任一空间或任一任务出错只跳过该条，不再中断整轮扫描（原实现一个 try 包住所有空间）。
5. **任务级联删除补齐评论与通知**（第九轮 #1/#2）：彻底删除任务（`DELETE /api/tasks/{id}/purge`、回收站每日自动清理）、清空空间、覆盖导入三处，都会一并删除 `task_comment` 与 `app_notification` 中该任务的记录。

   - 导入口径：评论与通知**跟随任务删除**，与"操作时间线保留"有意区分 —— 时间线是审计记录，评论/通知会把内容直接展示给用户，留着就是可见的数据错乱。

9. **启动兜底的事务语义**（第九轮 #7）：`ensureDefaults` 改为通过自身代理调用 `ensureDefaultsFor`，实现**每个空间一个独立事务**（此前 `@Transactional` 因同类自调用而失效，等于每个 mapper 各自提交）。

`GET /api/review` 的 `progressTasks` 原来只判断 `progressOf(t) > 0`，而 `TaskCalc.progressOf` 对**已完成列的任务一律返回 100** —— 于是已完成的任务会同时出现在「本周完成」和「推进中」两个区块里，读起来就是同一件事写了两遍。

现在三个区块严格互斥：

| 字段 | 口径 |
| --- | --- |
| `completed` | 已完成列，且 `completed_at` 落在本周期 |
| `pendingDone` | **未完成**列但进度 = 100%（单独成组，提醒去归档） |
| `progressTasks` | **未完成**列且 0 < 进度 < 100 |

响应结构不变，只是 `progressTasks` 的条数会变少（不再含已完成与进度 100% 的）。

> 已知局限（**部分已修，见 v1.5**）：`progressTasks` 取的是**当前**进度，不按周做历史快照。看历史周期时已按"那一周有活动"收敛（v1.5），但"进度数字"仍然是现在的值，不是上周结束时的值 —— 要精确到周需要每次改动都记录进度历史，属另一个量级的改造。

### 5. 补丁（v1.5）：历史周期的「进行中」按周收敛

**问题**（用户实测反馈）：切到「上一周」时，「进行中」面板仍然列出**当前**进行中的任务 —— 包括这一周才创建 / 才拖进进行中的任务，等于把本周的工作算进了上周。

**原因**：`progressTasks` 是"当前状态"，与周期无关。

**修法**：`GET /api/review` 在 `weekOffset < 0`（历史周期）时，对 `progressTasks` 再做一次收敛：

> 只保留「**该周期内有日志活动**」（`task_log.created_at` 落在周期内）**且**「周期结束时任务已存在」（`created_at <= 周期结束日`）的任务。

- **本周（`weekOffset == 0`）不收敛** —— 「进行中」就该是"我现在在做的事"，不受"本周有没有动过"限制；
- 没有状态快照，用日志近似还原。因此「上周开工、这周一直没碰」的任务在本周视图里仍然出现（符合直觉），在更早的周期里则按"那一周动过"判断；
- 新增 `TaskLogMapper.selectActiveTaskIds(workspaceId, from, to)`（`DISTINCT task_id`，排除 `CFG` 哨兵事件）；
- `ReviewResponse` 结构不变。

**仍存在的局限**：进度数字仍是当前值；"上周拖进进行中、本周已完成"的任务只会出现在「本周完成」里，不会同时出现在上周的「进行中」。

### 6. 补丁（v1.6）：日历里提前完成的任务不再往后铺

**问题**（用户实测）：任务 5 号开始、25 号截止，12 号就做完了，但日历从 13 号到 25 号仍然每天显示它。

**原因**：日历区间是 `[start_date, due_date]`，没有考虑 `completed_at`。

**修法**：引入"**实际结束日**"概念：

> `实际结束日 = (已完成 && completed_at < due_date) ? completed_at : due_date`

| 位置 | 处理 |
| --- | --- |
| `GET /api/calendar` | 用实际结束日判断"与本月是否有交集"，提前完成的任务不再因为 `due_date` 在未来而被返回 |
| 前端 `calRangeOf(t)` | 日历格子铺开、右侧当日列表的区间判断都用同一个函数；已完成任务的 chip 带 `done` 样式（划线），悬停提示显示「已完成 10-12」而不是「进行中，截止 10-25」 |
| 边界 | `completed_at` 为空（历史数据）→ 退回 `due_date`，行为与升级前一致；"取消完成"会把 `completed_at` 置空，区间自动恢复满铺 |

`CalendarResponse` 结构不变。

### 7. 补丁（v2.0）：停表后自动接力 + 每天 8 小时口径确认

#### 7.1 完成 / 暂停后自动接力计时

**问题**（用户实测）：正在计时的任务被拖进「已完成」或「待测试」后，表停了，但「进行中」列还有别的任务，却没有任何一个在计时 —— 得手动再去点一次。

**规则**：以下场景停表后，调 `TimeLogService.resumeInColumn(userId, workspaceId, 原列, 刚停表任务)`：

- `move` / `update` 把任务改到「已完成」
- `move` / `update` 把任务移到不可计时列（待测试 / 等待接续 / 执行结束）
- 用户手动点「停止计时」

| 条件 | 行为 |
| --- | --- |
| 我当前**还有**运行中的计时（比如别的空间的任务） | **不接力** —— 不能把别的任务抢掉 |
| 刚停表的任务不来自「进行中」列 | **不接力**（只允许进行中列接力） |
| 进行中列还有其他任务 | 按 `sort_order` 取**第一个负责人是当前账号、可写且未阻塞**的任务开始计时（复用 `start()`，含"个人同时只计一个"） |
| 进行中列没有属于当前账号的可接力任务 | 不接力，绝不把计时开到别人的任务上 |

`POST /api/tasks/{id}/move` 与 `POST /api/tasks/{id}/timer/stop` 响应新增 `autoTimerTask`（接力上的任务名，没有则为 `null`），前端在完成/停表提示后追加「· 已接着开始「X」的计时」。

**注意**：接力**只接当前账号自己的任务**，并且只在「进行中」列发生；不会把计时开到他人的任务上。这是对 spec G.5 的修正口径。

#### 7.2 每天 8 小时是「整天合计」，不是「每个任务各 8 小时」

**确认：已经是整天合计口径**，代码在 `WorkTime.effectiveMinutes()`：

```java
int used = usedMinutesOn.applyAsInt(day);          // 当天已记录的工时
int quota = Math.max(0, MAX_MINUTES_PER_DAY - used); // 480 - used
total += (int) Math.min(minutes, quota);
```

而 `usedMinutesOn` → `sumMinutesByUserOnDate` 的 SQL 是：

```sql
SELECT COALESCE(SUM(minutes), 0) FROM time_log
WHERE user_id = #{userId} AND ended_at IS NOT NULL AND DATE(started_at) = #{date}
```

**只有 `user_id` 和日期**，不限 `task_id`、不限 `workspace_id` —— 所以同一天多个任务共用 480 分钟额度，跨空间也算在一起。

实测（`WorkTime` 单测）：同一天三个任务各 200 分钟 → 记 200 + 200 + **80** = 480；额度满后再计 → 0；换一天重新有 8 小时。

## 附录 · 2026-10-26 分支管理（v3.2 增量）

### 1. 分支池：空间级公共分支 + 可选项目归属

分支池按空间维护，同时支持两种归属（`sql/31_branch_project.sql` 增量迁移）：

- `dev_branch.req_id` 为空 = **空间级公共分支**（历史数据默认落在这一档，行为与升级前一致）；
- `dev_branch.req_id` 非空 = **项目级分支**，直接归属 `requirement.id` 对应的项目。

不在分支上强制项目：主干、发布、跨项目的 feature 本来就会共用，强行切分会逼人重复建分支。
建任务时「所属分支」按当前项目过滤：直接归属该项目的分支 + 空间级公共分支（再按任务推导归属兜底），
避免不同项目的同名分支混在下拉里。表：`dev_branch` / `dev_branch_log`。

### 2. 状态与时间口径（两套，各管一件事）

状态：`dev`(开发中) → `testing`(待测试) → `merging`(待合并) → `released`(已发布)。
**允许任意方向切换**：现实里「待测试被打回开发中」很常见，强行单向只会逼人删分支重建、把历史丢掉。

| 记录位置 | 记什么 | 用途 |
| --- | --- | --- |
| `dev_branch.dev_at / test_at / merge_at / released_at` | **首次**进入该状态的时间（`COALESCE` 写入，回退不覆盖） | 算停留时长、发布周期（`released_at - created_at`） |
| `dev_branch_log` | **每一次**变更：动作、从哪到哪、谁、什么时候、附带说明 | 详情抽屉的操作记录；回答「谁把它退回了开发中」 |

新建时按初始状态盖上第一个时间点（默认 `dev` → `dev_at` = 创建时间），其余留空。
状态没变时不写日志（点错一次不该多一条噪音）。

### 3. 接口

| 接口 | 说明 |
| --- | --- |
| `GET /api/branches` | 分支列表。`?project=` 时返回「直接归属该项目 + 空间级公共分支」：公共分支按任务推导归属过滤，尚未关联任何任务的公共分支对所有项目可见；附带 `taskCount` / `doneCount`（排除回收站任务、只统计可见项目）与 `projects` 推导标签；排序 `FIELD(status)` + `updated_at DESC` |
| `GET /api/branches/{id}` | 详情（同一个实体） |
| `GET /api/branches/{id}/logs` | 状态变更时间线，倒序 |
| `GET /api/branches/{id}/tasks` | 挂在分支上的未删除任务（未完成在前） |
| `POST /api/branches` | 新建。body：`{name, status?, reqId?, targetBranch?, owner?, ownerUserId?, note?}`；`reqId` 空 = 空间级公共分支 |
| `PUT /api/branches/{id}` | 改基础信息（名字 / 所属项目 / 负责人 / 目标分支 / 备注）。**`status` 字段被忽略**；`reqId` 传空串表示退回空间级公共分支，不传（`null`）表示不改 |

校验口径：

- 分支名 `^[\p{L}\p{N}._/-]{1,80}$`（字母含中文、数字、点、下划线、中划线、斜杠；空格与 `@{}~^:?*[\` 本来 git 也不接受），同一归属维度内**唯一**（同项目不允许同名，不同项目允许；空间级公共分支之间不允许同名）；
- `reqId` 非空时必须是**本空间**的项目，否则 400「所属项目不存在」；
- `targetBranch` ≤80、`note` ≤200；
- 不填负责人 = 当前用户（与需求模块一致）。

> 为什么把「改状态」单独开一个接口：如果允许 `PUT` 顺手改 `status`，就会出现「改了状态但没走时间线/时间点」的
> 数据，统计和追溯立刻对不上。编辑弹窗里因此**不显示状态字段**。

### 3. 行为变化

1. **评论通知分层**：被 @ 的人优先收到 `task_comment` 通知；负责人若已被 @ 就不再重复收评论通知；任务关注者收到评论、列流转、移入回收站/恢复通知。字段编辑不再单独通知关注者（每次保存都会产生，属于高频打扰），操作者本人永远不会收到自己触发的通知。
2. **通知中心聚合**：前端把**同一任务 + 同一类型**的连续通知合并为一条（显示 `×N`），点击时整组标为已读；接口仍返回原始通知列表，聚合只发生在前端。
3. **站内通知保留期**：每天 03:20 清理超期 `app_notification`，默认 90 天，可用 `app.notification.retain-days`（环境变量 `NOTIFICATION_RETAIN_DAYS`）调整；跨空间统一执行，不影响 `task_log` 审计记录。
4. **邮件深链**：配置 `app.mail.base-url`（含 context-path，如 `https://host/hourglass/`）后，任务类通知邮件正文追加 `#/board?task=<id>` 深链；新建账号的欢迎邮件追加登录地址。未配置时不附链接，避免出现半截地址。
5. **关注关系清理**：任务彻底删除、清空空间、覆盖导入、账号删除、成员退出/被移出空间都会一并清理 `task_watch`；任务移入回收站时关注关系保留，恢复后继续生效。重新加入空间后需重新关注。

### 1. 权限与身份

所有写操作均要求项目可写；viewer、项目 read / none 无权。管理者为 workspace owner/admin 或项目 `ownerUserId` 对应账号且可写，身份不按 `displayName` / `owner` 文本识别。

| 操作 | 权限 |
| --- | --- |
| 需求 pass / rej / unpass / reopen | 仍仅 workspace owner |
| 需求 plan / replan / unplan / cancel / restore、发布计划维护 | 管理者 |
| 发布管理、版本 release-preview / release（含 redeploy / rollback） | 仅管理者，服务器提交时重新检查；任务负责人无整版本权，计划 ownerUserId 元数据不赋权 |
| 任务显式改版 | 管理者，或该任务 ownerUserId 对应账号且可写；不得修改成功事实冻结的关联 |
| 任务发布徽标 | 只读，由成功 production 实际记录推导，无人工 publish / unpublish |
| 计划、记录与历史读取 | 当前空间 / 项目可见；任务记录还校验当前任务及历史记录所属项目可见 |

`releasedBy` 必须为服务器当前登录者，不接受客户端冒充；executorUserId 仅记录实际执行人。发布事实不锁任务完成 / 回退 / 计时。

### 2. 需求排期

`DemandSaveRequest` 创建 / 待评审编辑使用 `reqId,title,description,source,itemKind,categoryId,priority,expectDate,plannedStart,plannedEnd,acceptText,wsjfBusiness,wsjfUrgency,wsjfRisk,wsjfEffort,revision`。目标版本可暂不指定，保存 DTO **不含 versionId**，排期 / 调期通过动作设置或清空目标。编辑带 revision；创建由服务端初始化 0。`plannedStart/plannedEnd` 为日期，与 `expectDate` 独立；两端都填时开始不得晚于结束。

`POST /api/demands/{id}/{action}` 返回 `Demand`：

| action | 状态与 body |
| --- | --- |
| plan | pass → plan，`{versionId,plannedStart,plannedEnd,priority,expectDate,note,revision}`；当前 revision 必填，versionId 可为 null（暂不指定目标版本）；选定目标时须同项目且未发布 |
| replan | plan → plan，同上；versionId 可为 null 以清空目标，仍属调期并保留 plan；note 原因与当前 revision 必填；计划日期省略 / null 可清空，绝不改旧任务 |
| unplan | plan → pass，`{note,revision}` 必填，清目标版本与计划起止 |
| cancel | review/pass/plan/rej → canceled，`{note,revision}` 必填；保留需求、目标版本、计划起止与历史，不取消 / 删除任务；目标引用仍参与版本删除保护 |
| restore | canceled → pass，`{note,revision}` 必填，清目标版本与计划起止，需重新排期 |
| pass / rej / unpass / reopen | 评审链路；可带 `{note,revision}`，提供 revision 时校验；rej 必填拒绝原因。与 canceled 的 restore 不是同一动作 |

`DemandActionRequest` 原因字段是 **note**，不是 reason；日期为 `yyyy-MM-dd`，priority 为 P0/P1/P2/P3，revision ≥ 0。plan / replan 允许 versionId=null，当前 revision 必填；选定目标时须同项目且未发布；清空目标仍调期，须 note 原因；冲突返回 409，刷新后重试。需求调期 / 撤排 / 取消 / 恢复不自动改任务版本、日期或状态；同一需求关联的多个任务可以跨版本。

### 3. 任务当前计划版本与只读发布字段

仅 Task 与版本改为 M:N；`TaskSaveRequest.versionIds` 保存 `version_task` 的当前计划集合，目标须同项目，**不是实际发布证据**。Demand / TestPlan 保留单目标 `versionId`，不扩展成数组。保存仍带 `versionChangeReason` 与 `oldUpdatedAt` 防并发覆盖。

| versionIds 输入 | 保存语义 |
| --- | --- |
| 省略 / null | 保留现有集合；新建默认空集合，不根据 demandId 或需求目标隐式改绑 |
| `[]` | 显式解绑；实际变更须原因与管理者或该任务负责人可写权限 |
| 非空数组 | 显式设置同项目版本集合；实际变更须原因与相应权限，不以空串代替数组 |

任务读取与 POST / PUT 保存响应返回实际落库的 `versionIds` / `versionNames` 数组及 `tags`；按最终项目 / 负责人重新判断可写权限。版本成功事实形成后内容关联冻结，不能以回滚或撤标解锁；**任务完成、回退、计时不受发布锁定**，按原流转与权限规则执行。冻结关联与历史证据不得因改项目 / 需求 / 版本或删除而破坏。

只读任务字段：`publishedAt,publishedReleaseId,publishSource,everPublished,publicationState,publicationTargets`；发布来源固定 `record`，仅成功 `production` deploy / redeploy 记录参与生产发布推导。`publicationState` 取 `unpublished / effective / partial / rolled_back / unknown`，表示未发布、有效、部分有效、引用范围已回滚或证据未知；结合目标覆盖理解，不把 unknown 当 full。test/staging 成功或 failed 事件不代表生产发布。badge 不是 `boardColumn` 新值，也不授权人工标记 / 撤标；旧 `canPublish/canUnpublish` 不得作为人工发布入口。

`DELETE /api/versions/{id}` 不会自动解绑：已发布或有实际尝试（含失败）、有任务绑定（含回收站）或需求目标引用（含 canceled）返回 422。无证据版本先按权限有因调整引用；回收站任务先恢复、已取消需求有因恢复以清目标。删除不得清除历史证据，也不存在「先撤徽标即可删除」的路径。

**发布日程**：`GET /api/release-plans` 只读汇总，`status=open` 表示草稿 + 就绪，`all` 或缺省表示全部；`from/to` 为计划时间区间（含首尾日）。归档项目不进入结果，普通成员按项目可见范围过滤，owner/admin/viewer 全量可见；返回行含 `projectName,projectNames,versionName,versionNames,versionCount,versionStatus,plannedAt,environment,coverage,status,ownerName,plannedTaskCount`，不含计划任务明细。跨版本 / 跨项目计划在 `projectNames` / `versionNames` 列出全部成员，`projectName` / `versionName` 为主版本展示值。

**Plan 字段**：`id,revision,versionId,versionIds,plannedAt,ownerUserId,status,notes,risks,reason,plannedTaskIds,environment,targetKeys,coverage`。`versionIds` 为计划覆盖的版本集合，可跨版本 / 跨项目（≤50），当前版本必须包含；`versionId` 保留为主 / 展示版本。写入须覆盖全部版本所属项目的管理权限；历史计划若没有关联行，按 `versionId` 单版本处理。可写状态为 `draft / ready / canceled`，`completed` 仅由全部包含版本的成功生产事实产生并且只读。ready 需计划时间、负责人与至少 1 个工作项；调整 ready 或取消需 reason，更新必须匹配所选计划 revision。notes ≤2000、risks ≤1000、reason ≤500。环境为 `production / staging / test`；`targetKeys` 是数组，覆盖为 `full / partial / unknown`。完成计划不可修改；后续另建计划，紧急无计划事实必须填写 deviationReason，不能倒改完成计划。

**时间语义**：Plan.plannedAt 为 LocalDateTime 本地墙钟，前端不先转 UTC 再丢偏移；显示补齐零秒不导致 planDirty 误报，未改变时保留原值。ActualContext.occurredAt 为带 offset 的实际时刻，服务规范化 UTC；date-only 信息仅显示日期、不伪造时间。

**三范围**：版本内容关联、计划 `plannedTaskIds`、实际 `actualTaskIds` 独立保存；计划范围取所选版本内容并集，实际范围始终只属于当前版本，也不以计划自动替代实际事实。一个版本生产只成功部署一次：已有成功生产事件时不得更换制品，补丁须新建 hotfix 版本；同一制品可 redeploy，可对成功事件 rollback。计划完成要求其全部关联版本都有关联同一计划的成功生产 deploy / redeploy，test/staging、rollback 与部分成功不完成计划；无关联行的历史计划按单版本处理。UI 明列 selected / omitted 两组及未选理由。

**ActualContext 字段与约束**：

| 字段 | 语义 |
| --- | --- |
| `planId` | 可选；紧急无计划必须 `deviationReason`，有计划则明确选定，不静默取最新 |
| `occurredAt` | 实际发生时间，带 UTC offset 的 ISO 8601（如 `2026-11-10T14:30:00+08:00`）；与服务器写入时间 `recordedAt` 分开，不再以仅日期 publishedOn 代替 context |
| `environment` | `production / staging / test` |
| `targetKeys` | 显式目标数组，与环境共同限定有效引用范围 |
| `coverage` | `full / partial / unknown`，未知不得冒充全量 |
| `artifactRef` / `artifactDigest` | 制品引用 / 64 位十六进制 SHA256，不用普通版本名代替制品证据 |
| `operation` | `deploy / redeploy / rollback` |
| `relatedReleaseId` | 关联实际事件；redeploy / rollback 明确所关联记录，rollback 仅撤销该记录在指定目标的引用范围 |
| `executorUserId` | 实际执行人元数据，不赋权，不替代提交者 releasedBy |
| `actualTaskIds` | 必须显式提供的唯一任务 ID 数组，最多 500 项；不自动选全部、不静默丢弃不符合普通计划条件的事实 |
| `deviationReason` | 紧急无计划、未完成事实及其他偏离须说明；未完成事实必须管理权限与该理由 |

预览显式接收实际 context，分别呈现版本内容、计划范围和实际范围，显示计划未选 `not_selected`、候选及 warnings。已发布不能自动排除（可能 redeploy）；未完成、完成时间晚于事件、需求取消、跨范围等应显示偏离警告，不静默缩减 actualTaskIds。首版统计折算不生成事实。范围与覆盖未知必须明确呈现，不用候选百分比推断 100% 验收。

确认在同一 context 外另带 `result=success / failed`、`notes`、`failureReason`、`idempotencyKey`（非空 ≤64）、预览返回的 `planRevision` 与 `scopeToken`（非空 ≤64）；无计划时也沿用预览返回值，不自行伪造 revision。notes ≤2000；failed 必填 failureReason（≤1000）。失败只追加不可变尝试与范围快照 / 日志，不产生生产发布或完成计划；成功按显式实际范围原子写记录 / 条目 / 快照，仅当计划全部包含版本均已有成功生产部署 / 重部署且关联同一计划时才完成计划。实际版本必须属于计划包含的版本；`planRevision` 与 `scopeToken` 覆盖版本集合。发布管理权限提交时重新检查，`releasedBy` / `recordedAt` 由服务器确定，客户端不得冒充。

rollback 本身是一条新事件：按 environment/targetKeys 与 relatedReleaseId 撤销所引用范围，失败回滚不撤销；原记录、快照及 everPublished 历史保留，不抹后续不同成功、不解锁版本内容关联。任务 publicationState/publicationTargets 从成功生产事件及有效引用推导，不能只用最后一条事件或版本 released 字段判断。

`scopeToken + planRevision + idempotencyKey` 防竞态：所选计划、范围、任务 / 需求或权限变化需复核、冲突后重新预览；同键同 body 重试返回持久化原 `VersionRelease`，同键不同内容返回 409，不重复落证据。**响应未知不等于失败**：sessionStorage 保留完整原 body/key，刷新 / 重开先 GET release-records?key=... 查询；查询失败不清请求、不生成新键、不盲重试。查到并核对一致记录后不重复创建；查询成功且无记录才允许显式重试原完整 body/key，明确拒绝也须先查询再显式重置、重新预览。最终 Chrome 恢复 27 断言 / 3 场景覆盖响应丢失、请求丢失及之后页面刷新 + 查询失败。

记录返回本次实际 context、result、planId/planRevision、server recordedAt/releasedBy、idempotencyKey、版本 / 计划 / 实际范围快照及 items；任务标题 / 负责人、需求与目标、完成时间、工时等历史信息读快照，不从当前对象补齐而漂移。记录、成功说明与快照 CSV 按事件读取；release-history 只查询，不提供发布历史 JSON 导出。

`GET /api/versions/stats` 将当前 taskCount/doneCount/workMinutes 与版本 / 计划 / 每次实际快照、覆盖和当前有效目标分开；实际交付与当次未选范围不等于当前剩余。M:N 关联和多事件不得放大全局工时。无正式记录显示 `no_release_record` / 未知证据，不把缺少证据当零交付或 full。需求取消不抹实际快照，零任务不能 100% 验收。`uniqueProductionTaskCount/effectiveProductionTaskCount` 分别表示生产曾交付去重数和当前生效数，与事件处理项次分开展示，不推断待交付数。移动端关闭按钮保持 sticky 可达；具体验证时点与 SW 版本见更新日志发布记录。

## 附录 · 2026-11-10 项目授权：新成员默认不参与 / 邀请预分配

### 1. 行为口径

- `workspace_member.project_access_mode` 区分两种成员口径：
  - `all`：默认参与。改动前的存量成员全部保留该值，升级后行为不变；没有 `project_member` 记录的项目仍然可见可写。
  - `assigned`：按项目分配。新成员通过邀请加入、或由平台管理员按登录名直接加入时使用；没有显式 `write` / `read` 的项目一律不可见。
- 新成员加入时默认不参与任何项目。邀请链接可在生成时预分配项目权限（只接受 `write` / `read`），加入时在同一事务内落库；已被撤销 / 已删除的项目授权自动跳过。
- 已是成员的人再次打开邀请链接时返回 `already=true`，不重复计数，也不覆盖其现有项目权限。
- 成员建新项目时：创建者获得该项目的 `write`；同一空间内其他 `assigned` 成员获得 `none` 种子行，默认看不到这个新项目。`all` 成员、空间主 / 管理员与查看者不受影响。
- 三档权限口径：`write` = 可参与（可查看、可编辑），`read` = 只读，`none` = 不可见。存量兼容码值 `pm` / `dev` / `qa` 继续归一到默认参与，不改变历史数据。
- 单格保存的 `access` 传空表示恢复该成员的默认口径：`all` 成员回到默认参与，`assigned` 成员回到不可见。
- 分配项目时，只有实际变化的单元格计入审计摘要与通知；批量提交一次只写一条配置记录、一条审计、一条系统通知。

### 2. 数据库

- 新增迁移 `sql/66_project_access_assigned.sql`（幂等）：
  - `workspace_member.project_access_mode varchar(16) NOT NULL DEFAULT 'all'`
  - `invite_project_grant(invite_id, workspace_id, project_id, access, created_at)`，主键 `(invite_id, project_id)`
  - 为 `assigned` 成员补齐 `project_member.access='none'` 种子行，仅补缺、不覆盖已有授权
- 完整基线同步为 55 张表（68 新增 `project_member_role`）；`project_member.access` 增加显式 `write`，既有列表 / 搜索 / 甘特 / 导出继续用「不存在 `none` 记录」过滤，无需逐处改 SQL。

### 3. 兼容与边界

- 不传 `grants` 生成邀请链接的行为与旧版一致，只是新成员加入后默认看不到项目，需要再加入后分配。
- 项目级权限不因项目负责人、任务负责人、创建人、显示名而提升；`assigned` 成员即使负责某个任务，没有显式授权仍看不到该项目。
- 通知与搜索沿用既有的可见性过滤：不可见项目不投递通知、不出现在提及候选与搜索结果中。
- 本次无线上数据改写；生产环境须先执行 `sql/66_project_access_assigned.sql` 再启动新 jar。
