## 0. 结论摘要

1. **问题不在层级深，而在入口宽**：导航最深只有 2 层（分组 + 项），但 17 个平级入口把"需求池、文档、测试、分支、版本、分析、报表、负载、风险"等对象逐个搬成了菜单（`frontend/index.html:78-161`）。这与"小而美、范围克制、不为对标大产品堆功能"的定位（`README.md:38-47`）直接冲突，菜单读起来像"系统功能目录"，而不是"完成工作的路径"。
2. **同一个东西有多个入口**：看板/列表/日历/甘特是同一数据集的四种投影却各占一级（系统内部 `TAB_OF` 已把它们归为同一组）；项目有"项目 / 项目总览 / 项目概览 / 项目看板 / 项目驾驶舱"五个名字、两个实体；成员负载 3 处、逾期与阻塞 4 处、周度统计 4 处。
3. **两处导航正确性缺陷**：移动端"消息"打开的是临时通知面板而非页面（无深链、返回键失效）；项目详情页侧栏高亮落在"项目总览"，且无面包屑与返回列表。
4. **推荐结构**：一级 12 项、4 组——我的（我的工作 / 周回顾）、规划（需求池 / 项目 / 版本）、交付（工作项 / 文档 / 测试 / 分支）、洞察（报表 / 成员负载 / 逾期与阻塞），设置与个人设置留页脚。全部旧 hash 保留直达，不做破坏性重定向。
5. **不建议角色化菜单**：小团队产品按角色增删入口会造成"看不见的功能=不存在"。仅在设置内按权限裁剪（平台级设置单独分组）。

## 3. 竞品导航对比

> 口径：各产品公开版常驻结构（截至 2026-11）。版本迭代快，具体菜单项与命名以实际账号为准，**待验证**；本表只比较组织机制，不比较功能多少。

| 产品 | 一级组织 | 多视图放在哪 | 可借鉴 / 不适用 | 适用性 |
| --- | --- | --- | --- | --- |
| Linear | Inbox / My Issues / 团队工作区 / Projects / Views | 页内视图切换 + 命令面板，不占一级菜单 | **借鉴**：视图不是菜单；⌘K 承担"记不住在哪" | 高 |
| Jira | 顶部 Projects / Issues / Boards / Plans / Reports | 项目内左侧：Summary / Board / Backlog / Timeline / Reports / 设置 | **借鉴**项目内 tab；**不借鉴**项目容器化的重结构 | 中 |
| Asana | Home / My Tasks / Inbox + 项目与团队列表 + Goals / Portfolios | 项目内 List / Board / Timeline / Calendar / Overview | **借鉴**项目概览作为项目内 tab；Portfolios 独立成域但对象清晰 | 高 |
| Trello | Workspace → Board → List → Card | 无多级菜单 | **借鉴**"不为每个对象建菜单"；不借鉴其能力范围 | 中 |
| 飞书项目（Meego） | 空间 → 工作项 / 视图 / 度量 | 工作项类型是筛选维度，不是菜单项 | **借鉴**类型进筛选、不进导航 | 高 |
| 飞书 | 工作台（应用聚合）+ 云文档 / 任务 / 日历 / 项目各自入口 | 各域独立入口 | **借鉴**低频能力聚合到工作台；自托管单实例不适合照搬 | 中 |
| 企业微信 | 工作台（应用聚合）/ 通讯录 / 文档 / 会议 | 原生无项目管理 | **反证**：不必把每个自建能力都塞进一级导航 | 参考 |
| 飞书任务 | 我的任务 / 清单 / 订阅 / 提醒 | 单层 | **借鉴**"我的工作=聚合收件箱"（沙漏已具备） | 高 |
| 禅道（补充） | 产品 / 项目 / 执行 / 测试 / 文档 / 后台 | 菜单≈对象目录，多层级容器 | **反面教材**：沙漏当前正朝此方向增长 | 警示 |

**共性结论（8 条）**

1. 一级入口普遍 5–9 个，与团队规模无关，与"默认路径短"有关。
2. 同一数据集的多视图永远在页内，从不进一级菜单。
3. 项目详情承载项目内功能（文档/测试/版本/成员），全局菜单只放跨项目能力。
4. 统计收敛到单一"洞察/报表"域，口径同页。
5. 低频管理进设置，且与日常入口物理分离。
6. 个人工作（我的任务/收件箱）永远置顶。
7. 命令面板/搜索是"找不到菜单"的兜底，而不是补充。
8. 选中态、层级回退、面包屑必须让用户随时知道"我在哪"。

## 4. 推荐菜单结构

### 4.1 新菜单树（12 项 / 4 组）

```text
沙漏
├─ 我的
│  ├─ 我的工作   #/mine（跨空间收件箱；我的/团队）
│  └─ 周回顾     #/review
├─ 规划
│  ├─ 需求池     #/demands（看板/列表）
│  ├─ 项目       #/projects（项目列表 ↔ 全局健康度；详情=项目驾驶舱）
│  └─ 版本       #/phase（按版本/按阶段/全部项目）
├─ 交付
│  ├─ 工作项     #/board ｜ #/list ｜ #/calendar ｜ #/gantt（页内四视图，记住上次）
│  ├─ 文档       #/requirements（列表/看板/阅读/动态）
│  ├─ 测试       #/testcases（用例/测试计划/覆盖矩阵/测试报告）
│  └─ 分支       #/branches（看板/列表）
├─ 洞察
│  ├─ 报表       #/analysis + #/report 合并（趋势｜完成记录｜流程体检｜交付图表）
│  ├─ 成员负载   #/workload
│  └─ 逾期与阻塞 #/risks
└─ 页脚
   ├─ 设置       #/settings（空间｜成员与权限｜工作流｜通知与集成｜数据与审计｜平台）
   ├─ 个人设置   #/profile
   └─ 退出
```

### 4.2 排序理由（按工作路径，不按数据表）

1. **我的工作置顶**：登录默认落点即此（`router.js:220` 品牌区回首页），每天第一眼。
2. **周回顾第二**：产品主张"任务管理不是目的，工时和回顾才是"（`README.md:44`），必须比任何对象都靠前。
3. **规划 → 交付 → 洞察**：对应"做什么 → 做完 → 看结果"，与 README 主链路（需求池 → 文档 → 工作项 → 版本 → 周回顾）一致。
4. **版本进规划**：与需求池排期、发布节奏同一决策链。
5. **文档进交付**：PRD/方案/验收是执行中产生的交付物，紧邻工作项。
6. **洞察置底**：管理者按周期查看；"逾期与阻塞"靠角标提示，而非位置前置。

### 4.3 二级层次约定

| 一级 | 二级形态 | 规则 |
| --- | --- | --- |
| 工作项 | 页内 seg：看板/列表/日历/甘特 | 共享筛选与保存视图；记住上次视图；四个 hash 均直达 |
| 项目 | 列表页 seg：项目列表 / 全局健康度；详情 tab：概览/史诗/成员负载/文档/测试/版本/活动 | 详情 tab 随项目档案完善分批上线 |
| 报表 | 页签：趋势与分布 / 完成记录 / 流程体检 / 交付图表 | 共用周期选择器；旧 `stats/completions/flow/report` 全部可达 |
| 测试 | 页签：用例 / 测试计划 / 覆盖矩阵 / 测试报告 | 现状保留，仅改名 |
| 版本 | seg：按版本 / 按阶段 / 全部项目 | 名称与页签口径统一，去掉"版本阶段"混用 |
| 设置 | 6 组，组内再分块 | 空间级与平台级物理分区 |
