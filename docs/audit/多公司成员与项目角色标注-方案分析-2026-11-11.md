# 多公司成员与项目角色标注 · 方案分析（已拍板）

> 版本：2026-11-11 · 交互原型 + 方案，不含权限改造
>
> 一句话：公司标在**空间成员**上，项目角色标在**成员 × 项目**上；两者只用于展示、筛选和找人对事，**不参与任何鉴权**。

## 1. 拍板结论

本轮需求已按以下口径收敛：

| # | 问题 | 结论 |
|---|---|---|
| 1 | 是否区分内部/外部 | **不区分**。没有内部/外部类型，也没有由此衍生的权限差异 |
| 2 | 公司是空间级还是项目级 | **空间级**。一个人在一个空间只有一个公司；跨项目不重复标注 |
| 3 | 一人一项目一个角色还是多角色 | **一个主角色**。同一人在不同项目可以不同 |
| 4 | 公司用自由文本还是公司目录 | **自由文本**。输入时提示空间内已有公司名，不建公司目录 |
| 5 | 谁能改 | 公司=空间主/空间管理员；项目角色=项目负责人/空间管理员；**不做成员自助修改** |
| 6 | 谁能看 | **空间成员都可见**。公司标签不隐藏 |
| 7 | 邀请时是否预填 | **不预填**。先加入，再由有权限的人标注公司和项目角色 |

因此本方案只新增两个展示属性：**公司**（空间成员级）和**项目角色**（成员 × 项目级）。

明确不做：

- 不做多租户、不做公司隔离、不拆独立空间；
- 不新增 `company_type`，不出现「本方/客户/供应商/合作伙伴」等类型标签；
- 不建 `workspace_org` 公司目录表；
- 不改邀请规则、邀请使用次数和加入逻辑；邀请不预填公司与角色；
- 不改 `project_access_mode`、`project_member.access`、`ProjectAccessService.effectiveAccess`；
- 不强制历史成员补全公司，空值就是「未标注」。

## 2. 现状落点

| 现状 | 证据 | 对本方案的含义 |
|---|---|---|
| 全局账号没有公司字段 | [`AppUser.java`](../../backend/src/main/java/com/hourglass/entity/AppUser.java#L10-L20) | 公司不能放全局账号；同一个人在不同空间可能属于不同公司 |
| 空间成员已有空间角色和项目参与模式 | [`WorkspaceMember.java`](../../backend/src/main/java/com/hourglass/entity/WorkspaceMember.java#L10-L20) | 公司适合加在空间成员上，和 `role` 并列但不参与判定 |
| 项目成员只有可见范围 | [`ProjectMember.java`](../../backend/src/main/java/com/hourglass/entity/ProjectMember.java#L14-L17) | `access` 是权限，不是职责；项目角色不能复用它 |
| 有效权限只读空间角色/参与模式/显式配置 | [`ProjectAccessService.java`](../../backend/src/main/java/com/hourglass/service/ProjectAccessService.java#L108-L117) | 新字段只要不进这条链路，就不会改变权限 |
| 成员列表当前展示姓名/登录名/空间角色/可见范围摘要 | [`settings.js`](../../frontend/js/views/settings.js#L406-L473) | 公司 chip 是**追加**，不能替换现有 `memberVisibilityText` 的可见范围摘要 |
| 项目详情当前是概览/史诗/成员负载 | [`project.js`](../../frontend/js/views/project.js#L34-L40) | 需要新增「成员与角色」分区，角色和权限分列 |
| 负责人下拉只有姓名 | [`task-drawer.js`](../../frontend/js/core/task-drawer.js#L1034-L1068) | 负责人选项补公司和本项目角色，按公司分组 |
| 邀请当前没有公司/角色字段，使用次数只增不封顶 | [`InviteMapper.xml`](../../backend/src/main/resources/mapper/InviteMapper.xml#L35-L37) | 邀请链路不动；新成员加入后再标注 |

## 3. 概念模型

| 层 | 存在哪 | 例子 | 作用 |
|---|---|---|---|
| 账号 | 全局 | 张伟、@zhangwei | 登录身份 |
| 空间成员 | 空间 | 公司=沙漏科技；空间角色=管理员 | 归属与空间权限 |
| 项目成员 | 项目 | 项目权限=可参与/只读 | 项目可见与可写 |
| 项目角色 | 成员 × 项目 | 项目经理、客户项目负责人 | 职责标签，仅展示 |

术语约定：

- **空间角色**：owner / admin / member / viewer，是权限。
- **项目权限**：可参与 / 只读 / 不可见，是权限。
- **公司**：空间级自由文本，是身份标签，不是权限边界。
- **项目角色**：项目经理、产品负责人、客户项目负责人等，是展示标签，一个成员在一个项目只有一个主角色。

四层概念互不替代：公司回答“他属于哪家”，项目角色回答“他在这个项目做什么”，两者都不回答“他能做什么”。

## 4. 最小数据模型

### 4.1 空间成员上的公司属性

```sql
-- sql/68_member_company_project_role.sql（示意，沿用 66 号脚本的幂等写法）
ALTER TABLE workspace_member
  ADD COLUMN company_name varchar(64) NULL COMMENT '公司名称（空间级自由文本，仅展示）';
```

- `NULL` = 未标注；存量数据不回填。
- 同一个成员在一个空间只有一个公司；同一个人在不同空间可以是不同公司。
- 不建公司目录。输入候选来自**当前空间成员已填写的公司名去重**，不是独立维护的公司表；改名只改当前成员这一条，不批量同步其他人。
- 公司名只用于 chip、筛选和分组，不参与任何判断。

### 4.2 项目角色表

```sql
CREATE TABLE IF NOT EXISTS project_member_role (
  workspace_id varchar(32) NOT NULL COMMENT '归属空间ID',
  project_id   varchar(32) NOT NULL COMMENT '项目ID（requirement.id）',
  user_id      varchar(32) NOT NULL COMMENT '成员账号ID',
  role_title   varchar(32) NOT NULL COMMENT '项目角色展示标签（不参与鉴权）',
  created_at   datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at   datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (workspace_id, project_id, user_id),
  KEY idx_pmr_user (workspace_id, user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='项目角色展示标签，不参与鉴权';
```

主键 `(workspace_id, project_id, user_id)` 天然保证**一人一项目一个主角色**；换角色是更新 `role_title`，不是新增第二个角色。

为什么不把 `role_title` 加到 `project_member`：

- `project_member.access` 是 `NOT NULL`，且只为“显式配置过权限”的成员建行；
- 默认参与的成员根本没有行，把角色加进去要么造假的权限行，要么角色只对少数人可用；
- 单独一张只有 `role_title` 的表，天然不进入鉴权，也不影响现有过滤 SQL。

数据清理：成员被移出项目/空间时，同事务删除对应 `project_member_role` 行；这是数据一致性，不是权限变更。

## 5. 权限边界：一行不改

鉴权链路只读：

- `workspace_member.role`
- `workspace_member.project_access_mode`
- `project_member.access`

`company_name`、`role_title` 不进入任何鉴权 SQL/Java，因此：

- 没有内部/外部之分，也就没有“外部成员不能当管理员”之类的拦截；
- 项目角色不会让只读成员变成可写；
- 邀请链接仍按现有规则可多人使用；
- 不新增 403 分支，不改 `effectiveAccess` 的返回值。

编辑权限复用现有规则，不新造权限：

| 操作 | 谁可以改 | 说明 |
|---|---|---|
| 改成员公司 | 空间主 / 空间管理员 | 和现有成员管理权限一致 |
| 改项目角色 | 项目负责人 / 空间管理员 | 和现有项目成员维护权限一致 |
| 查看公司和角色 | 空间成员 | 协作识别需要；不设隐藏开关 |

MVP 不做成员自助改公司或自助改角色；后续如要加，也只做「申请修改」，仍只是属性变更。

## 6. 界面设计

### 6.1 空间成员列表

```
[周] 周敏  @zhoumin · 可见 2/2 个项目（其中 2 个只读）· 按项目分配    蓝海银行    成员 ▾   [档案]
```

- 公司 chip 只显示公司名；未标注显示 `未标注公司`。
- 不显示公司类型，不出现内部/外部徽标。
- 保留现有可见范围摘要（`memberVisibilityText`），公司 chip 是追加信息，二者一行或两行均可，不能互相替代。
- 筛选只有「全部 / 已标注 / 未标注」和按公司筛选。
- 空间角色独立显示，不和公司混在一起。
- 列表只显示可见范围摘要，不展开项目角色；点档案看完整。

### 6.2 成员档案

- 公司归属：自由文本输入，带空间内已有公司名建议；留空表示未标注；只改展示。
- 空间角色：只读或按现有规则调整，和公司标注分开。
- 项目角色：按项目列出，每项目一个下拉，可编辑。
- 账号信息：登录名、加入时间、最近活跃；只读。
- 明确文案：「一人一个主角色；角色只做标注，不授予项目权限。」

### 6.3 项目成员与角色

```
成员      公司          项目角色              项目权限    来源
周敏      蓝海银行      客户项目负责人 ▾      只读        项目授权
张伟      沙漏科技      项目经理 ▾            可参与      项目负责人
李婷      沙漏科技      产品负责人 ▾          可参与      空间管理员
王浩      沙漏科技      后端开发 ▾            可参与      空间默认参与
```

- 项目角色一列、项目权限一列，视觉上必须分开。
- 列表范围 = 当前对项目可见、且**不是空间查看者**的成员，用「来源」说明为什么可见；空间查看者全局只读，只出现在空间成员列表，不进入项目成员表，也不出现在任务负责人下拉。
- 「添加成员」只列当前不可见的普通成员（空间主/管理员已天然可见，查看者不参与项目，均不重复添加）。
- 角色下拉预设为主，允许自定义；一人一个主角色。
- 「来源」解释当前成员为什么能看到该项目，取值固定为：
  - `项目负责人`：该项目负责人；
  - `空间主` / `空间管理员`：空间角色天然可见全部项目；
  - `空间默认参与`：空间成员且 `project_access_mode=all`；
  - `项目授权`：按项目分配，由显式 `project_member.access` 授予。
- 空间主/管理员的权限只读展示（锁定），不提供改权限下拉；普通成员的权限下拉仍走现有规则。
- 表头或底部提示：「角色只做标注，项目权限仍由『可见范围』控制。」
- 角色维护沿用现有项目成员管理权限（项目负责人/空间管理员）。

### 6.4 任务负责人

下拉按公司名分组，不带公司类型：

```
蓝海银行
  ○ 周敏 · 客户项目负责人
云启实施
  ○ 孙琪 · 实施顾问
```

选中后显示身份条：

```
周敏 · 蓝海银行
本项目：客户项目负责人（只读）
资金中台：业务代表（只读）
```

同名、同人跨项目角色不同，都能一眼区分。空间查看者不进入负责人下拉（全局只读，不承担项目职责）。

### 6.5 评论与动态

评论头部显示公司 chip，角色放在 hover 或人员卡片：

```
周敏 [蓝海银行] · 2 小时前
```

评论里不堆角色，避免噪音；公司是判断立场的关键信息。

### 6.6 人员卡片

- 公司（仅公司名）
- 空间角色（权限）
- 各项目角色（跨项目）
- 最近活跃 / 加入时间
- 不做组织架构、汇报线、公司管理员体系。

## 7. 角色词典

建议“预设为主、允许自定义”，MVP 一人一个项目一个主角色：

- 管理决策：项目负责人、项目经理、客户项目负责人
- 产品业务：产品负责人、业务代表、需求方
- 交付实施：技术负责人、开发、测试、实施顾问、视觉设计
- 其他：评审人、观察者

不建议一上来做 RACI 或角色继承；交付项目里容易过度设计。已拍板一人一个主角色；如未来确实普遍身兼多职，再单独评估多角色，不作为默认能力。

## 8. 接口设计（最小）

| 接口 | 用途 | 权限 |
|---|---|---|
| `GET /api/workspaces/{id}/members` | 成员列表返回 `companyName` | 现有成员可见 |
| `PUT /api/workspaces/{id}/members/{userId}/profile` | 保存公司名称 | 空间主/空间管理员 |
| `GET /api/workspaces/{id}/projects/{projectId}/member-roles` | 返回项目内 `userId -> roleTitle` | 现有项目可见 |
| `PUT /api/workspaces/{id}/projects/{projectId}/member-roles/{userId}` | 保存项目角色 | 项目负责人/空间管理员 |
| `GET /api/workspaces/{id}/members` + 项目角色映射 | 负责人下拉展示公司+角色 | 复用现有数据 |

注意：

- 公司字段只在空间成员接口返回，不要塞进全局账号接口；没有 `companyType`。
- 公司名保存前 `trim`，空串按 `NULL` 处理（未标注）；超过 64 字符拒绝。
- 项目角色接口只校验“该成员当前对项目可见”（复用现有 `canView`/可见范围判断，含空间角色与 `project_access_mode`），**不读写 `project_member.access`**，也不要求存在显式 `project_member` 行。
- `roleTitle` 保存前 `trim`；空值表示清除角色，直接删除对应 `project_member_role` 行，不保留空字符串。
- 权限判断复用现有成员管理/项目成员维护校验，不新增规则；不因 `role_title` 是否存在放开或收紧任何接口。
- 邀请接口不加公司、角色字段。

## 9. 边界与风险

| 场景 | 处理 |
|---|---|
| 历史成员没有公司 | 显示「未标注」，不阻塞任何操作，不回填 |
| 成员在空间但不在项目 | 没有项目角色；加入项目后再标注 |
| 成员被移出项目/空间 | 同事务删除对应项目角色行 |
| 失去项目可见范围 | 不只“移出项目”：切到按项目分配且无授权、或权限改为不可见、或空间角色变化导致不可见时，同事务删除角色行，避免出现“有角色却看不到项目”的悬空标签 |
| 项目角色表存在但成员已不可见 | 列表/负责人下拉查询时按现有可见性过滤，不能只 join 角色表；孤儿行由清理任务或下次写入时删除 |
| 同一人跨项目角色不同 | 人员卡片展示各项目角色；任务里只显示当前项目角色 |
| 同一个人换公司 | 所有展示位置显示当前公司；不做历史快照 |
| 公司重名/写法不一致 | 自由文本允许并存；输入时提示已有名称，减少写法分叉 |
| 邀请新成员 | 加入时公司和角色都为空；由有权限的人在成员列表补标 |
| 评论历史 | 显示当前公司，不显示“当时所属公司”；如需审计快照，后续单做 |
| 移动端/窄屏 | chip 截断公司名；人员卡片全屏抽屉；项目表格横向滚动 |

主要风险是“把角色误当权限”。控制手段：分列展示、固定文案、鉴权代码不引用新字段、回归测试校验权限结果不变。

## 10. 落地顺序

### P0：公司标签闭环

- 成员表新增公司字段，成员接口返回/保存；
- 设置页成员列表显示公司 chip，档案可编辑；
- 任务负责人/评论显示公司；
- 权限回归测试：加属性前后 `canView/canWrite/effectiveAccess` 结果一致。

### P1：项目角色闭环

- 新建 `project_member_role`；
- 项目详情新增「成员与角色」分区；
- 负责人下拉按公司分组并显示本项目角色；
- 人员卡片显示跨项目角色；
- 成员移出项目时清理角色行。

### P2：治理与效率

- 新成员加入后的批量标注；
- 按公司/角色筛选、按公司统计工作量；
- 角色历史、成员自助申请修改；
- 如重名、改名成为真实问题，再评估公司目录；不影响现有 `company_name`。

邀请时预填公司/角色不在计划内：已拍板“加入后再标注”。

## 11. 验收与验证

**权限护栏：**

- 同一批成员在加属性前后，`canView/canWrite/effectiveAccess` 快照一致；
- 全局搜索鉴权 SQL/Java，确认没有引用 `company_name/role_title`；
- 确认代码与界面不存在 `company_type`、内部/外部判断；
- 邀请仍可多人使用，加入逻辑不变。

**体验验收：**

- 成员列表能看出公司，未标注有明确状态，且原有可见范围摘要仍在；
- 公司可用自由文本输入，已有公司名有候选（候选来自成员已填值）；
- 项目成员表能设置角色，角色与权限分列，一人一个主角色；「来源」与现有可见性规则一致（默认参与=可写、按项目分配无授权=不可见）；
- 空间查看者不出现在项目成员表与负责人下拉，只保留在空间成员列表的只读摘要中；
- 负责人下拉按公司名分组，选中后身份条显示本项目角色和跨项目角色；
- 邀请不预填公司和角色，加入后标注；
- 空值、重名、移除成员、跨项目角色等边界可操作。

**指标：**

- 标注覆盖率：有公司的成员占比、有项目角色的项目成员占比；
- 采用率：公司筛选、身份卡、按公司分组派活的使用；
- 效率：找到正确负责人的时间、派错人的返工；
- 质量：公司名称写法分叉数、角色变更频率、长期未更新的角色。
