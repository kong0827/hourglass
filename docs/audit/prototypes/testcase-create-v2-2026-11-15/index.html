口径依据（原文）

禅道：「在“建用例”页面，选择相应的产品、需求模块、用例类型、适用阶段、相关研发需求等。」——撰写用例

禅道 API：必填 title、type、steps(desc/expect)；选填 module、story、stage、precondition、pri、keywords——创建用例

禅道场景：「添加场景时可以设置所属的产品、模块、上级场景」，「场景层级数量不受限制」——用例场景

PingCode：「按模块分级组织测试用例，同时自定义用例属性」「关联不同项目下的多个工作项」——测试管理；「灵活配置及共享用例，一键关联需求、任务」——Testhub

设计取舍

1项目不进表单，需求与模块才进

三家都把项目/产品当容器（权限、编号、目录树），禅道在页面顶部选产品，沙漏已经是页面级项目上下文。所以表单里只保留「项目：支付中台（只读）」一行，避免出现第二个可选项目导致搬移。

2类型给默认值，不复制禅道的“必填”

禅道类型必填，是因为它的执行报表要按类型切片；沙漏目前没有该报表，直接设必填只会增加一次点击。默认「功能测试」，想改再改，等报表需要时再收紧。

3步骤收紧到「至少一行 + 预期必填」，草稿放行

禅道 API 里 steps 的 desc 与 expect 都是必填，沙漏现在空步骤也能存，导致执行时无据可依。改成保存校验，但保留「保存为草稿」，不挡录入中的半成品。

4分组不合并进模块，也不做模板库

PingCode 用模块分级 + 模板，禅道用模块 + 场景。沙漏的模块是单归属、与需求同树，分组是多归属可嵌套，两者语义不同，合并会失去“一稿多圈”的能力；模板库成本高，本期只留入口。
