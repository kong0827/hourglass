需求提交前体检
缺验收标准、缺版本、相似需求		 评审前把话说清楚，减少返工；只读、无落库风险。 需求表单、关键词匹配 用户嫌烦 → 允许「不再提示」
只读查询扩展
版本进度、需求状态、谁改了什么		 已有五个固定模板，同一套路由可继续加；对「老板问进度」最实用。 TaskQueryService、审计 口径错 → 模板与报表同源
P1 钩子至 Gate 1 纪要 / 聊天 → 多条草稿 建单的下一步；粘贴即可，风险可控，价值在「会后 2 分钟录完」。 复用建单 + 确认卡 一次抽太多 → 上限 10 条
文档格式统一
标题层级、术语表、验收表格		 回应「格式化文档」；但依赖规则配置，放 P1 更稳。 模板、术语表、diff 规则不明 → 先只做术语与标题
Word / PRD 导入 → 三件套 产品团队本来就写 Word；这是最自然的录入路径，但依赖解析质量。 Word 导入方案 表格/图片解析不稳 → 先分节
测试侧：失败转缺陷、缺陷去重、测试报告 测试域记录最全，但 AI 渗透最低；先做三个闭环动作。 测试计划、用例、缺陷 严重度不能由模型定
追踪链问答 + 发布体检（只读） 差异化的第一层；规则先行，AI 只解释与排序。 版本、快照、发布记录 数据不全 → 显示「未记录」
P2 出证至 Gate 2 交付说明 / 变更台账 / 客户简报 护城河所在：承诺、变更、证据的对照，通用工具没有这套数据。 revision、发布快照 对外内容必须人工确认
排期 / 回归范围 / 依赖建议 价值有，但一旦像「考核建议」就会引发抵触；只给候选集。 工时、依赖、历史数据 被当成评分 → 不展示个人对比
语义搜索、项目集周报、证据包 提升找东西和跨项目汇报的效率，但依赖索引与项目集能力。 搜索、项目集 运维成本 → 先关键词
不做边界 自动改状态 / 自动发布 / 自动替人定稿 / AI 评分排名 / 无人确认批量写 / 自动监听 IM / 任意 SQL / Agent 市场。 这些要么破坏审计，要么把责任从人转给模型。
决策 1 · 文档改写做到哪一步
建议：P0 只做选区 + diff；整篇「按模板整理」放 P1，先看到全文差异再确认。原因：整篇重写用户无法判断改了哪。
决策 2 · 相似需求怎么判
建议：P0 用标题 + 关键词重合，只提示；P2 再评估向量检索。不要一上来引入向量库，2 人维护不起。
决策 3 · 批量创建确认颗粒度
建议：逐条勾选 + 整批一次确认；重复项默认不勾选，必须单独处理。不做「全自动创建」。
决策 4 · 入口形态
建议：场景按钮优先，助手兜底。文档页的「AI 改写」、需求页的「拆解」比一个常驻聊天框更符合沙漏用户。
