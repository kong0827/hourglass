分析说明 · 用例详情字段排序

模块是「归类」，不是「关键指标」。它不该和优先级、执行人抢首屏；用例真正要先回答的是「验证什么（需求与工作项）」，其次才是「放在哪个目录、进了哪些分组」。

1. 先回答：模块该不该靠后？

  • 业界口径：TestRail 把用例放在 Project → Section 的目录树里，Section 承担导航与归类；Jira/Zephyr 用 Folder/Component 归类；禅道用例的「所属模块」来自产品模块树，同样用于筛选与统计。它们都不把模块列成首屏主指标。
  • 首屏该放什么：优先级、执行人、最近执行结果——决定「这条要不要现在跑」；其次是需求与工作项——决定「为什么测」。模块与分组决定「以后怎么找」，属于第二层。
  • 本产品现状：截图版把模块放进六宫格，和优先级等权，信息量却只有一个叶子名；目录层级、需求追溯都看不到。推荐序把模块放回归类区，并展示完整路径。

2. 关联模块会不会自动关联项目？

不会，也不需要。模块表 test_module.req_id 本身就挂在项目下，后端选模块时用 requireNode(workspaceId, reqId, moduleId) 校验，只能选当前项目里的目录。项目由创建入口决定（从哪个项目/需求新建），详情里只展示不改；选了模块不会、也不能把用例挂到别的项目。反过来，换项目等于换一整套目录、需求与分组，应重建用例而不是在详情里改。

因此推荐序在编辑态把「项目」显式成一行只读上下文，并注明「由创建入口决定」，避免有人误以为模块能改项目。

4. 三套排序对比

排序结构问题 / 适用
现状（截图版）六宫格：优先级 / 模块 / 工作项；需求 / 执行人 / 最近执行模块与优先级等权；需求、工作项被压成计数，看不到内容
上一版关键三卡 → 归属（模块 / 需求 / 分组）→ 工作项独立模块仍排在需求前；「放在哪」先于「为什么测」
推荐序关键三卡 → 追溯（需求 → 工作项）→ 归类（模块 / 分组）→ 内容先因果后分类；模块回到第二层，目录路径完整可读

5. 参考新建文档的布局

  • 新建文档是「名称 → 存放位置（归属项目 + 分类）→ 起点」，只有名称必填，其余都有默认值。
  • 用例详情沿用同一套心智：标题在最上；「归属」拆成追溯（需求/工作项，建议填）与归类（模块/分组，可选）；正文（前置、数据、步骤）才是主体。
  • 编辑态把「项目」作为只读上下文放在归类区首行——它是「存放位置」的根，但不是可选项；模块是根下面的目录。

6. 落地影响

  • 只调整概览区的字段顺序与分组标题，不改接口、不改数据结构；分组归属仍用 GET /api/case-sets?caseId= 回显。
  • 「项目」不新增可写字段；编辑态只读展示，旁注说明来源。
  • 关键三卡、就地编辑、分组浮层、工作项状态点保持现有交互，不丢信息。
