# 需求全链路追溯 · 调整方案（2026-11-14）

## 结论

沙漏现在能追到「需求 → 工作项 → 版本」，缺的是「工作项 → 用例」的显式关系，以及「计划 → 发布」的测试证据。调整不重做测试模块，只补一张关联表、三处派生视图和一次发布快照。

原型：`prototypes/traceability-2026-11-14/index.html`

## 一、现状与缺口

| 环节 | 现状 | 结果 |
| --- | --- | --- |
| 需求 → 工作项 | `task.demand_id` 指向需求（`sql/baseline/01_schema_full.sql:672`） | 已通 |
| 工作项 → 用例 | 用例只有 `demand_id`，没有工作项关联（`01_schema_full.sql:867-892`） | **断点** |
| 用例 → 计划 | `test_plan_case` 多对多（`01_schema_full.sql:954-967`） | 已通，但计划不知道服务哪些需求 |
| 缺陷 → 用例 | `test_case_run.bug_task_id` 记录失败转出的缺陷（`01_schema_full.sql:903`） | 可反向追 |
| 版本 → 交付 | `version_release_item` 冻结工作项、`demand_id`、`demand_title`（`01_schema_full.sql:1198-1224`） | 已有快照落点，缺测试证据 |

覆盖矩阵目前按 `demand_id` 聚合（`frontend/js/views/testcases.js`），只能回答“这个需求有没有用例”，不能回答“这个工作项由哪条用例验证”。用例如不关联需求，还会整体落在覆盖之外。

## 二、竞品里值得拿的部分

- **Azure DevOps**：需求/故事是主轴，测试用例关联需求，用 RTM 正反查；发布检查允许警告通过。
- **Xray**：Requirement → Test → Test Run → Defect 的报告链，按版本和计划汇总。
- **TAPD**：测试计划先选需求范围，再用例关联待测需求。
- **PingCode**：计划关联迭代/发布，用例有版本和基线。

共同点是「需求主轴 + 显式关联 + 覆盖口径分开 + 发布时冻结」。不照搬“计划绑定单个需求”，因为沙漏的计划经常跨需求、跨版本。

## 三、调整原则

1. 需求是主轴，版本是交付容器，测试计划保持独立，可跨需求。
2. 显式关联优先，聚合只做兜底；需求级覆盖和工作项级覆盖分开显示。
3. 发布检查只做风险提示，不硬性阻断；带风险发布必须填原因并留痕。
4. 发布时冻结测试证据，之后改用例、改计划都不回写历史。
5. 不增加一级菜单，入口放在现有需求、测试、版本页面里。

## 四、数据模型：只加一张表

### 1. 新增 `test_case_task`

```sql
CREATE TABLE `test_case_task` (
  `id` varchar(32) NOT NULL,
  `workspace_id` varchar(32) NOT NULL,
  `case_id` varchar(32) NOT NULL,
  `task_id` varchar(32) NOT NULL,
  `created_by` varchar(32) DEFAULT NULL,
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_case_task` (`case_id`,`task_id`),
  KEY `idx_ws_task` (`workspace_id`,`task_id`),
  KEY `idx_ws_case` (`workspace_id`,`case_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='用例验证的工作项（多对多）';
```

一条用例可以验证多个工作项，一个工作项也可以由多条用例验证。原型里 TC-0192 同时关联 HG-2419 和 HG-2420，单值字段表达不了。

服务端校验三点：用例与工作项同空间、同项目；工作项属于用例的主需求；重复关联幂等。历史数据不回填，未关联的用例继续按需求级覆盖统计。

### 2. 不给 `test_plan` 加 `demand_id`

计划的需求范围由「计划 → 用例 → 主需求」实时派生：

```
test_plan_case → test_case.demand_id → demand
```

好处是计划仍然可以跨需求；某个需求后来补了用例，范围会自动跟上。坏处是“计划想覆盖但还没写用例的需求”不会出现，这类缺口交给覆盖矩阵和发布检查提示。

### 3. `test_case.demand_id` 语义定为“主需求”

保持单值、选填。工作项关联必须落在主需求下；没有主需求的用例只能计入需求级或“未归类”。这样避免同一条用例跨两个需求时覆盖口径打架。

### 4. 发布快照扩展 `plan_snapshot`

`version_release.plan_snapshot` 已存在（`01_schema_full.sql:1186`），不需要新表。发布时由服务端追加一段测试证据：

```json
{
  "testEvidence": {
    "plans": [{"id": "TP-009", "revision": 7}],
    "demandSummary": [{"demandId": "REQ-2026-018", "cases": 7, "passed": 4, "failed": 1, "blocked": 1, "untested": 1, "openDefects": 2}],
    "workItemCoverage": {"total": 5, "linked": 4},
    "openDefects": 2,
    "capturedAt": "2026-11-22T10:00:00"
  }
}
```

只由服务端计算，不接受客户端传入；历史发布没有这段字段时显示“未记录测试证据”，不补算。

## 五、四处界面

### 1. 需求详情 · 全链路

顶部五段链：需求 → 工作项 → 用例 → 测试计划 → 发布。每段给出数量、完成度和风险，点击跳到对应卡片。

下面按「工作项、用例、计划、缺陷、发布」分区：

- 工作项行显示验证用例、覆盖级别、结果。无工作项级用例时标“需求级”或“未覆盖”，不误报。
- 用例行显示验证工作项、最近结果、所属计划、关联缺陷。未关联工作项的用例单独筛选。
- 发布卡直接给测试计划、本需求通过率、未关闭缺陷、工作项完成四项，入口进发布检查。
- 右栏给交付判断分、链路完整度和风险清单；风险按发布影响排序。

### 2. 覆盖矩阵

按需求展开三层：需求 → 工作项 → 用例。列包含用例数、覆盖、结果、缺陷、风险。

- 绿色“工作项级”：有显式关联，能回答“谁验证这个工作项”。
- 蓝色“需求级”：用例挂在需求下但没精确到工作项，计入需求覆盖，不算工作项缺口。
- 红色“未覆盖”：没有任何用例；发布检查按工作项类型和优先级给阻断或提醒。

顶部指标分开“需求覆盖”和“工作项级缺口”，避免一个总覆盖率掩盖问题。搜索支持需求、工作项、用例三个层级。

### 3. 计划详情

计划头保留版本、周期、负责人。新增“需求范围”卡片，由计划内用例的主需求自动汇总，显示每个需求的总数、通过、失败、阻塞、未执行和覆盖级别。

用例执行表增加“需求”和“验证工作项”两列，可回答“这条用例属于哪个需求、验证哪个工作项”。筛选按需求、结果、执行人。创建计划时提供“按需求添加用例”，勾选需求即带入其全部用例，不改变计划的数据结构。

### 4. 版本交付

按需求看交付：工作项完成、用例通过、未关闭缺陷、覆盖级别、结论（可发布/有风险）。下面是发布记录时间线。

发布检查分阻断项和提醒项。默认规则：

| 项 | 级别 |
| --- | --- |
| 发布必测用例失败、阻塞或未执行 | 阻断 |
| 失败或阻塞用例未复测 | 阻断 |
| 阻断/严重缺陷未关闭 | 阻断 |
| P0 工作项未完成 | 阻断 |
| P1 用例未执行（非必测） | 提醒 |
| P1 工作项未完成 | 提醒（严格档为阻断） |
| P2/P3 工作项没有精确用例 | 提醒 |
| 计划仍是草稿 | 提醒 |

“发布必测”默认按 P0/P1 自动勾选，允许在计划里人工调整；严格/标准/宽松三档见第十节。

点击“带风险发布”必须填写原因，原因写入发布记录，和测试证据一起冻结。历史发布打开抽屉，展示当时的需求快照、用例数、通过率和未关闭缺陷。

## 六、正反两条链路

正向：

```
demand → task.demand_id → test_case_task → test_case
       → test_plan_case → test_plan → version_release.plan_id / plan_snapshot
```

反向：

```
version_release_item.demand_id / demand.version_id → demand
test_case_run.bug_task_id → 缺陷 → 用例 → 工作项 → 需求
```

计划范围、交付结论、覆盖矩阵都从这两条链路派生，不额外维护“需求-计划”映射。

## 七、实施顺序

**批次 1｜追溯底座**

- 建 `test_case_task`，补服务端校验和 API。
- 用例编辑/详情增加“验证工作项”多选，只列同主需求下的工作项。
- 需求详情的工作项行显示覆盖级别和验证用例。
- 验收：任选一个工作项，能看到关联用例；取消关联后回到需求级口径。

**批次 2｜覆盖与计划**

- 覆盖矩阵改成三层树，指标拆成需求覆盖和工作项级缺口，补搜索。
- 计划详情增加需求范围卡片、需求/工作项列、按需求添加用例。
- 验收：计划范围与计划内用例的主需求一致；未关联需求的用例进入“未归类”。

**批次 3｜发布证据**

- 发布检查接口输出阻断项和提醒项，带风险发布写原因。
- `plan_snapshot` 追加 `testEvidence`；版本交付页和历史发布抽屉读取快照。
- 验收：发布后改用例或改计划，历史快照不变；待发布版本能列出阻断和提醒。

三批可独立上线，批次 1 不改历史数据，批次 2 只读派生，批次 3 只扩展 JSON。

## 八、边界与不做

- 不把 `test_case.req_id`（项目）改成需求；项目仍是用例库的归属。
- 不做用例版本和基线。当前团队规模用“最近结果 + 发布快照”足够，版本化会显著增加维护成本。
- 不做自动化测试结果导入，先把人工关联跑顺。
- 不把测试计划绑定单个需求，也不要求计划必须关联版本。
- 默认不把发布检查做成硬门禁；阻断项是提示，决定权仍在发布人。严格档可要求审批，但仍保留带风险发布通道。
- 需求换版本后，旧发布记录不回写；工作项换需求后，旧用例关联保留但覆盖按新需求重算。

## 九、验收口径

1. 给定 REQ-2026-018，一屏内看到 5 个工作项、7 条用例、2 个计划、3 个缺陷、1 个目标版本。
2. 任一工作项能回答“哪条用例验证”；任一失败用例能回到缺陷、计划和版本。
3. 发布检查能列出阻断项和提醒项；带风险发布必须填原因；发布后的快照与当时一致。
4. 历史用例没有工作项关联时显示“需求级覆盖”，不计入工作项缺口。
5. 计划的需求范围与计划内用例的主需求一致，不出现手工维护的第二份范围。

## 十、待确认项与业内常用解法

四个问题在主流工具里都有成熟做法，下面按「业内怎么做 → 沙漏怎么选」给出建议。

### 1. 用例和工作项用什么关系

| 做法 | 代表产品 | 优点 | 代价 |
| --- | --- | --- | --- |
| 多对多关联表 | Azure DevOps（Tests / Tested By 双向链接）、Xray（Test 与 Requirement 的 Tests 链接）、Zephyr（issue links） | 覆盖报表准确，一条用例可验证多个工作项，反查也完整 | 多一张表，编辑界面要做多选 |
| 用例上放单个 `task_id` | 部分轻量测试工具 | 实现最快 | 多工作项场景只能拆用例或丢关系；TC-0192 这类场景表达不了 |
| 用例上存 JSON 数组 | 一些低代码/轻量工具 | 不用建表 | 不能建索引和外键，报表要在应用层展开，数据容易脏 |

业内主流是多对多。**建议选关联表 `test_case_task`**，同时保留 `demand_id` 做主需求分组。关联表加 `UNIQUE(case_id, task_id)` 保证幂等，服务端校验同空间、同项目、同主需求。如果以后要区分“验证/回归/冒烟”，再加 `relation_type`，首期不加。

### 2. 一条用例是否只能挂一个需求

业内常见三种：

- **单主需求 + 多工作项**：Azure DevOps 的测试用例本身不归属需求，而是通过 Tests 链接到多个故事；需求由故事向上归属。适合“用例库”模型。
- **多需求引用 + 一个主需求**：Xray、TestRail 的 refs 可以填多个需求，但通常有一个主归属，避免报表重复计数。
- **完全由工作项派生需求**：用例只关联工作项，需求 = 工作项的需求。追溯最干净，但历史用例没有工作项时会丢归属。

**建议首期保留单值 `demand_id` 作为主需求**，工作项关联允许多个。覆盖统计按这个优先级：有工作项关联时，需求覆盖从工作项的需求派生；没有工作项关联时，回退到 `demand_id`。两者冲突时以工作项为准并给提示。

这样做的好处是：计划范围、发布快照、需求详情都只认一个主需求，不会同一条用例在两个需求下各算一次。等真的出现“一条用例服务两个需求”的诉求，再加 `test_case_demand` 关联表并标 `is_primary`，迁移路径是通的。

### 3. 发布阻断规则怎么定

业内很少把规则写死，常见组合是「严重度 + 必测集 + 人工豁免」：

- **Azure DevOps**：分支策略和流水线 gate 可以要求某些检查必须通过，测试通过率阈值可配；不是所有项目默认强制。
- **Xray**：Test Plan 汇总执行状态，Jira 工作流可以加条件，要求计划通过后才能进入“待发布”。
- **qTest / PingCode**：发布范围 + 质量门禁，规则按项目配置，支持审批豁免。
- **TAPD**：发布评审看测试计划和通过率，最终由发布负责人确认。

共同点：**P0/P1 和“发布必测”用例是阻断主力，P2/P3 给提醒；允许带风险发布，但必须留原因和审批人。** 单纯按优先级一刀切，容易把“P1 但本次不影响发布”的用例变成噪声。

**建议做三档预设，不做规则编辑器**：

| 档位 | 阻断 | 提醒 |
| --- | --- | --- |
| 严格 | 发布必测用例失败/阻塞/未执行；阻断级缺陷未关闭；P0/P1 工作项未完成 | 非必测 P1 未执行；P2/P3 工作项无用例；计划草稿 |
| 标准（默认） | 发布必测用例失败/阻塞/未执行；阻断/严重缺陷未关闭；P0 工作项未完成 | P1 用例未执行；P1 工作项未完成；P2/P3 无用例；计划草稿 |
| 宽松 | 仅阻断级缺陷未关闭、发布必测用例失败 | 其余全部转提醒 |

同时在计划里给用例加一个“发布必测”开关，默认按 P0/P1 自动勾选，允许人工调整。这比单纯按优先级判断更贴近业内做法，也能解释“为什么这条 P1 没执行但不阻断”。带风险发布要填原因；严格档再要求审批人，普通档记录发布人即可。

### 4. 门禁放在需求级还是版本级

业内的通行做法是**门禁放在发布/版本级，需求级只做可见性**：

- Azure DevOps 的 gate 挂在流水线阶段/环境，不挂在单个故事上。
- Xray 的发布判断以 Test Plan 和版本为单位，需求覆盖是报告维度。
- TAPD、PingCode 的发布评审也是版本/发布单维度，需求状态只是汇总项。

原因很实际：一次发布通常包含多个需求，需求级各自拦截会产生大量重复确认；真正要签字的是“这个版本能不能发”。

**建议首期只做版本级发布检查**。需求详情的“发布检查”保留为预览，给出阻断/提醒和结论，不产生独立的审批流。如果某个需求要单独发布，就为它建一个版本或发布单，复用同一套检查和快照，不新增第二套门禁。

## 十一、落地优先级

按“先让数据可信，再让规则可配”的顺序：

1. **P0**：`test_case_task` + 用例多选工作项 + 发布必测标记。没有这三样，覆盖和门禁都不可信。
2. **P1**：标准档发布检查、带风险发布原因、快照写入 `testEvidence`。
3. **P2**：项目级三档预设、审批人、需求多主需求关联。等真实诉求出现再做。

首期不建议做：自定义规则编辑器、按人/按模块的复杂门禁、需求级独立审批流。
