# 沙漏 · 全站 UI/UX 评审

日期：2026-11-19
范围：router 表中 30 个路由视图、设置 4 个子页（空间 / 成员与权限 / 工作流 / 通知与集成）、7 类浮层；桌面 1440 与移动 390
证据：51 张截图（含 1 张复测）、运行时 DOM 测量、接口响应、14 处代码核查
环境：本机预览 `127.0.0.1:8081/hourglass`，空间 SXk01「运营研发中心」，账号 admin（管理员），10 名成员 / 22 个项目 / 428 个工作项
方法：`uiux-review` 六层透镜 + 页面四问 + 用户提供的 10 条快速清单
性质：只读评审，未改产品代码

## 0. 评审口径

每条发现按同一格式落表：

`ID | 严重度 | 透镜 | 位置 | 证据 | 用户成本 | 改法 | 验证方式`

严重度只分三档：

- **P0 破损**：错乱、裁切、错误数据、自相矛盾、不可完成任务。本周可改。
- **P1 结构**：主次颠倒、路径过深、状态语义混乱、跨页不一致。一个迭代。
- **P2 打磨**：对齐、字号、文案、空列、图标位置。随功能迭代。

每个页面回答四个问题：我在哪？现在是什么状态？我能做什么？做完会发生什么？任何一条答不出或需要学习，才记为问题。

本轮不改代码。修复顺序见第 7 节，需要拍板的口径见第 8 节。

## 1. 结论先行

**总体判断：局部达标，需要一次结构整改。**

基础层是在线的：登录页单主按钮、空态多数给下一步、焦点环可见、状态色有文字兜底、表格数字右对齐、任务抽屉与项目驾驶舱分组清楚。问题不在「基础交互差」，集中在三处：

1. **单一事实来源未收口**：同一页面出现两个状态、两种计数口径，或前端读了不存在的字段。
2. **工具栏与主操作没有分级**：版本、分支、需求池、交付说明、个人设置出现多个实心按钮，筛选控件压过创建动作。
3. **桌面优先、移动后补**：390 下默认表格、首屏被统计卡占满、FAB 遮挡列表、30/47 个控件小于 44px。

最硬的五条证据：

1. 项目列表在 1440 下表格宽 1276px、容器 1150px，「操作」列初屏被裁掉（`projects-1440.png`，`frontend/css/views-projects-settings.css:181`）。
2. 成员负载「剩余」恒为 0h：接口返回 `remainingMinutes: 2418`，界面读的是从未赋值的 `loadRemainingMinutes`（`workload-1440.png`，`frontend/js/views/workload.js:349`）。
3. 文档详情同屏出现「已发布」徽标与 meta「草稿」（`doc-detail-1440.png`，`frontend/js/views/requirements.js:1412-1413`）。
4. 周回顾「完成透视」优先级列顺序为「最高 | 中 | 高」，排序函数拿显示名去查 `P0–P3` 代码数组（`review-1440.png`，`frontend/js/views/review.js:209-215`）。
5. 390 下 47 个可见控件有 30 个小于 44×44，FAB 覆盖列表内容（`mine-390.png`、`board-390.png`、`list-390.png`）。

主要短板是**事实口径、主操作层级、移动端适配**，不是信息架构推倒重来。

## 2. 做得好的地方

- **登录页**：按用户要求保持原状（左侧品牌说明 + 右侧登录卡），本次不纳入调整；原设计单主按钮、层级清楚（`login-restored-1440.png`）。
- **任务抽屉**：负责人 / 优先级 / 计划时间三卡并列，项目、类型、分类、计划版本、文档、附件、标签、阻塞做成只读事实 chip；「交付证据」明确写「计划 ≠ 已发布」（`task-drawer-1440.png`）。
- **新建任务**：只有标题必填，标题行给「必填」与 0/60；内容、计划分节；底部「保存并再建一条」与主操作分开（`task-new-1440.png`）。
- **状态工作页**：从看板列下钻到「待处理」，当前列计数、逾期、阻塞、高优、工时消耗一屏给全；「当前显示 27/27 条」口径清楚（`workcolumn-1440.png`）。
- **文档历史（带参）**：左右 diff、分栏/统一切换、`+250/-0` 变更量、版本列表按时间排列（`doc-history-1440.png`）。
- **空态**：测试用例、发布计划、我的工作等空态都有下一步动作，不只写「暂无数据」。
- **焦点可见**：全局 `focus-visible` 为 2px `#2563EB` + 3px 外环，键盘用户能定位。
- **颜色不单独承载语义**：主状态徽标均带文字，优先级为色点 + 名称，图表有图例。
- **设置工作流**：系统列、处理规则、拖拽顺序、状态流转矩阵（允许 / 需填原因 / 禁止）结构完整（`settings-工作流-1440.png`）。
- **移动端版本时间轴**：首版启动 → 首版上线 → 迭代维护 → 今日，用色块长度表达投入，比表格更适合 390（`phase-390.png`）。
- **对比度**：抽查文字未发现低于 4.5:1 的正文；侧栏 meta `rgb(102,112,133)` 11px 约 5.2:1，达到 AA。

### 3.9 AI 前端落地四问

**这条说明是否不可替代？**

不可替代的：设置工作流的列处理规则、文档可见范围的权限后果、交付证据「计划 ≠ 已发布」。这些直接影响操作结果，且无法只靠布局表达。

可以删或挪的：甘特顶部整行说明、层级树工具栏脚注、个人设置 5 段字段解释、我的工作移动端口径说明、AI 周报两句说明、发布详情状态句。建议一律移到字段 `?`、帮助抽屉或首次提示，动作处不留常驻段落。

**能否用分组 / 间距 / 状态变化替代文字？**

- 交付说明的 17 个实心按钮 → 一组版本列表 + 行级次要按钮，主操作只留「批量生成」。
- 设置/空间的禁用输入 → 只读文本 + 「仅空间主可改」，比白底输入框更直接。
- 个人设置的两个保存 → 每张卡一个主按钮，字段解释进 `?`。
- 版本页 8 个控件 → 范围 / 筛选 / 显示 / 操作四段，控件数量不变但选择变快。

**核心操作是否 3 步内？**

| 任务 | 路径 | 步数 | 结论 |
|---|---|---|---|
| 新建工作项 | 入口 → 标题 → 保存 | 3 | 达标 |
| 新建分支 | 分支页 → 新建 → 表单保存 | 3 | 达标 |

## 5. 跨页共性问题

1. **日期格式**：列表 03-05、版本 2026-10-01、发布 9-22、动态 08-31 09:00、健康度 2026-04-08 并存。真不一致，建议统一规则（CO-1）。
2. **状态词表**：分支页同屏三套；版本页「进行中/已发布/待规划」；需求池「待评审/已通过/已排期/已完成/已关闭」。对象不同可以有不同词表，但同一对象必须有唯一词表，同页不能混用（CO-2）。
3. **主按钮数量**：登录 1、项目 1、版本 2、分支 2、需求池 2、交付说明 17、个人设置 2、通知页 2 个保存动作。真不一致，硬规则应为每屏 1 个；行级动作一律次要（IA-1/3/4、OP-5）。
4. **工具栏结构**：工作项 8–10 个、版本 8 个、分支 8 个、项目移动端 6 个、我的工作 12 个。缺四段式，建议统一「范围｜筛选｜显示｜操作」（IA-1、CO-4）。
5. **禁用态**：按钮 0.45 透明度、输入框全局浅底；设置/空间输入未命中，白底像可编辑。真不一致（CO-3）。
6. **空态**：测试用例、发布计划、我的工作给 CTA；文档历史、文档阅读、里程碑空态不给。建议空态一律「原因 + 下一步」，但不允许对空对象保留可执行按钮（IA-5、OP-7、VI-10）。
7. **计数口径**：列表写「共 428 项 · 已载入 100」「27/27」，看板只写「20/27」。看板缺分母说明（CO-5）。
8. **移动端默认视图**：看板→看板、列表→列表、需求→看板、项目→表格、我的→摘要。有理由差异，但项目默认表格在 390 不成立，应改卡片（OP-2）。
9. **版本与发布**：导航无发布入口，发布计划入口在版本页；这是既有 IA 决策，不建议加菜单，建议版本页空态直达（IA-6，待确认）。
10. **项目集与分类**：全局筛选仍使用「模块」一词，与「项目集 / 项目 / 分类」模型不完全一致；来自 11-18 项目集 UI 验收的残留，本轮未单独截图取证，列入待确认。

## 6. 关键体验断点

1. **管理层周一晨会**：全局健康度 → 已搁置且 0 工作项的项目显示绿色「正常」；版本详情 -57% 偏差红色。用户会把无人推进项目当健康，把低于预估当风险。影响管理层判断。对应 DA-3、DA-7。
2. **产品经理写文档**：阅读页同时显示「已发布」与「草稿」，用户不知道能否对外；从历史无参进入时看到空白页和可用「恢复此版本」，可能误操作。影响文档可信度。对应 DA-5、IA-5。
3. **开发接活**：手机打开我的工作 → FAB 压住风险卡；看板列切换只露 3.5 列；47 个控件中 30 个小于 44px。用户误触或漏看列。对应 FB-2、AC-1、AC-3。
4. **测试与发布**：测试空态能直接新建（好）；发布工作台里「新独立计划」既是下拉又是按钮，长表单无分节；交付说明把「版本已发布」写成「有发布记录」，同行又说「无生产发布记录」。用户可能填错计划或写错发布事实。对应 OP-1、DA-4。

## 8. 需要确认的决策

1. **文档状态以谁为准**：现状 `publishedAt` 判徽标、`status` 进 meta，两者可冲突。推荐以 `publishedAt` 为准，「有未发布修改」作为派生状态；代价是需要一次数据核对，把 `status=draft` 且已发布的记录归并。
2. **看板第 5 列**：压缩列宽到 220–240 让 5 列进 1440，还是保留宽列 + 横向滚动。推荐压缩 + 渐隐；代价是卡片标题更早截断。
3. **移动端项目默认视图**：卡片（推荐）还是保留表格。代价是丢失列对比能力，但 390 下表格本就需要横向滚动。
4. **发布计划与版本的关系**：现状计划挂在版本上，但表单里仍有「新独立计划」。推荐保留版本绑定，删除无实际数据的「独立计划」入口；若确有跨版本独立计划，再补对象与入口。
5. **健康度对 0 工作项项目的定义**：显示「无工作项」灰色（推荐），还是从健康度列表隐藏；代价是列表条数与「共 22 个」不一致。
6. **看板计数写法**：`27 项`（总数）还是 `显示 20/27`；推荐后者，和列表「已载入 100」一致。
7. **日期规则**：当年 `MM-DD`、跨年 `YYYY-MM-DD`、悬停完整时间（推荐）；代价是跨年任务在列表里更长。
8. **项目集全局筛选的「模块」**：是否统一改「分类」，与项目集/项目/分类模型一致；需产品确认，本轮未单独取证。
9. **交付说明「有发布记录」的定义**：版本状态已发布，还是必须有生产发布记录。推荐拆成「版本已发布」与「生产发布 有/无」两个事实，避免二选一。
