# 项目范围复选改造 · 影响与可行性分析

日期：2026-11-11  
范围：`frontend/`、`backend/`、`docs/`  
结论口径：本文只做现状核对与方案判断，不包含代码改动。

---

## 0. 结论先行

1. **方向成立，但不能全局一刀切。** 复选适合“跨项目浏览、汇总、对比”，不适合“单项目工作台、写入、发布”这类必须先确定唯一项目的场景。
2. **工作项其实已经支持项目多选。** 入口在筛选栏「更多筛选 → 项目」，状态是 `state.reqs` 数组，接口也接受 `reqs` 逗号多选；只是已选项目没有在工具栏上露出来，所以看起来像“只能选一个”。真正被单选卡住的是：需求池看板、用例、版本（按阶段/按版本）、项目驾驶舱，以及报表/周回顾/分支的项目筛选。
3. **版本和项目驾驶舱不建议改成复选。** 版本属于项目、不能跨项目绑定；驾驶舱本身就是单项目详情。它们已经有“全部版本 / 发布日程 / 全部项目 / 全部项目透视”等跨项目口径，应该保留，而不是把单实体工作台改成多选过滤器。
4. **全量列表不建议删除。** 只有“同布局、纯过滤”的「全部项目」选项可以收敛为复选控件的默认状态；有独立布局或跨项目操作的全量视图（全部版本、发布日程、全部项目、项目透视、需求池列表/甘特）必须保留。
5. **样式风险可控，前提是控件形态选对。** 不要用原生 `<select multiple>`，不要在工具栏平铺 N 个已选 chip。推荐“一个 30px 的项目范围触发器 + 300px 复选 popover + 一枚已选摘要 chip”，复用现有 chip/popover/checkbox 视觉语言；工具栏宽度基本不变，移动端走底部面板。真正会增加视觉负担的是表格/卡片补项目列、项目标签，而不是控件本身。

## 1. 现状盘点（先对齐事实）

### 1.1 一个重要更正：工作项已经是多选

工作项顶部没有“项目下拉”，项目筛选收在筛选栏「更多筛选」里（`frontend/js/core/filters-ui.js` 的 `renderMoreFilter`，约 135–207 行）：

- 状态：`state.reqs` 是数组，`toggleFilterValue("reqs", id)` 可反复勾选（`core/filters.js` 的 `FILTER_KEYS`，约 9–24 行）。
- 接口：`/api/board`、`/api/tasks/list`、`/api/calendar` 都接受 `reqs` 逗号分隔多选（`docs/接口契约.md` 第 70、292、1259 行）。
- 已选展示：只更新「更多筛选」上的计数 `moreFilterCount`，没有像负责人/优先级/类型/版本那样的已选摘要 chip（`filters-ui.js` 约 198–207 行）。所以用户如果不展开弹层，看不出来当前选了几个项目。
- 看板卡片：`views/board.js` 的 `cardHTML` 没有渲染项目名。默认就是全项目口径时，跨项目卡片本来就无法区分项目；这是现成的体验缺口，不只是复选才出现。

**判断：工作项不需要重做复选，只需要把“项目范围”提到筛选栏可见位置、补一枚已选摘要 chip、看板卡片补项目标签。**

### 1.2 各页面项目选择现状

| 页面 / 入口 | 当前控件 | 默认口径 | 是否已有全量 | 后端项目参数 | 复选判断 |

| 需求池：列表/甘特 | 无项目下拉；筛选 popover 项目多选 | 全部项目 | 是 | `/api/demands/page` 的 `reqs` 多选 | 已支持 |

### 1.3 产品语义约束

- 项目是交付单元，工作项、需求目标版本、计划交付版本归属项目；**版本不能跨项目绑定**（`docs/用户使用手册.md` 第 61、519–521 行）。
- 发布计划可以跨版本、跨项目（`docs/用户使用手册.md` 第 548 行；`docs/接口契约.md` 第 1621–1623 行），所以“全部版本/发布日程”这类跨项目视图不能被一个“单项目过滤器”替代。
- 用例、测试计划、覆盖矩阵、测试报告当前都以项目为聚合单元；读接口只需项目可见，写接口需项目写权限（`docs/接口契约.md` 第 587–595 行）。
- 分支允许空间级公共分支，但筛选参数目前是单项目（`docs/接口契约.md` 第 1061 行）。

## 2. 会影响哪些模块

### 2.1 前端共享层

| 影响点 | 具体内容 | 风险 |
|---|---|---|
| 控件 | 新增/复用“项目范围”控件：触发器 + popover + 搜索 + 全选/清空 + 复选行 | 原生 multiple 会破坏 30px 工具栏；需自绘 |
| 状态 | 每个视图维护 `reqs` 数组或 `null=全部`；归一化“全选 = 全部项目” | 全选后不要变成 N 个勾选，否则“全部”与“指定全部”两种状态会打架 |
| 已选摘要 | 工作项补 `fgReq` chip；其它页面触发器显示“项目 · 3 项” | 平铺 N 个 chip 会撑爆工具栏 |
| 保存视图 | 现有参数兼容：工作项/需求池已是数组；用例/文档是字符串 `reqId` | 旧视图必须继续可用；需要 `string | array` 兼容解析 |
| 深链 | 目前这些页面基本没有 `reqs` 深链；若新增需同时兼容单值 | 分享链接不能因多值失效 |
| 权限 | 项目列表只含可见项目；每行写操作要按 `reqId` 判断 | 复选不能绕过项目可见性；不能只按“当前项目”判断 |
| 列表/卡片 | 多项目时补项目列/项目标签/按项目分组 | 看板卡片现在没有项目名；用例行也没有 |
| 统计/导出 | 统计口径、CSV 文件名、导出列要带项目 | 不能把多项目汇总冒充分项目数据 |
| 移动端 | 触发器换行、popover 变底部面板、复选行 44px | 390px 工具栏容易挤 |

### 2.2 各页面具体影响

**工作项（低风险，优先）**

- 在筛选栏加一个“项目范围”触发器，与「更多筛选」并列；已选项目在 `fbActive` 里显示一枚 chip，点击清除。
- 看板卡片补项目标签（`card-tags` 行已有位置）；日历 tooltip、甘特分组按项目补名称。
- 不改接口，不改权限模型。

**需求池（中风险）**

- 看板从“单项目”变成“全部项目 / 指定多个项目”。需要后端 `/api/demands/board` 支持 `reqs`，并让列计数、facets、`totalAll` 都按当前范围聚合。
- 卡片补项目标签；「提需求」仍必须在弹窗里选一个目标项目（`dReq` 已有字段），不能因为浏览范围是多项目就省略。
- 列表/甘特已经是全空间 + 多选筛选，保留；把看板和列表的“项目范围”状态统一，避免看板选 3 个、切到列表又变成另一套筛选。

**用例（高风险，价值也最大）**

- 用例库、缺陷 tab 可以做“全部项目/多选浏览”，但以下动作必须绑定唯一项目：新增用例、AI 生成、CSV 导入、新建测试计划、执行用例、转缺陷、导出 CSV。
- 覆盖矩阵、测试报告、测试计划 tab 目前都是单项目聚合；多选浏览时如果直接切过去，会出现“列表是 3 个项目、报告却只算一个”的错位。建议：
  - 方案 A（推荐）：项目范围只作用于「用例/缺陷」两个浏览 tab；切到「计划/覆盖/报告」时保留单项目选择，并提示“该视图按项目统计，已切换到第一个选中项目”。
  - 方案 B：后端把计划/覆盖/报告也做成多项目聚合。成本明显更高，且“跨项目通过率”语义容易误导。
- 列表行补项目标签；统计条改成“3 个项目 · 128 条用例”并提供分项目小计；保存视图兼容旧的单值 `reqId`。
- 接口需要 `/api/test-cases`、`/api/test-cases/stats`、`/api/test-cases/coverage`、`/api/test-cases/linked-bugs`、`/api/test-plans` 支持 `reqIds`，并逐项目校验可见性。这是全案里最大的一块。

**版本（分层处理）**

- 按阶段/按版本：保持单选。版本属于项目，新建版本、发布、阶段统计都依赖唯一项目；改成复选会让“新建版本属于谁”“发布哪个项目”失去目标。
- 全部版本：把表格内的项目单选筛选改为复选，直接在已加载的全量 `allVersionsCache` 上过滤，不需要改接口；保留按项目分组的表格和“勾选版本 → 跨项目创建发布计划”。
- 发布日程：项目筛选可改复选，后端 `/api/release-plans` 的 `project` 需要支持多个项目（或返回后在服务端过滤）；保留日程布局。
- 全部项目：保留总览表，不改成可复选列表。

**项目（不建议复选驾驶舱）**

- 项目驾驶舱是单项目详情，复选没有语义。若目标是“同时比较几个项目”，建议单独做“项目对比”模式（2–4 个项目并排 KPI），而不是把驾驶舱的项目下拉改成复选。
- 「全部项目透视」已经按项目分组展开，可以在透视表上增加一个项目多选过滤（前端过滤即可），用于“只看这几个项目的透视”，成本低。

**分支 / 报表 / 周回顾 / 文档（低到中风险）**

- 分支：列表模式已经有全量行，可在前端复选过滤；看板分页走 `/api/branches/board|page`，需要后端 `projects` 参数，否则只能过滤当前页，计数会不准。
- 报表/周回顾：当前“全部项目”是同一套图表的聚合口径，多选只是“全部”的子集；要改就得让后端按 `reqIds` 重新聚合，收益不一定抵得上成本。建议放到后面。
- 文档：列表默认全部，项目筛选是“从项目页带过来的上下文”。改成复选价值不大，除非用户明确要“同时看几个项目的文档”。

### 2.3 后端接口改造清单

| 接口 | 现状 | 是否需改 | 说明 |
|---|---|---|---|
| `/api/board`、`/api/tasks/list`、`/api/calendar` | `reqs` 多选 | 否 | 工作项已支持 |
| `/api/demands/page`、`/api/demands/gantt` | `reqs` 多选 | 否 | 需求池列表/甘特已支持 |
| `/api/demands/board` | `reqId` 单选 | 是 | 增加 `reqs`，列计数/facets/totalAll 按范围聚合 |
| `/api/test-cases` | `reqId` 必填 | 是 | 增加 `reqIds`；分页与总数按范围 |
| `/api/test-cases/stats` | `reqId` 必填 | 是 | 增加 `reqIds`；建议同时返回分项目小计 |
| `/api/test-cases/coverage` | `reqId` 必填 | 是 | 增加 `reqIds` 或明确只支持单项目 |
| `/api/test-cases/linked-bugs` | `reqId` 可选 | 视方案 | 缺陷 tab 多项目浏览时需要 |
| `/api/test-plans` | `reqId` 必填 | 是 | 计划列表多项目浏览时需要 |
| `/api/manager/reports` | `reqId` 单值/null | 视优先级 | 多选需要聚合口径 |
| `/api/review` | `reqId` 单值/null | 视优先级 | 多选需要聚合口径 |
| `/api/branches/board`、`/api/branches/page` | `project` 单值 | 是 | 改 `projects`，否则分页计数不准 |
| `/api/release-plans` | `project` 单值 | 是 | 日程多选筛选 |
| `/api/req-docs` | `reqId` 可选单值 | 可选 | 文档多选筛选 |
| `/api/versions/cross-project`、`/api/versions/overview` | 全量 | 否 | 前端过滤即可 |

**不需要改表结构。** 项目筛选都是查询条件，不涉及新表或新列。

### 2.4 权限与边界

- 复选集合只能来自 `rt.reqList`（当前空间可见项目）；后端仍要逐个项目校验可见性，不能因为传了多个 ID 就跳过权限。
- 已归档项目：现有单选下拉只保留“当前选中”的归档项目；复选时建议默认不展示归档项目，已选中的归档项目保留并标注“已归档”，避免选择集突然变化。
- 项目被删除/隐藏：保存视图或深链里的 ID 失效时，剔除失效项并提示，不要整页 404。
- 每行写操作按 `c.reqId` / `d.reqId` / `t.reqId` 判断，不能只看视图级“当前项目”。用例尤其要改：`isWritable()` 现在只看 `caseReqId`。
- 复选“全部项目”时，页面上的“新建/导入/发布”必须要求先选定一个目标项目，或弹窗里显式选择；不能默认落到第一个项目而用户不知道。

### 2.5 性能与数据一致性

- 用例多项目不能在前端对每个项目各拉一页再合并：会 N 倍请求、分页总数失真。必须服务端分页 + 聚合统计。
- 需求池看板的列计数/facets 现在是按单项目算的，改多项目后要做 `req_id IN (...)` 的聚合；注意 `totalAll` 的语义要从“该项目总数”改成“当前范围总数”。
- 分支看板是分页的，前端只过滤当前页会导致“计数与列表不一致”；要么后端支持多项目，要么看板模式限制为单项目、只在列表模式复选。
- 保存视图、深链、实时刷新要能处理“选中的项目被删除/归档/权限收回”。

### 2.6 测试与文档

- 后端：需求看板多项目计数、用例列表/统计多项目、测试计划多项目、分支多项目、发布日程多项目；权限用例（部分项目只读、部分不可见）。
- 前端/E2E：项目范围控件的全选/半选/清空、保存视图兼容、移动端面板、每行权限。
- 文档：`用户使用手册`、`接口契约`、`常见问题`、`项目介绍` 里所有“按项目/全部项目”的描述要同步；如果有页面截图，也要重拍。
- 当前 E2E 对项目选择器的覆盖很少（`tools/e2e` 下只有需求排期单测涉及），改造时建议补一条跨项目浏览的冒烟。

## 3. 是否合适：分场景判断

| 场景 | 合适度 | 理由 |
|---|---|---|
| 跨项目浏览、检索、汇总 | 高 | 用户的问题就是“这几个项目一起看”，复选是自然表达 |
| 跨项目对比（项目健康度、版本交付） | 中 | 更适合专门的“对比”视图，而不是把详情页的项目下拉变复选 |
| 单项目计划/执行/发布 | 低 | 版本、计划、发布都必须有唯一项目；复选会让写操作失去目标 |
| 新建/导入/AI 生成/转缺陷 | 低 | 这些动作必须指定一个目标项目；复选只能作为浏览范围 |
| 单项目驾驶舱 | 低 | 驾驶舱的语义是“一个项目的详情”，多选不是它的使用方式 |
| 已有“全部 + 分组 + 筛选”的页面 | 低到中 | 如果“全量 + 按项目分组”已经够用，复选可能只是多一层操作 |

### 3.1 对“工作项”的判断

不需要改复选，改“可见性”：

- 在筛选栏固定一个“项目范围”入口，显示“全部项目”或“项目 · 3 项”。
- 已选项目在筛选摘要里显示一枚 chip，可一键清除。
- 看板卡片补项目标签；这是默认全项目口径下本来就该有的信息。

### 3.2 对“项目”的判断

- 如果指的是**项目列表**：它本来就是全量，不需要复选。
- 如果指的是**项目驾驶舱**：不建议复选。建议做“项目对比”模式（2–4 个项目并排），或使用「全部项目透视」；不要在单项目详情页里塞一个多选过滤器。
- 如果指的是**全部项目透视**：可以加项目多选过滤，成本低，语义也成立（“只看这几个项目的透视”）。

### 3.3 对“用例”的判断

- 浏览：适合。跨项目查找重复用例、看整体覆盖，是真实需求。
- 写入：不适合。新增、AI 生成、CSV 导入、执行、转缺陷、建计划都必须落到一个项目。
- 结论：做“只读的跨项目用例库”，同时保留一个明确的“目标项目”用于写操作；不要做一个“看起来能选 3 个项目、点新增却不知道建到哪”的控件。
- 计划/覆盖/报告三个 tab 建议保持单项目，或在多选时明确降级到第一个项目并提示。

### 3.4 替代方案

在动复选之前，先确认“全量 + 按项目分组 + 项目筛选”是否已经够用：

- 工作项列表、需求池列表已经支持“全部项目 + 按项目分组 + 多选筛选”。
- 版本「全部版本」已经按项目分组；项目「全部项目透视」已经按项目展开。
- 如果用户只是“想同时看几个项目”，一个“全部项目 + 按项目分组”的视图往往比复选更省事，也更不容易漏项目。

## 4. 全量列表要不要删？

**结论：不删。** 把“全量”当成项目范围的一个状态（scope = all），而不是一套独立的列表；只有“同布局、纯过滤”的「全部项目」选项可以收进复选控件的“全部”状态。

判断标准：

1. **同布局、只是范围不同** → 合并为复选控件的“全部/指定项目”状态。
2. **布局不同、操作不同、回答的问题不同** → 保留独立视图。

| 全量视图 | 处理 | 原因 |
|---|---|---|
| 版本 → 全部版本 | 保留 | 跨项目版本表 + 勾选多个版本创建跨项目发布计划，不是“单项目版本列表”的过滤结果 |
| 版本 → 发布日程 | 保留 | 跨项目计划日程，按时间/环境/状态筛选，布局与版本表不同 |
| 版本 → 全部项目 | 保留 | 首版/迭代的项目级总览，指标与单项目阶段页不同 |
| 项目 → 全部项目透视 | 保留 | 项目 → Epic → 任务逐层展开，和单项目驾驶舱不是同一张表 |
| 需求池 → 列表/甘特 | 保留 | 全空间布局，和单项目看板不是同一种呈现；只是项目范围默认全部 |
| 报表/周回顾/分支的「全部项目」 | 收敛为“全部”状态 | 同一套布局，纯过滤；复选后“全部”就是默认状态，不需要单独的 option |
| 用例 | 新增，不是删除 | 当前没有全量用例库；如果做多选浏览，它是新能力，不是旧列表的替代 |

需要删除/替换的只有一种：单选下拉里的 `<option value="">全部项目</option>`。它在新控件里变成“全部项目”这一行（或“全选”状态），不是删除一个页面。

**为什么不能删全量视图：**

- 全部版本承担“跨项目勾选版本 → 创建发布计划”的操作，删了会丢功能。
- 发布日程是计划汇总，不是版本列表的过滤。
- 项目透视是层级结构，单项目驾驶舱无法替代。
- 需求池列表/甘特是另一种布局，单项目看板无法替代。

## 5. 页面显示与样式

### 5.1 推荐的控件形态

```
收起（全部）       [项目 · 全部 ▾]
收起（单个）       [项目 · 资金小程序 ▾]
收起（多个）       [项目 · 3 项 ×]

展开：
┌─ 项目范围 ──────────────────┐
│ 🔍 搜索项目…                 │
│ [✓] 全部项目                 │
│ [ ] 资金小程序        12     │
│ [✓] 结算台             8     │
│ [✓] 官网改版           4     │
│ [ ] 已归档项目（默认隐藏）   │
│ ─────────────────────────── │
│ 全选        清空             │
└─────────────────────────────┘
```

状态规则：

- 未选任何项目 = 全部项目；触发器显示“项目 · 全部”。
- 选中 1 个 = 单项目；显示项目名。
- 选中 2 个及以上 = 显示“项目 · N 项”，hover `title` 列出名称；另在筛选摘要区放一枚可清除 chip。
- 选中全部可见项目 = 归一化为“全部项目”，不要显示“N 项”，避免“全选”和“全部”两种状态并存。
- 没有项目 / 全部归档 = 禁用触发器，提示“还没有项目”。

### 5.2 尺寸与视觉规范

- 触发器沿用 `.mini-select` 的 30px 高、12.5px 字号、10px 左右内边距；最大宽度 160px，超长项目名省略号 + `title`。
- Popover 宽 300–320px，最大高度 320px，内部滚动；搜索框吸顶；底部“全选/清空”固定。
- 复选行高 30–32px（桌面）/ 44px（移动端），选中用 `--primary-soft` 背景 + 主色勾选，不引入项目颜色（项目没有颜色字段）。
- 已选摘要在 `fbActive` 里只占一枚 chip，文案“项目 3 项”，点击清除；不要每个项目一枚 chip。
- 移动端：触发器可占满一行；popover 改为底部面板，搜索框 16px 字号（避免 iOS 缩放），底部按钮 sticky。

### 5.3 各页面布局调整

| 页面 | 调整 |
|---|---|
| 工作项 | 筛选栏“更多筛选”左侧加项目范围触发器；`fbActive` 加一枚项目 chip；看板卡片 `card-tags` 补项目标签；日历 tooltip、甘特分组补项目名 |
| 需求池看板 | 替换 `#demandReq`；卡片补项目标签；空状态/计数说明当前范围；“提需求”弹窗仍选目标项目 |
| 用例 | 替换 `#tcReq`；列表行 meta 补项目名；统计条加“N 个项目”；计划/覆盖/报告 tab 保持单项目并提示降级；新增/导入/AI 按钮要求目标项目 |
| 版本-全部版本 | 表格工具条的项目单选改复选；表格已按项目分组，不需要改列 |
| 版本-发布日程 | 工具条项目筛选改复选；表格已有项目列 |
| 项目-全部项目透视 | 可选加项目复选过滤；表格已按项目分组 |
| 报表/周回顾/分支 | 单选改复选；布局不变；默认“全部项目” |
| 文档 | 可保持上下文 chip；如做复选，列表行补项目名 |

### 5.4 样式会不会不好看？

**结论：按推荐形态不会；按错误形态会。**

| 做法 | 观感风险 | 说明 |
|---|---|---|
| 原生 `<select multiple>` | 高 | 桌面显示为列表框、最小高度 100px，直接破坏 30px 工具栏；移动端体验更差 |
| 工具栏平铺 N 个已选 chip | 高 | 3 个项目就多出 3 个 chip，测试/版本工具栏本来就满，必然换行拥挤 |
| 单个触发器 + popover + 一枚摘要 chip | 低 | 宽度稳定、层级清楚，和现有“更多筛选/负责人/版本”一致 |
| 多项目表格补一列“项目” | 中 | 工作项列表已有该列；用例建议放在标题下的 meta 行，不新增列，避免横向滚动 |
| 看板卡片补项目标签 | 低 | 卡片本来就有标签行，加一枚 ghost tag 即可；会增加一点卡片高度 |
| 移动端底部面板 | 低 | 复用现有 `.mob-sheet`/筛选面板；比在 390px 工具栏塞下拉更稳 |

**真正的视觉风险不在控件，而在“多项目列表的信息密度”：**

- 用例行如果同时出现项目、模块、需求、步骤数、执行人、时间，meta 行会很长；建议项目用一枚 tag 放最前，其余保持现状，超长省略。
- 看板卡片多项目时每张卡都带项目 tag，卡片高度会增加；只在一屏内项目数 > 1 时显示，单项目时不显示。
- 统计条/标题如果显示一长串项目名，会挤占工具栏；只显示“N 个项目”，完整名单放 tooltip 或 popover。

### 5.5 可访问性与一致性

- 触发器用 `<button aria-haspopup="menu" aria-expanded>`；popover 内复选行用 `<label><input type="checkbox">`，支持键盘和读屏。
- 全选/半选状态用 `indeterminate`；Esc 关闭、焦点回到触发器。
- 颜色只用现有 token（`--primary`、`--surface`、`--border`、`--text-*`），不新增项目色。
- 与现有“负责人/版本”多选保持一致：同样用 chip + popover，不新造一套视觉语言。

## 6. 建议的推进顺序

### P0：低风险、先把“已经支持但看不见”的补上

1. **工作项**：项目范围触发器 + 已选摘要 chip + 看板卡片项目标签。不改接口，不改权限。
2. **需求池看板**：后端 `/api/demands/board` 支持 `reqs`，前端项目范围支持全部/多选；卡片补项目标签。列表/甘特保持现状，统一状态。

### P1：价值最高、成本也最高

3. **用例**：先做只读跨项目浏览（用例/缺陷 tab），补项目标签、分项目统计；写操作要求唯一目标项目；计划/覆盖/报告保持单项目并明确提示。后端补 `reqIds`。
4. **版本-全部版本/发布日程**：全部版本前端复选过滤（小）；发布日程后端 `projects`（中）。按阶段/按版本保持单选。

### P2：按实际需求再做

5. 分支复选（列表模式可先前端过滤；看板需后端）。
6. 报表/周回顾复选（需后端聚合，先评估收益）。
7. 项目透视项目多选过滤（前端过滤即可）。
8. 文档项目复选（价值低，可不做）。

### 不建议做

- 版本按阶段/按版本改复选。
- 项目驾驶舱改复选；如果要比项目，做“项目对比”模式。
- 任何“复选浏览 + 写操作不指定目标项目”的组合。

### 粗略工作量

| 项 | 量级 | 主要工作 |
|---|---|---|
| 工作项可见性 | 小 | 控件 + chip + 卡片标签 |
| 需求池看板 | 中 | 后端 `reqs` 聚合 + 前端控件 + 卡片标签 |
| 用例只读多项目 | 大 | `reqIds` 列表/统计/覆盖/缺陷 + 权限 + 行项目标签 + 写入目标规则 + 保存视图兼容 |
| 全部版本/发布日程 | 小–中 | 前端过滤 / 后端 `projects` |
| 分支/报表/回顾 | 中 | 后端多项目参数 + 前端控件 |
| 项目透视过滤 | 小 | 前端 rows 过滤 |

## 7. 待确认

1. 真正想解决的是哪个页面？是「用例跨项目查看」，还是「需求池看板想一次看多个项目」，还是「项目驾驶舱想对比几个项目」？不同答案对应完全不同的改法。
2. “项目”具体指项目列表、项目驾驶舱，还是项目透视？
3. 用例只需要“看”，还是也要“跨项目执行/建计划”？后者会显著放大成本，且语义容易混乱。
4. 空间里通常有多少个项目？超过 10–20 个时，复选 popover 必须带搜索和“全选/清空”，不能平铺。
5. 写操作（新建工作项/需求/用例/版本/计划）在多项目浏览时，是要求用户先选目标项目，还是默认落到第一个项目？建议前者。

## 附：一句话回答

复选本身不难，难的是把“浏览范围”和“操作目标”分开：**浏览可以多选，写操作必须单选**。工作项已经把多选做在筛选里，缺的是可见性；需求池看板、用例是真正值得补的；版本和项目驾驶舱应保持单选。全量视图是“全部项目”这一范围状态和独立布局，不是复选的对立面，不应删除；只需把纯过滤型的「全部项目」选项收进新控件。样式上用一个稳定的项目范围触发器 + 复选 popover + 一枚摘要 chip，就不会难看；用原生 multiple 或平铺 chip 才会难看。
