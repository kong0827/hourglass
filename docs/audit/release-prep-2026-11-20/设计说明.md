# 发布准备与推送 · 设计说明

- 日期：2026-11-20
- 状态：原型 v1（`prototype.html`），未改产品代码
- 范围：发布计划制定后，向工作项负责人推送「发布准备」，负责人在「我的发布准备」逐项确认、标记风险；计划负责人看到汇总；关注列表为 P2 低优先级
- 合成数据：原型中的 38/42 人、8/20 确认、5 天后等均为示例，不代表真实数据

## 1. 设计简报

| 项 | 结论 |
|---|---|
| 谁 | 计划负责人 / 空间管理员（推送、查看汇总）；工作项负责人（接收、确认）；项目只读成员（可看进度，不能确认） |
| 任务 | 把「哪些工作项要赶在发布前处理、谁还没确认」推给对应负责人，并让负责人逐项确认或报风险 |
| 决策 | 这一屏要回答：距发布还有几天、谁还没确认、哪些有风险、这次要通知谁 |
| 成功标准 | ① 3 步内完成一次推送；② 负责人从通知到确认不超过 2 次点击；③ 计划负责人能按人看到确认/风险/未确认，且数字与明细一致 |
| 范围 | 计划详情的「发布准备」区、通知成员弹窗、通知中心条目、我的发布准备页、关注列表（P2）；不含发布检查/测试证据改造 |
| 约束 | 沿用现有发布计划与通知栈；外部推送只有空间群机器人，没有按人企微私信；计划任务保存时删除重建，确认记录不能挂在计划任务行上 |

## 2. 先读结论

1. **推送不等于改状态。** 负责人确认的是「我已核对该工作项的状态、版本和风险」，工作项状态仍在原抽屉里更新；确认也不构成发布证据。
2. **计划范围变化才让确认失效。** 范围 token 变化或发布时间提前，要求重新确认；只改备注不重来。
3. **默认全部项目成员推送，可只发未确认的人，也可指定成员。** 一次推送每人只收一条汇总，不按工作项轰炸。
4. **回执与逐项确认分开。** 回执表示「收到本次提醒」，逐项确认表示「这项我看过了」；两者互不覆盖。
5. **发布准备是提醒，不是发布门禁。** 首版不阻断发布，发布检查仍按原测试证据口径。
6. **关注是 P2。** 先做入口与列表，不新增关注偏好、不并入任务/需求关注，避免三个口径混用。

## 3. 现状与边界（已核对代码）

- 发布计划已有范围、负责人、计划时间、版本与任务，`scope_token` 由版本、任务、目标、环境、覆盖计算，**不含计划时间**；计划任务每次保存会删除并重建。
- 站内通知 `AppNotificationService.pushImmediate` 不去重，`push` 按「人 + 任务 + 类型」6 小时去重；通知保留 90 天。
- 邮件走 `NotificationEventService`，按个人偏好决定；外部推送是空间级群机器人，**不能按人送达**。
- 计划创建/改期/进入就绪目前不发通知，这是本设计要补的缺口。
- 现有「管理催办」是管理员手工、仅站内、6 小时去重，且不改任务状态；与本功能不合并。
- 需求没有负责人字段，因此本功能只按「工作项负责人」聚合，不按需求负责人聚合。

## 4. 对象与状态

### 4.1 对象

| 对象 | 关键字段 | 说明 |
|---|---|---|
| 发布计划 | `planId`、`plannedAt`、`ownerUserId`、`scope_token`、`revision`、`status` | 沿用现有 `version_release_plan`，不新增主状态 |
| 推送批次 | `pushId`、范围、渠道、发送人、发送时间、收件人数 | 一次「通知成员」= 一个批次，用于回执与记录 |
| 推送收件人 | `pushId`、`userId`、站内/邮件是否送达、`ackedAt` | 回执挂在批次上，而不是计划上 |
| 逐项确认 | `planId`、`taskId`、`userId`、`state(ok/risk)`、`note`、`scopeToken`、`checkedAt` | 一人一项一条；**不要外键到计划任务行**，因为任务会删除重建 |
| 关注 | `planId`、`userId` | P2；独立于任务关注、需求关注 |
| 里程碑发送记录 | `planId`、`userId`、`T-7/T-3/T-1/T-0`、`sentAt` | 防重复发送 |

### 4.2 派生状态

- **我的准备进度** = 我的工作项中 `ok` 数 / 总数；`risk` 计入「已回应」，不计入「已确认」。
- **计划准备进度** = 全部计划工作项中 `ok`、`risk`、未确认、未指派四类；四类互斥且相加等于工作项总数。
- **工作项未完成数** 是工作项自身的完成情况，只作参考，不参与确认进度。
- **回执** 是推送批次级事实；有回执不代表逐项确认完成。

### 4.3 逐项状态机

```
待确认 ──确认──▶ 已确认
   │               │
   └──有风险──▶ 有风险 ──撤销──▶ 待确认
已确认 ──撤销──▶ 待确认
```

约束：`risk` 建议填写一句风险说明；`ok` 与 `risk` 互斥；范围变化或发布时间提前时，旧记录保留但按「待重新确认」展示。

## 5. 权限矩阵

| 动作 | 空间管理员 / 计划管理者 | 计划负责人（有管理权） | 工作项负责人 | 项目只读成员 |
|---|---|---|---|---|
| 查看发布准备汇总 | 可 | 可 | 可（看自己的明细与总进度） | 可 |
| 通知成员 / 提醒 | 可 | 可 | 不可 | 不可 |
| 确认 / 标记风险 | 不可代替他人 | 不可代替他人 | 仅自己的项 | 不可（只读横幅） |
| 回执 | 可 | 可 | 可 | 可（如收到推送） |
| 关注计划 | 可 | 可 | 可 | 可 |
| 修改推送范围 | 可 | 可 | 不可 | 不可 |

说明：计划负责人字段本身不授予管理权，仍按现有 `ReleasePermissionService` 判定；无项目可见权限的人不进入收件人池。

## 6. 信息架构与入口

- 计划详情 →「计划」页签 →「发布准备」卡（不新增顶级菜单）。
- 顶栏铃铛 →「发布准备 · PL-012」条目 →「查看并确认」→ 我的发布准备。
- 计划卡「通知未确认 9 人」→ 通知成员弹窗，自动勾选「只发给尚未确认的人」。
- 负责人行「提醒」→ 通知成员弹窗，范围预选「仅负责人」且只选该人。
- 「关注此计划」→ 我关注的发布（P2）；入口只在版本域内，不新增菜单。

## 7. 页面规格

### 7.1 计划详情 · 发布准备（`?scene=plan`）

**结构**：页头（返回、标题、关注、通知成员）→ 倒计时条 → 页签 → 发布准备卡 → 三张说明卡。

- 倒计时条：`5 天后发布`、`2026-11-25 20:00`、`计划已就绪`、最近推送时间与人数、`已回应 10 / 20` 分段条。
- 发布准备卡头：标题、口径说明「负责人确认进度，只做发布前提醒，不改变工作项状态；未完成数仅作参考」、状态徽标、`通知未确认 9 人`。
- 汇总：`8 / 20 已确认`，`另有 2 项有风险`；四色分段条；四项指标（已确认/有风险/未确认/未指派，均带数字）。
- 推送信息条：范围、`修改范围`、最近推送按渠道拆分（`站内 38 人 · 邮件 12 人`）、推送记录。
- 负责人表：负责人（姓名 + 计划负责人徽标 + 项目）、工作项总数（下方灰色「N 未完成」）、已确认、有风险、未确认、最近确认、提醒。
- 未指派行：琥珀底，显示「未指派 · 需要先指定负责人」，操作为「去指派」，不计入未确认。
- 说明卡：推送范围（42 人 − 4 人无权限 = 38）、确认何时失效、关注（P2）。

**状态**：默认、无工作项（整卡隐藏）、无权限（只读查看，隐藏推送/提醒）、推送中（按钮 loading）、推送成功（轻提示 + 最近推送刷新）。

**口径**：已确认 + 有风险 + 未确认 + 未指派 = 工作项总数；「N 未完成」与确认状态可重叠，单独用灰色小字，不参与加总。

### 7.2 通知成员弹窗（`?scene=plan&modal=push`）

**结构**：标题与副标题 → 推送范围分段 → 范围说明与角色 chip →「只发给尚未确认的人」→ 推送方式 → 发送内容预览 → 底部人数与发送。

- 分段：`全部项目成员 38` / `仅负责人 6` / `指定成员 5`，带数量；切换即更新说明、成员列表与底部人数。
- 说明：`覆盖 3 个项目的 42 名成员；4 人没有项目可见权限，不会收到。同一人负责多项时只收一条汇总。`
- 角色 chip：负责人 6 / 测试 5 / 成员 27 / 只读 4（合计 42），用于解释范围构成。
- 筛选：`只发给尚未确认的人 9 人`，右侧注「避免重复打扰」；勾选后底部人数变为 9。
- 指定成员：搜索、全选/清空、成员行（姓名、项目/角色、未确认数）、已选数量；一个都不选时发送禁用并给原因。
- 渠道：站内通知（默认）、邮件（按个人偏好，仅已开启邮件的人收到）、企业微信群（只发到空间配置的群，不能按人送达）。
- 预览：标题 `发布准备 · PL-012`、`5 天后`、正文含发布时刻与「你负责 4 项：2 项未完成、1 项有风险、1 项待确认」、动作「查看并确认 →」。
- 底部：`将通知 38 人`、取消、`推送 38 人`；发送后成功条显示在弹窗底部操作区上方（`已推送 38 人；站内已送达。`），按钮变为 `完成`，再次点击关闭弹窗；推送后刷新计划页的最近推送。

**状态**：加载人数、可发送、未选成员（禁用）、无符合条件成员（空态 + 改范围）、发送中、发送成功、发送失败（保留选择，可重试）。

### 7.3 通知中心条目（`?scene=notice`）

- 未读条目：左侧「备」图标，标题 `发布准备 · PL-012` + `5 天后`；正文两行：`11-25 20:00 生产发布` / `你负责 4 项：2 未完成、1 有风险、1 待确认。`；元信息「计划负责人 林夏 · 运营研发中心 · 刚刚」。
- 主动作「查看并确认」，次动作「关注」；点击主体或主动作进入我的发布准备。
- 通知类型 `release_prep`；`ref_kind=release_plan`，`ref_id=planId`，供深链。
- 同一批次每人只一条；不使用任务提醒的 6 小时去重窗口。

### 7.4 我的发布准备（`?scene=prep`）

**结构**：页头（标题、计划时间、负责人、倒计时、关注、查看计划范围）→ 我的准备 hero → 回执条 → 工作项列表 + 右侧信息卡。

- Hero：`5 天后发布`、计划时间、`我的准备 2 / 5 已确认`、三段条（绿/橙/灰）、`1 项有风险 · 2 项未确认 · 3 项已回应`；`已回应 = 已确认 + 有风险`。
- 回执条：待回执时 `这条推送待回执` / `回执只表示收到本次提醒，不影响已完成的逐项确认。` / `确认已收到`；已回执为绿色 `本次推送已回执 · 今天 09:20`；只读时锁定横幅，不显示可点按钮。
- 列表头：`我负责的工作项` + 总数；筛选 `全部 5` / `待确认 2` / `有风险 1` / `已确认 2`，数字随操作实时更新。
- 行：优先级、标题、工作项状态徽标、`DM-xxx · 项目`、截止、预估；右侧 `打开工作项`、`有风险`、`确认`；已响应后出现 `撤销`。
- 风险行：琥珀底色 + 风险说明（可补充），负责人汇总里计入「有风险」。
- 已完成的工作项仍需确认（避免「做完了但没人告诉发布负责人」）。
- 侧栏：本次发布事实、确认口径（确认 ≠ 改状态 ≠ 发布证据）、打开第一个工作项；只读时隐藏口径卡，仅留事实卡与横幅。

**状态**：默认、无我的工作项（不显示 hero/回执/侧栏，空态给「查看计划范围」）、加载失败（重试）、只读（禁用确认/风险/撤销并给原因）、范围已变化（提示重新确认，旧确认置灰）、提交失败（回滚并提示）。

**交互**：确认/风险/撤销为乐观更新；失败回滚；变更后重算 hero、筛选计数和列表头总数；筛选不改变数据；长文本风险说明不撑破行。

### 7.5 我关注的发布（P2，`?scene=watch`）

- 标题旁标 `P2 · 低优先级`；页签 `全部 2` / `即将发布` / `有风险`。
- 卡片：计划名、项目数、负责人、倒计时、进度条、风险数与已确认数、主链接（我的准备/查看计划）。
- P2 说明：首版只做关注入口与列表，不新增消息偏好，也不并入任务/需求关注，避免三个关注口径混在一起。

## 8. 文案要点

| 场景 | 文案 |
|---|---|
| 推送范围 | 全部项目成员 / 仅负责人 / 指定成员；「4 人没有项目可见权限，不会收到」 |
| 去重 | 「同一人负责多项时只收一条汇总」 |
| 回执 | 「回执只表示收到本次提醒，不影响已完成的逐项确认」 |
| 确认口径 | 「确认只表示我已核对该工作项的状态、版本与风险，不改变任务状态，也不构成发布证据」 |
| 失效 | 「计划范围变化或发布时间提前，会要求负责人重新确认；只改备注不重来」 |
| 未指派 | 「需要先指定负责人」→「去指派」 |
| 空态 | 「这个计划里没有需要你确认的工作项」+ 一个动作 |
| 错误 | 「准备信息加载失败」+ 重试；原因写网络或权限校验，不伪装成空态 |
| 只读 | 「你对该项目只有查看权限，不能确认或标记风险」 |

## 9. 令牌与响应式

- 颜色：蓝=当前/主操作；绿=已确认/健康；橙=有风险/待回执；红=失败/未指派提示；灰=未确认/中性；紫=关注（P2）。
- 字体与间距沿用 `frontend/css/tokens.css`；数字右对齐、`tabular-nums`；进度条与徽标不新造颜色。
- 断点：1440 主视图；≤980 侧栏两列、关注卡单列；≤760 侧栏隐藏、表格转卡片、弹窗转底部抽屉、触控目标 ≥38–44px。
- 390 验证：无横向滚动；表格行按「负责人 → 数字两列 → 操作」重排；底部导航不遮挡可滚动内容（`padding-bottom: 84px`）。

## 10. 设计决策记录

| 决定 | 替代方案 | 代价 | 何时反悔 |
|---|---|---|---|
| 发布准备放在「计划」页签内 | 新增一级「发布准备」菜单 | 计划页更长 | 当它成为独立日常工作流、每天多次进入时 |
| 三种范围 + 只发未确认 | 只做全部/指定两人范围 | 多一个状态与计数 | 当「仅负责人」使用率极低时合并 |
| 回执按推送批次 | 回执按计划一次 | 多一张收件人表 | 当只需要「是否打开过」时退回通知已读 |
| 逐项确认独立于任务状态 | 确认即改任务状态 | 用户要切回原处改状态 | 永不：确认是核对，不是执行 |
| 范围 token + 计划时间提前使确认失效 | 任何编辑都失效 | 需要记录确认时的计划时间 | 当改期频繁导致确认疲劳时放宽 |
| 首版不做发布门禁 | 未确认则阻断发布 | 可能有人没确认就发 | 当项目明确要求「全员确认才可发」时做成项目策略 |
| 关注 P2、不新增偏好 | 首版就做关注通知 | 关注只收站内聚合 | 当关注量和使用频次证明需要独立偏好时 |
| 外部只发空间群 | 按人企微私信 | 无法私信到个人 | 接入企微应用消息/钉钉工作通知后 |
| 通知从铃铛进「我的准备」 | 新增「我的准备」顶级入口 | 入口较深 | 当每人每周多次进入时加到「我的工作」卡 |

## 11. 后端落地建议

### 11.1 事件与通知

- 新增事件类型 `release_prep`（个人偏好：站内默认开、邮件默认关），加入 `UserNotificationPreferenceService`；P2 关注再议 `release_watch`。
- 站内写入用 `pushImmediate`（事件不去重），以 `(pushId, userId)` 做幂等；不要复用任务提醒的 `push` 6 小时窗口。
- 邮件只发给已开启邮件偏好的人；企业微信群明确标注「群级、不可按人」。
- 深链：`ref_kind=release_plan`、`ref_id=planId`，前端路由落到我的发布准备。

```sql
  primary key(plan_id, task_id, user_id))
version_release_plan_watch(plan_id, user_id, created_at, primary key(plan_id, user_id)) -- P2
version_release_plan_milestone(plan_id, user_id, milestone, sent_at,
  unique(plan_id, user_id, milestone))
```

- `task_check` **不要**外键到 `version_release_plan_task`（该表保存时删除重建）；展示时 join 当前计划任务，任务移出计划后不再计入汇总，清理任务可日后做。
- 范围变化：读 `scope_token` 与 `planned_at_snapshot` 判定是否要求重新确认；只改备注不影响。
- 回执写 `push_recipient.acked_at`；计划页汇总「已回执人数」来自最近批次。

### 11.3 接口（建议）

- `GET /release-plans/{id}/prep`：汇总、按人计数、未指派、最近推送、我的状态。
- `GET /release-plans/{id}/prep/recipients?scope=&q=`：可选成员与未确认数。
- `POST /release-plans/{id}/prep/notify`：范围、成员、onlyUnconfirmed、渠道；返回 pushId 与人数。
- `GET /release-plans/{id}/prep/me`：我的工作项、确认状态、回执、倒计时。
- `POST /release-plans/{id}/prep/me/receipt`：回执（幂等）。
- `POST /release-plans/{id}/prep/items/{taskId}/check`：`ok|risk` + note + `expectedScopeToken`；版本冲突返回 409 提示重新确认。
- `DELETE .../check`：撤销回待确认。
- `POST/DELETE /release-plans/{id}/watch`：P2。

### 11.4 定时提醒

- T-7 / T-3 / T-1 09:00 给「未确认且未回执」的负责人发一条汇总；T-0 09:00 给计划负责人与关注者发「今天发布」。
- 以 `version_release_plan_milestone` 唯一键保证只发一次；计划改期后按新的 `plannedAt` 重新计算，不补发已过里程碑。
- 发布计划进入 `ready` 时可发首条；创建草稿不发。

### 11.5 与现有功能的边界

- 不改 `ReleaseCheckResponse` 的测试证据口径；发布准备的「有风险」不进发布检查。
- 不合并「管理催办」；催办是管理员对逾期任务，发布准备是负责人对发布前核对。
- 首版不阻断 `confirm` 发布；如未来做门禁，做成项目策略，默认关闭。

## 12. 验收清单

1. 计划管理者在「计划」页签看到发布准备卡，汇总四类数字相加等于工作项总数。
2. 全部项目成员范围排除无项目可见权限的人，人数与角色 chip 相加一致。
3. 勾选「只发给尚未确认的人」后，底部人数与卡片按钮人数一致，发送后只有这些人收到。
4. 同一人负责多项只收到一条汇总；同一批次重复点击不产生重复通知。
5. 收件人从铃铛进入我的发布准备，只看到自己负责的工作项。
6. 回执待办 → 已回执状态持久化；计划页能看到回执人数；回执不影响逐项确认。
7. 逐项确认后 hero、筛选计数、计划页负责人表同步更新；工作项状态不变。
8. 标记风险可写说明；计划页风险数与说明可见；撤销后回到待确认。
9. 计划范围变化或发布时间提前后提示重新确认；只改备注不失效。
10. 无工作项、加载失败、只读、无符合条件收件人、提交失败均有明确状态与下一步。
11. 390 宽度无横向滚动，表格转卡片，弹窗为底部抽屉，操作区不被底部导航遮挡。
12. 关注入口与列表可用（P2），不新增消息偏好；任务关注/需求关注口径不受影响。
13. 邮件只到已开启偏好的人；企业微信群文案明确「群级、不能按人送达」。
14. 键盘：Esc 关闭弹窗/通知，焦点可见；图标按钮有可读标签。
15. 原型无 lorem ipsum；合成数据有标注；数字与明细一致。

## 13. 假设与待确认

1. **「项目成员」口径**：按计划涉及项目的可见成员取并集，而不是空间全部成员；需要产品确认。原型按并集展示 42 人、排除 4 人。
2. **回执粒度**：原型按推送批次；如果产品只想保留「是否打开过」，可退回通知已读，不建收件人表。
3. **谁能推送**：按现有发布计划管理权限（空间管理员/项目负责人可写）；计划负责人字段本身不授权。
4. **邮件默认关闭**：沿用个人偏好；首次推送不强制发邮件。
5. **关注是否发通知**：P2 首版只做列表与入口，不发独立通知；是否新增 `release_watch` 待使用数据。
6. **发布门禁**：首版不建议阻断；若要阻断，需项目级策略与明确的豁免流程。
7. **计划任务删除重建**：确认记录按 `plan_id + task_id + user_id` 保存，任务移出计划后仅从汇总剔除，不物理删除，便于追溯。
