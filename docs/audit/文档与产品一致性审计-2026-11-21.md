## 六、结论与建议

### 6.1 结论

1. **文档与产品的主要矛盾不是「功能忘了写」，而是「定位、信息架构、角色模型」三层同时漂移。** 单点补字会让下一轮改版再次失配。
2. **最该先处理的是三类硬事实：** 入口 14 个、当前 85 张表、评审权限按项目写。它们不依赖定位决策，改完立刻减少错误信息。
3. **定位必须先拍板。** 内部 11-14 稿已经明确要求同步 README、项目介绍、战略文档与博客；公开文档目前仍全量旧口径。两套并行越久，帮助中心、销售材料和博客越难统一。
4. **角色视角是当前文档的最大盲区。** 评审人、测试计划执行人、发布准备/关注/群推送、多角色我的工作，都是「挂在现有主线上的角色动作」，恰好最容易被功能地图漏掉。
5. **图表与副本是第二发布面。** 只改 Markdown 不改图和 `frontend/` 副本，线上帮助中心仍然会展示旧数字。

### 6.2 建议的执行顺序

**第 0 步（决策，1 次会）：** 拍板定位。二选一：

- A：采用「轻量项目管理 / 研发协作工作台，干活即记录」，交付说明降为能力。
- B：维持「交付工作台」，把内部 11-14 稿标为草案。

**第 1 批（P0 硬事实，1–2 天）：**

1. 全站替换当前表数 80 → 85，补 113–117。
2. 入口清单按 `index.html` 重写为 14 个内容入口 + 设置。
3. 删除 8 处「评审仅空间主 / 仅 workspace owner / 空间主评审」，统一权限矩阵。
4. 重写「我的工作」为多角色工作台。
5. 补评审人、测试计划执行人、发布准备/关注/群推送四段。

**第 2 批（P1 结构，2–3 天）：**

6. 管理员指南新增 113–117 升级节。
7. 接口契约补新接口与字段。
8. 阶段工时口径拆分（版本页三段 / 驾驶舱两段）。
9. 重出 5 张图与 2 张主界面截图。

**第 3 批（P2 清理，随批次）：**

10. 术语「成员与角色」「项目集」「报表五个页签」。
11. FAQ 补新问题。
12. docs 索引、帮助中心副本、MD5 与图片同步。

### 6.3 不建议做的事

- **不要直接全量重写 8 份文档。** 现有文档大量口径（发布快照、工时裁剪、JSON 备份边界）是准确的，重写会引入新错误。
- **不要在定位未拍板前改主张。** 否则只是把「两套口径」换成「三套口径」。
- **不要为评审人/执行人/发布准备新增一级菜单。** 产品明确「不新增一级菜单」，文档也应沿用现有 IA，只补角色动作。
- **不要把 113–117 塞进 11-18 的旧上线清单。** 那份清单的线上前提是 78 表，时点已过；应新增 11-21 清单或 3.6 节，保留历史可追溯。

### 6.4 验收方式

改完后跑四项检查：

1. `grep -R "12 个入口\|12 个一级入口\|80 张表\|评审仍\|评审仍仅" docs README.md` 应只剩历史时点说明。

4. 副本检查：`docs/*.md` 与 `frontend/*.md` MD5 一致；重新生成的 PNG 在 `docs/diagrams`、`docs/images`、`frontend/images` 三处 SHA256 一致。
