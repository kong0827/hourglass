# 工作项 / 需求详情子页布局与交互审计（2026-11-13）

## 范围与方法

- 对象：任务看板点击卡片 → **工作项详情抽屉**；需求看板点击卡片 → **需求详情弹框**；以及需求详情里的「编辑」「拆分」「通过 / 不通过」等二级动作。
- 环境：本地预览 `http://127.0.0.1:8081/hourglass/`（服务 8080、MySQL 3307），工作区 `e537232`（含其他批次未提交改动），支付业务部演示数据。
- 视口：桌面 1440×900、移动 390×844。
- 量测：CDP 读取容器几何、滚动高度、焦点元素、层级与表格 `scrollWidth`，再逐张人工复核截图；文案取自真实演示数据。
- 对照：[页面设计理念](../页面设计理念.md)、[理念符合性检查-2026-11-13](理念符合性检查-2026-11-13.md) 与 [页面布局与交互审计-2026-11-12](页面布局与交互审计-2026-11-12.md)。

本次只做分析与原型，未改动业务代码；原型是独立 HTML，未接入应用。

## 结论

两个看板打开的是同一种东西——一条记录的详情，但用了两套容器、两套交互：

- **工作项**：1080px 右侧抽屉，打开即整页编辑表单。正文可视 774px，内容高 1845px（2.38 屏），98 个表单控件；检查清单 1628px、附件 1703px、工时 1778px、时间线 1853px，评论 855px 已在首屏之外。同一件事有两个状态入口。
- **需求**：720px 居中弹框，高 1198px，比 900 高视口多出 338px，头部不固定；手机上打开时页面已滚到 630px，标题和「通过」都在屏幕外。再点「编辑」，在弹框上又叠一个 560px 的右侧面板。
- 与设计理念直接冲突的三条：详情用抽屉、不用模态框做常规编辑、不做多层嵌套。

建议统一成**一套右侧抽屉 + 先读后改 + 四个页签**：工作项与需求共用外壳，只替换内容块；状态、进度、交付结论尽量由事实派生，单字段即改即存。

## 量测结果

| 指标 | 工作项（桌面 1440×900） | 需求（桌面 1440×900） | 需求（移动 390×844） |

| 滚动 | 正文可视 774，内容 1845（2.38 屏） | 遮罩层滚动 1278 / 900，弹框超屏 338 | 遮罩层滚动 1662 / 844 |
| 打开位置 | 顶部 | 顶部，但关闭按钮随内容滚出 | **scrollTop=630，头部 top=-589** |
| 首屏内容 | 到「计划」；评论 855 在首屏外 | 事实与描述；表格与底部动作在屏外 | 只剩描述中段，标题/状态/通过不可见 |
| 结构 | 2 栏（695 + 320），7 个主区 + 4 个折叠区 | 9 格事实 + 7 段内容 + 8 列表格 | 9 格事实折成 2 列 |
| 表格 | — | 容器 678 / 内容 715，右侧裁掉 37px | 容器 325 / 内容 715，需横滑 |
| 可操作点 | 98 个表单控件 | 头部 5 个按钮 + 表格内操作 | 同上 |
| 浮层 | z-index 120 | 详情 z-index 201；编辑 z-index 202、560×900 叠在其上 | 同左 |

工作项抽屉首屏只到「计划」，依赖关系 1284、检查清单 1628、附件 1703、工时 1778、操作时间线 1853（均为文档坐标）。也就是说，**要确认“做到哪了、谁说了什么”，至少要滚两屏**。

需求弹框打开时 `layer.scrollTop` 为 630——`openModal` 默认聚焦第一个输入框，正好落在底部隐藏的文档选择器 `#demDocPick` 上（`frontend/js/core/ui.js`）。这不是样式问题，是打开即错位。

## 与设计理念对照

| 理念 | 现状 | 判定 |
| --- | --- | --- |
| 详情用抽屉，保留列表上下文 | 工作项是抽屉；需求是居中模态 | 需求不符合 |
| 不用模态框做常规编辑（模态只用于确认与危险操作） | 需求详情本身是模态，编辑再叠模态 | 不符合 |
| 不做多层嵌套抽屉 | 需求详情 201 上叠编辑 202 | 不符合 |
| 一屏一判断 | 工作项 2.38 屏；需求超屏 338px | 不符合 |
| 数据只录一次 / 能派生就不让人填 | 状态两个入口；进度与清单并行 | 部分不符合 |
| 少一跳就完成（改一个字段 ≤ 2 次点击） | 事实条改状态可 2 次点击，但保存模型要求整单提交 | 部分符合 |
| 移动端维持现状，不新增投入 | 现状可维持，但需求详情首屏错位属于缺陷，不是投入问题 | 需修缺陷 |

## 方案：一套抽屉，两个内容

### 容器

- 桌面 1000px 右侧抽屉，移动端全屏；遮罩点击、`Esc`、`×` 均可关闭，关闭回到列表原位置。
- 头部固定：类型图标、标题（就地编辑）、状态胶囊、项目/版本/截止/负责人；右侧关注、更多、关闭。
- 底部固定，仅移动端放主操作（需求：不通过 / 通过；工作项：状态 / 关注 / 关闭），桌面不放保存栏。
- 正文独立滚动；打开时焦点落在标题或关闭按钮，`scrollTop=0`，不再抢焦点到表单控件。

### 页签（两个详情共用 4 个）

| 页签 | 工作项 | 需求 |
| --- | --- | --- |
| 概览 | 事实条 5 项、描述、检查清单 + 交付证据、最近动态 2 条 | 事实 6 项、描述/验收、WSJF、交付进度 + 关联工作项、最近记录 2 条 |
| 执行 / 交付 | 清单全量、工时、附件、依赖关系 | 交付判定、交付证据表（5 列）、人工判定 |
| 关联 | 版本、需求、文档、史诗/分支 | 关联工作项、文档、版本、发布 |
| 动态 | 评论 + 变更合并，筛选「全部/评论/变更」，输入框固定 | 同左 |

页签标题带计数（执行 2/5、动态 4），不用打开才知道有没有内容。

### 交互与保存

- 标题、描述、状态、负责人、日期、优先级：**就地编辑，失焦即存**；检查项勾选即存。只有「新建」保留整单保存。
- 状态只有一个入口（头部胶囊）；工作项菜单为待处理/进行中/待测试/测试中/已完成，需求为通过/不通过/排期/关闭。
- 需求编辑不再开侧板：标题、描述、验收在概览内展开工具条；字段多时进「交付」页签，仍在同一抽屉。
- 拆分工作项保留一级嵌套抽屉（例外），完成后回到需求概览并显示新工作项。
- 概览进度由检查清单派生，展示「2/5 · 40%」并注明来源；不再单独手拖。

原型里把这套交互都做成了可点的：顶部切换工作项/需求、桌面/手机、标注，标注 9 条对应上面的问题。

## 预期效果

- 工作项：首屏从 2.38 屏压到 1 屏；检查清单、评论各 1 次点击可达；状态入口 2→1；概览可操作点从 98 降到十余个，表单按需进入。
- 需求：超屏 338px→0；移动端打开位置 630px→0；交付表 715px→5 列适配，无横滑；编辑叠层 1 处→0。
- 一致性：2 套详情容器→1 套；同一个「详情」在两个看板的位置、关闭方式、页签结构一致。

| P1 | 需求详情改用同一抽屉外壳；编辑就地化；事实 9→6；证据表 8→5 列 | `frontend/js/views/demands.js`、`frontend/css/views.css`、`mobile.css` | 2–3 天 |

主要风险：

- 工作项保存现在是整单提交，单字段即存需要 `PATCH` 或前端合并后提交；评论、清单、附件已有独立端点，可先接这些。
- E2E 与脚本依赖 `#iTitle`、`#btnSaveTask` 等选择器，改读态要同步更新测试。
- 只读项目、只读成员必须保持不可编辑，就地编辑要按权限降级为纯文本。
- Service Worker 缓存与版本号需随发布升级。

需要拍板的三件事：

1. 读态字段是「失焦自动保存」还是保留显式保存（影响误改与撤销策略）。
2. 是否接受 1000px 抽屉宽度（原型值；现为 1080px）。
3. 需求拆分是否保留一级嵌套抽屉，还是改为页内展开。
